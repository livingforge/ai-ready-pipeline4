# ③ build ― 整理結果を正本にする

```bash
arp4 build --dry-run    # 書き込まずに案だけ出す
arp4 build              # 正本へ（status: review で入る）
```

ここから先が「我々の仕様」になる。**意味の判断は含まない。**やるのはマージ（同じ `concept`
なら同じアイテム。それだけ）・採番・向きの補正（種別が非対称な関係だけ）・出典の引き継ぎ・
`contradictions` からの課題の起票である。

**やらないこと。**推測しない（関係は `refs` からだけ）、必須属性を埋めない、承認しない
（すべて `status: review`）、矛盾を解決しない。

`name` と `statement` は完全なレコードからだけ採る。参照だけのレコードは出典と属性と
関係を持ち込むだけで、本文には触らない。

凍結していないラウンドでは動かない（`--force` で強行できるが、ゲートを通していない状態
なので、気づかれずに落ちるものがある）。

**機械が下した判断は `rounds/<ラウンド>/decisions.yml` に全件残り**、`arp4 publish` が
`out/決定記録.md` を組む。端末の出力は流れて消えるので、事後拒否権の窓口はそちらになる。

## マージで捨てたものは必ず見せる

| コード | いつ出るか | どうなるか |
| --- | --- | --- |
| `B017` | 同じ `subject` の `contradictions` が 2 件以上 | 先の 1 件へ両論を足す（課題は 1 件） |
| `B020` / `B022` | 同じ concept で `name` / 属性が食い違う | 先に読んだほうを採る（採らなかった値は `conflicts` へ） |
| `B023` | 同じ concept で `statement` が食い違う | いちばん長いものを採る |
| `B024` | 別々の資料が張った同じ関係で属性が食い違う | 先に読んだほうを採る |
| `B026` | 向きを機械が決められない関係を張った | 書いた向きのまま入る |

`B023` の「長いほう」は情報量の目安としては弱い（機能一覧の長い文が、画面一覧の適切な
説明を押しのける）。**`B023` が並ぶのは、同じ対象を複数シートで完全なレコードにしている
ということである。**直すのは整理層で、1 シートだけ完全にして残りを参照だけのレコードにする。

関係の属性はマージする。テーブル定義書の `has-column`（`pk: true` を持つ）とデータ項目
一覧の `has-column`（`pk` 列が無い）が同じ組み合わせを張っても、PK は落ちない。食い
違ったときだけ `B024` が出る。複数値の属性（`crud` / `permission`）は和集合にする。

## `build` はラウンド 1 本ぶんである

既定は最新のラウンド 1 本なので、日々の運用ではそのまま打てばよい。**正本を作り直す
ときだけ `--round` で古い順に replay する。**空の正本に `arp4 build` を一発打つと、
最新ラウンドのぶんだけの正本ができ、エラーは出ない。順を守らなかったときの `B012`
（関係の相手が正本にありません）は警告なので、止まらずに関係だけが落ちた正本ができる。

## `overridden` ― 出典と異なる値の記録

凍結後に分かったことは、整理結果ではなく正本で直す。

```yaml
- id: ent-9a3c4f21b8e0
  physical_name: T_ORDERS
  overridden:
    physical_name:
      was: T_ORDER
      reason: 実装確認の結果、資料が旧名のままだった（PR #142）
      at: 2026-08-20
```

**`reason` は必須**（無ければ `E017`）。空を許すと、ただの上書きと区別がつかない。
`overridden` に載せた属性は再構築でも守られ、守った件数は報告に出る。報告しないと、
「なぜ資料の記述が反映されないのか」が読み手に見えない。

## `known_gaps` ― 資料に定義が無いことの表明

一覧には載っているのに定義シートが無いテーブル・帳票・画面は必ず出る。`check` はこれを
`E027`（多重度違反）で正しく拾うが、そのままだと `publish` が止まる。**`--force` で押し
通さない。**承知しているなら、承知していると正本に書く。

```yaml
- id: rpt-3f21
  known_gaps:                       # ○ 1 アイテムの欠落は 1 つの known_gaps に並べる
    displays:
      reason: 納品書の出力項目シートが帳票一覧・レイアウトに無い
      at: 2026-08-12
    realizes:
      reason: 機能一覧が納品書を 1 度も参照していない（出力契機は夜間バッチのみ）
      at: 2026-08-12
```

- `reason` は必須（無ければ `E019`）。空を許すと、`E027` を消すだけのキーになる
- **書けるのは関係型と属性名の両方である。**関係の欠落（`E027` / `W031`）も属性の欠落
  （`E010`）も同じ場所に書く。書く側から見れば「この欄が資料に無い」の一言で足りる
- **`known_gaps:` を 2 回書かない。**YAML の重複キーで後ろが勝ち、前が消える
  （error も warn も出ない）
- 載っている多重度違反は **error から warn（`W032`）へ落ちる**。消えはしない
- 資料が届いて埋まったら `W033`（宣言が古い）が出る。そこで宣言を消す
- 綴りを間違えると `E018`。守っているつもりで守られていない状態は作らない

`overridden` は**値**の上書き、`known_gaps` は**欠落**の表明である。混ぜない。

## `conflicts`（機械が書く）が残ったら

同じ concept を複数のシートから起こして値が食い違うと、採らなかった値が `conflicts` に
残り、`W045` が出続ける。取れる手は 3 つ。

- 同じ事実なら、片方のシートを**参照だけのレコード**にする（`attrs` を書かない）
- 違う事実なら課題（`disputes`）にして、どちらへも寄せない
- 採った値でよいなら `overridden` に理由を書く

補足（`description`）は足し合わせる。2 つのシートが別々のことを書いているのは互いを補う
関係であって矛盾ではないので、`conflicts` には出ない。

## `E010`（必須属性が無い）が出たら

**機械が埋めるものではない。**取れる手は 4 つで、**この順に試す。**

1. **資料に書いてある** → 正本に書く。`overridden` は要らない
2. **その属性を持たない種類のものである** → 専用の値を使う。例: `data_type` の `操作` は
   「値を持たない画面部品（ボタン・ラベル）」を表す
3. **資料に欄そのものが無い** → `known_gaps` に**属性名**で宣言する
4. **欄はあるが値が空**（`―` / 空白） → 同じく宣言し、`reason` に**「欄はあるが空」と
   書く**。3 と書く場所は同じだが別の事実である。3 は資料の様式の問題（次の版でも埋まら
   ない）、4 は記入漏れ（催促すれば埋まる）で、次のラウンドで拾い直す相手が違う

**2 と 3 を混ぜない。**専用の値は「そういう種類のものだ」という判断なので、次のラウンドで
拾い直す必要が無い。`known_gaps` は「資料が書いていない」という事実の申告なので、拾い直す
必要がある。型が無いだけのものを `操作` へ流すと、拾い直す対象が消える。

## 表示 ID

```bash
arp4 number             # FR-001 / RUL-001 / CST-001 / ISS-001 …
```

**`check` より先に回す。**表示 ID は必須属性なので、採番していないと `E010` が種別の件数
ぶん出る。**一度振ったら動かさない**（採番が動くと設計書・議事録・課題票の参照が一斉に
壊れる）。

どの種別に表示 ID が振られるかは `arp4 model` の「採番」行に出る。振られない種別（用語・
エンティティ・データ項目・コード値）は名前や物理名で参照する。**内部 ID
（`rul-215d5bb15cf9`）は設計書に出さない。**採番を外した種別は `arp4 model` に「機械は
振らない」と出るので、そのときは**その ID を資料から取って整理のときに書く。**

**節の中で番号が飛んで見えるのは正常である。**採番は `sequence.by` でまとめ、設計書は別の
属性で節に割るので、節の中は昇順だが連続しない。番号は文書内の位置ではなく識別子である。

### 書式外の表示 ID（`E028`）

既に入っている値が採番の書式（`FR-{:03d}`）でなければ `arp4 check` が `E028` を出す。
元資料から持ってきた番号、実装が実際に使っているコード、手で振った通番が混ざっている
ということである。**機械は直さない**（元資料の番号は顧客との対応表であることがあり、
書き換えたら復元できない）。**まず「何件が書式外か」を見る。**件数で対応が変わる。

| 出かた | 何が起きているか | どうするか |
| --- | --- | --- |
| その種別のほぼ全部 | 宣言した書式のほうが実態と違う | メタモデルで `sequence` を外し `pattern` で宣言し直す（分かれ目は「その ID を誰が決めているか」で、実装や顧客が決めているなら機械が振ってはいけない） |
| 数件だけ・番号を固定したい | 資料・実装・契約書と突き合わせている | `overridden` に理由（`W042` へ落ちる） |
| 数件だけ・単に体系から外れた | 採番し損ねただけ | `arp4 number --fix-format` |

表示 ID の `overridden` に `was` は書かない。出典と違う値ではないからである（資料にそう
書いてあった）。**出典から写した値には `--fix-format` を使わない**（「出典と異なる値を
理由なしに作る」ことになる）。

## 検証

```bash
arp4 check --strict
```

構造・参照整合性・多重度・カバレッジに加えて、出典（`source` のラウンド・ファイル・
アンカーが実在するか、凍結ハッシュと一致するか）と `overridden` の理由を見る。

- **`W031` は「そのアイテムから出る関係が 0 本」**という意味で、上流とは限らない
  （`constrains` なら縛る先が 1 つも無い制約）。確かめたうえで相手が資料に無いなら
  `known_gaps` で宣言する
- **`W031` が語彙の不足で出ることがある。**縛る相手が語彙に無ければ、整理層からはどう書いても
  0 本になる。`known_gaps` は「資料に定義が無い」の宣言なので、語彙の不足に使うと原因が
  すり替わる。相手の種別が語彙に無いと分かったら `_metamodel-add.yml` の `notes` へ書く
- **課題（`open-issue`）の `W044` は「名前まで似ている」という意味である。**課題の仕様文は
  `name` から作るので、課題どうしで出たなら実際に見に行く価値がある
