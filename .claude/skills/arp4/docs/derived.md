# derived ― AI の解釈層（PM・顧客向けの設計書はここから出る）

資産の種類に依らない段である。コードでも Excel でも、正本（`spec/`）が
揃ったあと、`publish` の前に書く。

```
parsed（機械の事実）→ organized（資料に忠実な記録）→ spec（正本）→ derived（AI の解釈）★
```

`spec/` は「資料がこう書いている」を積んだものなので、**正本からは要約を作れない。**
概要も機能グループも処理フローも、資料のどこにも書かれていない。誰かが解釈して
初めて存在する。それを書くのがこの段である。**規律を緩めるのではなく、層を足して
混ぜない。**

## 書かないとどうなるか ― 6 種のうち 3 種が空で出る

```bash
arp4 publish --root "$R" --audience stakeholder
```

| 文書 | derived が無いとき | 必要な語彙 |
| --- | --- | --- |
| システム概要 | 空 | `概要`（無ければ `機能グループ` でも出る） |
| 機能一覧 | 空 | `機能グループ` |
| 処理フロー図 | 空 | `処理フロー` |
| テスト状況サマリ | 正本の `test-case` 次第 | ―（derived は要らない） |
| 構成図 | 出る | ―（正本の関係から組む） |
| 用語集 | 出る | ―（正本の `name` / `aliases` から組む） |

空の文書は必要な語彙を名指しして自己申告するので、気づかれずに壊れることは無い。ただし
読み手には、「資料が足りない」のか「手順に段が無かった」のかが区別できない。

## 書くもの

```yaml
# .arp/spec/derived/解釈.yml   （ファイル名は自由。1 ファイル = アイテムの配列）
- id: drv-受注管理
  type: 機能グループ            # 機能グループ / 概要 / 処理フロー が節になる
  name: 受注管理
  statement: 受注の登録から出荷指示までを扱う機能のまとまり。
  confidence: 高                # 高 / 中 / 低 のいずれか。必須。「AI が推定した」の宣言
  basis:                        # 必須。根拠。実在は arp4 check が照合する
    - { round: r001, file: 資料/受注管理_画面仕様書.xlsx/受注入力, anchor: s3-t1 }
    - mod-3f2a01bc9d21          # 正本のアイテム ID でもよい
  members: [scr-1a2b3c4d5e6f, mod-3f2a01bc9d21]   # 機能一覧の「対応する設計要素」列

- id: drv-概要
  type: 概要
  name: 新販売管理システム
  statement: 受注から請求までを 1 つの基盤で扱い、手入力の対象を減らすシステム。
  confidence: 中
  basis: [gol-9f8e7d6c5b4a]

- id: drv-flow-受注
  type: 処理フロー
  name: 受注の流れ
  statement: 受注受付から出荷指示までの推定の流れ。
  confidence: 中
  basis: [mod-3f2a01bc9d21]
  flow: [受注受付, 与信判定, 在庫引き当て, 出荷指示]   # mermaid の flowchart になる
```

| 欄 | 必須 | 中身 |
| --- | --- | --- |
| `id` / `type` / `name` / `statement` | ○ | 無いと `D001`（error）。`id` の重複は `D005` |
| `confidence` | ○ | `高` / `中` / `低` のどれか。ほかは `D004`（error） |
| `basis` | ○ | 1 件以上。アイテム ID か `{round, file, anchor}`。無ければ `D002`、指せなければ `D003` |
| `members` | ― | 正本のアイテム ID。実在は `D003` が見る |
| `flow` | ― | `処理フロー` のときの手順（文字列の配列） |

## 守ること

- **`basis` の指せない解釈は書かない。**指せないまま書くと `check` が `D003`
  （error）で止め、confidence を下げて残す道は無い。根拠が足りないなら
  **課題（`open-issue`）として正本に残す**（そちらが正しい行き先である）
- **`confidence` を全部「高」で埋めない。**読み手が「どこまで信じてよいか」を判断
  できなくなり、確度の欄があることの意味が消える
- **解釈を organized に書かない。**「資料に無いことを書かない」を破った整理結果は、
  凍結ハッシュごと正本に入り、あとから解釈だったと分からなくなる
- **`type` の語彙は固定していない**（解釈の形は資産ごとに違う）が、stakeholder 向けの
  生成が節として拾うのは `概要` / `機能グループ` / `処理フロー` の 3 つだけである

## どこに置くかの目安

**機能グループはモジュール・画面を業務の言葉でまとめる。**資材が既にサブシステムで
分かれているなら（`subsystem` 属性がある）、まずその軸でまとめてよい。まとめた根拠
（`basis`）は、そのサブシステムの一覧シートになる。

**概要は事業目標（`business-goal`）から書く。**計画書があるなら、そこが唯一
「このシステムは何をするものか」を書いている場所である。無ければ要件定義書の
冒頭を `basis` にする。

**処理フローは業務フロー（`flow-step`）が正本にあっても書く。**stakeholder の
処理フロー図は derived の `処理フロー` だけから組み、正本の `business-flow` /
`flow-step` を読まない。「正本にあるなら二重登録になる」と考えて書かないと、**その流れは
読み手に 1 本も出ない。**

二重登録を避けたいなら、本文を写すのではなく正本を指す。`flow:` にステップ名を
並べ、`basis` に元の `business-flow` の ID を置く。解釈層が持つのは「どの粒度で
1 本の流れとしてまとめたか」であり、それは正本には無い判断である。

derived にしか書けないのは、資料に流れとして書かれていないもの（コードの
呼び出し関係から推定した流れなど）である。そちらは `confidence` を下げる。

## 検証

```bash
arp4 check --root "$R" --strict     # D001〜D005 はすべて error
arp4 publish --root "$R" --audience stakeholder
```

`check` が見るのは「根拠を指しているか」「指した先が実在するか」「確度を宣言して
いるか」だけである。**解釈の中身が妥当かは機械には判定できない。**
