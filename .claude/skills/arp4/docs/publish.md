# ⑥ publish ― 正本から設計書を出す

```bash
arp4 publish                        # error があれば止まる
arp4 publish --audience stakeholder # PM・顧客向け 6 種（out/stakeholder/）
arp4 publish --full                 # 省略した行・列・章も全部出す
arp4 publish --force                # 承知のうえで出す（成果物に警告帯が残る）
```

出力は `.arp/out/` の工程ごとのフォルダ（Markdown と HTML）。**直接編集しない。**次の
`arp4 publish` で消えるので、直すのは正本のほうである。

## `--force` を常態化させない

`error` で止まるのは、「設計書ではなく正本を直す」という順序を守らせるためである。

`E027`（一覧には載っているが定義シートが無い）や `E010`（資料に欄そのものが無い必須属性）の
ように、資料が届くまで直しようがないものは、正本に `known_gaps` を書いて warn へ落とす
→ [build.md](build.md)。**`--force` を打つ前に、まず宣言できる欠落かどうかを見ること。**

`--force` で出した設計書には、目次と全文書の冒頭に警告帯が付く。**帯を消す方法は、正本を
直すこと 1 つだけである。**`--force` でなくても未解決の warn があれば、フッタが件数を出す。
**通ったからといって穴が無いわけではない。**

## 出したあとに読む 2 枚

### `0_この設計書の穴.md` ― この一式が何を書けていないか

目次の先頭に出る。`--force` の有無と指摘の内訳、決着していない矛盾（`disputes`）、機械が
読めなかったもの（`kind: 未読取`）、資料に定義が無いと確かめたもの（`known_gaps`）、設計要素に
繋がっていないもの（`W030` / `W031`）、様式にあるのに正本が値を持たない列が 1 枚に集まる。

**「資料に無い」とは言っていない。**様式が持つ欄に正本が値を持たない、としか言えない。
資料にその欄が無いのか、整理のときに写されなかったのかは、資料を見た人にしか分からない。

### `0_元資料と設計書の対応.md` ― 届いた資料のどれが使われなかったか

穴の 1 枚が正本に何が無いかを書くのに対して、こちらは反対側を書く。資料を渡した側から
見ると、これが最初に知りたいことである。

| 整理結果 | 読み方 | 次にやること |
| --- | --- | --- |
| なし | まだ整理していません | **整理する**（`freeze` の未整理一覧にも上がる） |
| 全アンカーが対象外の宣言 | 仕様にならないと宣言済み | **何もしなくてよい**（表紙・改訂履歴） |
| レコードあり | 整理結果が正本まで届いていません | 語彙外・concept 未割当・関係が張れていない |

**「使われていない」は「不要だった」ではない。**出典にならないのが正しい写しはある。

## 空になったものの読み方

空になったものは何も残さずに消えるのではなく、名前つきで脚注に並ぶ（全部見るには `--full`）。

- 省略した列の括弧の中は「どこを埋めれば出るか」を示す。`省略した列: 備考
  （displays.note）` なら、整理層がその欄へ写していない
- **トレーサビリティの表だけは列を省略しない。**この表は空欄そのものが結論だからである
  （`―` の行がテスト漏れそのものである）
- 章ごと省略されたときは、その関係型が正本に 1 本も無い。「調べたら 0 だった」ではなく
  「その語彙をまだ取り込んでいない」ということである

### 空の理由は 2 つに割れる。混ぜない

1 行も出なかった設計書は、冒頭に不足している語彙の名前を書いて自己申告する。

| 区分 | 判定 | 次にやること |
| --- | --- | --- |
| 資料 | その種別のアイテムが 1 件も無い | 資料を足す（テスト列が空ならテストコードを、論理名が空なら DDL の `COMMENT ON` を `arp4 parse` に渡していない） |
| 関係 | 両端のアイテムはあるのに関係が 0 本 | 資料を探しに行っても見つからない。整理層が張れなかった理由を取り除く |

```
> **この設計書に出せるデータが正本にありません**（必要な語彙: `accesses`）。
  `accesses` は両端のアイテム（起点 25 件 / 終点 33 件）は正本にありますが、
  関係が 1 本も張られていません。**資料の欠落ではありません。**
```

`関係` のほうは `arp4 check` が `W034` で、生成する前に指摘する。

## 出来上がった設計書の形（`P1xx`）

正本が正しくても、読み手が誤読しうる形で出ていることがある。すべて warn なので
`publish` は止まらず、指摘は `0_この設計書の穴.md` に残る。**`check` と `publish` の両方を
見ること。**

| コード | 何を見ているか | どうするか |
| --- | --- | --- |
| `P101` | 母集合をそのまま並べただけの表（結論の列が全行空） | 表を消すのではなく、関係を張れない理由を `known_gaps` に残す |
| `P102` | 升目の凡例が無い（空欄の意味が書かれていない） | 文書定義に凡例を足す（既定では自動で付く） |
| `P103` | 節の見出しが ASCII だけ（enum の生値） | メタモデルの `value_labels` に日本語の見出しを与える |
| `P104` | 同じ本文が何度も繰り返されている | 表の外に出すべき定型文 |
| `P105` | 争点のあるアイテムが、印も無く並んでいる | 読み手に対立が見えない。その 1 枚だけを配らない |
| `P106` | 同じアイテムが複数の設計書に全文で重複 | どちらかを参照（ID と名称だけ）にする |
| `P107` | 同じ種別なのに出典列を出す設計書と出さない設計書がある | 揃える（出典の有無は読み手の信頼度の判断に効く） |
| `P108` | 「未分類」の節が大きすぎる | 分類を埋める → [reconcile.md](reconcile.md)。資料に区分が無いときだけ未分類で残す |
| `P109` | 禁止を書ける升目に、禁止が 1 件も無い | 原典が `×` を書いているなら関係を張って属性に写す → [sheets.md](sheets.md)。原典に禁止が無いならこのままでよい |
| `P110` | 正本にあるのに、どの設計書にも出ていない関係型 | 様式に節を足す。整理層が張った関係は、出す先が無いと気づかれずに消える |
| `P111` | 正本に値があるのに、どの設計書の列にも出ていない属性 | 様式に列を足すか、整理層がそこへ書くのをやめる（書く先が要るなら `_metamodel-add.yml` へ提案） |

**升目は「関係がある」しか言えない。**原典が `○ / △ / ×` の 3 値でも、関係の有無に写した
時点で `×`（不可）と「記載が無い」は同じ空欄になる → [sheets.md](sheets.md)「権限マトリクス」。

**争点（`disputes`）のあるアイテムには「課題」の列が自動で付く**が、印が出ていなければ
`P105` が出る。印の無いまま**その 1 枚だけを配らない**（1 冊だけ渡された人は、互いに矛盾
する両論を確定仕様として受け取る）。

## Markdown の原文から値を読み取らない

升目の中で Markdown が別のものとして読む記号はエスケープしてある。原文は `arp4.\_\_init\_\_`
`dict\[str, str\] \| None` と出る（描画すると元の字に戻る）。**値が要るなら HTML 版か正本
（`.arp/spec/`）を見ること。**

## 読者別の生成

developer の末尾に付く決定記録（`out/決定記録.md`）は、機械が下した判断を型ごとにまとめた
表である。全件と根拠の出典アンカーは `rounds/<ラウンド>/decisions.yml` にある。

**`--audience stakeholder` は derived 層が空だと、6 種のうち 3 種が空で出る。**概要・機能
一覧・処理フロー図は解釈なので、正本からは組めない（残る 3 種 ―― 用語集・構成図・テスト
状況サマリ ―― は正本だけから組む）。**`publish` の前に `.arp/spec/derived/`
を書く** → [derived.md](derived.md)
