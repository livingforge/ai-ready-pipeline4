# 整理② ― 横断（同一性・分類・用語・矛盾）

整理①を全部書き終えてから、凍結の直前に 1 回だけ回す。

**横断でしか決まらない判断は 2 つある。**

| 判断 | 問い | 決まっていないと |
| --- | --- | --- |
| 同一性 | これとあれは同じものか | 同じ概念が別アイテムになり、片方が孤児になる |
| 分類 | これとあれは同じまとまりか | 設計書の目次が、資料の並び順の写しになる |

どちらも「他と比べて」しか答えが出ない。1 ファイルずつ読む整理①では答えようがない
問いなので、ここで 1 回だけまとめて片付ける。

**ただし食い違いの摘出だけは別である**（下記「矛盾」）。見つけられるのはそのファイルを
読んだ人だけで、後から横断で見ても資料の言い回しまでは戻れない。**整理①の途中で見つけた
その場で `_concepts.yml` に書き足す。**

## 同一性 ― 入力は台帳 1 本

```bash
cat .arp/spec/concepts.yml     # 過去ラウンドまでに確定した同一性
```

**過去ラウンドの整理結果は読まない。**台帳だけを見れば、「この新しい『受注番号』は既存の
`c-受注番号` と同じか」に答えられる。だから資料が増えても、この作業の入力量は増え続けない。

### 書くもの

```yaml
# .arp/rounds/<ラウンド>/organized/_concepts.yml
new:                                   # 台帳へ追加する提案
  - concept: c-受注番号
    type: データ項目
    label: 受注番号
    aliases: [受注No, 注文番号]        # 見つかった表記ゆれ
    reason: テーブル定義書と画面項目定義書で物理名 ORDER_NO が一致

assign:                                # 既存 concept への追加割当（別名を足すだけ）
  - { concept: c-顧客コード, aliases_add: [得意先コード] }

contradictions:                        # 摘出のみ。統合も解決もしない
  - subject: c-受注データの保持期間     # ★ 争点そのものの concept（課題ではない）
    positions:
      - { statement: 5 年間保存する, concept: c-受注データの保持期間-運用,
          source: { file: 資料/A/基本設計書.xlsx/受注テーブル, anchor: s1-t1 } }
      - { statement: 13 か月でアーカイブする,
          source: { file: 資料/B/運用設計.xlsx/運用方針, anchor: s4-t2 } }
```

形の正本は `arp4 schema concepts` である。書いたら `arp4 lint _concepts.yml` で
検査できる。形のほかに、`new` の `type` が語彙に無いもの（`G002`）と `assign` の相手が
台帳に無いもの（`G021`）を、`build` を待たずにその場で指摘する。

- **初回ラウンドで `assign` は使えない**（台帳は `build` を回すまで空なので必ず `G021` で
  落ちる）。初回に別名を足すなら `new` の `aliases` に書く
- **`new` はこのラウンドで初めて出た概念だけ。**前のラウンドで登録済みの concept を `new`
  に出すと `B002` になる（台帳を先に引いていないということである）
- **全 concept を書くのではない。**使われた concept は `build` が台帳へ自動登録するので、
  `new` に書くのは、他と比べないと同一と決められなかったものだけである（字義どおり
  「初めて出た概念」と読むと 4 桁件になるが、比較の判断があるのはその数%である）
- **`file` に拡張子（`.md`）を付けない。**付けると `…/3.機能要件一覧.md.md#s7-t1` に
  なり、`out/決定記録.md` から根拠パスを辿れない。整理①の `source` は `anchor` だけで
  済むが、`_concepts.yml` は共有ファイルなので、ここだけ `file` を書く
- **`_concepts.yml` と `_metamodel-add.yml` は分担で共有する 1 本のファイルである。**
  追記するときは必ず Read してから書くこと（丸ごと書き直すと先行者の記述が消える。
  error も warn も出ない）

### 同一だと言ってよい根拠

| 強さ | 根拠 |
| --- | --- |
| 強い | 物理名・シグネチャ・コード値が一致する |
| 中 | 論理名が一致し、同じ業務文脈（同じテーブル／同じ画面群）で使われている |
| 弱い | 名前が似ている、意味が近そう |

**弱いものはまとめない。**別の `concept` のまま残せば `E012` や重複として後から人が
気づけるが、記録を残さずに統合したものが違っていた場合、それに気づく仕組みは無い。表記
ゆれ（`受注No` / `注文番号`）は統合ではなく `aliases` に集める。

### 全体の資料とサブシステムの資料は、同じ対象を 2 度書く

**探す当てがある二重登録は、この 1 つだけである。**日本の設計書は「全体編」と「サブ
システム編」を別冊にするので、同じことが上位の 1 冊と下位の n 冊に書かれる。整理①は
1 ファイルずつ読むので、両方が完全なレコードになる。

やることは 2 つ。一字一句同じなら参照レコードにする。書いてあることが違うなら、それは
二重登録ではなく矛盾なので `contradictions` へ回す。

**上位の冊子を先に読む。**どちらをオーナーにするかは「詳しいほう」で決まるが、下位から
読むと上位に同じ記述があることに気づけない（→ [split.md](split.md)）。

## 命名のずれ ― 入力は分布 1 枚

**同じ資材の concept が同じ形をしているかを、凍結の前に 1 枚で見る**（分担して書いた
ラウンドでは必ず）。`lint` は 1 ファイルの中しか見ないので、「A が指した名前を B が名乗って
いない」は `freeze`（`G003`）まで誰にも見えない。しかも参照が張られていない食い違いは
`G003` にもならず、同じものが 2 つの別物になったまま通ってしまう。

```bash
grep -rho "concept: c-[a-z]*-[^. ,}]*" .arp/rounds/<ラウンド>/organized/ | sort | uniq -c | sort -rn
```

接頭辞の一覧が出るので、同じ資材で 2 系統以上に分かれていたら規約に合わせて改名する。
**凍結前の改名はただの置換である。**凍結後に直すのは 2 アイテムの統合になり、台帳と正本の
両方に手が要る。

## 分類 ― 入力は分布 1 枚

`arp4 model --attributes` で `※設計書の節になる` と印の付いた属性を、ここで揃える。
整理①で付いた分類は 1 ファイルの視野で付いたものなので、資料の並びを写しただけに
なっている（→ [organize.md](organize.md)）。**見るのは分布だけでよい。**

```bash
grep -rh "category:" .arp/rounds/<ラウンド>/organized/ | sort | uniq -c | sort -rn
```

**判定は 1 つ。その分類で割ったとき、1 節あたり 2 件以上入るかを見る。**割った数が中身の
数の半分を超えたら、それは分類ではなく見出しを増やしただけである。

| 分布 | すること |
| --- | --- |
| 1 件しか入らない分類がある | 既存の分類へまとめる。まとめ先が無ければ空ける（`未分類` に集まる） |
| 分類の数が件数の半分を超えた | 1 段上の軸で括り直す（工程・業務領域・サブシステム） |
| 語彙に無い分類がどうしても要る | 消費側のメタモデルへ値を足す提案を書く（下記） |

まとめる作業は値の書き換えだけなので、外れ値のあるファイルだけ開けばよい。同じことを機械も
見ている（`arp4 conform` の `C205`）が、出るのは `build` の後である。凍結済みの整理結果は
もう直せないので、**ここで直すほうが 1 ラウンド早い。**

### 語彙に無い分類が要るとき

分類の語彙は案件ごとに違う（業務領域・サブシステムの名前は標準にできない）。そのため標準
パックは `category` に値を持たず、プロジェクトのメタモデル（`.arp/spec/metamodel.yml`）が
宣言する。**これはあなたが書き換えるファイルではない**ので、`_metamodel-add.yml` の
`notes` に提案として書く。

提案には**値の並び順まで書く。並べた順がそのまま設計書の章立ての順になる**ので、意味のある順
（工程順・業務の流れ順）で挙げること。宣言に無い値は文字コード順で末尾に付く。あわせて
`extensible: true`（宣言外の値も通す）を外さないよう添える。固定すると、資料にある分類を
整理層が「近いほう」へ寄せる判断を強いられ、資料に無い分類が正本に残る。

## 使い残し ― 入力は分布 1 枚

**宣言されているのに、このラウンドで 1 度も使われていない属性・関係を出す。**整理①は
1 ファイルずつ読むので「この欄があることに気づかなかった」は誰にも見えない。`lint` は綴りしか
見ず、`freeze` も `check` も「宣言済みだが 0 件」を数えない。**凍結すると整理結果はもう
直せないので、確かめられるのはここが最後である。**

```bash
R=/path/to/対象のリポジトリ
ROUND=.arp/rounds/r001/organized

PYTHONIOENCODING=utf-8 arp4 model --root "$R" --attributes > /tmp/model.txt
grep -oE '[a-z][a-z_]+（' /tmp/model.txt | tr -d '（' | sort -u | grep -vE '_id$' > /tmp/attrs.txt
awk '/^\[関係\]/{f=1;next} f && /→/ && /^  [a-z]/ {print $1}' /tmp/model.txt | sort -u > /tmp/rels.txt

echo "=== 未使用の属性 ==="
while read a; do
  [ "$(grep -rho "\b$a:" "$ROUND" | wc -l)" -eq 0 ] && echo "  $a"
done < /tmp/attrs.txt
echo "=== 未使用の関係 ==="
while read r; do
  [ "$(grep -rho "rel: $r\b" "$ROUND" | wc -l)" -eq 0 ] && echo "  $r"
done < /tmp/rels.txt
```

`_id` で終わる採番用の属性は除いてある（`req_id` / `screen_id` は arp4 が振るもので、
整理層は書かない → [organize.md](organize.md)「表示 ID を鍵にしない」）。

**出たものを 1 件ずつ 3 つに分ける。**数えるのが目的ではなく、分けるのが目的である。

| 判定 | 例 | すること |
| --- | --- | --- |
| 資料にその欄が無い | テスト資産を渡していないラウンドの `expected` / `level` / `result` | 何もしない |
| 資料にあるが、別の欄へ流した | `state` `start_time` `retention` `route` `physical_name` | **書き先を移す**（→ [organize.md](organize.md)「資料にある値は宣言済みの欄へ入れる」） |
| 資料にあるが、関係ごと張っていない | `contributes-to` `supports` | 張る。この 2 本が 0 だと、事業目標と業務フローがトレーサビリティから丸ごと落ちる |

実測では 29 件が出て、うち `state` / `raised_on` / `raised_phase` / `start_time` /
`schedule` / `retention` / `route` / `package` / `constants` / `raises` / `default_value` /
`position` の 12 件が 2 番目（＝資料にあるのに流した）だった。**1 件も直さずに凍結したので、
設計書のその 12 列が空のまま出た。**

**この検査は名前で数えるので、取りこぼしが 1 つある。**同じ属性名を別の種別・関係が使って
いると、片方が 0 件でも「使用済み」に見える（`condition` は `leads-to` が使うので、
`business-rule.condition` が 0 件でも出てこない）。種別まで見るのは `build` の後に
`arp4 check --code W043 --code W047 --code W046` が `種別.属性` の形でやるので、
**3 つとも見る。**
後者で出たものは、このラウンドではもう直せない ―― 次のラウンドの整理①の宿題として控える。

## 矛盾 ― 摘出はするが解決しない

`5 年間保存` と `13 か月でアーカイブ` のような食い違いは、**どちらが正しいかを決めない。**
両論のまま `contradictions` に書けば、`build` が課題（`open-issue`）に起こし、課題管理表に
「両論」として出る。決めるのは人であって、その根拠は資料の外にしかない。片方を消すと、
消したという事実ごと残らなくなる。どちらの `statement` も、資料に書いてあるまま残す。

矛盾に見えて矛盾でないものもある。「受注テーブルの保持期間 5 年」と「受注ログのアーカイブ
13 か月」は別の対象の話なので、`subject` を分ければ矛盾ではない。

**見つけた食い違いは必ず `_concepts.yml` の `contradictions` に置く。**機械が数えない場所
（報告文）に置いた発見は、人が拾わなければ消える。

### 手順は 1 つ（順序を守らないと同じ争点の課題が二重に立つ）

1. **既存の課題を先に探す。**課題管理表・議事録から起こした課題（`open-issue`）に同じ争点が
   あることが多い。`_concepts.yml` と `organized/` を concept 名で検索する
2. あれば新しく起票しない。その課題のレコードの `refs` に `disputes` を張り足す
3. 無ければ `_concepts.yml` の `contradictions` に書き、`positions` に両論を**両方**書く。
   **`disputes` は書かない。**`build` が張る

**`disputes` を誰が張るかは経路で決まる。**

| 経路 | `disputes` を張るのは |
| --- | --- |
| `_concepts.yml` の `contradictions` に書いた争点（3） | `build`。手で張らない |
| 既に正本にある課題へ足す（2） | 人（課題のレコードの `refs`） |

`build` は自分が起票した課題にだけ `disputes` を張る（正本の課題は書き換えない）ので、
**両方に手で張ると、前者だけが二重になる。**

### 突合はこの 5 か所を必ず見る

食い違いを見つける目の細かさは、同じラウンドの中でも揃わない。「注意深く読む」では揃わない
ので、**見る場所を列挙して結果を残す。**

| 突合 | 何と何 | 見つかるもの |
| --- | --- | --- |
| ① 一覧 × 明細 | 画面一覧・帳票一覧 × 各項目シート | 一覧にあるのに定義が無い（`known_gaps` 行き） |
| ② 図 × 表 | レイアウト・様式イメージ × 項目一覧 | 紙にしか無い欄・ボタン（課題行き） |
| ③ メッセージ | 入力チェックの種別 × メッセージID | チェック内容と表示文が合っていない |
| ④ コード定義 | コード定義書 × 使っている側の値 | 定義に無い値・使われない値 |
| ⑤ 権限 | 権限マトリクス × 画面一覧の利用権限 | 同じことを別々に言っている（課題行き） |

**「見て、無かった」も結果である。**③〜⑤ は 1 冊では終わらないので、`_concepts.yml` の
コメントに「見た範囲」を残しておくこと。

### `subject` は争点であって課題ではない

課題 ID は `subject` から決まるので、既にある課題を指すと同じ ID の課題をもう 1 件起こそうと
して衝突する（`B015` で止める）。

```yaml
subject: c-RULE-消費税の計算      # ○ 争点そのもの
subject: c-課題-消費税の計算単位  # × 課題を指している（B015）
```

### 争点が 1 つの concept に収まらないときは `name` を付ける

`subject` は 1 つしか取れないので、複数のアイテムにまたがる争点（ジョブ 5 本の先行後続、
4 冊 7 行に同じ形で出る欠陥）では代表を選ぶしかない。既定の課題名は
`<争点の label> の記述が資料間で食い違う` なので、そのままだと課題一覧から中身が
読めない。

```yaml
contradictions:
  - subject: c-job-EDI受注取込
    name: 夜間バッチの実行順序が図と表で食い違う   # ← 課題の名前になる
    positions:
      - { statement: ジョブフロー図は 7 本の先行後続を引いている, … }
      - { statement: バッチ一覧は 5 本を「時刻起動（先行なし）」と書いている, … }
```

**代表を選んだこと自体も残す。**`positions[].statement` に「ほか 4 冊 6 行が同じ形」と
書いておけば、課題を読む人が範囲を取り違えない。

### 同じ `subject` を 2 回書けない（合流のときにまとめる）

**1 subject につき 1 課題である。**同じ `subject` の 2 件目は新しい課題にならず、`build` が
先の 1 件へ両論を足して `B017` で知らせる。消えはしないが、両論が 1 本の文字列に並ぶだけで、
「別の争点だった」がどこにも残らない。

**分担したラウンドでは同じアイテムに争点が集まる。**合流のときに `subject` ごとにまとめ、
`positions` を足す。まとめた範囲は `positions[].statement` に書いて残す。
**別の争点として立てたいなら `subject` を分ける。**

### `positions` に concept を書くと、争点を個別に指せる

`build` は課題から争点へ `disputes` を張る。`positions[].concept` を書けば両論のそれぞれ
に張り、書かなければ `subject` 1 つに張る。

`disputes` の相手になれるのは要件・業務ルール・制約・処理単位・モジュール・事業目標と、
データ要素（エンティティ・データ項目・コード値）である。データ項目そのものが争点である
ことは普通にあり（「消費税の計算単位」の証拠は受注ヘッダと請求ヘッダの 2 つの「消費税額」）、
**業務ルールへ迂回させると、課題管理表から証拠へ辿れなくなる。**

相手になれない種別が争点のとき（メッセージ・利用者・テストケース）だけ、それを扱う業務
ルールか制約を `subject` にする。そのときは、何の話なのかを `positions[].statement` に
名指しで書く。書かないと、課題一覧から争点そのものへ戻れない。

## 語彙の追加提案

種別が足りないと気づくのもこの段である。既存種別で書けないかを先に確かめ、どうしても
要るなら `_metamodel-add.yml` に書く → [organize.md](organize.md)

**提案を書いたラウンドは、`freeze` が `G007` で止まった状態が正常である。**止まったまま人の
承認を待ち、承認されてから凍結する。「凍結できないから」という理由で、提案を報告文だけに
書いて済ませない。
