# 分担するとき ― 書いていない判断は人数分に分かれる

この文書は、Excel 資産の整理を複数人で分担するときのものである。コード資産は
`arp4 draft` が規約を機械で実行するので、分担で分かれる判断がそもそも残らない。

整理①は 1 パースファイル : 1 整理ファイルなので並列に分担できる。ただし `lint` は
1 ファイルの中しか見ない。ファイルをまたぐ食い違い（A が指した concept を B が名乗って
いない、命名の形が人ごとに違う）は、**全員が完了報告したあと**の
`freeze` で初めて出る。**配る前に 9 つ、合流したあとに 1 つ。**

## 1. 較正では「一覧シート」を先に読む

代表 1〜2 ファイルを通しで整理して、concept の命名・粒度・空欄にした判断を実例として配る
（規約は [organize.md](organize.md) にあるが、規約に無い判断が資料ごとに必ず出る）。

**ただし次項のオーナー表は、代表ファイルの整理からは作れない。**日本の設計書は必ず一覧
シートを持っているので、そこだけを先に読む。画面一覧・機能一覧・テーブル一覧・データ項目
一覧・IF 一覧・バッチ一覧・モジュール一覧・業務ルール一覧・課題管理表である。ここで確定
するのは 3 つ。

- **対象の全数と名前**（他のロットが参照する綴り。1 文字も変えさせない）
- **オーナー**（いちばん詳しい 1 シート。詳細シートが無い対象は一覧が名乗る）
- **課題台帳**（既存の課題を全件。新規起票を禁じる根拠になる。8 項）

あわせて **concept の鍵に使う列が資料に実在するかを確かめる**
→ [organize.md](organize.md)「表示 ID を鍵にしない」

**鍵に何を使うかだけでなく、「その識別子はどの種別のものか」まで決めて配る。**同じ語が
冊子ごとに別の種別に見えることがある ―― 実測では「テナント識別子」を、一方の冊子が
`利用者・ロール`（利用者を表す語として）、もう一方が `制約・前提`（規模の前提として）で
**同じ concept 名の完全なレコードにし、`type` が衝突した。**これは誰も指摘しない ――
`lint` は 1 ファイルしか見ず、`G013` は「誰も名乗っていない」しか言えず、`build` は
**先に読んだほうの種別で 1 アイテムを組み、もう片方の属性を「この種別に無い属性」として
捨てる**（`B021`。名前の食い違いなら `B020` が出るが、種別の食い違いには専用の警告が無い）。
較正で配る表に、鍵・綴りと並べて**種別の列を 1 本足す。**

**接頭辞の規約も、配る側が決めて配る。**`c-<物理名>` / `c-<論理名>` は
[organize.md](organize.md) が定めているが、**種別ごとの接頭（`c-scr-` / `c-cst-` /
`c-nfr-` / `c-act-` …）の一覧は手順書に無い**（資料ごとに要る種別が違うため）。使うなら
**使ってよい接頭辞の一覧そのものを配る** ―― 「接頭辞を付けること」だけを配ると綴りが割れる
（`c-cst-` と `c-const-`、`c-act-` と `c-actor-`）。合流後に直すと `_concepts.yml` の
統合作業になる。

**一覧シートに行が無い語も配る。**一覧シートは資材（画面・テーブル・バッチ）を数えるが、
複数の資料が本文で使う業務の語には一覧が無い。**一覧が無い語は誰も較正しないので、担当の
数だけ concept が生える。**実測（kotonoha r001）では「テナント」に一覧シートが無く、8 冊の
うち 5 冊が本文で使っていて、concept が 3 通りに割れた。**接頭辞の規約（`c-scr-` /
`c-rule-` …）を配っただけでは揃わない** ―― 揃うのは接頭辞だけで、その後ろの語は各自が
資料から採る。較正で代表 1〜2 冊を通しで読んだときに出てきた業務の語を、綴りごと表にして
配ること（対象・オーナー・課題台帳と同じ 1 枚に足せばよい）。合流後に直すと、
`_concepts.yml` の統合作業になる（→ [reconcile.md](reconcile.md)「命名のずれ」）。

## 2. 較正の成果に「オーナー表」を必ず入れる（最も食い違うのはここ）

「同じ対象が複数シートに出たら 1 シートだけ完全なレコードにする」という規約はあるが、**どの
シートがそれかは 1 ファイルの視野からは決まらない。**`lint` も `freeze` も判定しない（`G013` は
「誰も名乗っていない」しか言えない）ので、2 人が同じ対象の完全レコードを書くと、出るのは
`build` の `B023` になる。

配る形は「concept 群 → 完全レコードを書くファイル → 残りは参照だけ」の表 1 枚。

**関係にもオーナーが要る**（レイアウトと項目一覧のように同じ関係を別の角度から書く 2 枚が
あると、`B024` で先に読んだほうが採用される）→ [organize.md](organize.md)

## 3. オーナー表には 3 つの但し書きを添える

- **オーナーが資料に存在しないことがある**（共通基盤の画面に画面仕様書が無い）。そのときは、
  その対象を書いている資料が名乗る
- **シートは在るのに、その対象の行が 1 行も無いことがある。**表題が合っているだけでオーナーに
  指名すると、担当は書くものが無いまま `G003` を抱え、対象は誰にも書かれずに終わる（実測で
  現状課題のオーナーをプロジェクト計画書としたが、そのシートには別種の 2 行しかなかった）。
  **オーナーを決めるのはシート名ではなく行である** ―― 指名する前に、その対象の行が実在するかを
  パース結果で確かめる
- 「詳しい」がレコード単位ではなく属性単位で分かれることがある（バッチは一覧だけが起動時刻の
  列を持ち、仕様書だけがステップを持つ）。**参照だけのレコードにも「そのシートにしか無い属性」は
  書ける**
- **オーナーが未着手のあいだ `G003` が出るのは正常である。**消すために `statement` を書き足すと
  `B023` になる。出たままにして先へ進む

## 4. 整理②（横断）は 1 人でやる

同一性・分類・命名の食い違いは「他と比べて」しか決まらないので、分担できない
→ [reconcile.md](reconcile.md)。**ただし食い違いの摘出だけは各自がその場で書く**（見つけ
られるのはそのファイルを読んだ人だけである）。

## 5. 合流のたびに `arp4 freeze --dry-run --path <担当ぶん>` を打つ

全員の完了を待ってからだと、食い違いが最後に全部いちどに出る。

## 6. 完了条件を `lint` だけにしない

`lint` が見るのは「1 ファイルだけで決まるもの」なので、`G001` / `G003` / `G013` / `G020` は
出ない。**完了条件は `lint` と `freeze --dry-run --path` の 2 つ揃えて配る**
（何が出て何が出ないかの表は → [freeze.md](freeze.md)）。**配るのは説明ではなく、この
2 行そのものである。**

```bash
arp4 lint   --root "$R" <担当ぶんのフォルダ>              # ① 1 ファイルで決まるもの
arp4 freeze --root "$R" --dry-run --path <担当ぶん>      # ② 残りのうち自分に効くもの
```

`--path` は表示だけを絞り、判定はラウンド全体で行う。隠した件数は必ず出るので、**「自分の
ぶんは error 0」を「凍結できる」と読ませない。**

**②を配り損ねると、出るのは全員の完了報告のあとである。**実測（kotonoha r001）では 8 人が
①だけで完了報告し、`G020` 83 件と `G003` 2 件がそこで一度に出た。`G020`（要る関係が 1 本も
無い）の相手はたいてい同じファイルの本文に書いてあるので、**担当がそのファイルを開いて
いるうちなら 1 件ずつ足せる** ―― 全員が閉じたあとだと、83 件を 1 人が資料を開き直して
当たることになる。**張れないと分かった件も同じである** ―― 「調べたうえで相手がいない」と
書けるのは資料を開いた本人だけなので、`known_gaps` をそのレコードへ書くところまでを
担当の作業に含めて配る（→ [organize.md](organize.md)）。`G003` は 3 項のとおり**オーナーが未着手のあいだ出るのが正常**だが、
**全員が完了したあとに残っている `G003` は「誰も名乗らなかった」という別の意味になる。**
②を合流のたびに打っていれば（5 項）、その 2 件が「まだ未着手」なのか「書く担当が居ない」
のかを、まだ直せるうちに分けられる。

**そして「残してよい warn」を必ず並べて配る。**「warn 0 で完了」と配ると、資料が正しくて
語彙に受け皿が無いだけの warn まで消しにかかる ―― 消す手は散文へ崩す・`statement` へ畳む・
concept 名へ逃がすの 3 通りあり、**担当ごとに違う手を選ぶので、同じ対象の綴りがそのまま
割れる。**分担では消えない warn のほうが多い。

| 残してよい warn | なぜ残るか | 担当がすること |
| --- | --- | --- |
| `G003` オーナーが未着手 | 3 項。書き足すと `B023` | 出たままにする |
| `G030` 見出しに受け皿の属性が無い | 帳票の取得元など、語彙の不足であって書き方の誤りではない。**「受け皿が無い」と決める前に `arp4 model --attributes` を引く**（課題管理表の状態・起票・工程・区分は宣言済みで、これは `G029` 側である） | 残す。報告文に `about` / `reason` / `source` |
| `G015` 絵があるのに `未読取` | `render` を打てない環境では絵を見られない | `reason` にそう書いて残す。**絵はあるが見ても確定できなかったときは、その絵の名前を `reason` に書けば消える**（→ [organize.md](organize.md)） |

**空欄そのものは warn にならない。**資料が書いていない属性を埋めないのは正しいが、それを
言う指摘は整理層に無い（`E010` として `build` の後に人へ渡る）―― 「warn 0」を完了条件に
すると、担当は鳴っていない欄まで埋めにかかる。

`G029`（宣言済みの欄があるのに `description` へ流した）と `G020`（要る関係が 1 本も無い）は
**残すほうではない。**前者は移す先が名指しされているので担当ごとに割れず、後者は張れない
ことが正しくても**そのレコードの `known_gaps` に理由を書いて降ろす**（→
[organize.md](organize.md)「「調べたうえで相手がいない」は宣言する」）。降ろした件数は集計に
出るので、**黙って消えることはない。**

**報告文の形まで配る。**残した warn は「コード・件数・`about`（何が）・`reason`（なぜ残したか）・
`source`（どの資料か）」の 1 行にする。書き先が無いと、残してよい warn と消し忘れた warn が
同じ見た目になる。

## 7. 気づきの宛先を先に配る

語彙の不足は `_metamodel-add.yml`（受け取るのは `add_item_types` と `notes` だけ）、資料の
欠落は正本の `known_gaps`、手順書そのものの不備は依頼した側が場所を名指しする。**読み落としに
書き先があるのと同じで、気づきにも書き先が要る。**配らないと、質の高い発見が報告文にしか
残らず、人が拾わなければ消える。

**争点の書き先を配るときは「1 つの争点（`subject`）につき 1 件。既に誰かが同じ subject を
使っていたら `positions` を足す」まで配る** → [reconcile.md](reconcile.md)

## 8. 課題の concept 名を較正のときに全件確定して配る

資料どうしの食い違いは分担した全員が見つけるが、**新規に起票させると同じ争点が人数分立つ。**
先に台帳を配って「見つけたら既存の課題へ `disputes` を張り足す」に統一する。ただし既存の
どれにも当たらない争点は必ず出るので、その書き先（整理②へ回す申し送り）も同時に配ること。

## 9. 共有ファイルは書き込み役を決める

`_concepts.yml` と `_metamodel-add.yml` は各 1 ファイルなのに、7 項・8 項はそこへの起票を
分担させる。並列に追記すると、書きかけを別の担当が読むことになる。壊れた YAML は `G014` で
丸ごと読み飛ばされ、そのファイルが覆っていたアンカーが `G001` として出る。配る形はどちらかに
する。**どちらにするかを較正で決めて配る** ―― 決めずに配ると、担当は「書いてよいのか」が
分からないまま `G030` に当たり、6 項の 3 通りの回避へ散る。

- **書き込み役を 1 人に決める**（他は申し送りで渡す）。争点が多いラウンドではこれが確実で、
  整理②の担当がそのまま受けるのが自然である
- 各自が追記するなら、追記の作法（Read してから書く・追記のたびに `arp4 lint`）まで
  配る → [reconcile.md](reconcile.md)

**書き込み役を 1 人に決めたなら、担当には「書けないときの逃げ道」まで配る。**
[organize.md](organize.md) は、改名した語の `aliases`（「移行」→「移行するデータの範囲」）も
語彙の提案も、この 2 本に書けと言う。**書くなと配られた担当は、そこで行き先を失う** ――
書く先が無いまま改名だけが残ると、資料を持っている人が名寄せできなくなる。**分担中は担当の
最終報告へ回し、合流のときに配る側がまとめて書く**と決めて配ること（報告文の形は 6 項の
「コード・件数・`about`・`reason`・`source`」と同じでよい）。**「書くな」だけを配らない。**

## 10. 報告に載せる数字は、機械が印字したものだけにする

通し終わったら成果を 1 枚にまとめることになるが、**そこに書く数はコマンドの出力から採る。**

| 数 | 出どころ |
| --- | --- |
| パースファイル / アンカー | `arp4 parse` の最終行 |
| レコード / 対象外 / 未整理 / 凍結したファイル | `arp4 freeze` |
| アイテム / 関係 / 機械の判断 | `arp4 build` |
| 採番 | `arp4 number` |
| error / warn と内訳 | `arp4 check --strict --summary` |
| 生成したファイルと**うち設計書** | `arp4 publish` |

**印字されない数は数えない。**関係の本数（`realizes` が何本か）・`_metamodel-add.yml` の
`notes` が何件か・`out/` に何ファイルあるかは、どのコマンドも言わない ―― 手で数えると
外れる。実測（sales-corpus r001）の報告で、印字された数（201・621・1127・447・757・875・
171・460・error 0 / warn 213）は**全部合っていて**、手で数えた 2 つ（`realizes` を 25 と
書いた。実際は 28 ／ 語彙の穴を 25 件と書いた。実際は 27）だけが外れた。

**どうしても要るなら、数える代わりに出典を書く。**「`realizes` は
`.arp/spec/relations/realizes.yml` にある」と書けば、読む人が開いて数えられる。

**内訳は `--summary` の行をそのまま写す。**`check` は 1 つの `code` が複数の言い分に
割れているとき件数つきで展開する（`W031 71 件` の内訳は constrains 60 / realizes 11）。
**「warn 213」だけを書くと、何が 213 なのかが報告から消える。**
