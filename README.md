# ai-ready-pipeline 4 ― 設計書を書かず、仕様をデータで持つ

**この文書は利用者向けである。**エージェントへの手順書は `surface/` にあり、
`build/build.py` が `.claude` / `.github` へ展開する。

既存資産 ―― Excel の設計書・ソースコード・DDL・Markdown の設計メモ ―― を起点に、
**仕様をリレーショナルな正本データ**にする。設計書はそこから生成する。

```
既存資産（Excel・コード・DDL・Markdown）―― いまある場所のまま
    │  arp4 parse            機械：資料 → パース結果（意味を判断しない）
    ▼
.arp/rounds/r001/parsed/**.md   編集可・git 管理
    │  ★ エージェント       整理：型付きレコード・concept 割当・矛盾摘出
    ▼                        ここだけが意味を判断する
.arp/rounds/r001/organized/  ── arp4 freeze ──→ 凍結（出典を固定する）
    │  arp4 build            機械：マージ・採番・整合性（意味を判断しない）
    ▼
.arp/spec/  concepts.yml + items/ + relations/（＋ derived/ ―― AI の解釈層）
    │  arp4 check → arp4 publish
    ▼
.arp/out/<工程>/   設計書 12 種 ＋ 決定記録 ＋ 点検の 2 枚
```

**判断が要る層は 1 つだけである。** 機械抽出はセルの中身をそのまま出す、エージェントは
意味だけを決める、機械構築は照合・採番・整合性だけをやる。責任の所在を層で分けている
ので、「なぜこの仕様がこう書かれているのか」は必ず 1 つの層まで辿れる。

## 何が出てくるか

`arp4 publish` が V 字の工程ごとのフォルダへ Markdown と HTML を出す。

| 工程 | 設計書 |
| --- | --- |
| `1_企画` | プロジェクト計画書 |
| `2_要件定義` | 要件定義書 |
| `3_基本設計` | 基本設計書・テーブル定義書・画面帳票項目定義書・CRUD 図・権限マトリクス |
| `4_詳細設計` | 詳細設計書 |
| `5_テスト` | テスト仕様書・テスト結果報告書 |
| `6_管理` | 課題管理表・トレーサビリティ・マトリクス |

**番号はメタモデルの `layers`（V 字の順）である。**工程を足すと繰り下がるので、生成物へ
外部からリンクを張っているなら張り直しが要る（`out/` は再生成物なので、直すのは指している
側である）。

これに加えて、**この束が何を言えていないかを言う 2 枚**が目次の先頭に出る。

| | 中身 |
| --- | --- |
| `0_この設計書の穴.md` | 未解決の指摘・決着していない矛盾・機械が読めなかったもの・資料に定義が無いと確かめたもの・様式にあるのに値を持たない列 |
| `0_元資料と設計書の対応.md` | **反対側** ―― 届いた資料のどれが設計書に 1 度も出ていないか。資料を渡した側が最初に知りたいのはこちらである |

```bash
arp4 publish --audience stakeholder   # PM・顧客向け 6 種（out/stakeholder/）
```

読者別の生成は**解釈層（`.arp/spec/derived/`）から組む**ので、そこが空だと 6 種のうち
3 種が空で出る。概要・機能一覧・処理フロー図は「資料のどこにも書かれていないもの」なので、
正本からは作れない（用語集・構成図・テスト状況サマリは正本だけから組む）。

`out/決定記録.md` には、**機械**（`draft` / `build` / `auto`）が下した判断が全件出る ――
**無承認で通したパイプラインの事後拒否権の入口**である。**エージェントの判断はここへ来ない**
―― 整理層の記録は `organized/**.yml` そのもの（git の差分）と、`out_of_scope` の `reason`・
`known_gaps` の理由である。

## 導入

**PyPI には出していない。**ソースの場所を指して入れる。LLM の API 鍵は要らない
（整理はエージェントがやるので、パイプラインの中に LLM 呼び出しは無い）。

```bash
python -m venv .venv                                      # Python 3.11 以上
.venv/Scripts/python -m pip install -e ".[parse]"         # console script arp4 が入る
arp4 --help
```

| extras | 何のために | 前提 |
| --- | --- | --- |
| （なし） | メタモデル・正本・検証・生成。依存は PyYAML 1 本 | ― |
| `[parse]` | `arp4 parse` が Excel を読む（openpyxl） | ― |
| `[render]` | `arp4 render` がシートを画像化する | **Windows ＋ Microsoft Excel** |
| `[check]` | 開発用（生成した Markdown を人と同じ規則で読み戻す） | ― |

`[render]` に代替は無い ―― 図形・罫線・塗りを見た目どおり撮れるのは Excel 自身だけである。
入っていない環境では、機械が読めなかった図は `未読取` のまま次のラウンドへ持ち越される
（黙って「対象外」にはならない）。

**日本語 Windows で出力が化けたら、端末の符号化を先に直す。**指摘も件数も読めないまま
進むことになる。

```bash
PYTHONIOENCODING=utf-8 arp4 model                    # Git Bash など UTF-8 の端末
```
```powershell
[Console]::OutputEncoding = [Text.Encoding]::UTF8    # PowerShell（1 回でよい）
```

## 使い方

**`--root` を必ず明示する。**省くと置き場は cwd から決まる ―― エージェントは一時フォルダで
作業することがあり、そこで打つとエラーも警告も出ないまま、成果物がセッションの終わりに
消える場所へ出る。

### 資産がコードだけなら 2 コマンド

```bash
arp4 auto --root "$R" "$R"/src "$R"/tests --exclude "tests/dataset/正解/*"
#   → exit 3: エージェントの手番（文章化スロットの一覧が出る）
arp4 auto --root "$R" "$R"/src "$R"/tests --exclude "tests/dataset/正解/*"
#   → exit 0: 設計書一式
```

`auto` は parse → draft → freeze → build → number → check → publish を通す。止まるのは
**エージェントの手番**（exit 3）と**機械では判断できない矛盾**（exit 1）だけで、承認のための
停止は無い ―― 機械の判断は全件 `decisions.yml` に残り、`out/決定記録.md` から差し戻せる。

### Excel が混ざるなら 1 コマンドずつ

```bash
R=<対象のリポジトリ>

arp4 init   --root "$R"
arp4 model  --root "$R"                                  # 使ってよい語彙
arp4 schema --root "$R"                                  # 書いてよい形
arp4 parse  --root "$R" "$R"/src "$R"/ddl "$R"/資料       # ① パスは必須
arp4 draft  --root "$R"                                  # コードの骨格
arp4 render --root "$R" "$R"/資料                        # 図形を絵にする
arp4 freeze --root "$R" --dry-run                        # 残作業の一覧
#   ★ ここでエージェントが parsed/ を読んで organized/ を書く
arp4 freeze --root "$R"                                  # ② 凍結
arp4 build  --root "$R"                                  # ③ 正本へ
arp4 number --root "$R"                                  # 採番（check より先）
arp4 check  --root "$R" --strict
arp4 publish --root "$R"
```

**渡すパスは「何を仕様として見るか」の宣言である。**根ごと渡すと `.venv/` も
`node_modules/` も歩く。パース結果のフォルダ構造は**渡したパスの共通の親**から写すので、
`src/` と `ddl/` を渡せば `src/…` `ddl/…` と並ぶ。

**コードと DDL と設計メモも渡すこと。**Excel の資料だけを渡すと、テスト仕様書・テーブル
定義書・課題管理表が空のまま出る ―― それらの語彙は `.sql` と `test_*.py` と `.md` にしか
無い。

### コマンド

| コマンド | 何をするか |
| --- | --- |
| `arp4 init` | 置き場（`.arp/`）の骨組みを作る |
| `arp4 model` | 使ってよい語彙（`--attributes` で属性・enum の値まで） |
| `arp4 schema` | 書いてよい形（`model` と対。整理層の契約） |
| `arp4 parse <パス>…` | ① 既存資産 → パース結果 |
| `arp4 render <パス>…` | 機械が読めなかった範囲を絵にする |
| `arp4 declare <型>` | 同じ構成のシートを一括で対象外宣言する（表紙・改訂履歴） |
| `arp4 draft` | コードのパース結果から整理結果の骨格を機械生成する |
| `arp4 lint <パス>…` | 整理結果を 1 ファイル単位で検査する（`freeze` の部分集合） |
| `arp4 freeze` | ② 凍結（`--dry-run` は残作業の一覧になる） |
| `arp4 build` | ③ 整理結果 → 正本 |
| `arp4 number` | 表示 ID を採番する（`FR-001` / `RUL-001` / `CST-001`） |
| `arp4 check` | 正本を検証する（構造・参照整合性・多重度・出典・設計書の形） |
| `arp4 publish` | 設計書を生成する（`--audience stakeholder` で読者別） |
| `arp4 auto <パス>…` | parse から publish までを通す |
| `arp4 lock` / `conform` | 標準パック準拠（CI 用） |

**整理はコマンドではない。**エージェントが `parsed/` を読んで `organized/` を書く。

### 指摘の読み方

`check` / `lint` / `conform` の**終了コードは 3 値**である ―― error = 1 / warn のみ
（`--strict`）= 2 / clean = 0。そのほかのコマンドは 2 値（0 = 成功）で意味が違う。

指摘は数百件になるので**畳んで出る**。全体像から 1 種類ずつ開く。

```bash
arp4 check --summary          # code ごとの件数（十数行）
arp4 check --code W043        # その系だけを切らずに全部（--code W0 で系ごと）
cat .arp/out/findings.json    # 全件。毎回書かれる（UTF-8・畳みなし）
```

**打ち手はメッセージ本文に書いてある。**`[error] G013 …/受注.yml:47 s1-t1: 参照だけの
レコードしかありません（いちばん詳しい 1 シートで type / name / statement を書いて
ください）` の形で、`ファイル:行` がそのまま開ける場所である。

| 系 | 何を見ているか |
| --- | --- |
| `P0xx` | パース ―― **資料を読めたか** |
| `G0xx` | 整理結果と凍結ゲート |
| `B0xx` | 機械構築（マージ・関係・台帳） |
| `E0xx` / `W0xx` | 正本データの不備 / 警告 |
| `P1xx` | **出来上がった設計書が読めるものになっているか**（すべて warn） |
| `D0xx` | 解釈層（根拠・確度） |
| `M0xx` / `C0xx` / `I0xx` | メタモデル / パック準拠 / 置き場 |

`P1xx` は `publish` を止めない ―― 指摘は `0_この設計書の穴.md` に残るので、**`check` と
`publish` の両方を見る。**

## 置き場

```
<project>/                         arp4 はここに何も作らない
├── src/  ddl/  docs/  資料/       元資料。いまある場所のまま。触らない
└── .arp/
    ├── rounds/r001/               ラウンド ①（ディレクトリで切る）
    │   ├── round.yml              いつ・なぜ起こしたか
    │   ├── sources.yml            撮った時点の原本の指紋（G019 の根拠）
    │   ├── decisions.yml          機械（draft / build / auto）が下した判断の全件
    │   ├── parsed/                機械抽出。編集可・git 管理
    │   ├── images/                シートから取り出した画像と render の絵
    │   └── organized/             整理結果。凍結後は編集しない
    │       ├── 資料/A/…/受注テーブル.yml   整理①（parsed と 1:1）
    │       ├── _concepts.yml               整理②（同一性・用語・矛盾）
    │       ├── _metamodel-add.yml          語彙の追加提案
    │       └── .frozen.yml                 凍結マニフェスト
    ├── spec/                      正本 ― プロジェクトが決めたこと
    │   ├── metamodel.yml          extends: jp-sier-std
    │   ├── concepts.yml           同一性の台帳（ラウンドをまたぐ）
    │   ├── items/*.yml  relations/*.yml
    │   └── derived/               AI の解釈層（basis / confidence 必須）
    ├── policy.yml                 任意 ― auto_approve の宣言（下記）
    ├── out/                       生成物（直接編集しない）
    └── .gitignore                 out/ だけを無視する
```

**arp4 が作るものは 1 つ残らず `.arp/` の中へ入る。**`rounds` も `sources` も一般名詞なので、
配布先の直下に置くと相手の持ち物と衝突する ―― arp4 は他人のリポジトリで動くツールである。

**`.arp/` は「機械のもの」ではない。**中の `rounds/` は人とエージェントが編集し、git で
管理する。だから `.arp/.gitignore` が無視するのは `out/` だけである ―― `.arp/` を丸ごと
無視すると「機械が最初に出したもの」と「人が直したもの」の区別が消えるが、**エラーには
ならない。**

**`organized/` と `spec/` を分けているのは、「資料にそう書いてある」と「我々がそう決めた」を
混ぜると、決定の責任者が誰なのかが永久に分からなくなるからである。**あとから分かったことは
整理結果ではなく正本側に `overridden`（値の上書き）・`known_gaps`（資料に定義が無い）として
記録する ―― どちらも理由必須。

**元資料は動かさない。**集める先を作らないのは、パース結果を編集可能にしたためである ――
**元資料が動かないことだけが、パース結果の編集を検証可能にする。**コピーすると
`sources.yml` の指紋が写しの指紋になり、上流のずれ（`G019`）を見なくなる。

**ラウンド名は連番**（`r001`）で、日付では切らない。日付名にしていたときは、同じ資料を別の日に
処理し直すだけで別ラウンドになり、整理をやり直すことになった。ラウンドは「いつ作業したか」
ではなく「**どの資料の版を扱っているか**」の単位である。`arp4 parse` の既定の宛先は
まだ凍結していないいちばん新しいラウンドで、資料が更新されたときだけ `--new-round` で次を
起こす。

### 承認の方針

既定ではすべて `status: review` で入る。`check` が error 0 のとき approved へ自動昇格させたい
プロジェクトだけ、`.arp/policy.yml` に書く。

```yaml
auto_approve: true
```

課題（`open-issue`）は設定に関わらず昇格しない ―― **矛盾の裁定だけは常に人の仕事**として
残す。昇格も決定記録に載る。

## エージェントに任せる範囲

整理層だけである。`parse` / `draft` / `build` / `check` / `publish` は機械の仕事で、
エージェントがやるのは `parsed/**.md` を読んで `organized/**.yml` を書くこと 1 つ。

```bash
python build/build.py                      # このリポジトリへスキルを展開する
python build/build.py --root <消費側>      # 消費側プロジェクトへ展開する
python build/build.py --check              # 展開が古くないか（CI 用）
```

展開されるのは `SKILL.md`（工程の地図）と `docs/` 11 ページで、**必要になったページだけを
読ませる**設計である。**展開先（`.claude` / `.github`）を直接編集しない** ―― 直すのは
`surface/` のほうで、宣言は `surface/manifest.yaml` に 1 行足す。

| ページ | いつ読む |
| --- | --- |
| `parse.md` | パース結果を読むとき（アンカーの種類・空欄に見えて空欄でないもの） |
| `organize.md` | **整理層の本体**（レコードの契約） |
| `sheets.md` | 日本の Excel 設計書の形ごとの落とし穴 |
| `code.md` | コード資産（draft・文章化・auto） |
| `reconcile.md` | 横断整理（同一性・分類・命名・矛盾） |
| `split.md` | Excel の整理を複数人・複数エージェントで分担するとき |
| `freeze.md` / `build.md` / `publish.md` | 各工程 |
| `derived.md` | PM・顧客向けを出すとき |
| `troubleshooting.md` | 検出コードの索引 |

**分担するときは配る前に `split.md` を読むこと。**手順書に書いていない判断は人数分に割れる。

## 設計 ― なぜこの形なのか

### 決定論の抽出をやめた

3 は「型が合う表は決定論、合わない表だけ LLM」という分業で、実測（Excel 30 冊 /
67,191 文字）では決定論が 59% を読めていた。これは**当時の LLM の信頼性を前提にした節約**
である。やめた理由は 2 つ。

1. **LLM の精度が、機械の当てにいく精度を上回った。** Excel の表領域・結合セル・見出し段組みは
   本質的に曖昧で、機械が当てにいくとルールが際限なく増える。宣言（3 の `tables.yml`）を
   保守し続ける負債に見合わない
2. **宣言が当たらない資料では 0 点になる。** 決定論は当たれば正確だが、当たらなければ何も
   返さない。既存資産を起点にする現場では、**当たらない資料のほうが多い**

ただし**コードは例外**である。クラス・メソッド・シグネチャは構文木で曖昧さゼロに取れるので、
ここに LLM を使っても精度は上がらない。**Excel はエージェント一本、コードの骨格だけ決定論**
という非対称を持つ → [docs/parsed.md](docs/parsed.md)

### 凍結が保証を担う

3 の中核は再現性ゲート（`R001`「同じファクトから 2 回で同じ正本」）だった。抽出者が
エージェントになった 4 では、この保証は原理的に作れない。

代わりに置いたのが**凍結**である。整理結果は横断整理まで終えた時点で凍結し、以後編集しない。
**凍結は制約ではなく保証**で、出典アンカーが永久に動かないので、正本のどのレコードからでも
「資料はこう言っていた」に確実に辿り着ける。3 はファクト層を再生成対象にしていたので、この
保証が無かった。

凍結は宣言ではなく**ゲート**として実装する。5 条件（未整理 0 / 語彙外 0 / concept 実在 /
関係の組み合わせ / 参照だけのレコードの種別）を通ったときだけハッシュを固定する。通れば
機械構築は原理的に失敗しない → [docs/freeze.md](docs/freeze.md)

### 「資料に無い」と「機械が読めていない」を混ぜない

パース層がいちばん強く守っている規律である。どちらも表の上では空欄にしか見えないが、
**次のラウンドで拾い直すかどうかが正反対になる。**だから計算結果の無い数式・エラー値・
取り消し線・非表示シート・貼り付け画像は、それぞれ別のアンカーとして必ず申告される。

同じ規律は下流にも通す ―― 対象外の宣言は `対象外`（仕様が書かれていない）と `未読取`
（機械が読めていない）に分かれ、正本では `known_gaps`（資料に定義が無い）が理由付きで残り、
生成物では `0_この設計書の穴.md` が「様式が持つ欄に正本が値を持たない」としか言わない
（資料にその欄が無いのか、整理のときに写されなかったのかは**資料を見た人にしか分からない**）。

### 3 から捨てたもの

| 捨てたもの | 理由 |
| --- | --- |
| `tables.yml`（表の型宣言） | LLM が整理するので型を当てにいく必要がない。保守負債も消える |
| `reconcile` / `ledger`（名寄せ・裁定台帳） | 整理②で `concept` が確定済み。機械のマージは「同じキーなら同じアイテム」だけ |
| `R001`（再現性ゲート） | 再生成しないので 2 回目が走らない。凍結ハッシュが代替 |
| `name` / `classify`（暫定名の修正・分類） | 整理段階で最初から名前と `rule_kind` を付ける |
| `extract --measure` | 凍結ゲートの網羅条件に吸収 |
| `prose.py` / `llm.py`（CLI 内の LLM 呼び出し） | エージェントが直接読む。プロバイダ設定・キャッシュ・`.env` が不要になる |
| `edited`（再変換からの保護） | 再生成しないので保護が要らない。代わりに `overridden`（理由必須）を持つ |
| `facts` 層の内容ハッシュ ID | 出典がアンカーで固定されるので、内容から ID を作る必要がない |

## 資材（バイナリは置かない）

Excel はバイナリなので、**中身がコードで読める形**でしか置かない ―― 置いてしまうと「この
資料は何を写したものか」が半年後に誰にも分からなくなる。3 つとも生成器である。

| 資材 | 規模 | 何のためにあるか |
| --- | --- | --- |
| `examples/from-excel` | 資料 2 冊 | `parse → 整理 → freeze → build → publish` を**通しで**確かめる最小サンプル（`tests/test_example.py` が同じ道を通る） |
| `tests/corpus.py` | 20 冊 / 35 シート | **パースの検体**。数式・非表示・貼り付け画像・マクロ付き・シート名衝突・壊れたブックなど、実物によくある書かれ方を集めたもの |
| `examples/sales-corpus` | 30 冊 / 201 シート ＋ Java 114 本 | **架空の新販売管理システム一式**。日本の SIer の設計書の形（2 段見出し・縦結合・図形＋コネクタ・結合セル作図）と、矛盾・粒度差・表記ゆれ・重複を仕込んである → [README](examples/sales-corpus/README.md) |

```bash
python examples/make_sample.py                  # 最小サンプルの資料 2 冊
python tests/corpus.py <ディレクトリ>            # パースの検体
python examples/sales-corpus/build.py --clean   # 資料 30 冊・実装 116 ファイル
```

`tests/corpus.py` と `sales-corpus` は役割が違う。**前者は 1 つの欠陥を 1 つのシートで突く
検体**（壊れ方が特定できる）、**後者は 30 冊を丸ごと通したときに何が起きるかの検体**（現場の
規模でしか出ない問題を出す）。片方だけでは足りない。
