# ai-ready-pipeline 4 ― 設計書を書かず、仕様をデータで持つ

> この文書は**利用者向け**です。エージェントへの手順書は `surface/` にあり、
> `build/build.py` が `.claude` / `.github` へ展開します。

いま手元にある資産 ―― Excel・Word・PowerPoint・PDF・CSV の設計書、ソースコード、DDL、
Markdown の設計メモ ―― を起点にして、**仕様をリレーショナルな正本データ**にします。
設計書は、そのデータから生成します。

```
既存資産（文書・コード・DDL）―― いまある場所のまま
    │  arp4 parse            機械：資料 → パース結果（意味を判断しない）
    ▼
.arp/rounds/r001/parsed/**.md   編集可・git 管理
    │  ★ エージェント       整理：型付きレコード・concept 割当・矛盾摘出
    ▼                        ここだけが意味を判断する
.arp/rounds/r001/organized/  ── arp4 freeze ──→ 凍結（出典を固定する）
    │  arp4 build            機械：マージ・採番・整合性（意味を判断しない）
    ▼
.arp/spec/  concepts.yml + items/ + relations/（＋ derived/ ―― AI の解釈層）
    │  arp4 check → arp4 publish
    ▼
.arp/out/<工程>/   設計書 13 種 ＋ 決定記録 ＋ 点検の 2 枚
```

判断が要る層は 1 つだけです。パースはセルの中身をそのまま出し、エージェントは意味だけを
決め、構築は照合・採番・整合性だけをやります。責任の所在を層で分けているので、
「なぜこの仕様がこう書かれているのか」は必ず 1 つの層まで辿れます。

## 何が出てくるか

`arp4 publish` が、V 字の工程ごとのフォルダへ Markdown と HTML を出します。

| 工程 | 設計書 |
| --- | --- |
| `1_企画` | プロジェクト計画書 |
| `2_要件定義` | 要件定義書 |
| `3_基本設計` | 基本設計書・テーブル定義書・画面帳票項目定義書・CRUD 図・権限マトリクス |
| `4_詳細設計` | 詳細設計書 |
| `5_プログラム設計` | プログラム設計書 |
| `6_テスト` | テスト仕様書・テスト結果報告書 |
| `7_管理` | 課題管理表・トレーサビリティ・マトリクス |

先頭の番号はメタモデルの `layers`（V 字の順）です。工程を足すと番号が繰り下がるので、
生成物へ外部からリンクを張っているなら張り直しが要ります。`out/` は再生成物なので、
直すのは指している側です。

### 「言えていないこと」を言う 2 枚

設計書に加えて、**この束が何を言えていないか**を示す 2 枚が目次の先頭に出ます。

| | 中身 |
| --- | --- |
| `0_この設計書の穴.md` | 未解決の指摘・決着していない矛盾・機械が読めなかったもの・版差で写さなかったもの・資料に定義が無いと確かめたもの・様式にあるのに値を持たない列 |
| `0_元資料と設計書の対応.md` | **反対側**。届いた資料のどれが設計書に 1 度も出ていないか。資料を渡した側が最初に知りたいのは、こちらです |

### 読者別に出す

```bash
arp4 publish --audience stakeholder   # PM・顧客向け 6 種（out/stakeholder/）
```

読者別の生成は解釈層（`.arp/spec/derived/`）から組み立てます。そこが空だと 6 種のうち
3 種が空で出ます。概要・機能一覧・処理フロー図は「資料のどこにも書かれていないもの」なので、
正本からは作れません（用語集・構成図・テスト状況サマリは正本だけから組みます）。

### 決定記録

`out/決定記録.md` には、**機械**（`draft` / `build` / `auto`）が下した判断が全件出ます。
無承認で通したパイプラインに対する、事後拒否権の入口です。

エージェントの判断はここへは来ません。整理層の記録は `organized/**.yml` そのもの
（git の差分）と、`out_of_scope` の `reason`・`revisions` の `reason`・`known_gaps` の
理由です。

## 導入

PyPI には出していないので、ソースの場所を指して入れてください。LLM の API 鍵は要りません
（整理はエージェントがやるので、パイプラインの中に LLM 呼び出しはありません）。

```bash
python -m venv .venv                                      # Python 3.11 以上
.venv/Scripts/python -m pip install -e ".[parse]"         # console script arp4 が入る
arp4 --help
```

| extras | 何のために | 前提 |
| --- | --- | --- |
| （なし） | メタモデル・正本・検証・生成と、Word・PowerPoint・PDF・CSV の取り込み。依存は PyYAML と PDF の読み手（pypdfium2 / Pillow） | ― |
| `[parse]` | `arp4 parse` が **Excel** を読む（openpyxl） | ― |
| `[render]` | `arp4 render` がシートを画像化する | **Windows ＋ Microsoft Excel** |
| `[check]` | 開発用（生成した Markdown を人と同じ規則で読み戻す） | ― |

### 画像まわりの前提

`[render]` に代替はありません。図形・罫線・塗りを見た目どおり撮れるのは Excel 自身だけです。
入っていない環境では、機械が読めなかった図は `未読取` のまま次のラウンドへ持ち越されます
（黙って「対象外」にはなりません）。

貼り付け画像の中の文字は `arp4 parse` が読みます。Windows OCR を使うので、extras も追加の
インストールも要りません（Windows に最初から入っているものを `powershell.exe` 経由で呼びます）。
Windows でない環境や言語パックの無い環境では読まずに `P016` で申告します。画像の実体は出て
いるので整理層が開けば読めますが、そのぶん読む量は増えます。

### 日本語 Windows で文字化けしたら

先に端末の符号化を直してください。そのままだと、指摘も件数も読めないまま進むことになります。

```bash
PYTHONIOENCODING=utf-8 arp4 model                    # Git Bash など UTF-8 の端末
```
```powershell
[Console]::OutputEncoding = [Text.Encoding]::UTF8    # PowerShell（1 回でよい）
```

## 使い方

まず 1 つだけ。**`--root` は必ず明示してください。**省くと置き場は cwd から決まります。
エージェントは一時フォルダで作業することがあり、そこで打つと、エラーも警告も出ないまま
成果物がセッションの終わりに消える場所へ出ます。

### 資産がコードだけなら 2 コマンド

```bash
arp4 auto --root "$R" "$R"/src "$R"/tests --exclude "tests/dataset/正解/*"
#   → exit 3: エージェントの手番（文章化スロットの一覧が出る）
arp4 auto --root "$R" "$R"/src "$R"/tests --exclude "tests/dataset/正解/*"
#   → exit 0: 設計書一式
```

`auto` は parse → draft → freeze → build → number → check → publish を通します。
止まるのは**エージェントの手番**（exit 3）と**機械では判断できない矛盾**（exit 1）の
2 つだけで、承認のための停止はありません。機械の判断は全件 `decisions.yml` に残るので、
`out/決定記録.md` から差し戻せます。

### Excel が混ざるなら 1 コマンドずつ

```bash
R=<対象のリポジトリ>

arp4 init   --root "$R"
arp4 model  --root "$R"                                  # 使ってよい語彙
arp4 schema --root "$R"                                  # 書いてよい形
arp4 parse  --root "$R" "$R"/src "$R"/ddl "$R"/資料       # ① パスは必須
arp4 draft  --root "$R"                                  # コードの骨格
arp4 render --root "$R" "$R"/資料                        # 図形を絵にする
arp4 freeze --root "$R" --dry-run                        # 残作業の一覧
#   ★ ここでエージェントが parsed/ を読んで organized/ を書く
arp4 freeze --root "$R"                                  # ② 凍結
arp4 build  --root "$R"                                  # ③ 正本へ
arp4 design --root "$R"                                  # プログラム設計の骨格（→ ★ 文章化 → freeze → build）
arp4 number --root "$R"                                  # 採番（check より先）
arp4 check  --root "$R" --strict
arp4 publish --root "$R"
arp4 emit    --root "$R"                                  # 決まっているものだけコードにする
arp4 verify  --root "$R" "$R"/src                        # 実装と正本を突き合わせる
```

渡すパスは「何を仕様として見るか」の宣言です。根ごと渡すと `.venv/` も `node_modules/` も
歩きます。パース結果のフォルダ構造は**渡したパスの共通の親**から写すので、`src/` と `ddl/` を
渡せば `src/…` `ddl/…` と並びます。

**コードと DDL と設計メモも渡してください。**Excel の資料だけを渡すと、テスト仕様書・
テーブル定義書・課題管理表が空のまま出ます。それらの語彙は `.sql` と `test_*.py` と `.md`
にしかありません。

### コマンド

| コマンド | 何をするか |
| --- | --- |
| `arp4 init` | 置き場（`.arp/`）の骨組みを作る |
| `arp4 model` | 使ってよい語彙（`--attributes` で属性・enum の値まで） |
| `arp4 schema` | 書いてよい形（`model` と対。整理層の契約） |
| `arp4 parse <パス>…` | ① 既存資産 → パース結果 |
| `arp4 render <パス>…` | 機械が読めなかった範囲を絵にする |
| `arp4 declare <型>` | 同じ構成のシートを一括で対象外宣言する（表紙）。`--dropped <版>` で旧版の冊子 |
| `arp4 draft` | コードのパース結果から整理結果の骨格を機械生成する |
| `arp4 lint <パス>…` | 整理結果を 1 ファイル単位で検査する（`freeze` の部分集合） |
| `arp4 freeze` | ② 凍結（`--dry-run` は残作業の一覧になる） |
| `arp4 build` | ③ 整理結果 → 正本 |
| `arp4 design` | 正本からプログラム設計の骨格を機械生成する（`draft` の鏡像。引数・問い合わせ・実装の座標） |
| `arp4 number` | 表示 ID を採番する（`FR-001` / `RUL-001` / `CST-001`） |
| `arp4 check` | 正本を検証する（構造・参照整合性・多重度・出典・設計書の形） |
| `arp4 publish` | 設計書を生成する（`--audience stakeholder` で読者別） |
| `arp4 emit` | 正本から**決まっているものだけ**をコードにする（DDL・骨格・コード定義・メッセージ。本体は書かない） |
| `arp4 verify <パス>…` | 実装を読み直して正本と突き合わせる（引数の食い違いは error）。**揺れを測る口** |
| `arp4 show <出典>` | 設計書の出典からパース結果の塊を開く（索引の逆関数） |
| `arp4 grep <語>` | パース結果を横断して探す（当たりは塊で返る。表は段を重ねた列名付き、写しの名前にも当たる） |
| `arp4 index` | パース結果の索引（塊の一覧）を出す |
| `arp4 auto <パス>…` | parse から publish までを通す |
| `arp4 lock` / `conform` | 標準パック準拠（CI 用） |

整理はコマンドではありません。エージェントが `parsed/` を読んで `organized/` を書きます。

### 指摘の読み方

`check` / `lint` / `conform` の**終了コードは 3 値**です ―― error = 1 / warn のみ
（`--strict`）= 2 / clean = 0。そのほかのコマンドは 2 値（0 = 成功）で、意味が違います。

指摘は数百件になるので、既定では畳んで出ます。全体像を見てから 1 種類ずつ開いてください。

```bash
arp4 check --summary          # code ごとの件数（十数行）
arp4 check --code W043        # その系だけを切らずに全部（--code W0 で系ごと）
cat .arp/out/findings.json    # 全件。毎回書かれる（UTF-8・畳みなし）
```

打ち手はメッセージ本文に書いてあります。

```
[error] G013 …/受注.yml:47 s1-t1: 参照だけのレコードしかありません
        （いちばん詳しい 1 シートで type / name / statement を書いてください）
```

`ファイル:行` は、そのまま開ける場所です。

| 系 | 何を見ているか |
| --- | --- |
| `P0xx` | パース ―― **資料を読めたか** |
| `G0xx` | 整理結果と凍結ゲート |
| `B0xx` | 機械構築（マージ・関係・台帳） |
| `E0xx` / `W0xx` | 正本データの不備 / 警告 |
| `P1xx` | **出来上がった設計書が読めるものになっているか**（すべて warn） |
| `D0xx` | 解釈層（根拠・確度） |
| `M0xx` / `C0xx` / `I0xx` | メタモデル / パック準拠 / 置き場 |

`P1xx` は `publish` を止めません。指摘は `0_この設計書の穴.md` に残るので、
`check` と `publish` の両方を見てください。

## 置き場

```
<project>/                         arp4 はここに何も作らない
├── src/  ddl/  docs/  資料/       元資料。いまある場所のまま。触らない
└── .arp/
    ├── rounds/r001/               ラウンド ①（ディレクトリで切る）
    │   ├── round.yml              いつ・なぜ起こしたか
    │   ├── sources.yml            撮った時点の原本の指紋（G019 の根拠）
    │   ├── decisions.yml          機械（draft / build / auto）が下した判断の全件
    │   ├── parsed/                機械抽出。編集可・git 管理
    │   ├── images/                シートから取り出した画像と render の絵
    │   └── organized/             整理結果。凍結後は編集しない
    │       ├── 資料/A/…/受注テーブル.yml   整理①（parsed と 1:1）
    │       ├── _concepts.yml               整理②（同一性・用語・矛盾）
    │       ├── _metamodel-add.yml          語彙の追加提案
    │       └── .frozen.yml                 凍結マニフェスト
    ├── spec/                      正本 ― プロジェクトが決めたこと
    │   ├── metamodel.yml          extends: jp-sier-std
    │   ├── concepts.yml           同一性の台帳（ラウンドをまたぐ）
    │   ├── items/*.yml  relations/*.yml
    │   └── derived/               AI の解釈層（basis / confidence 必須）
    ├── policy.yml                 任意 ― auto_approve の宣言（下記）
    ├── out/                       生成物（直接編集しない）
    └── .gitignore                 out/ だけを無視する
```

**arp4 が作るものは 1 つ残らず `.arp/` の中へ入ります。**`rounds` も `sources` も一般名詞
なので、配布先の直下に置くと相手の持ち物と衝突します。arp4 は他人のリポジトリで動くツール
です。

`.arp/` は「機械のもの」ではありません。中の `rounds/` は人とエージェントが編集し、git で
管理します。だから `.arp/.gitignore` が無視するのは `out/` だけです。`.arp/` を丸ごと無視
すると「機械が最初に出したもの」と「人が直したもの」の区別が消えますが、エラーにはなりません。

### なぜ `organized/` と `spec/` を分けるのか

「資料にそう書いてある」と「我々がそう決めた」を混ぜると、決定の責任者が誰なのかが永久に
分からなくなるからです。あとから分かったことは、整理結果ではなく正本側に記録します ――
`overridden`（値の上書き）と `known_gaps`（資料に定義が無い）で、どちらも理由が必須です。

### なぜ元資料を動かさないのか

集める先を作らないのは、パース結果を編集可能にしたためです。**元資料が動かないことだけが、
パース結果の編集を検証可能にします。**コピーすると `sources.yml` の指紋が写しの指紋になり、
上流のずれ（`G019`）を見なくなります。

### ラウンドは日付で切らない

ラウンド名は連番（`r001`）です。日付名にしていたときは、同じ資料を別の日に処理し直すだけで
別ラウンドになり、整理をやり直すことになりました。ラウンドは「いつ作業したか」ではなく
「**どの資料の版を扱っているか**」の単位です。

`arp4 parse` の既定の宛先は、まだ凍結していないいちばん新しいラウンドです。資料が更新された
ときだけ `--new-round` で次を起こしてください。

### 承認の方針

既定ではすべて `status: review` で入ります。`check` が error 0 のときに approved へ自動昇格
させたいプロジェクトだけ、`.arp/policy.yml` に書いてください。

```yaml
auto_approve: true
```

課題（`open-issue`）は設定に関わらず昇格しません。**矛盾の裁定だけは常に人の仕事**として
残します。昇格も決定記録に載ります。

## エージェントに任せる範囲

整理層だけです。`parse` / `draft` / `build` / `check` / `publish` は機械の仕事で、
エージェントがやるのは `parsed/**.md` を読んで `organized/**.yml` を書くこと、1 つです。

```bash
python build/build.py                      # このリポジトリへスキルを展開する
python build/build.py --root <消費側>      # 消費側プロジェクトへ展開する
python build/build.py --check              # 展開が古くないか（CI 用）
```

展開されるのはスキル 2 つです。

- **`arp4`** ―― `SKILL.md`（工程の地図）＋ `docs/` 11 ページ。必要になったページだけを
  読ませます
- **`arp4-setup`** ―― 1 枚。起動コマンドの決定・導入・端末の符号化

環境の話を arp4 側に書いていないのは、これを読ませたいのが**arp4 が打てない状態のとき**で、
工程の地図とは読むタイミングが違うからです。

展開先（`.claude` / `.github`）は直接編集しないでください。直すのは `surface/` のほうで、
宣言は `surface/manifest.yaml` に 1 行足します。

| ページ | いつ読む |
| --- | --- |
| `parse.md` | パース結果を読むとき（アンカーの種類・空欄に見えて空欄でないもの） |
| `organize.md` | **整理層の本体**（レコードの契約・版の判断） |
| `sheets.md` | 日本の Excel 設計書の形ごとの落とし穴 |
| `code.md` | コード資産（draft・文章化・auto） |
| `reconcile.md` | 横断整理（同一性・分類・命名・矛盾） |
| `split.md` | Excel の整理を複数人・複数エージェントで分担するとき |
| `freeze.md` / `build.md` / `publish.md` | 各工程 |
| `derived.md` | PM・顧客向けを出すとき |
| `troubleshooting.md` | 検出コードの索引 |

分担するときは、配る前に `split.md` を読んでください。手順書に書いていない判断は、人数分に
割れます。

## 設計 ― なぜこの形なのか

### 決定論の抽出をやめた

3 は「型が合う表は決定論、合わない表だけ LLM」という分業でした。実測（Excel 30 冊 /
67,191 文字）では決定論が 59% を読めており、これは当時の LLM の信頼性を前提にした節約です。
やめた理由は 2 つあります。

1. **LLM の精度が、機械の当てにいく精度を上回った。**Excel の表領域・結合セル・見出し段組みは
   本質的に曖昧で、機械が当てにいくとルールが際限なく増えます。宣言（3 の `tables.yml`）を
   保守し続ける負債に見合いません
2. **宣言が当たらない資料では 0 点になる。**決定論は当たれば正確ですが、当たらなければ何も
   返しません。既存資産を起点にする現場では、当たらない資料のほうが多いのです

ただしコードは例外です。クラス・メソッド・シグネチャは構文木で曖昧さゼロに取れるので、
ここに LLM を使っても精度は上がりません。**Excel はエージェント一本、コードの骨格だけ決定論**
という非対称を持ちます → [docs/parsed.md](docs/parsed.md)

### 凍結が保証を担う

3 の中核は再現性ゲート（`R001`「同じファクトから 2 回で同じ正本」）でした。抽出者が
エージェントになった 4 では、この保証は原理的に作れません。

代わりに置いたのが**凍結**です。整理結果は横断整理まで終えた時点で凍結し、以後編集しません。
凍結は制約ではなく保証です ―― 出典アンカーが永久に動かないので、正本のどのレコードからでも
「資料はこう言っていた」に確実に辿り着けます。3 はファクト層を再生成対象にしていたので、
この保証がありませんでした。

凍結は宣言ではなく**ゲート**として実装しています。5 条件（未整理 0 / 語彙外 0 / concept 実在 /
関係の組み合わせ / 参照だけのレコードの種別）を通ったときだけハッシュを固定します。通れば
機械構築は原理的に失敗しません → [docs/freeze.md](docs/freeze.md)

### 「資料に無い」と「機械が読めていない」と「旧版だから落とした」を混ぜない

パース層がいちばん強く守っている規律です。3 つとも表の上では空欄にしか見えませんが、
**次に取るべき行動が正反対**になります。

| 空欄の正体 | どこに出るか | 次にやること |
| --- | --- | --- |
| 資料に定義が無い | `out_of_scope: 対象外` → `known_gaps` | 資料を作った側に聞く |
| 機械が読めていない | `out_of_scope: 未読取` | 次のラウンドで拾い直す |
| 旧版なので写さなかった | `revisions`（`dropped`） | 何もしない。要るなら元資料のその塊を開く |

だから計算結果の無い数式・エラー値・取り消し線・非表示シート・貼り付け画像は、それぞれ
別のアンカーとして必ず申告されます。貼り付け画像は中の文字も読んで別のアンカー（`o1`）に
出します。機械の読みなので読み違えが混ざりますが、そのぶん「絵である」画像がどれかは枚数で
言えます。

版差を独立させたのは、置き場が「矛盾」と「読み落とし」の 2 つしか無かったからです。1 冊の
中に旧版と新版が並ぶのは日本の設計書では普通の書かれ方で、判断せずに両方をレコードにすると
同じ concept に `statement` が 2 つ集まり、`build` は「長いほうを採る」（`B023`）でしか
決められません ―― 新旧と無関係な基準で現行仕様が決まってしまいます。凍結ゲートは、版の別が
書かれた塊を判断せずに写していると `G034` で止まります。

同じ規律は下流にも通します。生成物では `0_この設計書の穴.md` が「様式が持つ欄に正本が値を
持たない」としか言いません ―― 資料にその欄が無いのか、整理のときに写されなかったのかは、
**資料を見た人にしか分からない**からです。

### 3 から捨てたもの

| 捨てたもの | 理由 |
| --- | --- |
| `tables.yml`（表の型宣言） | LLM が整理するので型を当てにいく必要がない。保守負債も消える |
| `reconcile` / `ledger`（名寄せ・裁定台帳） | 整理②で `concept` が確定済み。機械のマージは「同じキーなら同じアイテム」だけ |
| `R001`（再現性ゲート） | 再生成しないので 2 回目が走らない。凍結ハッシュが代替 |
| `name` / `classify`（暫定名の修正・分類） | 整理段階で最初から名前と `rule_kind` を付ける |
| `extract --measure` | 凍結ゲートの網羅条件に吸収 |
| `prose.py` / `llm.py`（CLI 内の LLM 呼び出し） | エージェントが直接読む。プロバイダ設定・キャッシュ・`.env` が不要になる |
| `edited`（再変換からの保護） | 再生成しないので保護が要らない。代わりに `overridden`（理由必須）を持つ |
| `facts` 層の内容ハッシュ ID | 出典がアンカーで固定されるので、内容から ID を作る必要がない |

## 資材（バイナリは置かない）

Excel はバイナリなので、**中身がコードで読める形**でしか置きません。置いてしまうと
「この資料は何を写したものか」が半年後に誰にも分からなくなるからです。4 つとも生成器を
持っています。

| 資材 | 規模 | 何のためにあるか |
| --- | --- | --- |
| `examples/from-excel` | 資料 2 冊 | `parse → 整理 → freeze → build → publish` を**通しで**確かめる最小サンプル（`tests/test_example.py` が同じ道を通る） |
| `examples/from-documents` | 資料 4 冊 | **Excel 以外の見本**（`.pptx` `.docx` `.pdf` `.csv` を 1 冊ずつ）。中身は `tests/dataset/` の検体そのもので、開いて何が読めるかを確かめるためにある。密度は実案件の 1 冊に近い。内訳は下記 |
| `tests/dataset/難読.yml` ＋ `tests/organized/難読/` | 資料 6 冊 / 整理結果 42 本 | **束としての通し。**`from-documents` と同じ 4 形式（＋ TSV）で、1 案件ぶんが企画から管理まで揃っている。メタモデルの **32 種別・36 関係がすべて立つ**（見本の通しで立つのは 16 種別）。冊をまたぐ表記ゆれと食い違いも入れてある → `tests/test_dataset_pipeline.py` |
| `tests/corpus.py` | 20 冊 / 35 シート | **パースの検体。**数式・非表示・貼り付け画像・マクロ付き・シート名衝突・壊れたブックなど、実物によくある書かれ方を集めたもの |
| `examples/sales-corpus` | 30 冊 / 201 シート ＋ 追加資料 8 冊 / 56 シート ＋ Java 114 本 | **架空の新販売管理システム一式。**日本の SIer の設計書の形（2 段見出し・縦結合・図形＋コネクタ・結合セル作図）と、矛盾・粒度差・表記ゆれ・重複を仕込んである。`追加資料/` は 2 ラウンド目の検体 → [README](examples/sales-corpus/README.md) |
| `examples/kotonoha` | Python 110 本 / DDL 7 本 / 設計メモ 22 本 ＋ Excel 8 冊 | **架空の社内エンベディング基盤一式。**`sales-corpus` の鏡像で、実装が先にあって文書が後追いの検体。`draft` が主役になり、`.sql` / `test_*.py` / `.md` があるのでテーブル定義書・テスト仕様書・課題管理表の語彙がここから立つ → [README](examples/kotonoha/README.md) |

`from-documents` の 4 冊は、それぞれ次の難所を持ちます（合わせて写し 31 本 / アンカー 90 件）。

- **PowerPoint 12 枚** ―― ゾーンで括った構成図・群の中の群・貼り付け画像・フェーズ計画・
  権限マトリクス・1 枚に表 2 枚のコード体系・コメント 3 件
- **Word 10 節** ―― 見出し 2 段・箇条書き 3 段・貼り付け画像 2 枚・テキスト枠の機能構成図・
  升の中の改行と `|`・変更履歴・脚注・コメント
- **PDF 16 ページ** ―― 2 階層のしおり・しおりの無い巻末の章・綴じ込まれたスキャン 1 枚
- **CSV** ―― 引用符と改行とカンマが同時に入り、末尾の升が落ちた行と重複コードもある

```bash
python examples/make_sample.py                  # 配る見本（Excel 2 冊 ＋ 文書 4 冊）
python tests/corpus.py <ディレクトリ>            # パースの検体
python examples/sales-corpus/build.py --clean   # 資料 30 冊・追加資料 8 冊・実装 116 ファイル
python examples/kotonoha/build.py --clean       # Excel 8 冊（コード・DDL・設計メモは生成物ではない）
```

`examples/*/資料/` の実ファイルは git に入れています。arp4 が何を読めるのかは、生成器の
コードより**開いた 1 冊**のほうが早く分かるからです ―― Python を動かさずに確かめられること
に価値があるので、ここだけはバイナリを置きます。`tests/` の検体は置きません（61 本・11MB
あり、変更のたびに全部差し替わるため）。**数と変更頻度が違うから、置き方も違います。**
置く以上は再生成しても差分が出ないようにしてあり（`build/reproducible.py`）、古くなって
いないかは `tests/test_example.py` が見ています。

`tests/corpus.py` と `sales-corpus` は役割が違います。前者は**1 つの欠陥を 1 つのシートで突く
検体**（壊れ方が特定できる）、後者は**30 冊を丸ごと通したときに何が起きるかの検体**（現場の
規模でしか出ない問題を出す）です。片方だけでは足りません。

`sales-corpus` と `kotonoha` は軸が反対です。前者は Excel の設計書が先にあって実装が後
（受託・ウォーターフォール）、後者は実装が先にあって文書が後追いで散らばっている（社内内製）。
「コードと DDL と設計メモも渡すこと」を示すのは後者で、`kotonoha` の Excel 8 冊は設計書では
なく稟議・台帳・点検表という別の層です。

### 公開用に配る

`build/deploy.py` が、このリポジトリから**配布するものだけ**を別のフォルダへ展開して git へ
入れます。何を出すかは `deploy.py` の `INCLUDE` だけが決めます。中身の列挙は `git ls-files`
に任せています ―― `.gitignore` と二重に「出さないもの」を書くと、片方を直したときにもう
片方が古いまま残り、`__pycache__` やローカル設定が公開側へ漏れるからです。

```bash
python build/deploy.py                     # 隣の arp4-publish/ へ展開してコミットまで
python build/deploy.py --dest <パス>       # 展開先を変える
python build/deploy.py --check             # 書かずに対象の一覧だけ見る
python build/deploy.py --no-git            # コピーだけして git は触らない
```

展開先の中身は毎回作り直します（`.git` だけ残します）。元から消したファイルが公開側に残り
続けると、「消したのに出続ける」の原因が展開側に散るためです。
