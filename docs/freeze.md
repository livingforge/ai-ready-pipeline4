# 凍結とラウンド

## 凍結は 3 つの意味を持つ

`arp4 freeze` は 1 つの操作で 3 つのことをやる。

1. **網羅の確認** ―― 資料が黙って落ちていないか
2. **ハッシュの固定** ―― 以後、出典が動かないことの保証
3. **機械に渡せる状態であることの検査** ―― 通れば `build` は原理的に失敗しない

3 の再現性ゲート（`R001`「同じファクトから 2 回で同じ正本」）は、抽出者がエージェントに
なった時点で作れない。**凍結がその代わりに保証を担う。** 再現できないなら、動かない
ことを保証すればよい。

## ゲートの 5 条件

| 条件 | 検出コード | 何を防ぐか |
| --- | --- | --- |
| 未整理のアンカーが 0 | `G001` | 資料が黙って落ちる |
| 語彙外の `type` / `rel` が 0 | `G002` | 受け皿の無いレコードが機械構築で消える |
| `concept` が全レコードにあり、参照先が実在する | `G003` | 機械がマージできない状態での凍結 |
| 関係の `from` / `to` が宣言と合う | `G012` | **凍結が通ったのに `build` が `B013` で落ちる** |
| 参照だけのレコードの種別が決まる | `G013` | **凍結が通ったのに `build` が `B014` で落ちる** |

4 つ目・5 つ目は実測から足した条件である。`G002` は「語彙にある関係か」しか見ていなかったので、
語彙にある関係（`constrains`）を語彙に無い組み合わせ（相手が外部インターフェース）で
使うと**凍結は通るのに `build` が落ちた**。凍結を解いて整理をやり直すしかなくなる
―― 「原則やるな」と書いている操作である。判定は `metamodel.orient` を `build` と
共有する。**規則が 2 つあると、同じ問題が形を変えて戻る。**

補助的に、アンカー実在（`G004`）と、`statement` の主要語がアンカー本文に含まれるか
（`G005`）も見る。後者は warn ―― 言い換えは許されるので、機械が真偽を決められない。

**照合は上下 2 方向に掛ける。** `G009` は下流（凍結後に整理結果が動いていないか）、
`G019` は上流（撮ったあとで**原本**が動いていないか）を見る。上流を見ていなかった
あいだ、原本が差し替わってもパース結果は古いまま残り、アンカーは全部実在し、
`G001` も `G004` も `check` も `conform` も通った ―― **落ちるところが 1 つも無い。**
気づけるのは生成された設計書を人が読み直したときだけである（→ 決定 39）。

`G0xx` の全体は次のとおり。

| コード | 段 | 意味 |
| --- | --- | --- |
| `G000` | 整理結果 | ファイルの形が違う（`records` が配列でない、`refs` の書式） |
| `G001` | ゲート | 未整理のアンカー |
| `G002` | ゲート | 語彙に無い種別・関係 |
| `G003` | ゲート | `concept` が実在しない |
| `G004` | 補助 | アンカーが実在しない（`check` では正本の `source` も見る） |
| `G005` | 補助 | 本文に出てこない語だけで書かれている（**warn**。本文の側に語が 0 個なら黙る） |
| `G006` | 整理結果 | 必須の欄が無い（`out_of_scope` の `reason` を含む） |
| `G007` | ゲート | 語彙の追加提案が未承認 |
| `G008` | 整理結果 | レコード直下の見慣れない欄（**warn**。属性は `attrs` へ） |
| `G009` | 凍結 | 凍結後に整理結果が編集・追加・削除されている |
| `G010` | 出典 | 正本が指すラウンドが無い |
| `G011` | 整理結果 | `out_of_scope` の `kind` が `対象外` / `未読取` のどちらでもない |
| `G012` | ゲート | 関係の起点・終点の種別が宣言と合わない |
| `G013` | ゲート | 参照だけのレコードしかなく、種別が決まらない |
| `G014` | 整理結果 | YAML として壊れている |
| `G015` | 補助 | 絵があるのに `未読取` のまま（**warn**。`render` の撮り直しは `--pending`） |
| `G016` | 整理結果 | 宣言に無い属性名（**warn**。`build` が黙って捨てる → [lint.md](lint.md)） |
| `G017` | `--fix` | 直した結果が期待値と違ったので**書き込んでいない** |
| `G018` | 補助 | 出典の欄は埋まっているのに属性が空（**warn**） |
| `G019` | 補助 | **撮ったあとで原本が変わった・消えた**（**warn**） |
| `G020` | 補助 | 語彙が要ると言っている関係が 1 本も無い（**warn**。`known_gaps` で降ろせる） |
| `G021` | 整理結果 | `assign` の相手が台帳に無い（`_concepts.yml`） |
| `G022`〜`G025` | 補助 | コード整理の規約（`calls` のまとめ方・dunder・`package`・出典の塊） |
| `G026` | 補助 | 文章化スロット（`<TODO 抽出元 …>`）が残っている（**error**） |
| `G027` | 補助 | 抽出的文章の外形（10〜200 字・識別子の包含。`drafted:` の印のあるファイルだけ） |
| `G028` | 整理結果 | 閉じた enum の値が宣言に無い（**warn** → [lint.md](lint.md)） |
| `G029` | 整理結果 | 宣言済みの欄があるのに `description` へ流した（**warn**） |
| `G030` | 整理結果 | 同じ見出しが種別内で 4 件以上 ―― 受け皿の属性が無い（**warn**） |
| `G031` | 補助 | `known_gaps` の名前が語彙に無い（**error**）／宣言が残っているのに関係が書いてある（**warn**） |
| `G032` | 整理結果 | `organized/` 直下の `_` 付きで相方のパース結果が無い ―― 読まなかった（**warn**） |

**`G032` は決定 23 で `G015` として入れたものである。**`freeze` の「絵があるのに `未読取`」
が同じ綴りを使っており、**どちらも warn なので段でも見分けが付かなかった**（`P003` が
2 つの意味を持っていたのと同じ形 → 決定 78）。後から入ったこちらを移した → 決定 102。

`G019` / `G020` は `lint` では出さない。前者は原本 1 件が複数のパース結果に
またがり、後者は同じ `concept` のレコードが複数のファイルに散るので、
**1 ファイルだけ読んでも判定できない**（`_pairs` の規律と同じ）。`G031` は
2 つに割れる ―― 名前が語彙にあるかは 1 ファイルで決まる（相手は語彙であって
他の整理結果ではない）ので `lint` でも出し、「宣言したのに関係が書いてある」は
`G020` と同じ理由で `freeze` だけで出す。

**`G020` には降りる口がある。** レコードの `known_gaps` にその関係型を理由つきで
宣言すれば `G020` を出さない ―― 縛る先がこのラウンドの資料に入っていない制約は
実在し、宣言する口が無いと**正しく処理した warn が永久に鳴り続けて、処理済みと
未処理が一覧の上で区別できなくなる**（正本側で `W031` → `W032` が同じことをして
いる理由と同じ → [spec.md](spec.md)）。降ろしたぶんは**必ず集計に出す** ――
黙って消えるのがいちばん悪い形である。書き方は [organized.md](organized.md)。

```
$ arp4 freeze --dry-run

ラウンド r001 ― パース 201 ファイル / アンカー 447
  レコード 691（うち参照だけ 138） / 対象外 323 / 未整理 296
  known_gaps の宣言 12 件（うち G020 を 9 件「調べたうえで相手がいない」として
  出していません。build が正本へ引き継ぎ、check では W032 として理由つきで出続けます）
  そのほかの指摘: G002 1 件 / G008 15 件 / G012 1 件

[error] G002 資料/A/帳票定義.yml[3]:  語彙に無い種別です: 帳票レイアウト
[warn]  G008 資料/B/非機能一覧.yml[0]: レコード直下の見慣れない欄です: description
[error] G012 資料/C/受注登録.yml[2]:  constrains は business-rule と external-interface の間に張れません

未整理のアンカー 296 件（これが作業キュー）
  資料/A/基本設計書.xlsx/受注テーブル:s1-x3: 整理も対象外宣言もされていません
  …ほか 276 件（全部出すには --list）
```

**集計を先に、そのほかの指摘を次に、作業キューを最後に置く。** 整理の途中は未整理が
数百件あるのが正常なので、素直に全部並べると `G002` / `G008` / `G012` が最後の
1 画面より上へ流れて**完全に埋もれる** ―― 実測では `G008` 15 件に気づくのに
`Where-Object {$_ -notmatch 'G001'}` が要った。既定で並べるのは先頭 20 件で、
残りは `--list`。

**未整理を 0 にする方法は 2 つある** ―― レコードを起こすか、`out_of_scope` に理由付きで
宣言するか。「読まなくてよい」と判断したことが記録に残るので、あとから
「なぜこのシートは仕様になっていないのか」に答えられる。

## 分担するとき ―― `--path` は表示だけを絞る

`freeze --dry-run --path <部分パス>` は指摘を担当ぶんに絞る。**判定は絞らない**
―― ゲートの条件はファイルをまたぐので、自分のロットだけを見て「凍結できる」と
言えることは無い。分担の完了条件がこれになっているのは、`lint` が見るのは
1 ファイルで決まるものだけで `G001` / `G003` / `G013` / `G020` が出ないためである
（→ 決定 81）。

```
--path 資料/A のぶん: error 0 件 / warn 3 件
--path で隠したぶん（ほかの担当）: error 1 件 / warn 12 件（判定はラウンド全体で
行っています。外すと全部出ます）

あなたの担当（--path 資料/A）は凍結の条件を満たしています。ラウンド全体では
他の担当ぶんに error が 1 件残っているので、まだ凍結できません（その error は
--path で隠しています。全部見るには --path を外してください）
```

**「上の error」が上に無い状態を作らない。** 隠した件数だけを言っていたころは、
担当が error 0 でも末尾が必ず「凍結できません（上の error を潰してください）」で
終わり、**その error は `--path` で隠れていて画面に 1 件も出ていなかった** ――
実測で 3 人が独立に「自分の担当が落ちていると読んだ」と報告した。いまは担当ぶんと
隠したぶんを分けて数え、結びも分ける（担当ぶんに error があるときは従来どおり
「上の error を潰してください」で、そのときは本当に上にある）。

**どのファイルにも当たらない `--path` は `exit 2`。** 絞り込みは指摘を消す仕組み
なので、当たらないパスを黙って通すと**打ち間違い 1 つが「担当ぶんは全部きれい」に
見える** ―― 消えたのか無かったのかが打った人から区別できない（`lint` の規律に
揃えた → [lint.md](lint.md)）。照合の相手は**指摘が名指ししうるファイルの一覧**
（整理結果とパース結果）である ―― 指摘の側で照合すると、error も warn も無い
きれいな担当ぶんが「当たらなかった」になる。ゲートを回す前に止めるのは、
200 ファイル読んでから打ち直させないためである。

`--format json` には `path` / `path_findings` / `hidden_findings` が出る。
**絞ったぶんの内訳は機械にも渡す** ―― 人向けの行だけに書くと、CI が「自分の担当は
通ったが他人のぶんで止まっている」を判定できない。

## 凍結マニフェスト

```yaml
# .arp/rounds/r001/organized/.frozen.yml
frozen_at: 2026-08-02
files:
  資料/A/基本設計書.xlsx/受注テーブル.yml: 9a3c1d2e4f60
  資料/A/基本設計書.xlsx/画面項目.yml:     7b21e8c04d13
  _concepts.yml:                            3f8a92b1c007
records: 412
out_of_scope: 61
unreadable: 18        # うち「機械が読めていない」もの（図形・画像）
```

ファイル単位のハッシュを持つ。**凍結後に整理結果が編集されるとハッシュがずれ、機械が
検出する。**

`unreadable` を別に数えるのは、`out_of_scope` が 2 種類の事実を混ぜているからである。
「資料にそもそも仕様が書かれていない」（表紙・改訂履歴）と「機械が読めていない」
（図形で描かれた業務フロー）は、**次のラウンドで拾い直すかどうかが正反対**になる。
整理層は `kind: 未読取` で後者を宣言する。

## 原本の指紋

```yaml
# .arp/rounds/r001/sources.yml ―― arp4 parse が書く
files:
  資料/A/基本設計書.xlsx:
    digest: 4f80a1c3e29b
    parsed: [A/基本設計書.xlsx/受注テーブル.md, A/基本設計書.xlsx/画面項目.md]
```

`.frozen.yml` と**役割が逆**である。あちらは `organized/`（下流）が凍結後に
動いていないかを見る。こちらは**上流** ―― パース結果を撮ったときの原本と、いま
手元にある原本が同じかを見る。`organized/` の外に置くのは、原本が凍結の対象では
ないからである（arp4 が管理していない他人のファイルである）。

**言うのは「変わった」だけで、「変えるな」ではない。** 資料はラウンドのあいだに
当然改訂される。`G019` が出たときの手当ては次の 2 つで、どちらも正しい。

| 状況 | 手当て |
| --- | --- |
| 新しい版で整理をやり直す | **新しいラウンドを起こす**（`arp4 parse --new-round`） |
| いまのラウンドはこの版のままでよい | `arp4 parse` で撮り直す（指紋も更新される） |

記録するのは**書けたパース結果の原本だけ**である。編集済みで上書きを見送ったものまで
指紋を更新すると、ディスクの上には古い写しが残っているのに指紋だけ新しくなり、
**ずれが消えたように見える**。

## 凍結後に誤りが見つかったら

| 状況 | 手当て |
| --- | --- |
| 軽微（属性 1 つが違う、名前が不適切） | **正本側で `overridden`**（理由必須）→ [spec.md](spec.md) |
| 資料の解釈が根本から変わる | **新しいラウンドを起こす** |
| 利用者が明示的に整理結果の修正を求めた | 整理結果を直し、`.frozen.yml` を理由付きで更新する |

原則は**正本側で直す**である。整理結果は「資料はこう言っていた」の記録で、正本は
「我々はこう決めた」の記録だから、あとから分かったことは正本の変更として残るべき
である。混ぜると決定の責任者が永久に分からなくなる。

3 番目は例外だが、経路としては用意しておく。凍結しているからこそ、例外的な手当てが
**例外として見える**（ハッシュがずれ、`.frozen.yml` の更新理由が残る）。

```yaml
# .frozen.yml の更新履歴
amendments:
  - at: 2026-08-20
    file: 資料/A/基本設計書.xlsx/受注テーブル.yml
    was: 9a3c1d2e4f60
    now: c04d137b21e8
    reason: 利用者の指示により、OCR が読み違えた桁数（10 → 16）を修正
```

## ラウンド

資料が更新されたら**新しいラウンドディレクトリ**を起こす。過去ラウンドは入力情報
として残し、削除しない。

```
.arp/rounds/r001/     ラウンド ①（初回。資料 30 冊）
.arp/rounds/r002/     ラウンド ②（更新された 4 冊だけ）
```

**ラウンド ② の `parsed/` は差分だけ**でよい。更新されていない資料について、正本の
レコードはラウンド ① の整理結果を指し続ける ―― これが正常な状態である。過去ラウンドは
凍結済みなので、出典が動いていないことは `.frozen.yml` でいつでも検証できる。

正本はラウンドをまたいで 1 つである。ラウンドは**入力の履歴**、正本は**現在値**。

### ラウンド ② の整理②

横断整理の入力は**正本の `concepts.yml` 1 本**である。「この新資料の『受注番号』は
既存の `c-受注番号` と同じか」を判断するのに、過去ラウンドの整理結果を読み返す必要は
ない。だから資料が増えても横断整理の入力は単調増加しない。

### 出典の 3 ホップ

```
正本レコード → 整理結果（ラウンド・ファイル・レコード）
             → パース結果（アンカー）
             → 元資料（シート・セル範囲 / ファイル・行範囲）
```

各ホップが機械で検証できる。ラウンドが凍結されているので、**このリンクは時間が経っても
切れない。**

## 検出コードの体系

3 の体系を引き継ぎ、層ごとに前置きを分ける。

| 系 | 意味 |
| --- | --- |
| `M0xx` / `C0xx` | メタモデル自身の欠陥 / パック解決・準拠 |
| `P0xx` | パース（読めない形式・壊れたファイル・上書き） |
| `G0xx` | **凍結ゲート**（未整理・語彙外・concept・アンカー） |
| `B0xx` | 機械構築（マージ・採番・関係の向き） |
| `E0xx` / `W0xx` | 正本データの不備 / 警告 |
| `X0xx` | 矛盾（両論併記で課題化） |

3 にあった `T0xx`（表の読み取り）・`RC0xx`（名寄せ）・`N0xx` / `CL0xx`（命名・分類）・
`R0xx`（再現性）は、対応する機構ごと消える。
