# 検査 ― 位置・機械可読・段の境界

**規則は揃っていた。足りなかったのは lint としての人間工学である。**

`G0xx` / `B0xx` / `E0xx` / `W0xx` / `C0xx` / `M1xx` は既に 90 近くあり、書いた
YAML が語彙に合っているかも、参照が解決するかも見ていた。にもかかわらず、
整理層（エージェント）は日本語の文章を正規表現で割って次の一手を決めていて、
指摘の**位置**はどこにも構造として無かった。

プログラミングの道具立てと並べると、埋まっていなかったのは規則ではなく周辺である。

| プログラミング側 | arp4 で対応するもの | 直す前 |
| --- | --- | --- |
| 構文エラー（parser） | `G014` | ○ ただし位置が文章の中 |
| 型検査（mypy） | `G002` / `G012` / `G013` | ○ ただし `freeze` でしか回らない |
| 未定義参照（linker） | `G003` / `E0xx` | ○ ただし段が違う |
| 未使用（unused） | 孤児 | **ほぼ無い** |
| `file:line:col` | ― | **✕** |
| 機械可読出力 | ― | **✕** |
| 1 ファイルだけ検査 | ― | **✕** |

## `target` に位置を混ぜていたのをやめた

`Finding` は `(level, code, target, message)` の 4 つで、`target` には
`資料/A/受注テーブル[3]`（レコードの添字）・`__main__.py:i1`（アンカー）・
`ent-037a3625a979`（内部 ID）が同じ欄に入っていた。**どれもエディタから開けない**
―― 添字は行ではないので数え直しが要り、内部 ID に至っては正本を全文検索するしかない。

```python
class Finding(NamedTuple):
    level: str; code: str; target: str; message: str
    file: str | None = None      # どこを開くか（プロジェクト根からの相対）
    line: int | None = None      # 1 始まり
    hint: str | None = None      # 次の一手。--fix の種でもある
```

`target` は「**何の話か**」（アンカー・種別・アイテム ID）、`file` / `line` は
「**どこを開くか**」に分けた。151 か所ある `Finding(...)` は既定値つきの追加なので
1 つも壊れない。

**位置は行頭に置かず `[level] CODE` の後ろに置いた。** `file:line:` を先頭に出す
のが gcc 以来の作法だが、既存の出力の読み方が全部変わる。端末とエディタのリンク
検出は行頭でなくても当たるので、得るものは同じで壊すものが無い。

**基準はプロジェクト根**にした。`organized/` からの相対にすると、読み手が頭の中で
連結しないと開けない ―― 位置を持たせた意味が消える。

`Record` は `file`（拡張子なし・パース結果との 1:1 対応の鍵・正本の出典にも載る）と
`path`（開くための実ファイル）を**別に持つ**。1 つに畳むと、拡張子が `.yaml` の
資料が混ざった瞬間に対応が切れる。

## 行番号は値の外に置く

行番号を値の側へ埋め込む実装 ―― `dict` の派生型にして `__line__` を持たせる ――
は広く使われているが、**その値はそのまま書き戻せない**（`yaml.safe_dump` は派生型を
知らないので落ちる）。`plan_declare` は読んだものを書き戻すので、そこで壊れる。

`yamlio.load_marked` は `(値, Marks)` を返し、値には手を入れない。構文解析は 1 回
だけ走らせる（`get_single_node` してから `construct_document` するのが
`yaml.safe_load` の中身そのもの）。

`Marks.line("records", 3, "statement")` は**キーの行**を返す（値の行ではない）――
`statement` が複数行にまたがるとき、値の行は 2 行目以降を指し、どの欄かを探すのに
読み手が上へ戻る。**引けなければ親へ遡る**のも意図的で、深い位置が取れないときに
`None` を返すと指摘から位置が消える ―― それは位置を持たせる前と同じものである。

## 機械可読は「日本語をエスケープする」ほうを既定にした

`--format json` / `--format sarif` を **検査するコマンドにだけ**付けた（`freeze` /
`check` / `conform` / `lint`）。何かを作るコマンド（`parse` / `build` / `publish`）の
出力は「何をしたか」であって指摘ではないので、同じ器に入れると読み手が中身を推測する。

**JSON は `ensure_ascii=True` で出す。** 日本語 Windows の既定コンソールは cp932 で、
そこへ生の日本語を流すと `_resilient_output` の `backslashreplace` が潰す ――
**JSON として壊れたものが出る。** 出力先が端末かファイルかは呼ばれる側から決められ
ないので、どこへ出しても壊れないほうを既定にする。読み手は必ずエスケープを解く。

**書式は出し方だけを変える。** `arp4 freeze --format json` はゲートを通れば凍結
する。変えると「JSON で見たときだけ凍っていない」という差が生まれ、CI と手元で結論が
ずれる。終了コードも書式に依存しない。

作業キューは人向けには 20 件で切るが、JSON では切らない ―― 切るのは画面が有限だから
であって、読み手が機械なら理由が無い（`--list` を打ち忘れて「未整理は 20 件だ」と
読む事故のほうが重い）。

## `arp4 lint` ― 線引きは「そのファイルだけで決まるか」

`freeze --dry-run` は 200 ファイルを読んでゲート 5 条件を見るので、1 ファイル書いた
直後には重く、しかも出てくるのは**未整理 296 件の山**で、いま書いた 1 件が埋もれる。

| 出す（1 ファイルで決まる） | 出さない（横断が要る） |
| --- | --- |
| `G014` 構文 / `G000` 形 / `G006` 必須欄 / `G008` 属性の置き場所 / `G011` 区分 | `G001` 未整理 |
| `G002` 語彙 / `G016` 属性名 / `G028` enum の値（warn）/ `G012` 関係の向き | `G003` concept 実在 |
| `G004` アンカー実在 / `G005` 作文の疑い（warn） | `G013` 参照だけのレコード / `G007` 語彙の追加提案 |
| `G018` 出典の欄の取りこぼし（warn） | `G019` 原本のずれ / `G020` 要る関係が 0 本 |
| `G029` / `G030` `description` への逃がし（warn） | `G031` の「宣言したのに関係が書いてある」（warn） |
| `G031` `known_gaps` の名前が語彙に無い | ― |

`G004` を出せるのは、整理結果とパース結果が**名前で 1:1** だからである（相方は 1 つに
決まるので他のファイルを読まない）。幻覚の最頻形は「存在しない出典」なので、ここで
潰せるのは大きい。

`G019` / `G020` を出さないのは同じ線引きの裏側である ―― 原本 1 件は複数のパース結果に
またがり（ブック 1 冊 → シート 9 枚）、同じ `concept` のレコードは複数のファイルに散る。
**1 ファイルだけ読んで「関係が 1 本も無い」と言うと嘘になる**（別のファイルに
書いてあるかもしれない）ので、全部読んでいる `gate` でしか言えない。

**`G031` は 1 つのコードが線の両側にある。** `known_gaps` の**名前**が語彙
（関係型・属性名）にあるかは 1 ファイルで決まる ―― 相手は語彙であって他の整理結果
ではない。誤字の宣言は「守っているつもりで守られていない」を作り、しかも `build` が
そのまま正本へ運ぶので**気づけるのは凍結の後**（`check` の `E018`）になる ――
そのとき整理結果はもう編集できない。**宣言が効いているかは書いた手元で言う。**
一方「宣言したのに関係が書いてある」は関係が別のファイルにありうるので `gate` だけ。
書いた宣言が読まれたことは件数でも言う（`lint` の集計に `known_gaps の宣言 N`
が出る ―― `G020` が出ない層では、**0 なら書いた場所か綴りが違う**という手がかりが
件数しか無い）。

**判定は `gate` と同じ関数を呼ぶ。** 別実装にすると、`G002` が `B013` を取りこぼして
いたのと同じ事故が lint と freeze のあいだで起きる。lint が出せるのは `gate` が出す
ものの**部分集合**である ―― `G012` は相手の種別が分からなければ黙るので、他の
ファイルでしか定義されていない concept との関係は `freeze` まで持ち越される。
**lint が通ったことは凍結できることを意味しない**ので、そう出力に書く。

正本（items / relations）は読まない。lint の判定に 1 つも使わないのに、読むと 300 件の
アイテムを毎回舐めることになる ―― **速さが要件である。**

当たらなかったパスは `exit 2` で言う。黙って落とすと「lint が通った」と「そもそも
検査していない」が同じ顔になり、**打ち間違い 1 つで直したファイルが検査されないまま
緑になる。** `freeze --path`（分担用の絞り込み）も同じ規律に揃えた ―― あちらは
指摘を消す仕組みなので、当たらないパスは「担当ぶんは全部きれい」に見える
→ [freeze.md](freeze.md)

**フォルダも受ける。** 「1 ファイル書くたびに打て」という線引きは正しいが、**分担で
配る単位は 1 ブック（＝1 フォルダ）**である ―― sales-corpus の分担（11 ロット）で、
ディレクトリを渡して `exit 2` になったと **8 ロット中 6 つ**が報告した。回避策
（ファイルを 1 本ずつ並べる）は、日本の設計書のシート名に**空白が普通に入る**
（`受注入力 項目.yml`）ためシェルで壊れやすく、**壊れても「lint は通った」と同じ顔で
終わる** ―― 上の規律がシェルの分割には効かない。中に整理結果が 1 本も無いフォルダは
「当たらなかった側」にする（0 件を黙って通すと、打ち間違いが「レコード 0・error 0」で
緑になる）。

### `E011` → `G028`（enum の値）

`B021` → `G016` と**まったく同じ形の穴**が値の側に残っていた。属性の名前は書いて
いる最中に言うのに、**値の検査は `check` の `E011` にしかなかった** ―― 出るのは
`freeze` の後で、そのときには整理結果はもう編集できない。

閉じた enum（`extensible` でないもの）に限る。`data-item.data_type` のような
extensible な enum は、資料の語をそのまま採れるようにするための設計（決定 40）
なので、鳴らすと**規律を守った側が鳴らされる。**

段は `G016` と同じ warn である ―― 値の取り違えは `build` を落とさない。

### `description` への逃がし（`G029` / `G030`）

**予約キーには検査が 1 つも掛かっていなかった。** `description` は
`RELATION_RESERVED` なので宣言なしにどの関係へも書けて、`G016` にも `G028` にも
当たらない ―― 実測（r001）で正本の `description` 628 件のうち **528 件（84%）が
どの生成物にも出ないまま消えた。**

`G030` の件数は**読んだファイルの中でしか数えられない**（`G020` と同じ線引き）ので、
ラウンド全体でしか閾値に届かないものは `freeze` まで持ち越される。判定そのものは
`lint` と `gate` で同じ関数を呼ぶ。書き方は [organized.md](organized.md) にある。

## 段の境界 ― 下流のコードから上流の穴を逆算する

`G012` は後から足した条件だった。`G002` が「語彙にある関係か」しか見なかったので、
語彙にある関係を語彙に無い組み合わせで使うと**凍結は通るのに `build` が `B013` で
落ちた**。同じ形の穴が他にもあるはずなので、下流のコード全部について「上流でどの条件が
検出すべきだったか」を書き出した。

**`B010` / `B013` / `B014` は既に埋まっていた**（コード中に「凍結ゲートが通っていれば
起きない」と書いてある）。`B022` / `B023` / `B024` はマージの食い違いで、横断が要るので
前倒しできない。残ったのが 2 つである。

### `B021` → `G016`（属性名の語彙）

`build` は宣言に無い属性を**捨てる**。捨てたことは `B021` で言うが、出るのは凍結した
あと ―― **整理結果はもう編集できない。** 直すには正本を手で埋めるか、ラウンドを
起こし直すしかない。桁数を `length` ではなく `桁数` と書く類の取り違えは語彙の綴りの
問題であって意味の判断ではないので、書いている最中に言えば直る。関係の属性のほうは
`build` が黙って捨てるだけなので、言われなければ気づく手がかりが無い。

**warn に留めた。** ゲートの 5 条件は「通れば `build` が落ちない」ことの保証で、
属性の取り違えは `build` を落とさない ―― 段の重みを勝手に上げると、いま凍結できて
いるものが凍結できなくなる。

### `check` → `publish` → `W034`（資料は届いているのに空になる設計書）

いちばん空いていた境界である。実測では CRUD 図が空になったのは `accesses` の関係が
1 本も張られなかったためだったのに、設計書にはこう出ていた。

> **この設計書に出せるデータが正本にありません**（必要な語彙: `accesses`）。
> 取り込んだ資料に「基本設計」工程の資料が含まれていない可能性があります。

**読み手を反対側へ誘導していた。** エンティティ 33 件・モジュール 25 件は正本にあり、
資料は届いている。`publish.unmet` が空の理由を 2 つに割る。

| 区分 | 判定 | 次の一手 |
| --- | --- | --- |
| `資料` | その種別のアイテムが 0 件 | 資料を足す |
| `関係` | **両端のアイテムはあるのに関係が 0 本** | 整理層が張れなかった理由を潰す |

`関係` が 1 つでもあれば資料の話にはしない。併記すると読み手は探しやすいほう（資料）を
先に疑う。`check` は `関係` のものだけを `W034` で前倒しする ―― `資料` のほうは
11 種のうち 8 種が該当する「正しい空」なので、全部並べると本当に困っているものが埋もれる。
判定は `_blocks` と `unmet` を `publish` と共有する。

実測（arp4 自身のソース 23 本を入力にした正本）では `W034` は **CRUD図 1 件だけ**に
出た。要件定義書・トレーサビリティなど残り 7 種は正しく黙る。

## 逆向きの対応 ― 「静かに消える」のはいつもこちら側

検査が順方向に偏っていた。

| キー | 順方向 | 逆方向 |
| --- | --- | --- |
| ファイル名 | パース結果 → 整理結果（`G001`） | **整理結果 → パース結果（無かった → `G004`）** |
| `concept` | 整理結果 → 台帳（`G003`） | 台帳 → 正本（無かった → `E029` / `W035`） |
| item `id` | 関係 → アイテム（`E0xx`） | `warn_if_unreferenced` で宣言済み（`W030`） |
| ハッシュ | `.frozen.yml` → 整理結果（`G009`） | ― |

### 孤児の整理結果（`G004` をファイル単位に）

資料が改訂されてシート名が変わると、整理結果は前の名前のまま残る。**中身は 1 件も
正本に入らないのに凍結が通っていた。** とくに `out_of_scope` だけのファイルは
レコード側の `G004` が 1 件も出ないので、**いちばん静かに消えるのがこの形**である。

レコード 1 件ずつではなく**ファイル 1 件で言う。** 50 レコードあるファイルが孤児に
なると 50 件並び、3 ファイルあれば 150 件の山になる ―― 直す操作はどのみち
「ファイルの名前を直す」1 つしかない。

### 切れた写像（`E029`）

`concept` を item の ID と同一視しないのがこの設計の肝で、そのぶん**写像が切れても
誰も気づかない**穴が空いていた。切れたまま次のラウンドを組むと、同じ `concept` を
書いたレコードは写像を解決できないので**新しいアイテムとして起こされる** ―― 統合
したはずのものが 2 つに割れ、しかも凍結物は無傷なので差分にも出ない。

`W035`（写像が空）は warn に留める。整理②が `new` で宣言した concept をそのラウンドの
レコードが 1 件も使わなければこうなるが、**次のラウンドで使われる予定かもしれない**
―― 機械には決められない。

## 形はスキーマが持つ ― 手続きを消した

`G000` / `G006` / `G008` / `G011` は `organized.py` に手続きで散っていて、同じ契約が
**3 か所**にあった。

1. `_records` / `_refs` / `_out_of_scope` の中（実行されるもの）
2. `docs/organize.md` の例示（**実行されないので古くなっても誰も気づかない**）
3. `RESERVED` / `DEFINING` / `SCOPE_KINDS` の定数（`arp4 declare --kind` の選択肢は
   ここを見ていた）

`src/arp4/schemas/organized.yml` を正にし、1 と 3 を消した。`arp4 schema` が原文を
そのまま出すので、2 は「スキーマを読め」に置き換わる。

**汎用のスキーマ言語にはしない。** JSON Schema を持ち込めば `dependentRequired` で
「3 つ揃えるか 3 つとも省くか」も書けるが、依存が増えるうえ、**置き換えた手続きより
読みにくいものが残る**（`organized.yml` は 182 行で、そのうち 4 割はなぜそう決めたかの
コメントである）。構文は**いまある検査 1 つにつき 1 つ**しか用意しなかった。

| 構文 | 置き換えた検査 |
| --- | --- |
| `shape` | 節の型が違う（`G000`） |
| `required` | 必須の欄（`G006`）。`together: true` が「3 つ揃えるか 3 つとも省くか」 |
| `keys.values` | 決められた値（`G011`） |
| `keys.sequence` | 配列の要素の形 |
| `keys.mapping` | 連想配列の**値**の形。**名前は書く側が決める**（`known_gaps` の関係型・属性名） |
| `unknown` | 宣言に無い欄（`G008`。`ignore` なら黙って通す） |

**コードも文言もスキーマが持つ。** 実装が持っていると、スキーマを読んでも「破ると
何が出るか」が分からない ―― 書く側にとって、規則と罰は 1 つのものである。

**error は落とし、warn は落とさない。** 手続き版の `continue` をそのまま宣言に
移した規律で、「書けているが置き場所が違う」（`G008`）を捨てると**資料が黙って
消える**。落とした要素のぶんは詰めない ―― `records[3]` が落ちたときに 4 番目が
3 番になると、指摘の位置と整理結果の行がずれて**直す人が別のレコードを見る**。

`source.anchor` のような入れ子は**ドットで 1 つの名前として引く**。`source` を
もう 1 段の形として宣言しても同じ検査はできるが、そうすると指摘が `source` の話に
なって「必須の欄がありません: **concept、source.anchor**」と 1 件にまとめられない
―― 直す人が見るのはレコード 1 件である。

### 消したことで直った穴

手続き版は `out_of_scope` が**配列かどうかを見ていなかった**。連想配列を渡すと
`enumerate` がキーを回し、**キー 1 つずつに「書式が不正です」を並べていた**。
宣言では `sequence` を書くだけなので、書き忘れようがない。

### やはり残したもの

- **`SPECIAL`**（`_concepts` / `_metamodel-add`）はファイル名の規約であって、
  ファイルの中身の形ではない
- **`UNREADABLE = "未読取"`** ―― 値の一覧はスキーマが持つが、**どの値がどちらの
  意味かは arp4 の都合**である（`unreadable` は「次のラウンドで拾い直す対象か」を
  answering する述語で、スキーマは列挙しか知らない）
- **空ファイルは空**（契約違反ではない）。書き始める前に置き場だけ作ることがあり、
  error にすると作業の順序を縛る

## `--fix` ― 直せるものより、直さないものを決めるほうが仕事だった

**直すのは 1 種類だけである。**

| 直す | `G008` レコード直下に書かれた**宣言済みの属性**を `attrs` の中へ移す |
| --- | --- |

着手時の見立てでは 3 つ直せるはずだった。**2 つは調べたら直せなかった。**

`G014`（YAML が壊れている）
: 実測でいちばん多い指摘なので直したかったが、**ファイルが構文解析できないので
  どんな直しも本文の推測になる。** `（固定: 130010）` のどこからどこまでが値なのかは
  壊れた構文からは決められず、引用符を当てる位置を 1 つ間違えると**資料の値が黙って
  別のものになる。** 位置とヒントを出すところで止める。

`G011`（`kind` が不正）
: 表記ゆれを寄せるつもりだったが、**寄せる相手が決まらない。** YAML の平文スカラは
  前後の空白を自分で落とすので、空白ゆれはそもそもここへ届かない ―― 残るのは
  `対象外外` のような別の語で、どちらに寄せるかは意味の判断である。

`G016`（宣言に無い属性名）も同じ理由で直さない。`桁数` を `attrs` へ移しても
`build` が捨てる先が変わるだけで、**直っていないのに指摘が消える。** `length` なのか
`precision` なのかは資料を読まないと決まらない。

### 書く前に読み直して検算する

行をいじる実装である以上、**器用にやるほど壊し方も器用になる。** 賢さで安全を
担保しない ―― 直した結果を必ず読み直し、**期待した値と 1 文字でも違えば書かない。**
期待値は「読み込み済みの値に Python でその移動を施したもの」で、両者が完全に一致した
ときだけ書き込む（違えば `G017` で「書き込んでいません」と言う）。

この検算があるので、`_move` の実装がどれだけ素朴でも安全側に倒れる。テストは
**直し方だけを壊した実装にすり替えて**、1 文字も書かれないことを確かめている。

### 値は生のテキストのまま運ぶ

読み直して `yaml.safe_dump` で書き戻すと、`"1,200,000/年"` の引用の有無もコメントも
失われる。整理結果は**人とエージェントが読む面**なので、直した覚えのない差分を出さない。
実測で、`entity_kind` を `attrs` の外に出したファイルを `--fix` にかけると、
**元のファイルとの差分が残った 1 行だけ**になった（移した行は元どおりの位置・書式に戻る）。

改行の種類も保つ。`arp4 declare` が書いたファイルは Windows では CRLF なので、
素直に読み書きすると**直した覚えのない差分が全行に出る。**

### 1 回に 1 つだけ直して読み直す

まとめて直すと行番号が互いにずれ、**ずれたことに気づく手立てが無い**（そこが
いちばん静かに壊れる）。1 件直すたびに読み直すので、位置の付け替えが要らない。

行の位置を引くときは**遡らない**（`Marks.exact`）。指摘を出すときは遡ってよいが
―― 1 つ上の行が出れば人は辿り着ける ―― **書き換えるときに遡ると別の行を書き換える。**
`attrs` の無いレコードで遡ると返るのはレコードの先頭行で、そこへ属性を足すと
`concept` の行が壊れる。

### 凍結済みのラウンドは直さない

直すと `G009` でハッシュが合わなくなり、**「凍結後は正本側で直す」という決まりを
機械が破る**ことになる。`exit 2` で止める。

## 段はどこを見ているか ―― `P0xx` を足した

`G0xx`（整理結果）・`E0xx` / `W0xx`（正本）・`B0xx`（構築）・`C0xx`（適合）は
**入力と正本**を見ていた。抜けていたのは**出力**である。

`publish.lint` は文書定義（どの章にどの列を出すか）を見るが、**組み上がった表**は
誰も見ていなかった。規則は先に書かれていたのに、確かめる者がいなかった ――
`publish.md` の「列見出しは日本語」があるのに `7.1 business` が出荷され、
「母集合そのものを並べない」があるのにトレースの 80 行が全行 `―` で出た。

`P1xx` は `publish` の直前の `Block`（文字列まで落ちた章）を見る。Markdown と HTML の
両方を舐めるのではなく**共通の材料**を見るので、片方だけ直って片方が腐る形にならない。

| 段 | 見るもの | 出るところ |
| --- | --- | --- |
| `G0xx` | 整理結果（人が書く面） | `lint` / `freeze` |
| `E0xx` `W0xx` | 正本（items / relations） | `check` / `freeze` |
| `B0xx` | 構築 | `build` |
| `C0xx` | 適合（conformance） | `conform` |
| `P0xx` | 資料を読めたか（**取り込みの側**） | `parse` |
| **`P1xx`** | **組み上がった設計書** | **`check`** |
| **`W043` `W046` `P111`** | **書かれたものが出ているか**（下記） | **`check` / `publish`** |

**番号を `P1xx` にしたのは、`P0xx` と衝突していたからである。** どちらも「紙
（Paper）の側」のつもりで P を採ったが、`parse` は既に `P001`〜`P014` を使って
いた ―― **同じ `P003` が「非表示のシート」と「節の見出しが ASCII だけ」の 2 つの
意味を持ち**、配布ドキュメントでも `parse.md` が前者を、`publish.md` が後者を、
同じ綴りで説明していた。`troubleshooting.md` を引いた読み手は**別の指摘の直し方を
読む。** 段が違えば別物だと気づけるが、ここは両方 warn なので手がかりも無い。

**段の名前は、どのコマンドが出したかを覚えていなくても引ける**ことが要件である。

`W045`（`conflicts`）だけは段が 1 つ手前にある ―― 検出するのは `build`
（`B022` / `B023`）だが、**build の出力は端末に流れて消える**ので、捨てた値を正本に
残して `check` が言い続けるようにした（→ 決定 70）。「検出はできていたのに持続して
いなかった」は `P1xx` と同じ形で、**段を足すより先に、既にある検出の寿命を見る**
ほうが効くことがある。

**`P1xx` はすべて warn である。** 見ているのは「読み手が誤読しうる形」であって
データの不備ではない ―― error にすると `--force` を押す理由をまた作り、
`_gate.json`（→ 決定 67）が塞いだ穴を別の場所に開け直すことになる。

**検査を足すだけで済ませない。** `P102`（升の凡例）と `P103`（enum の生値が
見出しに出る）は、検査と同時に**元を直した**（凡例の自動生成と `value_labels`）。
実測で両方 0 件になっている ―― 直せるものを警告で回し続けるのは、警告一覧の
ノイズを増やして本物を埋もれさせるだけである。

**本物が件数に埋もれる検査は無いのと同じ。** 最初の実装は 77 件出た。`P104` は
出典列を数えていて 54 件中 45 件が「同じシートから来た行が同じアンカーを出す」
当たり前の重複だった。出典列を外し、`P106` は列の顔ぶれが 3 つ以上一致すること、
`P107` は一覧の章だけ、と絞って 19 件になった。**19 件は全部が実在の指摘である。**

## 「書かれたものが出ているか」を誰も見ていなかった

段を並べ直すと、`G0xx` は**書かれたものが正しいか**を見て、`E040` / `W043` /
`P1xx` は**様式が正しいか**を見ていた。**どちらも「書かれたものが出ているか」を
見ていない。** 実測（r001）で `description` 628 件のうち 528 件（84%）が
どの生成物にも現れず、error も warn も 1 件も出なかった。

| コード | 言うこと | 直す先 |
| --- | --- | --- |
| `W043`（warn） | 列は全行空で、値は正本の**同じ名前の別の欄**にある | 様式の列 **または** 整理層の書き先 |
| `W046`（warn） | 様式が持つ列を**全行空で畳んだ** | 資料を見に行く（畳んでよいこともある） |
| `W047`（warn） | 列は全行空で、母集合が `description` を使っている | `description` を開く。別の値なら `W046` と同じ扱い |
| `P111`（warn） | 正本に値があるのに、**どの設計書の列にも出ない**属性 | 様式に列を足す **または** そこへ書くのをやめる |

**`P110` の粒度を関係型から属性へ下げたのが `P111` である。** `P110` は
`section.relation` の集合しか見ておらず、`columns` を 1 つも見ていない ――
**節さえあれば属性が全部落ちても黙る。**

数えるのは種別×属性ではなく**そのレコードが出たか**である。非機能要件 15 件の
`description` は非機能要件の節に列が無いので出ないが、機能要件の節には
`description` 列があるので、種別で見ると「出ている」ことになってしまう。

`W043` の取りこぼしは 2 つあった。①`kind: relation` の章にしか走っていなかった
（一覧・トレースは素通り）②探す先が「**同名**の属性が関係の**反対側**」だけで、
`displays.note`（空）と `displays.description`（154 件）は**同じ側**なので
`None` を返していた。`description` は**最後に**見る ―― 先に見ると、コード定義の
`value`（正しくは `to.value`）のように**指す先が 1 つに決まる取り違え**まで
「補足に入っています」と答えることになる。

**`W043` と `W046` は構造的に排他である。** 畳むかどうかを決める `_trim` と
`W043` が**同じ関数**（`publish._alternative`）を呼ぶので、値が別の欄にある列は
畳まれず（`W043`）、畳まれた列には別の欄が無い（`W046`）。穴の 1 枚でも
**別の表**に出す ―― 「資料を見に行け」と「正本の中で置き場所が違う」は次の
一手が正反対である。

**`W043` から `W047` を割ったのは、指し先の強さが違うからである。** `W043` は
**同じ名前の欄**を指すので指す先が 1 つに決まる（書き先を間違えた、と言い切れる）が、
`description` は**中身を照合していない** ―― 母集合のどれか 1 件が `description` を
持っていれば返るので、`W047` が言えるのは「この列は空」と「誰かが `description` を
持っている」の 2 つだけである（実測では、`category` を鳴らした `description` は別の
レコードの「測り方」だった）。混ぜると、**読み手は「値はそこにある」と読んで資料に
当たらなくなる** ―― `W047` の次の一手は `W046` と同じ「1 件ずつ資料に当たる」である。

**検査を足すだけで済ませない**（`P102` / `P103` と同じ規律）。標準パックの
`documents/*.yml` には 40 か所以上の列を足した ―― `補足` はもちろん、
`operates.condition`（権限マトリクスの △ の条件）・`accesses.note`（参照の目的）・
`code-master` の一覧そのもの。**升は俯瞰、表は値**で、升目だけの設計書は
関係の属性を 1 文字も印字しない。

残るのは 2 種類だけで、どちらも様式では閉じられない。`tests/test_escapes.py` が
**その一覧を固定して、増えたら落ちる**ようにしている。

- 全種別が持つ属性（`owner` / `priority` / `subsystem`）―― 様式は種別ごとに
  出す/出さないを選んでいる（決定 75）。埋まっていれば鳴るのが正しい
- トレースの章にしか出ない関係（`realizes` / `supports` / …）の `description`
  ―― トレースはアイテムを行にするので、関係の属性を置く列を作れない。
  ここは整理層の側で閉じる

## やっていないこと

- **正本（items / relations）のスキーマ。** 形の宣言は整理結果にしか無い。正本の形は
  メタモデルが属性まで宣言しているので二重になる ―― 足すなら `validate.py` が
  メタモデルを引いている経路と重ならないことを先に確かめる
- **LSP / `--watch`**。`--format json` と 1 ファイル指定があれば、呼ぶ側が 3 行で書ける
