# 整理結果 ― `.arp/rounds/<ラウンド>/organized/`

**唯一、意味を判断する層。** エージェントが `parsed/` を読み、リレーショナルな
正本にできる形へ起こす。ここが終われば、あとは機械が照合するだけになる。

整理は 2 段に分かれる。**分けないと凍結できない。**

| | やること | 単位 |
| --- | --- | --- |
| 整理① ローカル | パース結果を型付きレコードへ。OCR や表の崩れもここで直す | 資料 1 本 |
| 整理② 横断 | `concept` の割当・用語の統一・矛盾の摘出 | プロジェクト全体 |

同一性の判断（テーブル定義書の「受注番号」と画面項目定義書の「受注番号」は同じか）は
**ファイル横断でしか決まらない**。これが決まっていない整理結果を機械に渡しても、
同じ概念が別アイテムになり、片方がどの関係からも指されない孤児になる。

## 整理① ― レコードの契約

**パース結果 1 ファイル → 整理結果 1 ファイル。** 対応が 1:1 なので、書き込み競合が
構造的に起きず、未整理のものが一目で分かり、1 資料の再整理が局所的に済む。

```yaml
# .arp/rounds/r001/organized/資料/A/基本設計書.xlsx/受注テーブル.yml
records:
  - concept: c-T_ORDER
    type: エンティティ
    name: 受注
    statement: 受注テーブル T_ORDER は受注 1 件を 1 レコードで保持すること
    attrs: { physical_name: T_ORDER, volume: 月 3 万件, retention: 5 年 }
    source: { anchor: s1-t1 }
    refs:
      - rel: has-column
        to: c-受注番号
        attrs: { physical_name: ORDER_NO, pk: true, not_null: true }

  - concept: c-受注番号
    type: データ項目
    name: 受注番号
    statement: 受注番号は文字列型（10 桁）の項目であること
    attrs: { data_type: 文字列, length: 10 }
    source: { anchor: s1-t1 }

  # 参照だけのレコード ―― 同じ concept が別シートにも出るとき
  - concept: c-T_ORDER
    source: { anchor: s6-t1 }
    refs: [{ rel: has-index, to: c-IX_T_ORDER_01 }]

out_of_scope:
  - { anchor: s1-x1, reason: 表紙・改訂履歴 }
  - { anchor: s2-t1, kind: 未読取, reason: 業務フローは図形で描かれており本体が出ていない }
```

**フロー記法（`{ … }`）に入れられない値がある。** 値にカンマが入ると区切りとして、
`{` が入るとフローマッピングの開始として解釈され、YAML が壊れる。想定件数
`1,200,000/年`・コミット間隔 `1,000 件`・メッセージ本文 `{0}を入力してください。` は
日本の設計書にごく普通に出てくるので、ブロック記法にするか引用符で囲む。

**`:`＋空白はフロー記法でなくても壊れる**（「（固定: 130010）」）。実測ではこれが
いちばん多く、`statement` の中に出てくる。壊れたファイルは `G014` で**全部まとめて**
報告する ―― 1 件ずつ止めると、200 ファイルあれば「直す → また落ちる」を 200 回
繰り返すことになる。

| 欄 | 必須 | 何のためにあるか |
| --- | --- | --- |
| `concept` | ○ | **同一性キー**。機械のマージ判断はこれだけを見る |
| `source.anchor` | ○ | パース結果のアンカー。ファイルは 1:1 対応から決まるので書かない |
| `type` | ①のみ | メタモデルの語彙に載っている種別。載っていなければ凍結が通らない |
| `name` | ①のみ | 設計書の見出しになる。**暫定の切り出しをしない**（3 の命名パスはここに吸収） |
| `statement` | ①のみ | 仕様の本文 |
| `attrs` | | 種別ごとの属性（桁・PK・保持期間…）。ここで拾わないと設計書が空欄だらけになる |
| | | **レコード直下に属性を書くと `G008`**（属性は `attrs` の中へ） |
| `refs` | | 本文から読み取った関係。**推測で張らない** |
| `known_gaps` | | **調べたうえで相手がいない**ことの宣言（関係型・属性名 → `reason`）。`build` が正本へ引き継ぐ |

## レコードの形は 2 つ ―― 完全と参照だけ

`type` / `name` / `statement` を持つ**完全なレコード**が concept を定義し、3 つとも
省いた**参照だけのレコード**は「このアンカーも同じ concept の話をしている」とだけ
言う（3 つ揃えるか 3 つとも省くかで、中途半端は `G006`）。

**日本の設計書は同じ対象を必ず複数シートに書く。** 画面「受注入力」は画面一覧・
機能一覧・画面仕様書・項目一覧の 4 シートに現れ、アンカーはレコードでしか解決
できない（`G001`）。3 つを必須にしていた頃は 4 シートぶんの `statement` を書かされ、
**食い違うのが当たり前**になっていた ―― 実測で `B023`（長いほうを採る）が 58 件出て、
テーブル 6 本で索引一覧の説明がテーブルの役割を押しのけた。整理層に回避手段が無い
以上、これは書き手の不注意ではなく**仕様の欠陥**である。

種別は「同じラウンドの完全なレコード」か「台帳（前ラウンドの成果）」から引く。
どちらにも無ければ凍結が `G013` で止める ―― `build` の `B014` を前倒しする条件で
ある。属性と `refs` と出典（アンカー）は参照だけのレコードからも拾う。

`out_of_scope` は仕様にならないブロック（表紙・改訂履歴・WBS）の宣言である。
**`reason` は必須**（`G006`）―― 理由の無い宣言は、黙って飛ばすのと変わらない。
**黙って飛ばすのではなく、理由を付けて宣言する** ―― 凍結ゲートの網羅条件は、
レコードにもならず対象外でもないアンカーを許さない。

`kind` は 2 つある（既定は `対象外`）。**「資料に仕様が書かれていない」と「機械が
読めていない」は、次のラウンドで拾い直すかどうかが正反対**なので分ける。xlsx の
図形は**テキストだけ**別アンカー（`s4-g1`）に出るので、箱の中の語で仕様が起こせる
なら普通のレコードにしてよい。`kind: 未読取` になるのは**線の接続と配置が仕様その
もの**のとき（業務フローの順序と分岐条件）である ―― 資料に情報が無いわけではない。

表紙・改訂履歴のように**同じ構成のシートが資料の数だけあるもの**は、`arp4 declare`
でまとめて宣言する。意味の判断ではなく作業だからである。理由だけは人が与える。

```bash
arp4 declare 表紙 改訂履歴 --reason "表紙・改訂履歴（仕様ではない）"
arp4 declare "*/業務フロー" --kind 未読取 --reason "本体は図形でパース結果に出ていない"
```

## 書いてよいこと・いけないこと

**言い換えてよい。** 3 は `evidence`（原文の写経）を必須にしていたが、4 は
**写経からリンクへ**変えた。アンカーが凍結後も動かないので、原文はいつでも引ける。

**ただし本文から辿れること。** `check` は「`statement` の主要語がアンカー本文に
含まれるか」を検査する。含まれないものは作文である可能性が高い ―― 幻覚の最頻形は
「存在しない出典」と「出典にない主張」の 2 つで、前者はアンカー実在、後者はこの検査で
拾う。

**関係は本文に根拠があるものだけ。** 散文から関係を推測しない。「たぶんこの画面は
この要件を実現している」は整理層の仕事ではなく、正本を人が育てる過程で決まる。

**必須属性を埋めない。** 資料に書いていない桁数を推測で埋めると、それが正しいかを
誰も確かめられなくなる。空欄のまま出せば `build` 後に `E010` が出て、人が埋める。

**`rule_kind` は整理時に付ける。** 業務ルールの区分（business / calculation /
validation / processing / default / error）が空だと詳細設計書から黙って消える。
条件語で決まるものが大半なので、整理の時点で付けきる（3 の分類パスはここに吸収）。

### 「調べたうえで相手がいない」を宣言する（`known_gaps`）

**「必須属性を埋めない」の裏側である。** 埋めなかった欄・張れなかった関係について、
**探したうえでそう決めた**と言う場所が整理層に無かった。

```yaml
records:
  - concept: c-cst-月間上限-cs-support
    type: 制約・前提
    name: cs-support の月間上限
    statement: テナント cs-support の月間上限を 500,000 チャンクとすること
    source: { anchor: s4-t1 }
    known_gaps:
      constrains:                # 関係型 ―― この関係が 1 本も張れない
        reason: 規模の想定で、縛る先の列がそもそも無い（このラウンドの資料に無い）
      data_type:                 # 属性名 ―― 資料にその欄が無い、でもよい
        reason: 帳票の出力項目シートに型の欄が無い
```

宣言できるのは長く**正本側だけ**だった（→ [spec.md](spec.md)）。ところが正本の
`known_gaps` は `build` を打った人の欄で、**分担しているとき配る側は `build` を
禁じる**（凍結済みのラウンドを勝手に組み立てさせない）―― 担当には `G020`（語彙が
「1 本は要る」と言っている関係が 0 本）を warn のまま残して報告文に書く以外の手が
無い。実測（8 冊を 8 人で分担した通し実行を 2 周）で **80 件超の `G020` が 2 周とも
warn のまま親へ渡り、8 人のうち 4 人が「宣言する場所が無い」と独立に報告した。
「調べた」と「まだ調べていない」が正本を組むまで区別できない**のがいちばん悪い形
である。

名前は**関係型でも属性名でもよい**（正本の `known_gaps` が両方を受けるので揃える
―― 書く側から見れば「この欄が資料に無い」の一言で足りる）。`reason` は必須で、
無ければスキーマが宣言ごと落とす（`G006`）―― **理由の無い宣言は、黙って飛ばすのと
区別が付かない**（`out_of_scope` の `reason` と同じ規律を、書く側の手元へ前倒しした
ものである）。`at`（宣言した日）は省いてよい。

| どこで | 何が起きるか |
| --- | --- |
| `freeze` | 宣言した関係の `G020` を出さない。**降ろした件数は必ず集計に出る** |
| `build` | 正本の `known_gaps` へそのまま運ぶ。**正本側に既にある宣言は上書きしない** |
| `check` | `W032`（承知している欠落）として理由つきで出続ける。**消えはしない** |

降ろした件数を言うのは、`known_gaps` が指摘を 1 件消す仕組みだからである ――
件数が無いと「直したから減った」と「宣言で降ろした」が画面から区別できない。
`build` が正本側を上書きしないのは、凍結後に人が書いた理由を整理結果の側から
書き換えると**なぜ理由が変わったのかがどこにも残らない**ためである。

**名前の綴りは `G031`（error）で見る。** 誤字の宣言は二重に効く ―― `G020` を
降ろさないうえ、`build` がそのまま正本へ運ぶので**凍結の向こうで `E018` の error に
なり、そのとき整理結果はもう編集できない。** `G016`（宣言に無い属性名。`build` が
黙って捨てるだけ）を warn に留めているのとは行き先が違うので、段は `E018` に揃える。
属性名は種別が決まって初めて引けるので、**種別を名乗らない参照だけのレコードでは
関係型しか照合できない** ―― そこで決められないものは黙る（知らないことを error に
しない）。

逆に**関係が書いてあるのに宣言が残っている**なら `G031`（warn）で「宣言を消せ」と
言う（`check` の `W033` と同じ）。埋まった欠落の宣言が残ると、承知しているものと
放置しているものが区別できなくなる ―― **古い言い訳が正本に残るほうが error より
始末が悪い。** こちらは関係が別のファイルにありうるので `freeze` でしか出ない
（`G020` と同じ線引き → [lint.md](lint.md)）。

同じ concept を 2 つのレコードが**同じ名前を別の理由で**宣言したら、`build` は
先に読んだほうを採って `B027` で言う（`B022` / `B024` と同じ扱い ―― どちらが正かは
意味の判断なので機械が決めない）。

### `description` を逃がし先にしない（`G029` / `G030`）

`description` は**補足の受け皿**で、`merge: append`（足し合わせ）で持つ（決定 70）。
だから宣言なしにどの関係へも書けるし、書ける場所を減らすつもりも無い。問題は
**書けるのに設計書のどの列にも出ない**ほうである。

実測（sales-corpus・r001）で、正本の `description` 628 件のうち **528 件（84%）が
どの生成物の本文にも現れなかった** ―― error も warn も 1 件も出ないまま消えた。
`description` は `metamodel.py` の `RELATION_RESERVED` の予約キーなので、
`G016`（宣言に無い属性名）にも `G028`（enum 外）にも当たらず、**スキーマ検査を
素通りする。**

| コード | 言うこと | 直し方 |
| --- | --- | --- |
| `G029`（warn） | **宣言済みの欄があるのに** `description` へ流した | 名指しされた欄へ写す |
| `G030`（warn） | 同じ見出しが種別内で 4 件以上 ―― **受け皿の属性が無い** | `_metamodel-add.yml` へ属性を提案する（または `statement` へ畳む） |

判定は**見出し語の完全一致**だけである。`物理名 ORDER_NO ／ 既定値 0` のように
`A ／ B` の形に割れていて、見出しがその種別の属性の `label`（または属性名）と
一致したものを数える。

- **2 つ以上一致して初めて言う。** 補足の 1 文が偶然に欄の名前で始まることはある
  （「条件 が複雑なため…」）
- **対応する欄が既に埋まっていれば黙る。** 言い直しは誤りではない

同じ穴を出口の側からも見る ―― `description` に残ったものがどの設計書にも出て
いなければ `P111` が鳴る（→ [lint.md](lint.md)）。**整理層と様式のどちらを直すかは
人が決める**ので、機械は両側から同じ穴を指す。

## 整理② ― 横断の出力

```yaml
# .arp/rounds/r001/organized/_concepts.yml
new:                                   # 正本の concepts.yml へ追加する提案
  - concept: c-受注番号
    type: データ項目
    label: 受注番号
    aliases: [受注No, 注文番号]        # 見つかった表記ゆれ
    reason: テーブル定義書と画面項目定義書で物理名 ORDER_NO が一致

assign:                                # 既存 concept への追加割当
  - { concept: c-顧客コード, aliases_add: [得意先コード] }

contradictions:                        # 摘出のみ。**統合も解決もしない**
  - subject: c-受注データの保持期間     # ★ 争点そのものの concept（課題ではない）
    positions:
      - { statement: 5 年間保存する, source: { file: 資料/A/…/受注テーブル.yml, anchor: s1-t1 } }
      - { statement: 13 か月でアーカイブする, source: { file: 資料/B/…/運用設計.yml, anchor: s4-t2 } }
```

`subject` は**争点そのもの**であって課題ではない。課題 ID は `subject` から決まるので、
資料の課題管理表にある課題を指すと、同じ ID の課題を二重に起こして `E002` / `E012` に
なる（いまは `B015` で止める）。`positions[].concept` を書けば両論それぞれに
`disputes` を張り、書かなければ `subject` 1 つに張る。

ラウンド ② 以降の入力は**正本の `concepts.yml` 1 本**である（過去ラウンドの整理結果を
読み返さない）。だから資料が増えても横断整理の入力は単調増加しない
→ [spec.md](spec.md)

**矛盾は自動解決しない。** 両論を残したまま正本の課題（`open-issue`）になり、
`build` が争点へ `disputes` を張る。どちらが正しいかは資料の外にしかなく、機械にも
LLM にも決められない。

## 語彙に無い種別が出たら

```yaml
# .arp/rounds/r001/organized/_metamodel-add.yml
add_item_types:
  - name: 帳票レイアウト
    layer: 基本設計
    reason: 帳票定義書 4 冊が持つ「印字位置・書体・改ページ」を既存 report では持てない
    attributes:
      font: { kind: string }
      page_break: { kind: string }
```

人が承認して `.arp/spec/metamodel.yml` に反映するまで、**凍結は通らない**。受け皿の
無いレコードが機械構築で黙って消えるのを防ぐためである。

**追加と厳格化だけが許される。** 既存種別の必須属性を外すような緩和は拒否される
（標準パック準拠が壊れ、設計書の様式が案件ごとに崩れる）。

**機械が読むのは `add_item_types` だけである。** 種別以外の提案（既存種別への属性
追加・関係の組み合わせ）を書く節は無いので、宛先として `notes`（自由記述）を置いた
―― 機械は解釈しないが、**読み飛ばしたことを黙らない。**

この 2 つ以外の節は `G000`（warn）で言う。以前はこのファイルだけ schema が無く、
`add_attributes:` と書いても **error も warn も出ないまま読み飛ばされていた**
（隣の `_concepts.yml` には schema があるのに）。実測で 3 ロットが独立に踏み、
うち 1 人は `add_item_types` に嘘の種別名で載せて機械に数えさせていた → 決定 80

## エージェントが最初に見るもの

```bash
arp4 model        # 使ってよい種別・関係・属性の一覧
arp4 freeze --dry-run   # まだ整理されていないアンカーの一覧
```

`model` は「メタモデルの語彙」を知るために要る。語彙を知らずに書いた `type` は
凍結ゲートで弾かれるので、**先に読む**。あわせて 2 つを見せる。

- **採番の有無** ―― その種別に表示 ID（`FR-001` / `RUL-001`）が振られるか。
  振られない種別は設計書から名前でしか参照できないので、整理の時点で分かっていたい
- **整理結果からは書けない種別** ―― 写像（`fact_types`）を持たない種別。正本には
  あるが整理層からは起こせないので、**資料が届いていてもその語彙は永久に 0 件**に
  なる。標準パックではいま 0 件である（`decision` / `test-run` が該当していたが、
  どちらも属性が資料を写す欄しか持たないのに入口が無く、実測で議事録の決定事項が
  1 件も正本に入らなかった → 決定 77）。消費側が種別を足すときの検出口として残す
