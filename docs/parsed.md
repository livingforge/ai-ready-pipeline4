# パース結果 ― `.arp/rounds/<ラウンド>/parsed/`

機械が既存資産から取り出したもの。**意味を判断しない**のが唯一の規律である。

## 置き場は元のフォルダ構造をそのまま写す

```
資料/A/基本設計書.xlsx
src/order/service.py

.arp/rounds/r001/parsed/資料/A/基本設計書.xlsx/受注テーブル.md
.arp/rounds/r001/parsed/資料/A/基本設計書.xlsx/画面項目.md
.arp/rounds/r001/parsed/src/order/service.py.md
```

**一意性はフォルダパス＋ファイル名で担保する。** 3 は資料 ID を表示名のハッシュ
（`sha256(ファイル名)`）で作っていたため、別フォルダの同名資料が同じ ID になり、
ブロックのファイルが黙って上書きされ、ファクト ID まで衝突していた。パスをそのまま
使えばこの問題は構造的に起きない。

Excel は**シート 1 枚 = ファイル 1 本**で、ブックのファイル名がディレクトリになる。
1 ファイルが大きくなりすぎず、シート単位で差分が読める。

**残っていた衝突は同じブックの中である。** ファイル名にできない記号を落とすので
（`safe_name`）、`受注/一覧` と `受注:一覧`、`受注 ` と `受注` は同じファイル名になる。
パスで担保しているのはブックまでで、シート名までは担保されていなかった ―― 実際には
**後から書いたほうが勝ち、シートが 1 枚黙って消える**。いまはあとから来たほうに `~2`
を足して `P002` で報告する。**先に出たほうは動かさない**（既に整理結果がそのパスを
指しているかもしれないので、付け替えていいのは新しいほうだけである）。

## 再実行時は上書きを確認する

同じラウンドで `arp4 parse` を再実行すると、既に存在するパース結果を上書きすることに
なる。**編集済みの内容が消えるので、必ず利用者に確認する。**

```
.arp/rounds/r001/parsed/資料/A/基本設計書.xlsx/受注テーブル.md は既にあります
（最終更新: 2026-08-02 / git 上で編集あり）
上書きしますか？ [y/N/すべて/差分を見る]
```

git 上で編集があるかどうかを併せて出すのは、**未編集のものは黙って上書きしてよい**
からである。全部を同じ重さで聞くと、確認そのものが読み飛ばされる。

資料が更新された場合は、上書きではなく**新しいラウンド**（`--new-round`）を起こす
→ [freeze.md](freeze.md)。既定の宛先は**まだ凍結していないいちばん新しいラウンド**
なので、同じ資料を別の日に処理し直しても別ラウンドにはならない。

## 図形（オートシェイプ）はテキストと接続を取る

xlsx の図形は openpyxl が読まないので、**業務フロー・ER 図・状態遷移図・画面
レイアウトはパース結果に残らない**（表題と凡例だけになる）。Word・PDF・OCR が
未対応であることは書いてあったが、これは書かれていなかった。r001 では 14 シートが
`未読取` になった。

ここには当初「線の接続は矢印が持っており、座標から復元するしかない（＝意味の判断に
なる）ので取らない」と書いてあった。**前提が事実と違った。** 接続子は繋がっている
図形の id を `a:stCxn` / `a:endCxn` に、矢羽根を `a:headEnd` / `a:tailEnd` に
**明示的に持っている** ―― 読むのは復元ではなく転記である。

| 図形が持つもの | 取れるか |
| --- | --- |
| **箱の中のテキスト**（`xl/drawings/*.xml` の `<a:t>`） | zip から機械的に取れる（`s4-g1`） |
| **線の接続**（`a:stCxn` / `a:endCxn` を持つ接続子） | 書いてあることの転記として取れる（`s4-c1`） |
| **配置**（ゾーン・段組み・注記の位置） | 座標にしか無い。取らない |
| **繋がっていない線**（目分量で置いた線） | 両端の id が無い。本数だけ申告する |
| **貼り付け画像の中身** | 図形ではない。枚数だけ申告する |

「受注登録・与信判定・在庫引当」という**語だけでも整理層は仕事ができる** ――
ER 図の実体名、状態遷移図の状態名、画面レイアウトの項目名は、たいていこれで足りる。

セル由来の塊とは**別のアンカー**にする。図形は番地を持たないので、表の出典
（`B8:J20`）と同じ枠に混ぜると出典が辿れなくなる。箱（`g1`）と線（`c1`）も分ける
―― 片方だけを出典にしたいことがある。

取れなかったことを黙るのは、いまも変わらずまずい ――「資料に情報が無い」と「機械が
読めていない」は、次のラウンドで拾い直すかどうかが正反対になる。だから**何がいくつ
あって、そのうち何が取れたか**を申告する。

```markdown
# 基本設計書.xlsx / 業務フロー

<!-- source: 資料/A/基本設計書.xlsx / シート: 業務フロー -->

> このシートには 図形 19 個・接続子 11 本 があり、12 個からテキスト（`s4-g1`）、
  接続 9 本（`s4-c1`）を取り出しました。ただし接続子 2 本は両端が図形に
  結びついておらず…

## 図形（テキスト）  <!-- a:s4-g1 at=図形 19 個・接続子 11 本 -->

- `図形1` 受注登録
- `図形2` 与信判定<br>NG は差戻し

## 図形の接続  <!-- a:s4-c1 at=接続 9 本 -->

| 元 | 向き | 先 | 名前 | 線種 |
|---|---|---|---|---|
| 受注登録 | → | 与信判定 | コネクタ 7 | 実線 |
| 品質保証部 | → | AI 基盤 | 点検依頼 | 実線 |
```

**数えるのは図形そのものであってアンカー（載っている枠）ではない。** グループ化
された業務フローは箱 10 個でアンカー 1 個になるので、アンカーを数えていた頃は
「図形が 1 個あり、10 個からテキストを取り出しました」と**自分で矛盾したことを
言っていた**。申告が信用されなくなるのは、申告しないのと同じくらい悪い。

**画像を図形と混ぜない。** 貼り付けたスクリーンショットは「テキストの取れない図形」
ではなく「そもそも図形ではないもの」で、`arp4 render` で撮り直しても絵が絵のまま
出るだけである。同じ案内をすると空振りさせる（中の**文字**は `o1` に読んである ――
下記「貼り付け画像は中の文字も読む」）。

テキストは**図形ごと**に集める（アンカーごとではない）。グループ化された業務フローは
アンカー 1 個の中に箱が 10 個入っていることがあり、まとめると
「受注登録与信判定在庫引当」と繋がって語が壊れる。

**同じ壊れ方が 1 つの箱の中でも起きていた。** DrawingML の改行は段落（`a:p`）と
行区切り（`a:br`）の 2 通りあり、後者を読み飛ばしていたぶん `承認待ち` と
`3 営業日以内` が `承認待ち3 営業日以内` になっていた ―― 整理層はそれを 1 つの
状態名として読む。**繋げてしまうと元の 2 語には戻せない。**

セルが 1 つも無くても、図形があればファイルを出す ―― シートごと消えると、
そのシートが存在したことすら整理層に伝わらない。整理側は語だけで足りるならレコードに
し、流れが要るなら `kind: 未読取` で宣言する → [organized.md](organized.md)

### 線に付いた言葉と線種 ―― 接続の表は 3 列では足りなかった

接続は長く `元 / 向き / 先` の 3 列だった。**線そのものが仕様を持っている図がある。**

| 列 | いつ出すか |
| --- | --- |
| `元` / `向き` / `先` | 常に |
| `名前` / `線種` | **値が 1 つでもあれば出す** |
| `線色` / `太さ` | **行のあいだで値が違うときだけ出す** |

**線の名前は、線に付いた言葉の唯一の在り処である。** 図形の名前（`図 3` /
`Picture 1`）は Excel が振った番号なので取らないと決めてあり、人の言葉は代替
テキストのほうにある ―― **接続子はそこが違う。** 線には代替テキストを書く習慣が
無く、テキスト枠も持たない。実測（kotonoha r001）の体制図では `委託` `点検依頼`
`提供` `月次締め` が名前にだけあり、**「どれが委託か」は他のどこにも書かれて
いなかった。**

`コネクタ 10` のような自動名が混ざるが、**捨てる判断は整理層がする。** 機械が
「これは自動名だ」と判定して落とすと**落とした判断が誰にも見えなくなる**うえ、
判定は言語ごとの綴り（`コネクタ` / `Straight Arrow Connector`）に依るので、
資料の言語が変わるだけで人の付けた名前を捨てる。ここは転記に徹する。

**線種は「7 本とも実線でした」自体が答え**なので、値があれば必ず列にする。凡例が
「実線＝指揮命令 / 破線＝委託」と描き分けを謳っていても、図に破線が 1 本も無いなら
整理層が決められることは何も無い（**資料の側に情報が無い**、と分かる）。列が無いと、
それが「線種が無い図」なのか「線種を読んでいないパーサ」なのか読み手から区別
できない ―― 実測ではこれが通し実行で唯一の `未読取` 1 件になった。

読むのは `a:ln` に**書いてあるものだけ**である。`a:prstDash` があればその値
（`dash` → 破線）、無くて `xdr:style`（テーマを引く形）も無ければ OOXML の既定
どおり実線、`a:ln` が無ければ**言わない**。**解決しないものを断定しない** ――
テーマの線種は `a:lnRef` → `theme1.xml` を辿らないと決まらず、そこまでやって
いないので空のまま出す。「実線」と埋めると破線で描き分けてある図が全部同じに見え、
しかも**申告のほうが嘘になる。**

色と太さを違いのあるときだけ出すのは、`publish` が全行空の列を畳むのと同じ規律で
ある ―― 実測では 7 本とも `#404040` / `1pt` で、全行同じ値の列は表を横に伸ばす
だけだった。**描き分けていない属性は描き分けを伝えない。** 値も訳すだけで意味は
付けない（「破線＝委託」と読むのは凡例を見た整理層の仕事である）。表に無い
`prstDash` の値は原文のまま出す ―― 知らない値を「実線」へ丸めると、描き分けて
あるものが同じに見える。

## 図形（`xdr:sp`）を数えるだけでは足りなかった

上の約束（セルが無くても図形があればファイルを出す）は、**図形の数え方に穴が
あったぶんだけ守られていなかった。** 検証コーパスを増やした日に、`xdr:sp` を
1 つも持たない図が 3 種類出てきた ―― どれも図形 0 個・セル 0 個になり、
**ファイルが 1 本も出ずに消えていた**。資料に無いのでも読めなかったのでもなく、
シートが存在したことすら伝わらない。ここまでのどの申告にも引っかからない、
いちばん静かな消え方である。

| 消えていたもの | 実体 | いま出るもの |
| --- | --- | --- |
| **SmartArt**（組織図・手順・循環） | `xdr:graphicFrame` ＋ `xl/diagrams/data*.xml` | 箱の文字を `g1` に出す |
| **グラフ**（シートに貼られたもの） | `xdr:graphicFrame`（uri が `…/chart`） | タイトル・系列・参照範囲を `k1` に出す |
| **グラフシート** | そもそも `Worksheet` ではない | シート 1 枚として `g1` と `k1` を出す |

### 「別のシートの値です」だけでは誰も探しに行かない

グラフは長く「`グラフ 1 個`」と数えるだけで、申告は「中身は取れていません
（系列が指しているのは別のシートの値です）」だった。**言っていることは正しいが、
どのシートのどこかを言っていない** ―― 読み手はブックを端から探すしかなく、
実際には探されずに終わる。グラフシートに至っては、セルが 0 個なので**それ以外に
書くことが 1 つも無い**ファイルが出ていた。

参照範囲は `c:f` に `'元データ'!$B$2:$B$3` と**そのまま書いてある**ので、読むのは
座標からの復元ではなく転記である。タイトルと系列名は人が書いた文字で、図形の
`<a:t>` を読むのと同じことをしている。

**ただし「人が書いた文字」の入る場所は 1 か所ではなかった。** セルから引いたタイトル
（`c:strRef`）は `a:t` を持たないので、`<a:t>` だけを見ていた間は**そのグラフだけ**が
「（タイトルなし）」になっていた ―― 実物では表題をセルから引くほうが多い書き方である。
参照範囲も同じで、棒・折れ線・円は `c:cat` / `c:val` だが**散布図とバブルは
`c:xVal` / `c:yVal`** で、分類も値も空欄のまま「参照範囲を取り出しました」と申告して
いた（読み落としより悪い ―― **申告のほうが嘘になる**）。

```markdown
## グラフ（タイトル・系列・参照範囲）  <!-- a:s2-k1 at=グラフ 1 個 -->

| グラフ | 系列 | 分類 | 値 |
|---|---|---|---|
| 月別の受注・出荷件数 | '元データ'!B1 | '元データ'!$A$2:$A$3 | '元データ'!$B$2:$B$3 |
```

**図形の文字（`g1`）とはアンカーを分ける。** 前者は「このシートに描いてある文字」、
後者は「別のシートを指す案内」で、後者は読みに行く先であって資料の中身ではない。

**値そのものは出さない**（グラフにはキャッシュが入っていることがある）。指し先の
シートは同じパース結果の中に必ずあるので、そちらを読めばよい ―― 2 か所に同じ数を
置くと、片方だけ直された状態が生まれる。

読めたグラフについては「中身は取れていません」と**言わない**。`k1` にタイトルも
参照範囲も出ているのに読めていないと言うと、どちらを信じればいいのか分からなくなる
―― 申告が信用されなくなるのは、申告しないのと同じくらい悪い。

何であるかは `a:graphicData` の `uri` に書いてあるので、分類は転記である。3 つを
別々に数えるのは、**次にやることが 3 つとも違う**からである ―― グラフは元データの
シートを読めばよく、SmartArt は箱の文字が取れ、埋め込みオブジェクト（Word・PDF の
貼り込み）は元ファイルも `arp4 parse` に渡すしかない。ひとまとめに「図形」と数えて
いたら、どれも「絵にして読んでください」で終わっていた。

**SmartArt の文字は描画パートには無い。** シート → 描画 → `diagramData` と 2 段
たどった先の別ファイルにあり、箱・繋ぎの点（`parTrans` / `sibTrans`）・見た目用の
複製（`pres`）が同じ一覧に並んでいる。複製まで拾うと同じ語が 2 回出るので、
**箱だけを取る**。近年の設計書の体制図はこれで描かれていることが多く、
`xdr:sp` の数え方では「図がありません」と報告していた。

**箱どうしの繋がりは取らない。** オートシェイプの接続子と違い、SmartArt の `dgm:cxn`
が指しているのは箱ではなく内部の点（`presOf` / `presParOf` など役割つきの参照）で、
どれが「A の次が B」に当たるかはレイアウト定義まで解かないと決まらない ―― そこは
転記ではなく復元なので、やらずに数だけ申告する。

たどる段が 1 つ増えたが、実測は 30 冊で 0.009 秒（`drawing_parts` が 0.011 秒、
`formula_gaps` が 0.061 秒、パース全体が 1.4 秒）―― zip を開くのは 1 回に
まとめてある。

## 貼り付け画像は中の文字も読む（`o1` ―― Windows OCR）

長いあいだここは「画像の中身は機械には取れていません。実体を出すので、読むのは
整理層です」で止まっていた。**その申告は正しかったが、1 段足りなかった。**

貼ってある画像の多くは**絵ではなく字**である ―― 表・現行画面・帳票をそのまま
撮ったものが実物では圧倒的に多い。字であるなら機械が読める。読まずに渡していた
あいだ、整理層は**文字しか無い平坦な画像まで 1 枚ずつ開いて**いた。

読んでおくと 3 つ変わる。

- **平坦な画像は開かずに済む**（開くのは、読んだ字だけでは足りない絵だけでよい）
- **出典として指せる**（画像は開けても、開いた中身は引用できない ―― `o1` は指せる）
- **`grep` に入る**（「受注番号」がどの資料に出てくるかの検索に、画像の中身も入る）

### 別のアンカーにする（`i1` と混ぜない）

`i1` はブックに入っていたバイト列の写しで、`o1` は**機械の読み**である。同じ塊に
入れると、整理層は「資料にそう書いてある」と読む ―― OCR は必ず読み違えるので、
そこは分けておかないと**誤読が資料の値として正本へ入る**（次のラウンドではもう、
それが正本の値である）。見出しにも毎回「読み違えが混ざります」と書く。

実測（`tests/picture.py` の絵柄）―― `ORDER-001` は `ORDER-OOI` に、印刷物から
取り込んだ社章は `T 鋤 Lロら工 TEC` になった。**人には読めるが機械には読めない**
という検体の主張は、OCR を入れたあとも成り立っている。

**アンカーが 1 本増えるぶん、整理層の仕事も 1 件増える**（`o1` も `G001`（未整理）に
数える）。それでよいと判断したのは、`o1` に出るのが**引用できる中身**だからである ――
字が出ていない `o1` は画像そのものと同じ理由で `out_of_scope` へ落ちるだけだが、
字が出ている `o1` を数えないことにすると、**読めた仕様が誰にも整理されないまま
凍結が通る**（`i1` を数えている理由とまったく同じである）。

### 何が「読めなかった」かを言い分ける

`o1` は**空にしない**。空の塊は「画像に文字が無かった」に見え、それは arp4 が
いちばん避けたい取り違え（「資料に無い」と「機械が読めていない」）そのものである。

| `o1` に出るもの | 意味 | 次にやること |
| --- | --- | --- |
| 読めた行 | engine が字として読んだもの | 値に使う前に画像を開いて確かめる |
| 文字は見つかりませんでした | engine は動いた。**画像は絵である** | 開いて見る（`arp4 render` ではない） |
| 読めませんでした（理由） | その 1 枚が開けない（EMF・壊れた実体） | 元の画像ファイルを当たる |
| 読みにいっていません | `--no-ocr`、または環境に engine が無い | 環境の話（`P016`）。画像は開けば読める |

環境が理由のとき（Windows でない・言語パックが無い）は `P016` を**走らせた人にも
1 度だけ**出す ―― パース結果の中だけに書いても、それを読むのは整理層であって、
言語パックを入れられる人ではない。

### なぜ Windows OCR で、なぜ PowerShell 経由か

パース層は意味を判断しない層なので、読む相手は**転記の域を出ないもの**でよい ――
ここに LLM を置くと、パース層が資料に書いていないことを書き始める。Windows OCR は
最初から入っていて、ネットワークも要らず、同じ画像からは同じ結果が出る。

WinRT（`Windows.Media.Ocr`）を Python から直に呼ぶには `winsdk` / `winrt-*` の
追加インストールが要る。**「常に読む」を pip の追加インストールに条件付けると、
実際にはほとんどの環境で読まれない** ―― Windows PowerShell 5.1 は WinRT を呼べる
ので、追加インストールなしで届く道はここしかない（`pwsh` では代われない。WinRT の
射影は .NET Framework 側にしかない）。

起動は**ブック 1 冊につき 1 回**にまとめ、同じ実体は 1 度しか読まない（会社ロゴ・
帳票の枠は 1 冊の中で何十回も貼り回される）。実測で 6 枚 1 秒。

### 読んだ字に 2 つだけ手を入れる

**全角と全角に挟まれた空白を詰める。** Windows OCR は日本語を 1 文字ずつ語に割るので、
素の行は `受 注 番 号 ORDER-001` になる ―― 資料にそう書いてあったことは一度も無い。
字の種類だけで決める（辞書も文脈も見ない）ので判断ではなく、日付を画面の表記へ
直すのと同じ**忠実性の回復**である。英数との間は残す ―― そこは engine の割り方が
正しいことも多く、詰めると本当の区切りまで消える。

**小さい画像は 2 の冪で拡大してから読む**（長辺 1600 px を目安、最大 4 倍）。Excel に
貼られたスクリーンショットは縮めて貼られていることが多く、そのままでは字が潰れる
（実測 300×100 の画面コピーは、拡大しないと 1 行落ちた）。倍率を 2 の冪に限るのは、
**同じ画像からは同じ結果が出る**ことのほうが、あと一息の精度より大事だからである。

### 決定的ではあるが、環境をまたぐと同じではない

読める字は**入っている言語パックで変わる**（読んだ言語タグは `Reading` が持つ）。
同じ資料を別のマシンでパースし直すと `o1` だけが変わるので、それは編集として
git の差分に出る。揃えたいときは `--no-ocr` で読まないほうを選べる ―― 落としたことは
`o1` に必ず書くので、「読めなかった」と「読まなかった」は混ざらない。

### これで解決していないもの

**絵は絵のままである。** 業務フローの図・写真・レイアウトは字を読んでも伝わらない
（`o1` は「文字は見つかりませんでした」になる）。手書き・網点・斜行の乗った取り込みも
落ちる ―― そこは実体を開いて見る整理層の仕事のままで、変わったのは**開かなくて
よい画像がどれか**を機械が言えるようになったことである。

## 形式は Markdown

編集されることが前提なので、編集しやすさを機械可読性より優先する。

```markdown
# 基本設計書.xlsx / 受注テーブル

<!-- source: 資料/A/基本設計書.xlsx / シート: 受注テーブル -->

## 表 B8:J20  <!-- a:s1-t1 at=B8:J20 -->

| 論理名 | 物理名 | 型 | 桁 | PK | 必須 | 備考 |
|---|---|---|---|---|---|---|
| 受注番号 | ORDER_NO | 文字列 | 10 | ○ | ○ | 採番ルールは別紙 |
| 受注日 | ORDER_DATE | 日付 | | | ○ | |

## セル B2  <!-- a:s1-x1 at=B2 -->

- `B2` 受注テーブル（T_ORDER）定義書  改訂 2.1
```

表にならなかった塊は**セル番地を付けた箇条書き**で出す。番地を落とさないので、
区切りが間違っていても整理層が読み直せる。

**アンカーは HTML コメントで持ち、本文を汚さない。** `a:s1-t1` が識別子、`at=` が
元 Excel の位置である。

## アンカーの規律

| 規律 | 理由 |
| --- | --- |
| 編集してもアンカーを消さない | 元資料との照合が二度とできなくなる |
| 本文を直してもアンカーは変えない | 整理結果が指す先が壊れる |
| 行を分割・追加したら新しいアンカーを振る | 出典が「どの行のことか」を保てる |

アンカーは**行番号ではなく ID** である。行番号にすると、OCR を 1 行直しただけで
それ以降の出典が全部ずれる。

### セルの値はアンカーになれない

アンカーを HTML コメントで持つ形には穴があった ―― **資料のセルに
`<!-- a:s9-t9 -->` と書いてあると、書き出した Markdown を読み戻した側には
本物のアンカーに見える。** HTML の画面仕様書・テンプレートの設計書には普通に
出てくる文字列である。

実害は 3 つ重なる。表の途中に**無い塊が生え**、そこから先の本文が別のアンカーの
中身になり、整理結果が偽のアンカーを出典にしても `freeze` は通ってしまう
（アンカーは実在するので G004 に引っかからない）。**出典が資料の側から
書き換えられる**という、いちばん静かな壊れ方である。

いまは書き出すときに `<!--` `-->` を実体参照（`&lt;!--` `--&gt;`）にする。
Markdown でも HTML でも表示は変わらないので、**画面に見えている表記は保たれる**
―― 文字を捨てたり記号を足したりすると「セルの値をそのまま出す」ほうの約束が
破れる。申告（`notes`）にもリンク先のファイル名など資料由来の文字列が混ざるので、
同じ処理を通す。

## Excel から何を取るか

機械がやるのは 3 つだけで、**どれも意味の判断ではない**。

**① 非空セルの位置と値をそのまま出す。** 書式だけのセル・削除済みデータの残骸で
使用範囲が膨らむので、完全な空行・空列は落とす。値の解釈はしない。

**② 縦に広がる結合セルを下の行へ展開する。** 表の分類列で「同上」を表す日本の慣習で、
openpyxl は左上にしか値を返さない。**これは判断ではなく忠実性の回復**である
（画面上は全行に値が見えている）。

**当初は「幅 1 の縦結合」に限っていたが、幅で切るのが間違いだった。** 区分と小区分を
持つテーブル定義書では、区分の列を **2 列ぶんまとめて縦に括る**（`A10:B11`）のが
ごく普通の書き方である ―― 画面ではその区分が全行に掛かって見えているのに、幅 1 だけを
展開していたぶん 2 行目以降が空欄になり、**整理層には「区分の無い行」に見えていた**。
面結合を「タイトル用途が大半」と書いていたのは、検体に面結合が 1 つも無かったからで
ある（実物を数えたのではなく、横結合からの類推だった）。

切るべきなのは**方向**である。1 行だけの結合（`A1:D1`・二段見出しの上段）は「同上」
ではなく表題で、画面上も値は 1 つしか見えていない ―― 縦へは広げ、横へは広げない。

**ただし展開するのは値のある範囲までである。** 結合は列を丸ごと選んで掛けられる
（`A2:A1048576`）ので、素直に最終行まで埋めると **3 行の表から 100 万行の表が生えた**
―― 画面には 3 行しか見えていないのだから、これは忠実性の回復ではなく捏造である。
実測では列全体を結合した 1 シートだけでパースが 1.6 秒（10 万行の結合で計測）、
書き出した Markdown は 10 万行になった。他のセルが 1 つでもある最終行で止める
―― **表の外に行は無い。**

**③ 画面に見えている表記へ直す。** `str()` に任せると、資料に一度も書かれていない
表記が出てくる ―― **② と同じ忠実性の回復**であって、値の解釈ではない。

| セルの中身 | 素の `str()` | パース結果 |
| --- | --- | --- |
| 日付 | `2026-08-02 00:00:00` | `2026-08-02` |
| 時刻 | `09:30:00` | `09:30` |
| 真偽 | `True` | `TRUE` |
| パーセント（`0.0%` 書式） | `0.153` | `15.3%` |
| 計算結果（`=1200*0.08`） | `96.00000000000001` | `96` |
| 15 桁を超える数 | `1234567890123457024` | `1234567890123460000` |

`00:00:00` は資料のどこにも無く、`0.153` と `15.3%` では**整理層が別の値を読む**。
直すのは**表記が値そのものを偽っているものだけ**である。`￥1,200` を `1200` と出すのは
桁区切りと通貨記号が落ちるだけで数は同じなので触らない ―― 書式の再現を始めると、
どこまでやるかの線が引けなくなる（罫線・塗り・フォントまで行き着く）。

#### 数の桁は「書式の再現」の側ではない

`96.00000000000001` を `96` と出すのは、桁区切りを足すのとは違う ―― **Excel 自身が
有効数字 15 桁までしか持てない**ので、その 17 桁目は画面のどこにも出ていない。
二進の浮動小数点なので `=1200*0.08` の結果はそう保存されるだけで、**資料に一度も
書かれていない桁**である。日付の `00:00:00` をやめたのと同じ基準（表記が値そのものを
偽っている）がそのまま当てはまる。

15 桁を超える整数（会員番号を数値で持った表）でも同じで、Excel は下位の桁を 0 で埋めて
見せる。**型で扱いを変えない** ―― `int` と `float` で桁数が変わると、同じ表の隣り合う
2 行が別の桁数で出て、読み手は「片方は 19 桁の番号だ」と読む。文字列として持たれた
番号（`'1234567890123456789'`）は数ではないので触らない（そちらは 19 桁のまま画面に
出ている）。

#### 書式の `%` はパーセントとは限らない

`#,##0"%表示ではない"` の引用符の中は塞いであったが、**`\` のエスケープ**（`0\%` ――
次の 1 文字をそのまま出す）は素通りしていた。画面に `15%` と出ている評価点が `1500%`
になる ―― 読み落としではなく、**資料に無い数を作っていた**ぶんだけ質が悪い。

**④ 塊ごとに区切って出す。** 非空セルを空白ギャップ 1 行／列まで許して繋ぎ、塊ごとに
1 つの見出しにする。**これは意味の判断ではなく、トークンを減らすための提示上の区切り**
である ―― 区切りを間違えても LLM が読み直せるよう、**セル番地を必ず併記する**。
3 はここで「表かテキストか」を決め、その判定に後工程が依存していたが、4 は依存しない。

3 が持っていた「表の型を当てる」（`tables.yml`）は無い。**それは意味の判断なので
整理層の仕事**である。

### 番地を併記するだけでは読み直せなかった

④ が許されているのは「番地があるから読み直せる」からだが、**その番地から表の中の
位置を割り出せていなかった。** 塊の中の空行・空列を詰めて出していたので、
`at=B3:F8`（5 列 6 行）と書いてある表の中身が 4 列 5 行しかなく、3 本目が D 列なのか
E 列なのかを読み手が決められない。番地は「あるが使えない」状態だった。

いまは**塊の中の空行・空列を残す**。詰めていたときの実害はもう 1 つあって、
**空列 1 本を挟んで横に並べた 2 つの表**（実物の一覧シートにごく普通にある）が
地続きの 1 枚になっていた ――

```
| 画面ID | 画面名 | ボタン | 動作 |          ← 詰めていたとき（同じ行に無いものが並ぶ）
| SCR001 | 受注入力 | 登録 | 受注を確定する |

| 画面ID | 画面名 |  | ボタン | 動作 |       ← いま（D 列が空のまま残る）
| SCR001 | 受注入力 |  | 登録 | 受注を確定する |
```

前者は「受注入力画面に登録ボタンがある」と読めてしまうが、資料はそう言っていない
（隣に別の表が置いてあるだけである）。**区切りを間違えたのではなく、事実でない
並びを作っていた** ―― これは提示上の都合では済まない。

膨らむ心配は要らない。塊の中の空きは**たかだか 1 行／列**である（2 行以上空けば
別の塊になる）。実測は 30 冊 201 シートで 156,393 → 159,139 文字（＋1.8%）。

### その「たかだか 1 行／列」が成り立たない図がある

上の見積もりは、**空きが表の中の隙間である**ことを前提にしていた。工程表
（ガントチャート）はその前提の外にある ―― 斜めに並んだ `■` は空白 1 マスずつで
繋がるので**全部が 1 つの塊**になり、`62 行 × 121 列` の枠に値が 362 個という表が
出る。書き出した Markdown は **24,026 字で、その 9 割以上が `|  |`** である。
トークンを減らすための区切り（規律の ④）が、逆にいちばん大きなファイルを作っていた。

いまは**枠が実セル数の 8 倍を超えたら**（＝ 8 分の 7 以上が空欄なら）表の体裁を
やめて番地付きの箇条書きにする。小さい枠には掛けない（面積 100 未満）――
3 行 3 列に値が 3 つは**書きかけの表**であって工程表ではない。

| | 表として | 箇条書きとして |
| --- | --- | --- |
| 工程表 1 シート（62×121 に 362 セル） | 24,026 字 | **4,417 字** |
| コーパス 20 冊ぶん | 34,050 字 | **14,441 字** |
| パース時間（コーパス 20 冊） | 0.31 秒 | **0.12 秒** |

**失うものは無い。** どのセルにも番地が付くので、格子から位置を数えるより精確
である ―― 番地さえあれば読み直せるというのが区切りの前提そのものだった。
むしろ表にしていたときのほうが、`at=A1:DQ62` の 121 列を目で数えないと
`■` がどの日付の列なのか分からなかった。

**表の形で出していないことは言う**（`notes`）。黙ると「表が無いシート」に見えて、
読み手は表を探しに行く。

### 行頭の字下げは落とさない

項目定義書の「項目名」列は**字下げで親子を表す**（`受注ヘッダ` / `　　受注番号`）。
値をまとめて `strip()` していたぶん、**階層がまるごと平らになっていた** ―― 親と子が
同じ深さの項目として並ぶ。行末の空白は画面に出ないので落とす。

表として描画すると字下げは見えなくなるが、**読むのは Markdown の原文**なので
残っていれば伝わる（`| 　　受注番号 |`）。

### 走るのは実在するセルだけ

使用範囲（`sheet.dimensions`）は**信用できない**。削除済みデータの残骸や、遠くに
1 個だけ残った書式セルで `A1:GR20000` に膨らむ ―― 実案件のブックでごく普通に起きる。
端から端まで回すと**400 万回の空回り**になり、1 シートに 7.5 秒かかっていた
（実セルだけを回すと 0.03 秒）。30 冊のパースが分単位になると、「遅いから通さない」
が始まって資料が落ちる。**性能の問題が網羅性の問題になる**。

## 空欄に見えて空欄でないもの

パース結果の空欄には 2 通りある ―― **資料に値が無い**のと、**機械が読めていない**の。
表の上では見分けが付かないので、後者は必ず申告する。

**計算結果の保存されていない数式（`s1-f1`）。** `data_only=True` が返すのは「Excel が
最後に計算して保存した値」で、ツールが書き出したブック・LibreOffice 保存・手動計算の
まま保存したブックにはそれが無い。openpyxl は黙って `None` を返すので、**合計欄・率の
列がまるごと空**になり、整理層は「資料に記載なし」と読む。値は入れない（推測しない）
が、番地を並べたアンカーを出す ―― `未読取` を宣言する先が要る。**数式しか無いシートも
落とさない**（非空セルが 0 でもシートが存在したことは伝える）。

判定は zip の中のシート XML を直接見る。`data_only=False` でもう一度開けば同じことは
分かるが、大きなブックで読み込みが 2 倍になる。**値が無い書かれ方は 2 通りある**
――`<v>` がそもそも無いのと、`<v></v>` と空で置かれているの。後者を数え落としていた
ぶん、**いちばん値が入っていないブック（ツールが書き出したもの）だけが申告から
漏れていた**。`t="str"` の空値は数式が空文字を返した結果なので数えない。

**非表示の行・列。** 読むが、混ざっていると言う。非表示シートは読まないのに行・列は
読むのは、壊れ方が違うからである ―― ブック単位の非表示は作業用が大半だが、行・列の
非表示は**アウトラインの折りたたみ**（生きている仕様が畳まれているだけ）が普通にある。
「非表示だから廃止された仕様だ」と決めるのは意味の判断なので機械はやらない。

### 隠すフラグだけを見ていたので、潰れた行が「見えている行」になっていた

`hidden` しか見ていなかった。**Excel は行の高さ 0・列の幅 0 を普通に受け取り、
そのときフラグは立たない** ―― 行は画面から消えるのに、パース結果には**ほかの行と
まったく同じ顔で**並ぶ。非表示行の裏返しの壊れ方だが、**そちらより静かである**。
非表示行には「混ざっています」という申告が付くのに、潰れた行には何も付かない ――
`未読取` を宣言する先が無いので、読み手は疑う手掛かりすら持てない。

現場で潰れる理由は 2 つあり、どちらも実案件で普通に起きる。

| 潰れ方 | どういう資料か |
| --- | --- |
| ツールが書き出した | 帳票ツール・レポート出力。計算結果が保存されていない数式と同じ側の資料 |
| 人が境目を詰めた | 客先に出さない作業用の列・版を上げずに入れた改訂行。**列ごと消しはしない** |

**申告の文句を分けるのは行だけである。** ここは危うく間違えた ―― 「潰れたものは
再表示で戻らない」と行にも列にも書いてから、実物の Excel（16.0）で確かめた。

| 潰れたもの | 「再表示」（`Hidden = False`）を掛けると | 申告 |
| --- | --- | --- |
| 高さ 0 の行 | **0 のまま戻らない**（`Hidden` も True のまま） | 「高さを入れ直してください」を足す |
| 幅 0 の列 | **既定幅 8.11 に戻る**（`Hidden` も False になる） | 非表示列と同じ文句でよい |

列にまで「戻りません」と書けば、**戻る操作を戻らないと言う**ことになる ――
「繋がっているが相手が無名の線」と「どこにも繋がっていない線」を同じ文句で
申告していたのと同じ失敗である（**申告のほうが嘘**になる）。`veryHidden` に
「再表示してください」と言ってメニューに無いところで止まったのは、逆向きの
同じ間違いだった。

**確かめ方はコードではなく実物である。** COM で開いて `Rows("7:9").EntireRow.Hidden
= False`（＝右クリックの「再表示」がやること）を掛け、高さを読み直した。仕様書に
何と書いてあるかではなく、**その案内どおりにやった人の画面がどうなるか**しか
申告の正しさを決められない。

検体は `tests/dataset/設計書.yml` にある（→ 後述の 1 冊）。3.2 版のあとに入った
3.3 版の改訂が改訂履歴に高さ 0 で残り、機能一覧の作業用列（見積番号）が幅 0 で
潰れている ―― **表紙も目次もフッタも 3.2 版のまま**なので、その 1 行だけが
3.3 版の存在を知っている。

なお **openpyxl では検体を書けない**。行の高さも列の幅も `if value:` で絞って
書き出すので、0 は「指定なし」として落ちる（`customHeight="1"` だけが残り、
**普通の行として出てくる**）。`tests/dataset.py` はここだけシート XML に直に
`ht="0"` / `width="0"` を書く ―― **`hidden` は立てない**。立てたらそれは
「隠した行」で、この検体が突きたいものではなくなる。

**非表示のシート。** 読まないが、**あったことは言う**（`P003`）。読まないと決めた
のと黙って落とすのは別である ―― 作業用が大半とはいえ「旧版」「Ver1.0」を隠しただけ
のブックは実案件にごく普通にあり、そこに現行仕様が入っていることがある。シートが
1 枚も出てこなければ、誰もそれを疑わない。ブック単位の報告なので、シートごとの
`notes` ではなく findings に出す。

**隠し方は 2 通りあり、同じ案内をしていた。** 右クリックの「再表示」で戻せる
`hidden` と、そこに出てこない `veryHidden` である。後者に「Excel で再表示してから
回し直してください」と言うと、**言われたとおりにやってメニューに無い**ところで
止まる ―― 案内どおりにやって届かない申告は、申告しないのと同じである。いまは
VBE のプロパティで戻すことまで言い、**画面から隠す手間を掛けたシートなので作業用
とは限らない**ことを添える。

**エラー値（`s1-e1`）。** `#REF!` `#N/A` は画面にもそう見えているので表にはそのまま
残すが、**その欄の仕様は資料から読み取れていない**。数式の未計算（`f1`）と分けて
あるのは、**次にやることが正反対**だからである ―― あちらは「Excel で開いて保存し
直せば値が入る」だが、こちらは開き直しても直らない（資料そのものが壊れている）。
混ぜて出すと、保存し直して直らなかった側が「やっても無駄だった」で放置される。

## セルの値ではないところに乗っている仕様

空欄に見えるのですらなく、**表にそもそも出てこない**ものがある。黙ると丸ごと消える。

**セルのコメント（メモ）（`s1-m1`）。** 決定の理由・積み残し・レビュー指摘がここに
溜まり、**本文より新しいことが珍しくない**。値の無いセルに付いたものも取る ――
値で足切りすると、いちばん多い「空欄への指摘」だけが消える。記入者も出すのは、
誰の指摘かで重みが変わるからである。

### いまの Excel のコメントは旧形式ではない

2018 年以降の Excel が書くのは**スレッドコメント**で、旧形式は「メモ」に名前が
変わり既定では作られない。openpyxl が返すのは旧形式だけなので、**資料でいちばん
新しい情報が、いちばん読めない形で出ていた。**

スレッドコメントを付けた Excel は、古い Excel でも読めるように**同じ内容を旧形式
でも書く**。その本文は「[Threaded comment]」で始まる 200 字あまりの Microsoft の
但し書きで、記入者は表示名ではなく `tc={GUID}` である ―― 指摘 1 件ごとに
但し書きが 1 つ載り、本文はその末尾に埋もれる。3 件も並べば読むのをやめる。

```
- `C3` tc={7A1B2C3D-…}: [Threaded comment]  Your version of Excel allows you to
  read this threaded comment; however, any edits to it will get removed if the
  file is opened in a newer version of Excel. Learn more about…  Comment:  採番は…
```

`xl/threadedComments/*.xml` を読むと、旧形式に無いものが 3 つ取れる。

| 取れるもの | なぜ要るか |
| --- | --- |
| **返信** | 指摘への回答がそこにしか無い（「10 桁へ」に対する「8/20 まで」） |
| **記入者の表示名**（`xl/persons/`） | なりすましは GUID しか持たない。誰の指摘かで重みが変わる |
| **解決済みか**（`done`） | 片付いた指摘と生きている指摘が混ざると、整理層は全部を積み残しとして読む |

```markdown
- `C3` 設計者（2026-07-01）: 採番は 2026 年度から 10 桁へ。旧 8 桁は移行対象
- `C3` 返信 レビュア（2026-07-02）: 移行対象の洗い出しは 8/20 まで
- `C4` [解決済み] レビュア（2026-06-20）: 桁あふれの検討結果は別紙のとおり
```

**旧形式と分けずに同じ `m1` へ出す。** 読み手にとってはどちらも「セルに付いた
指摘」で、書かれ方の違いは資料が作られた年の違いでしかない。同じ番地に両方ある
ときは**スレッド側を採る** ―― 混ぜずに 2 件出すと、レビュー指摘の件数が倍に見える。

**名簿から名前が引けなくても落とさない**（`記入者不明`）。退職者・外部のレビュアは
`xl/persons/` から消えていることがあり、そこで捨てると**いちばん外から来た指摘**
だけが消える。

**返信は 1 段とは限らず、親が居るとも限らない。** `parentId` の連なりを 1 段しか
辿っていなかったぶん、**返信への返信**が黙って落ちていた（画面では返信が縦に並ぶ
だけなので、落ちていても誰も気付かない）。もっと静かに消えるのが**親を失った返信**
である ―― 起点のコメントだけ削除された資料・抜粋して配られた資料でこうなり、
起点が無いので 1 件も出ず、**そのセルにコメントが付いていたことすら伝わらない**。
いまは起点の無いものも「返信（起点のコメントは資料に残っていません）」として出す。

**パートを落として配られた資料**（抜粋・別ツールでの再保存）ではなりすましだけが
残る。そのときは但し書きを剥がして本文を出す ―― 記入者も返信も取れないが、
**但し書き 200 字より本文のほうが要る。**

**リンクの行き先（`s1-l1`）。** 表に出ているのは表示文字列だけである。落とすと
目次シートが「語の一覧」にしか見えないが、実際には**どの資料がまだ手元に無いか**の
一覧である ―― `arp4 parse` に渡していないブックを指すリンクは、資料の取りこぼしの手がかりに
なる。ブックの中を指すリンクは `location` に、外を指すものは `target` に入り、
**別ブックの特定シートを指す形では両方に分かれて**入る（片方だけ見ると半分になる）。

**外部ブック参照（`P004`）。** リンクと同じ理屈だが、**表からいっそう見えない。**
`='[単価表.xlsx]単価'!B2` の参照先の値は**キャッシュされている**ので、画面に出て
いるのはただの `1200` である ―― それが別ブック由来だとは誰も気付かない。リンクが
「人が辿る先」なのに対してこちらは「数式が読んでいる先」で、その資料が集まって
いなければ**その数の根拠は次のラウンドでも確かめられない**。参照先は
`xl/externalLinks/_rels/` の Target に、参照先のシート名は本文にキャッシュされて
いる（どちらも転記）。ブック単位の事実なので、非表示シート（`P003`）と同じく
findings に出す。

**代替テキスト（`s1-a1`）。** 貼り付け画像の中身は取れないままだが、`descr` に
「受注入力画面のイメージ（明細は 20 行まで）」と書いてあれば**何の画像かは分かる**。
名前（`Picture 1`）を取らないのはその裏返しで、Excel が自動で振った番号は並べても
行が増えるだけである ―― `descr` は人が書いたときにしか入らない。Word の貼り込みでは、
そこに**`arp4 parse` に渡すべき資料の名前**が入っていることがある。

**画像と埋め込みオブジェクトからしか取っていなかった。** `descr` は図形
（`xdr:sp`）にも群（`xdr:grpSp`）にも SmartArt にもグラフにも書ける ―― そして
**構成図はゾーンごとに 1 文添えるのが普通の書き方**である。「現用／待機の 2 系統で
構成する。DR 環境は別紙 5 を参照」は箱の文字にも表にも無く、**そこにしか書かれて
いない**。画像だけを見ていたぶん、いちばん図全体を説明している 1 文が落ちていた。

### 紙にしか出ないもの（`s1-p1`）

**日本の設計書は綴じて配る文書である。** 文書番号・版・機密区分・ページ番号は
ヘッダとフッタに入り、**どのページにも刷られている**のに、セルには 1 つも書かれて
いない。表だけを読むと、その 1 冊が何の文書なのかが落ちる ―― 表紙のあるブックなら
まだ拾えるが、シート 1 枚がファイル 1 本になる以上、**どのファイルにも出典として
版が要る**。

`&P` `&N` `&D` は**書いてあるまま出す**。ページ番号は刷ってみないと決まらない値で、
機械が埋めれば資料に一度も書かれていない数を仕様にすることになる（日付を
`2026-08-02 00:00:00` と出さないのと同じ基準）。

**印刷タイトル行は「どこまでが見出しか」の申告である。** `arp4 render` が
`--title-rows` を人に聞くのは、**どこまでが見出しかを機械が当てるのは意味の判断**
だからだった。ページ設定に書いてあるのはその答えではなく、**資料の作成者がそう
決めたという事実**である ―― 転記なので取る。何行目までを見出しとして扱うかを
決めるのは、それを読んだ整理層である。

**空のシートを 1 本増やさない。** ページ設定は全シートを選択してまとめて掛けるのが
普通なので、フッタがあることを「シートに中身がある」根拠に数えると、**作業用の白紙が
ぜんぶパース結果になる**。資料が増えたのではなく器が増えるだけなので、数には入れない。

### 誰がいつ触ったかはブックのプロパティにしか残らない（`P005`）

改訂履歴のシートは**人が書いた申告**である。書き忘れれば何も残らないし、版を
上げずに直せばどこにも出ない。ブックのプロパティ（`docProps/`）は Excel が黙って
書くので、**そこに無い更新がここにだけ残る** ―― 課題管理のコメントが本文より
新しいのとまったく同じ形である。

取るのは表題・作成者・作成日時・最終更新者・最終更新日時・会社・作成アプリで、
どれも転記である。**作成アプリを取るのは、Excel で作られていない設計書があるから**
だ ―― 帳票ツールの出力は計算結果が保存されておらず、行が高さ 0 で潰れている。
そうと分かっていれば、空欄を見たときの身構え方が変わる。

**食い違っていても機械は何も言わない。** 最終更新日時が最新版の改訂日より後なら
「載っていない更新がある」のか「開いて保存し直しただけ」なのかは資料からは決まらない
―― どちらかを当てるのは意味の判断である。並べるだけにして、突き合わせは整理層へ渡す。
ブック単位の事実なので、非表示シート（`P003`）・外部参照（`P004`）と同じく findings
に出す。**日時は UTC** なので、そう書き添える（画面のプロパティは現地時刻で出る）。

### 取り消し線だけは書式から取る

ここには「**罫線・塗り・フォント・取り消し線**は取らない ―― 数は変わらない。
書式から意味を決める（取り消し線＝廃止）のは整理層の仕事である」と書いてあった。
**前半は正しいが、後半が成り立っていなかった。**

判断を整理層に任せると書いておきながら、**整理層に届いていたのは `受注一括取込`
という文字だけ**で、画面に見えている `~~受注一括取込~~` ではない。任せた先が
判断の材料を受け取っていないので、そこで下される判断は 1 つしかない ――
「これは生きている機能だ」。既存資産の棚卸しで、**やめたはずの機能が現行仕様に
混ざる**のがこの穴の実害である。

塗り・太字・色と線を引くところは引ける。**取り消し線は「その文字が消されている」
ことを表す唯一の書式**で、強調は値を偽らないが取り消し線は偽る ―― 日付を
`2026-08-02 00:00:00` と出すのをやめたのと同じ基準（表記が値そのものを偽って
いる）に、これだけが当てはまる。行を消さずに線を引くのは**いつ何をやめたかを
残すため**なので、資料としてはむしろ丁寧な書き方である。それが値だけ抜き出すと
消える。

**それでも「廃止」とは言わない**（`s1-d1`）。出すのは「この番地に取り消し線が
掛かっている」という転記だけで、廃止・消し忘れ・未実装のどれなのかは整理層が
決める ―― 非表示の行・列とまったく同じ扱いである（落とさず、混ざっていると言う）。

### 取らないと決めたもの

| 取らないもの | なぜ |
| --- | --- |
| **入力規則の選択肢**（区分の候補） | クリックするまで画面に出ない。「画面に見えている表記へ寄せる」の外側である |
| **条件付き書式・数式の分岐** | 同上。ここを取り始めると Excel の設定を仕様として読み直す作業になり、境目が引けない |
| **罫線・塗り・フォントの色・太字** | 強調は値を偽らない。数も表記も変わらないので、再現を始めるとどこまでやるかの線が引けない |
| **図形・画像の名前**（`Picture 1`） | Excel が自動で振った番号でしかない。並べても行が増えるだけで何も伝わらない（人が書く `descr` は取る） |

入力規則は迷ったところである ―― 区分の候補（通常・返品・見積）が**そこにしか
書かれていない**設計書は実在し、取れば整理層は明らかに楽になる。それでも取らない
のは、「クリックすると出る」を認めると条件付き書式・数式の分岐・コメント以外の
オブジェクトまで同じ理屈で入ってきて、**どこまでが「資料に書いてあること」なのかを
機械が決める**ことになるからである。取り消し線がこの線を越えないのは、
**クリックしなくても画面に出ている**からである。

**取らないと決めたものは、取れていないとも言わない。** 申告は「画面に見えているのに
取り落としたもの」だけに絞る ―― 何でも申告すると、本当に読めていないもの
（`f1` `e1` `g1`）が申告の山に埋もれて読み飛ばされる。

**ただし検体には入れてある。** 決定が正しいかどうかは、実物で何を落としているかを
見ないと確かめようがない ―― `tests/dataset/設計書.yml` の機能一覧には区分の候補
`保守`、課題管理には状態の候補 `取り下げ` が入力規則にだけ入っており、**どの行にも
選ばれていない**。課題が 4 件あるように見えて、取りうる状態は 5 つある。この 1 語が
パース結果に最後まで出てこないことを `test_入力規則の候補は現実の1冊でも取らない`
が見ている ―― 決定を覆すなら、まずこの検体で何が変わるかを読んでからにする。

## コードから何を取るか

**骨格は AST で取る。** クラス・メソッド・シグネチャ・戻り値・例外は構文木から
曖昧さゼロで取れるので、ここに LLM を使っても精度は上がらない。

```markdown
# src/order/受注ヘッダ.py

## クラス: OrderHeader  <!-- a:m1 at=src/order/受注ヘッダ.py#L6-L24 -->

| メンバ | 種類 | 注釈 | シグネチャ | 戻り値 | 例外 | 行 |
|---|---|---|---|---|---|---|
| OrderHeader | クラス | @dataclass(frozen=True) | class OrderHeader | | | 6 |
| order_no | フィールド | | order_no: str | | | 9 |
| line_count | メソッド | @property | line_count() | int | | 17 |
| parse | メソッド | @staticmethod | parse(text: str) | 'OrderHeader' | ValueError | 22 |

## 取り込み  <!-- a:i1 at=src/order/受注ヘッダ.py -->

| 取り込み | 元 | 名前 | 行 |
|---|---|---|---|
| from order.採番 import 次の番号 | order.採番 | 次の番号 | 8 |
```

**列の並びは Java と同じに揃えてある。** 整理層は出自を気にしないので、同じものを
2 つの形で出す理由が無い。

書き出しは `parsed/src/order/service.py.md`（元のパスに `.md` を足すだけ）。Excel は
ブック名がディレクトリになりシートごとに 1 本、コードは 1 ファイル 1 本である。

塊の頭文字は出自を表す ―― `m` が骨格、`i` が取り込み、`t` がテスト、`j` が Java の
型、`t`/`k`/`x`/`c` が DDL の表・制約・索引・コメント。**番号を通しにしない**のは、
取り込みを 1 つ足しただけで既存の出典が全部ずれるからである。

### 引数は 4 つの入れ物に分かれている

`ast.arguments` は引数を位置専用・普通・可変長・キーワード専用に分けて持つ。長らく
`args` しか読んでいなかったので、**`*` より後ろがまるごと消えていた** ―― 詳細設計書に
`plan_worksheet(worksheet, extent)` と出ていたものの実物は
`(worksheet, extent=(0, 0), *, boxes=(), max_px=MAX_PX, ...)` である。

読み落としなら申告できるが、これは**書いてある数と違うものを書いている**
（その表を見て書いた呼び出しは通らない）。**申告のしようがない壊れ方**は、
読み落としより先に直す。既定値も出す ―― 「省略できるか」は呼ぶ側がまず知りたい
ことで、AST に書いてある。

### 1 本ずつを塊にしない ―― 行は列で持つ

出典の精度と、整理に迫られる件数はぶつかる。1 関数 1 塊にすれば出典は正確になるが、
`freeze` は塊 1 個ずつに整理か対象外宣言かを迫るので、**補助関数 30 本のモジュールが
未整理 30 件**になる。通すために宣言を量産させると、**宣言そのものが読まれなくなる**。

塊は 1 個のまま、`行` 列を持たせて原本を 1 行ずつ読み直せるようにした。塊の `at` も
ファイル名だけで終わらせず、その塊が覆う範囲（`#L37-L81`）を出す。

### デコレータと属性 ―― 層を決める手がかりはここにしかない

**`@dataclass` が付いているかどうかは、そのクラスが値の入れ物なのか処理を持つ層なのかを
分ける** ―― 詳細設計書の `tier`（Common / Repository / Service / Validator）を決める
最大の手がかりである。出していなかったあいだ、**57 モジュールの層分けを整理層が全部
推測で付けていた**。`@property` も同じで、呼び出しではなく値に見えるメンバかどうかが
変わる。どちらも AST に書いてあり、当てにいく作業が 1 つも無い。

**クラス直下の属性も出す。** `@dataclass` だと分かっても、それが**何を持つ入れ物なのか**
はどこにも書いていなかった ―― Java の `private String orderNo` にあたるものが Python
側だけ落ちていた形で、データ項目を起こす根拠がここにしか無い。継承（`class X(Base)`）も
同じ用途で、注釈を使わない現場ではこちらが唯一の手がかりになる。

**種類（クラス／フィールド／メソッド）は構文木の位置だけで決める。** `@property` を
「プロパティ」と呼び替えるのは解釈なので、注釈は注釈のまま別の列に出す ―― Java で
`@Entity` を本体と混ぜないのと同じ理由である。

### 取り込みは機械が出す

`import` は構文木からゼロ曖昧に取れるのに出していなかったので、呼出関係（`calls`）は
整理層が原本を読んで手で起こしていた。**「構文木から取れるものに LLM を使っても精度は
上がらず、コストと見落としだけが増える」と決めた当のもの**である（決定 2）。
30 本なら通っても、114 本・200 本の規模では手作業が先に破綻する。

**関数の中の取り込みも拾う**（重い依存を遅らせる書き方は普通にある）。どれが自分たちの
モジュールかは決めない ―― `from . import` の点の数も書いてあるとおりに出し、
どこを指すかを解くのは置き場を知っている側の仕事である。

**1 行 = 1 名前。** `from arp4 import mdio, yamlio` は 2 行に割る。1 行で出していた
あいだ「元」に書けるのは `arp4` だけで、**2 本の依存が 1 升に畳まれていた** ――
整理層はそこから `calls` を 2 本起こすことになり、実測で `arp4.parse → arp4.yamlio`
が落ちた（92 本のうち 91 本）。畳まれていると、機械には**落ちたことすら言えない**
（升の中身と関係の本数が対応していないので、数えることも突き合わせることもできない）。
`import a.b` はモジュールそのものを束ねるので「名前」は空にする ―― `a.b` と書くと
`from a import b` と同じ形になって区別が付かなくなる（→ 決定 46）。

**取り込みが 0 本でも塊を出す。** `i1` の `at` はファイルそのものなので、これは
取り込みの一覧であると同時に**モジュールを指す唯一のアンカー**である。0 本のとき
落としていたので、`import` を 1 つも持たないモジュールには指す先が無かった ――
自身の `__init__.py` がそれで、パッケージの冒頭に書いてある「意味の判断は整理層
だけが行う」が**モジュールとして 1 件も起きなかった**。未読取でも対象外でもなく、
アンカーが無いので `G001` にすら上がらない。**読めていないものほど静かに消える**
の、いちばん静かな形である（→ 決定 41）。

中身が 1 つも無いファイルには出さない ―― 書くことが無いものにアンカーを立てると
対象外宣言だけが量産され、**宣言そのものが読まれなくなる**（上の「1 本ずつを塊に
しない」と同じ理由）。空のファイルは今までどおり `P009` で申告する。

### `raise` に渡す補助関数は、宣言された戻り値で出す

`raise _broken(path, exc)` の `例外` 欄に `_broken` と出していた。これは private な
ヘルパの名前であって例外の型ではないので、整理層は**書きようがない** ――
`raises: _broken` は嘘になり、落とせば `G018`（出典の欄が埋まっているのに属性が空）が
鳴る。**どちらを選んでも正しくない欄**を機械が出していた。

原本には `def _broken(...) -> YamlError:` と書いてあるので、辿るのは宣言された
戻り値 1 ホップだけである ―― 当てにいっているところが 1 つも無い（規律の表でいう
**忠実性の回復**）。注釈が無ければ名前のまま出す。**呼び出しの形のときだけ**辿る
（`raise saved` は変数を投げているので、名前が関数と同じでも別物である）。

実測（自身のソース 26 ファイル・`例外` 欄が埋まっているメンバ 15 件）で 2 件が変わり、
`yamlio.load` は `YamlError, _broken` → `YamlError` になった ―― 決定 38 が
「private なヘルパを落としただけで正しい」と書いた**曖昧さの発生源のほう**が消えた。

### テストはテストとして出す

`test_*.py` / `*_test.py` の中の `test` で始まる関数は `t1` の塊へ分ける。集める規則は
**pytest のものをそのまま写す** ―― 規約であって解釈が要らない（`~$` を Excel の一時
ファイルと見るのと同じ）。呼ぶ側が名前で決めているものを、こちらだけ疑う理由が無い。

分けていなかったあいだ、テストは「モジュール」として詳細設計書へ流れるだけで、
**テスト仕様書は空のまま**だった ―― このリポジトリには 340 件のテストがあるのに、
トレーサビリティは「要件 44 件すべてテスト漏れ」と出していた。**事実に反する表**を
出すほうが、空の表より悪い。fixture と補助関数はテストと混ぜない（混ぜると
「何件あるか」が言えなくなる）。どの要件を検証しているか（`verifies`）は整理層が決める。

**意図の層（業務ルール・条件分岐の業務的意味）はここに出さない。** コードは元ファイルが
テキストなので、整理層のエージェントが**原本を直接読める** ―― Excel と違って中間表現を
挟む必要がない。この非対称は意図的である。

| | 骨格 | 意図 |
| --- | --- | --- |
| Excel | 機械（`parsed/` に出す） | LLM（`parsed/` を読む） |
| コード | 機械（AST → `parsed/` に出す） | LLM（**原本を直接読む**） |

## Java は宣言と注釈だけを取る

`jp-sier-std` という名前のパックが、**日本の受託開発でいちばん多い資産を読めなかった**。
`examples/sales-corpus` は Java を 114 本生成しておきながら「arp4 は Java を読まない」と
自認していた。

ただし**全文を読みにいってはいけない** ―― 世代ごとの文法・生成コード・ロンボクに
付き合う作業が永久に続き、決定 1 が捨てた側（宣言の保守が永久に続く）へ戻る。読むのは
`{` の対応だけで取れるところ、つまり**宣言の頭と注釈**に限る。実測は
114 本 → 型 114・メンバ 1,173・0.3 秒。

```markdown
## クラス: OrderEntity  <!-- a:j1 at=src/main/java/…/OrderEntity.java#L13 -->

| メンバ | 種類 | 注釈 | 宣言 | 行 |
|---|---|---|---|---|
| OrderEntity | クラス | @Entity @Table(name = "T_ORDER") | public class OrderEntity | 13 |
| orderNo | フィールド | @Id @Column(name = "ORDER_NO", length = 10) | private String orderNo | 17 |
```

**注釈を別の列にするのが要点である。** Java の現場では種別を決める手がかりが本体では
なく注釈に載っている（`@Entity` はエンティティ、`@Column` はデータ項目、
`@RestController` は外部インターフェース）―― 混ぜて 1 つの文字列で出すと、整理層が
正規表現を書くことになる。引数の中身まで残す（**物理名の根拠がそこにしか無い**）。

やめた案が 3 つある。

| やめた案 | 何で駄目だったか |
| --- | --- |
| `{` の深さでメンバを決める | **本体の中の文がメンバに見える**。`int matched = 0;` がフィールド、`for (...)` がメソッドとして出ていた。波括弧 1 つずつに「それが型の本体か」を覚えさせ、型の本体だけを通ってきた宣言をメンバとする |
| 元のテキストからそのまま出す | **javadoc が宣言の欄へ丸ごと入る**（1 行が数百字になる）。意図の層は出さないと決めてある |
| 文字列を潰した写しから出す | `@Column(name = "ORDER_NO")` の中身が消える。潰す理由が「対応を数えるため」と「意図を出さないため」の 2 つあって範囲が違うので、**写しも 2 つ要る** |

`"}"` という文字列や `// }` というコメントが 1 つ混ざるだけで、**そこから先の型が全部
ずれる**。ずれるのは読み落としではなく作り替えなので、申告のしようがない ―― だから
数える用の写しでは文字列もコメントも潰す。

C# は**移すまでは「無い」と言う。**

## 原本は git が保存する

パース結果を編集可能にしたので「機械が最初に出したもの」との差が要るが、**別途 raw を
持つ必要はない**。ラウンドディレクトリの初回コミットがそのまま原本である。

```bash
git log --follow .arp/rounds/r001/parsed/資料/A/基本設計書.xlsx/受注テーブル.md
git diff <初回コミット> -- .arp/rounds/r001/parsed/
```

そのぶん、**編集理由をコミットメッセージに残す**規律が要る。OCR の訂正と都合のいい
書き換えは diff では区別がつかず、ここは機械では守れない。

## 撮った版は指紋で残す

git が保存するのは**パース結果**であって、**原本**ではない（元資料は他人の
ファイルで、リポジトリに入っているとは限らない）。だから「このパース結果は原本の
どの版を撮ったものか」は、どこにも書かれていなかった。

`arp4 parse` は撮った原本のハッシュを `.arp/rounds/<r>/sources.yml` に残す。原本が
差し替わってもパース結果は古いまま残り、アンカーは全部実在するので、**`freeze` も
`check` も `conform` も通る** ―― 落ちるところが 1 つも無く、気づけるのは生成された
設計書を人が読み直したときだけである。実測で自身のソース 26 ファイル中 2 本が
その状態だった（→ 決定 39・[freeze.md](freeze.md)）。

**記録するのは書けたパース結果の原本だけ**である。編集済みで上書きを見送った
ものまで指紋を更新すると、ディスクの上には古い写しが残っているのに指紋だけ新しく
なり、**ずれが消えたように見える**。

## 検証用のコーパス

パース対象の資料は、テストがその場で 1 冊ずつ組み立てていた。それだと**実物には
あるがテストには無い書かれ方**が誰の目にも触れない ―― 数式の合計欄・非表示の行・
貼り付け画像・マクロ付きのブックは、どれも実案件の設計書に普通にあるのに 1 度も
パースに通されていなかった（ここに挙げた欠陥は全部、コーパスを作った日に出てきた）。

`tests/corpus.py` が実物によくある書かれ方を 20 冊 35 シートぶん組み立てる。テストは
`arp4 parse` と同じく**丸ごと 1 度に**通し、各テストは 1 つの観点だけを見る
―― 実運用で起きるのは「1 冊が壊れていて 19 冊が落ちる」であって、「1 冊だけを完璧に
パースする」ではない。**バイナリは置かない**（中身がコードで読めないと、その資料が
何を写したものか半年後に誰にも分からなくなる）。

**同じことが 3 度起きた。** 最初の 10 冊で出てきた欠陥（数式の合計欄・非表示の行・
貼り付け画像・マクロ付きのブック）を直したあと、6 冊を足しただけで**次の 7 つ**が
出てきた ―― グラフだけのシートが消える、SmartArt が「図形 0 個」になる、
セルのコメントとリンクの行き先が丸ごと落ちる、`#REF!` を値として出す、非表示シートを
黙って落とす、字下げを潰す、番地から表の位置を割り出せない。

さらに 4 冊（＋既存 3 冊への追記）を足したら、**次の 8 つ**が出てきた。

| 検体 | 出てきた欠陥 |
| --- | --- |
| `レビュー記録.xlsx` | スレッドコメントの本文が 200 字の但し書きに埋もれ、記入者が GUID になる。返信と解決済みが取れない |
| `工程表.xlsx`（工程） | ガントチャートが `62 行 × 121 列` の表になり、9 割が空欄の Markdown が出る |
| `工程表.xlsx`（体制） | 列ごとの縦結合を展開して、3 行の表から 2000 行の表が生える |
| `やっかいな値.xlsx` | セルに書かれた `<!-- a:s9-t9 -->` が**読み戻しで本物のアンカーになる** |
| `廃止一覧.xlsx` | 取り消し線で消した行が、生きた行と見分けが付かない |
| `外部参照.xlsx` | 別ブックを参照していることが、どこにも出ない |
| `実績報告.xlsx` | グラフの参照先シートを言わないので、誰も読みに行かない |
| `画面レイアウト集.xlsx` | 画像の代替テキスト（人が書いた唯一の文字）を捨てている |

**どれも実装を読んでいても見つからず、検体を書いた日に出た**（3 度とも同じである）。
アンカーの偽造に至っては、**パース結果を書いて読み戻すところまでやらないと**
見えなかった ―― 書き出したものだけを見ていれば、値が正しく出ているようにしか
見えない。

パースの精度は、コードを睨んで上がるものではなく**検体の多様さぶんしか上がらない**。
`src/arp4/parse.py` に手を入れるときは、先に再現する 1 シートを足すこと ―― 直した
証拠がそこにしか残らない。

### 検体は道具ではなく資料の写しである（`tests/dataset/*.yml`）

4 度目に検体を増やすとき、**書き方のほうを変えた。** `tests/corpus.py` は 1 冊ごとに
Python の関数を書く形で、20 冊まではそれで足りていたが、増やそうとすると
「資料の写し」と「Excel の組み立て方」が同じ関数の中で混ざる。

| 混ざると起きること | 実際に起きたこと |
| --- | --- |
| **検体を足すのに Python が要る** | 「B5 にこう書いてあった」という事実の列が手続きになり、関数を実行しないと中身が言えない |
| **組み立ての癖が検体に混ざる** | `inject_drawing` が `.rels` を丸ごと書き換えていたので、**1 冊に描画を 1 枚しか置けなかった** ―― 資料の都合ではなく道具の都合である |

いまは検体を **YAML の宣言**（`tests/dataset/*.yml`）で書き、組み立ては
`tests/dataset.py` が読む。**資料の知識をそちらに 1 つも置かない**のが分け目で、
「この検体は何を突くか」は YAML の `なぜ` に書く（`corpus.py` の docstring と同じ
役目である）。**バイナリを置かない**という約束は変わらない。

```yaml
置き場: 資料/F/テーブル定義書.xlsx
なぜ: |
  **面結合（複数行 × 複数列）が画面と食い違う。** …
シート:
  - 名前: 受注ヘッダ
    表:
      A1:
        - [区分, 小区分, 論理名, 物理名]
        - [ヘッダ, キー, 受注番号, ORDER_NO]
    結合: [A4:A9, A10:B11]
```

最初の 13 冊 24 シートで **YAML 733 行 ＋ 読み込み器 311 行**（`corpus.py` は
20 冊 31 シートで 846 行）。組み立て 0.51 秒・パース 0.57 秒で、`corpus.py`
（0.43 / 0.67 秒）と変わらない ―― **宣言にした代償は無い。**（いまは 20 冊
46 シートで YAML 1,850 行 ＋ 読み込み器 1,020 行 ―― 後述の実測）

`corpus.py` は移さずに残してある。**新しい検体だけをデータで書く**（移し替えは
検体の内容を 1 つも増やさないのに、35 シートぶんの期待値を書き換える）。

```bash
python tests/dataset.py <ディレクトリ>   # 実ファイルとして書き出す
```

### Excel が描けないものは検体ではない

**宣言にした最初の版は、Excel で開いても図が 1 つも出なかった。** 描画パートを
zip に置き、シートから関係を張るところまでは合っている ―― arp4 は関係だけを
辿るので**パースは通り、テストも全部通る**。実物の Excel で開いたときにだけ
図が消えていた。

これは検体としては致命的である。人が開いて「この資料は何を写したものか」を
確かめられず、`arp4 render` も空の絵しか撮れない ―― パースの申告
（「図形 4 個・接続子 5 本があります」）が正しいことを**目で確かめる手段が無い**。

足りなかったのは 3 つで、どれも**資料の中身ではなく組み立ての作法**である。

| 足りなかったもの | 無いとどうなるか |
| --- | --- |
| `[Content_Types].xml` の申告 | 「ただの XML」として素通りする（Excel は描画だと思わない） |
| シート XML の `<drawing r:id=…>` | 関係があっても Excel は描画を探しに行かない |
| 図形の必須要素（位置・寸法・形・文字枠） | 要素が欠けた図形は描かれない |

だから YAML には**箱と線だけ**を書き、DrawingML の作法は `tests/dataset.py` が
埋める。位置は番地（`位置: B3:D5`）で書く ―― 座標を検体に書かせると、箱を
1 つ足すたびに EMU を計算することになる。

**ここで 2 つ、実物の Excel でしか出ない失敗が出た。**

| 失敗 | 中身 |
| --- | --- |
| コメントのあるシートが**ブックごと開けない** | 要素の順番はスキーマで決まっており、`<drawing>` は `<legacyDrawing>` より前 ―― 図の無いシートでは起きないので、1 枚ずつ見ていると気付けない |
| 円グラフだけ**ブックごと開けない** | 人が打ったタイトル（`c:rich`）には `<a:bodyPr/>` `<a:lstStyle/>` が要る（セル参照のタイトルには要らない） |

どちらも「図が出ない」より悪い。**申告した種別のパートは Excel が中身まで
検査する**ので、揃っていなければブックが開けなくなる ―― 逆に言えば、申告する
なら完全に揃える。スレッドコメントだけは旧形式のコメント一式との対応が要るので、
パートは置くが申告しない（arp4 は関係を辿るので読める）。

#### 図が出るだけでは足りない ―― フローがフローに見えていなかった

ブックは開き、箱も線も出た。**それでも業務フロー集の受注フローは、開いた人に
壊れて見えた。** 線は箱の角から角へ斜めに走り、自己ループ（差戻し）は箱と何の
関係も無いところに浮いた 1 本の斜線で、どの箱とどの箱を結んでいるのか目では
分からない。

これも**パースは正しく通り、テストも全部通る**。接続は座標ではなく id
（`a:stCxn` / `a:endCxn`）に書いてあるからで、`図形 4 個・接続子 5 本` という
申告も、`承認待ち → 承認待ち` という自己ループも合っている ―― **実物で開いた
人にだけ壊れて見える**。検体は「この資料は何を写したものか」を人が目で確かめる
ためにあるので、申告が正しいことを確かめようとした人が最初に見るのがこの絵である。

原因は**端をセルの格子にしか置けなかった**ことである。`xdr:from` / `xdr:to` の
`colOff` / `rowOff` を 0 に固定していたので、線の端は必ずセルの境目に来る
―― 図形の接続点は**辺の真ん中**にあるので、番地では届かない。

直したのは検体の書き方のほうである。**繋がっている線の位置は資料の情報ではない**
―― 端は接続点にあり、箱を動かせば Excel が引き直す。だから YAML から線の `位置`
を落とし、通り道は `tests/dataset.py` が決める。

```yaml
- 線: {元: 3, 先: 4, 矢: 両方}     # 番地は書かない（端は箱が決める）
  id: 21
- 線: {矢: 終点}                   # 目分量で置いた線だけが番地を持つ
  id: 24
  位置: N4:P7
```

番地を持つのが目分量の線だけ、というのは**偶然ではない。** 位置にしか情報の無い
線がまさに arp4 が「どこからどこへか決められない」と申告する線であり（→
`接続子 2 本は両端が図形に結びついておらず`）、**書けることと読めることが同じ
ところで切れている。**

通り道を機械が決めるようにして、実物の Excel でしか出ない間違いが 2 つ出た。

| 間違い | どう見えたか |
| --- | --- |
| どちらの辺から出るかを**中心の差**で決めた | 真下にある**横長のゾーン枠**は中心が左寄りにあるので「左へ流れる」と判定され、線が箱を突っ切って斜めに走った ―― 辺と辺の**隙間**で決めれば向きは一意に決まる |
| `flipH` / `flipV` を書かなかった | 矩形は左上から右下へしか書けないので、右から左へ引いた線は反転で表す。落とすと**矢羽根が反対の端に付く**（資料と逆を向いた矢印が出て、しかも図としては自然に見える） |

自己ループだけは端が同じ箱の 2 辺なので、まっすぐ引くと箱の角を横切る。
`bentConnector3` の曲がり位置（`adj1`）を**負にする**と縦の一節が枠の外を通り、
箱を跨がずに右から出て天へ返る ―― Excel が自分で描くのと同じ形である。

#### 箱は 1 辺に 1 本しか受けられない ―― 崩れは線ではなく置き方から出る

線を辺に付けてもまだ図は崩れて見えた。**3 つの箱を横一列に並べていた**ので、
承認待ちの右辺から次工程への線と自己ループの両方が出ており、2 本が同じ点から
同じ向きへ**重なって走った** ―― 目には「出荷指示から出た線」に見え、どの箱の
差戻しなのか読めない。横長のゾーン枠へ落ちる線も、中心がずれているぶん斜めに
走っていた（辺の真ん中どうしを結ぶので、中心を揃えなければ必ず斜めになる）。

どちらも線の引き方ではなく**箱の置き方**の問題である。実物の業務フローが折れ
曲がって描いてあるのは体裁の趣味ではなく、**1 つの箱の 1 辺に 2 本を付けない**
ためだった ―― 検体も折り、ゾーン枠の中心を上の箱と揃えた。

| 直す前 | 直した後 |
| --- | --- |
| 受注登録 → 承認待ち → 出荷指示 を横一列 | 横へ 1 つ、あとは下へ（承認待ちの右辺と天が自己ループに空く） |
| ゾーン枠は `B11:L14`（中心が左寄り） | `D16:J19`（中心を上の箱と揃える） |

結果、繋がっている線は**全部が水平か垂直**になり、斜めに走るのは目分量で置いた
1 本だけになった ―― **図の上でも「読めない線」がひと目で分かる。**

確かめ方は `arp4 render`（絵を描くのは Excel 自身）で撮って目で見る。受注フロー
（箱 4・線 5）と画面遷移（箱 3・線 2）を撮り直し、7 本すべてが箱の辺に付き、
自己ループが箱を回り、目分量の 1 本だけが浮いていることを確認した。

#### 同じ 2 つが 30 冊の側にも残っていた（2026-08-12）

上の 2 つは `tests/dataset.py` だけを直していた。`examples/sales-corpus` の
生成器（`xlsxkit.py`）は別系統で、**どちらも入っていなかった。**

| | 実測（30 冊 / 図のある 15 シート / 接続子 160 本） |
| --- | --- |
| `flipH` / `flipV` 無し | **56 本**が矢羽根を反対の端に付けていた（右から左・下から上へ流れる線が全部） |
| 箱を突っ切る線 | **7 本**（5 シート） |

見つかったきっかけは、パース結果と絵の食い違いを人が見つけたことである
―― 要件定義書の業務フローで、資料は `銀行 → 入金消込 → 会計システム` なのに、
絵は `入金消込 → 会計システム → 銀行` に見えた。**2 つの間違いが重なると
「会計システムが銀行の手前にある」という、資料に無い流れが自然に読めてしまう。**

- 矢羽根が反転していないので `銀行 → 入金消込` の矢印が銀行を指す
- 銀行を入金消込の右に並べていたので、その線が**会計システムの箱を突っ切る**
- 短い `入金消込 → 会計システム` の矢印はその線の下に隠れる

パース結果は 1 字も変わらない（接続は `stCxn` / `endCxn` の id にあり、**配置は
そもそも取れていないと申告している**）。テストも 713 件すべて通る。つまり
**実物で開いた人にしか見えない**まま 30 冊に入っていた。

直したのは `flipH` / `flipV` と、銀行を入金消込の**真下**へ移したこと。残る 6 本は
箱の置き方の問題なので、`_crossings` が組み立てのたびに数えて警告に出す
―― 通り道は接続点どうしを結んだ矩形にしかなく、この道具は障害物を避けない。
**避けられないものは避けたふりをせず、数えて申告する**（読めなかったものの扱いと同じ）。

#### 「手で書けない」は思い込みだった（SmartArt）

SmartArt は箱の文字（`data`）だけでは描かれず、並べ方（`layout`）・体裁
（`quickStyle`）・配色（`colors`）の 3 パートを `dgm:relIds` で指していなければ
ならない。**一度は「並べ方は数百行の図表レイアウト定義なので手で書けない」と
判断して、この 1 冊だけ Excel に描かせないことにした。**

それは**Microsoft が配っている 130 種類のレイアウトの話**だった。あれは
どんな階層にも耐える汎用の定義なので大きいだけで、**縦に箱を並べるだけなら
20 行で足りる**（`dgm:forEach` が子の点を 1 つずつ箱にする）。体裁と配色も、
箱に掛かる 3 つのラベルを書けば残りは Excel が既定で埋める。

検体に要るのは「箱の文字が読めること」であって体裁の再現ではない ―― そこを
取り違えて、**確かめずに諦めていた**。いまは `tests/dataset.py` が 4 パートを
組み立て、YAML には箱の文字だけを書く。

```yaml
- 図表:
    種類: SmartArt
    箱:
      - [PM]
      - {文字: [品質保証], 種別: asst}
      - [[基盤チーム, （インフラ・共通）], 受注・請求]
```

データモデルも**箱だけでは成り立たない** ―― どの箱が親の何番目かは `dgm:cxn`
が持ち、箱の間には繋ぎの点（`parTrans` / `sibTrans`）が要り、Excel は見た目用の
複製（`pres`）も必ず書く。生成側がそれを揃えるので、**arp4 が「箱だけを数える」
規律は本物と同じ形で検査される**（以前の手書きの検体は繋ぎの点を飾りで置いて
いただけだった）。

実物の Excel で開くテストは置けない（CI に Office は無い）ので、
`test_検体がExcelで開ける形になっている` が**Excel が見に行く場所に書いてあるか**
だけを構造で押さえる。13 冊すべてを実物の Excel で開いて確かめた結果は
―― 業務フロー集（図形 6・5）、体制と役割（SmartArt 2）、実績グラフ（グラフ 1・1）、
画面仕様書（図形 4）、残りは図形の無いブックとして正常、壊れた 1 冊だけが開けない。

**検体の側が間違っていると、いちばん直す場所が決まらない。** YAML 1.1 は `No` を
偽と読むので、素直に書いた課題一覧の見出し `No` が `FALSE` になって Excel に入って
いた ―― パース結果は正しいのに検体が間違っている、という失敗である（`ON` / `OFF` の
区分値、`Y` / `N` のフラグでも同じことが起きる）。引用符で囲めば済むが**囲み忘れが
静かに通る**ので、真偽値として読むのを `true` / `false` だけに絞ってある。

### 14 冊目は現場の 1 冊を丸ごと写した（`tests/dataset/設計書.yml`）

13 冊はどれも**1 つの欠陥を 1 つのシートで突く**形にしてある ―― 落ちたテストから
直す場所が一意に決まるので、これは変えない。**ただしその形には隙間がある。**
1 つずつなら通る観点が、**1 冊に全部入ったときにどう見えるか**はどのテストも見て
いない。実案件の基本設計書は表紙・改訂履歴・目次・構成図・機能一覧・テーブル定義・
画面レイアウト・外部 IF・課題管理が 1 冊に綴じられた形でしか来ない。

14 冊目はその形にしてある（架空の企業・製品・担当者による受注管理システムの基本
設計書 1 冊 ＝ 9 シート ＋ 非表示 1 枚）。**主題は複雑な図形を組み合わせた構成図**で、
ゾーンの囲み枠・見出し帯・機器の箱・冗長構成の対・監視の線・凡例・注記が入れ子の群に
なっており、セルにあるのは表題と機器一覧だけである ―― 構成そのものは図にしか無い。

#### 「正解結果」は形式ごとに 1 冊ずつ置く

`tests/dataset/正解/` にパース結果をそのまま置いてあり、テストが 1 文字ずつ
突き合わせる。**観点テストでは見えないものがあるから**である ―― 申告の文が二重に
なっても、塊の並びが入れ替わっても、アンカーの採番が 1 つずれても、観点を 1 つずつ
見るテストはどれも落ちない。それに、**機械が何を出すのかを仕様の文章ではなく
出来上がりそのもので読める**ものが 1 つも無かった。

置いてあるのは 5 形式の 5 冊（`tests/test_parse_dataset.py` の `FROZEN`）である。

| 形式 | 1 冊 | 本数 |
| --- | --- | --- |
| `.xlsx` | 受注管理システム基本設計書（第3.2版） | 9 |
| `.docx` | 受注登録機能仕様書（第1.2版） | 5 |
| `.pptx` | 新販売管理システム方式提案（第2.1版） | 3 |
| `.pdf` | 受注管理システム検収仕様書（第1.0版） | 4 |
| `.csv` | 得意先マスタ移行 | 1 |

**Excel だけに掛けていたあいだ、この番人は Excel にしかいなかった。** 割り方
（シート／節／スライド／しおり）も申告の文も形式ごとに別の実装なので、**観点の
隙間も形式ごとに別の場所にある** ―― Word の写しが存在しない `s1-g1` を案内して
いた類の壊れ方は、Excel の正解を 1 文字ずつ突き合わせても 1 度も触れない。

代償は正直に言う ―― **申告の文言を 1 つ直すと期待値がまとめて書き換わる。** これは
`corpus.py` を移し替えない理由（中身は増えないのに期待値だけ書き換わる）とまったく
同じ性質の代償なので、**1 形式に 1 冊しか掛けない**。書き直すときは差分を読んでから
にする。

```bash
ARP4_GOLDEN=write .venv/Scripts/python -m pytest tests/test_parse_dataset.py -q
git diff tests/dataset/正解/         # ← **読んでから**コミットする
```

PDF の 1 冊も同じように掛かる（読み手の `pypdfium2` は本体依存なので、環境で
母集合が変わることは無い）。ただし PDF の本文は pypdfium2 が読んだ字なので、
**読み手を上げたときにここだけ差分が出ることがある**（arp4 が壊れたのではない）。

#### 出てきた欠陥は 4 つで、どれも図が複雑になるまで表に出てこない

| 出てきた欠陥 | 何が起きていたか |
| --- | --- |
| **図形と群の代替テキストを取っていない** | 画像からは取るのに図形からは取らない。構成図にゾーンごとに添えた 1 文（「現用／待機の 2 系統。DR は別紙 5」）は**箱の文字にも表にも無い** |
| **箱の中の字下げを潰す** | セルの値では残すと決めた規律（`受注ヘッダ` / `　　受注番号`）が図形の側に掛かっていない。機能構成図を 1 つのテキストボックスで書くと、**親子は段落頭の全角空白にしかない** |
| **取れない線 2 種類を同じ文句で申告する** | 「繋がっているが相手が無名」と「どこにも繋がっていない」を混ぜていた。前者は絵にすれば読めるので、**申告のほうが嘘**になっていた |
| **画像しか無いシートに「絵にして読め」と言う** | 表紙の会社ロゴ・スキャンした帳票見本がこの形。`arp4 render` で撮り直しても**絵が絵のまま出るだけ**で、案内どおりにやって届かない |

#### 綴じて配る文書にしたら、さらに 2 つ出た

構成図と画像を直したあとで、**この 1 冊を「印刷して綴じる文書」として書き足した**
―― フッタの文書番号・繰り返す見出し行・版を上げずに入れた改訂・客先に出さない
作業用列・ブックのプロパティである。実物の基本設計書はこの形でしか配られない。

| 出てきた欠陥 | 何が起きていたか |
| --- | --- |
| **高さ 0 の行を「見えている行」として出す** | `hidden` しか見ていない。Excel は高さ 0・幅 0 を普通に受け取り、そのときフラグは立たない ―― **非表示行と違って申告も出ない**ので、混ざっていることすら言えない |
| **紙にしか出ないものを丸ごと落とす** | 文書番号・版・機密区分はフッタにあり、**どのページにも刷られている**のにセルには 1 つも書かれていない。シート 1 枚がファイル 1 本になる以上、どのファイルにも版が要る |

どちらも**1 枚のシートでは出ない**種類ではない（単独で再現する）。出なかったのは、
**「綴じて配る」という形をそれまで検体が写していなかった**からである ―― ページ設定
も改訂の履歴もブックのプロパティも、1 つの欠陥を突く 1 枚のシートには出てこない。

ついでに、**1 冊の中の食い違い**もここで初めて写せた。機能一覧のフッタは第 3.1 版の
まま、改訂履歴と表紙は 3.2 版、そして高さ 0 で潰れた行だけが 3.3 版を知っている ――
プロパティの最終更新者（川瀬）は表紙の承認欄にも他の改訂行にも出てこない。
**どれが正しいかを機械は言わない**（言えるだけの材料が資料に無い）。並べるところ
までが機械の仕事で、突き合わせは整理層がやる。

前の 3 度と同じで、**どれも実装を読んでいて見つかったものは 1 つも無く、検体を
書いた日に出た。** 4 つ目に至っては、パース結果を読んでいるだけでは気付けない
（「絵にして読んでください」は正しい案内に見える）―― 書いてあるとおりにやろうと
したときにだけ、そこに絵にしても読めないものしか無いことが分かる。

**画像は「読めなかったもの」の中でもいちばん先が無い。** 数式の未計算は開いて保存し
直せば入り、エラー値は資料が壊れていると分かり、囲み枠へ落ちた線は絵にすれば読める。
画像だけは**撮り直しても読めるようにならない** ―― 図形と違って絵にする以前から絵
である。だから代替テキストの有無で分けて数える（あれば何の画像かは分かる、無ければ
元の画像ファイルか紙を当たるしかない）。

**ここに OCR を足したのは後の話で、この検体の主張は変わっていない**（下記
「貼り付け画像は中の文字も読む」）―― 網点・かすれ・斜行の乗った 4 枚は、Windows OCR
に掛けても `T 鋤 Lロら工 TEC` にしかならない。読めるようになったのは**平坦で字しか
無い画像**のほうで、そちらは検体が写していなかった側である。

#### 検体の側でも 2 つ出た ―― どちらも実物の Excel でしか出ない

| 検体の欠陥 | 中身 |
| --- | --- |
| **外部ブック参照でブックが丸ごと開けない** | `='[1]単価'!B2` の `[1]` は `<externalReferences>` の並び順である。関係（`.rels`）を張っただけでは Excel は参照先を数えず、**番号の指す先が無い数式**になる。`[Content_Types].xml` の申告も要る（3 つ揃って初めて開ける） |
| **列幅が無いと人が検体を確かめられない** | 既定幅のままだと承認欄の和暦が `########` になり、名称が隣の列で切れる ―― パース結果（値そのもの）は 1 文字も変わらないのに、**目で突き合わせる側だけが読めなくなる** |
| **openpyxl では高さ 0 が書けない** | 行の高さも列の幅も `if value:` で絞って書き出すので、0 は「指定なし」として落ちる。`行高: {8: 0}` と書いても**普通の行として出てくる** ―― 検体が突きたいのはまさにその 0 なので、ここだけシート XML に直に `ht="0"` を書く（`hidden` は立てない。立てたら別の検体になる） |

前者はいつもの形の失敗である ―― arp4 は zip の関係だけを辿るので**パースは通り、
テストも全部通る**。実物の Excel で開いたときにだけ壊れており、`arp4 render` を
掛けるまで誰も気付かない（`<drawing>` を書き忘れたときとまったく同じ）。

**列幅は図のあるシートには掛けない。** 図形は既定幅を前提に番地から座標を出して
いるので、列を広げると**図のほうが歪む** ―― 機器一覧が読みやすくなるより、構成図が
資料どおりに見えるほうを採る。

#### 灰色の矩形は「読めない画像」ではない（`tests/picture.py`）

検体に貼る画像は長いあいだ灰色の矩形 1 枚だった。理由は**実体が要るだけ**で、
`r:embed` の先が無い画像を Excel が壊れたファイルとして修復してしまうからである
―― 絵柄に意味は無かった。

**この 1 冊ではそれが足りない。** パースは「貼り付け画像の中身は取れていません。
`arp4 render` で撮り直しても読めるようにはなりません」と申告するが、**その申告が
正しいかを開いた人が判定できない** ―― 灰色の矩形は「読めない」のではなく「何も
描いていない」で、両者はまったく違う。実物に貼ってあるのは**人には何の資料か
分かり、機械には読めない**もの（網点に潰れた社章、サーバ室で撮った機器ラック、
コピー機を通した画面のハードコピー、斜行した帳票のスキャン）であって、そこを
写していない検体では「読めないこと」を確かめようがない。

いまは 4 通りを**手続きで描く**（`絵柄: ロゴ` など）。バイナリをリポジトリに
置かない約束は画像にも掛かるので、**中身がコードで読める形でしか置けない** ――
`tests/dataset.py` が YAML を Excel にするのとまったく同じ理屈である。外部の画像も
生成モデルも使わない（使うと、その絵が何を写したものか半年後に誰にも言えなくなる）。

| 絵柄 | なぜ機械に読めないか |
| --- | --- |
| `ロゴ` | **網点**（ハーフトーン）で文字の輪郭が点に割れる。人には `TOWA LOGITEC` と読める |
| `写真` | 陰影と粒。機器名はラベルにしか写らず、**結線はパッチケーブルの束に重なる** |
| `画面` | 印刷して取り込み直したので**網点とかすれ**が乗る |
| `帳票` | 斜行・かすれ・地紋。文字に見えるものが文字ではない |

##### 手書きを描き込む方向で 3 度直して、3 度とも間違えていた

絵柄を持たせた最初の版は、結線を手で書き込んだ写真と朱書きの入った画面だった。
そこから 3 度直している ―― **機器名が 1 つも写っていない**（何の写真か言えない）、
**手書きが心電図に見える**（基線も語の切れ目も無い）、**結線がどこにも引かれて
いない**（代替テキストは「結線は手書きで書き込んである」と言っているのに）。
どれも実際に絵が良くなった。

**それでも方向が間違っていた。** 手で結線を書き込んだ写真は、実案件の設計書に
**めったに無い**。そもそも写真で結線を持っているのは**パッチケーブルそのもの**で
あって、人の書き込みではない（写っているからこそ現場は写真を撮る）。検体が写すのは「実物によくある書かれ方」であって、珍しい書かれ方を
上手に写しても値打ちにはならない ―― そこを直しても、直った先が実物で起きない。
実物で圧倒的に多いのは**撮り方・通し方が読めなくしている**もの（網点・かすれ・斜行・
陰影）で、いまはそちらだけを描く。手書きのための道具（走り書き・手描きの線・丸）は
使わなくなったので消してある。

**手書きを外したときに、結線ごと絵から消えていた。** 実物のラック写真に結線が
写っていないことはないので、これはこれで実物から外れる ―― いまはパッチケーブルを
描く。**ケーブルは宙で終わらせない** ―― 必ずどこかの口に挿さっているか、画面の外
（床下・天井・隣の部屋）へ抜けている。途中で切れている線は写真に見えず、描き損ない
に見える（口は 2 本のラックの**向かい合う側**に置いてあるので、渡りがラックの面を
横切らない ―― 横切ると機器名をケーブルが覆う）。**写っていても読み取れない**（束になって重なり、色は 4 色しかなく、奥の 1 本は
前の 1 本に隠れる）というのが写真の性質で、図形で描かれた構成図が別に要るのは
そのためである。この 1 シートはその対比を持っている ―― **同じ結線が、図では
`s4-c1` に 10 本取れ、写真からは 1 本も取れない。**

**「絵が良くなったか」と「検体として正しいか」は別である。** 3 度の手直しは前者
だけを見ており、**そもそも何を写すべきか**を問い直していなかった。絵を見て直せる
ぶん、この取り違えは気付きにくい ―― パースのほうで何度も踏んだ「実物を数えたのでは
なく類推で決めていた」（面結合を「タイトル用途が大半」と書いていたのと同じ）と
同じ形の間違いである。

**砂嵐にはしない。** 画素ごとに乱数を振った最初の版は、絵が汚いうえに PNG が
圧縮できず、**検体 1 冊が 104KB から 195KB に膨らんだ**（粒だけで 88KB）。陰影は
行ごとに揺らし、粒は疎な点で作る ―― いまは 1 冊 116KB、描くのに 0.16 秒である。
**画像の中身はパース結果を 1 文字も変えない**ので、絵柄を変えても正解結果は
そのままである（変わったらそれはパースが画像を読んでいることになる）。

#### 直さないと決めたものが 2 つある

| 直さないもの | なぜ |
| --- | --- |
| **和暦の日付**（`[$-411]ggge"年"m"月"d"日"`） | 画面に `令和8年6月22日` と出ていても値は同じ日である ―― `￥1,200` を `1200` と出すのと同じ側（書式の再現）で、直し始めると罫線・塗りまで線が引けなくなる |
| **2 行ぶん結合した表題が 2 度出る** | 表紙の `B2:E3` は縦へ広がる結合なので下の行へ展開され、`B2` と `B3` に同じ表題が並ぶ。**幅では切らない**と決めてあるので（区分を 2 列ぶん括る面結合と形が同じ）、ここだけ表題として扱うと判断が入る |

後者は雑音だが、**捏造ではない** ―― 画面でもその表題は 2 行ぶんの高さを占めている。
ここで「1 行だけの結合は表題」と同じ理屈を 2 行へ広げると、区分の面結合と見分ける
基準が「中身が表題っぽいか」しか無くなる。

#### 実測

検体は **14 冊 38 シート**（YAML 1,220 行 ＋ 読み込み器 904 行）になった。組み立て
0.61 秒・パース 0.64 秒で、13 冊のとき（0.51 / 0.57 秒）から**1 冊ぶんしか増えて
いない**。パース結果は 33 本 26,817 字、うちこの 1 冊が 9 本 12,300 字である
（1 冊が全体の 46% を占めるのは、これだけが現場の分量を持っているからである）。

図は実物の Excel で開いて確かめた ―― 構成図（図形 18・接続子 12・画像 1）は
繋がっている 10 本すべてが箱の辺に付いて水平か垂直に走り、**斜めに走るのは目分量で
置いた 1 本だけ**である。機能構成図の字下げも画面に出ている（左寄せにしていない
テキストボックスでは字下げが画面のどこにも出ず、残す理由そのものが無くなる）。

### 15 冊目は下流の 1 冊にした ―― 横に長い表と時間の値（`tests/dataset/詳細設計書.yml`）

14 冊目（基本設計書）は**シートの種類が多くて 1 枚が浅い**。9 種類が 1 冊に綴じられ、
表紙も目次も課題管理も入っているぶん、**1 枚あたりの列は多くて 9 列**しか無かった。
実案件の設計書はもう 1 種類あり、そちらは逆の形をしている ―― **機能 1 本に 1 冊**
あって、シートは 5 枚しか無いのに 1 枚が 16 列に伸びる（項目 1 つにつき型・桁・
小数・必須・入力可否・初期値・編集規則・丸め・エラーコード・画面と帳票の出方が
1 行に並ぶ）。**縦に伸びる表と横に伸びる表は、機械から見て別の資料である。**

15 冊目はその形にしてある（同じ架空案件の受注登録 詳細設計書 1 冊 ＝ 5 シート）。
ここで 2 つが出た。どちらも**横に長い表と、時間の値**でしか表に出てこない。

#### 繰り返し印刷する見出し「列」を一度も見ていなかった

`_print` は `print_title_rows` と並べて `print_title_cols` も読んでいる。読んでいる
のに、**34 冊のどれも指定していなかったので申告に 1 度も出たことがなかった** ――
コードは通っているのに検体が無い、いちばん見つけにくい空白である（`parse.py` の
被覆は 93% あり、この行は「読まれてはいるが値が常に空」だった）。

横に長い表は紙にすると左右に割れるので、実物では左の 3 列を毎ページ刷る。取らないと、
**2 枚目以降が「項目 No も名前も物理名も無い、型と桁だけの紙」である**ことが読み手に
伝わらない。どこまでが見出しかを決めたのは人なので、機械はそれを取るだけでよい
（見出し行とまったく同じ理屈である）。

```
- `印刷タイトル行` $2:$3
- `印刷タイトル列` $A:$C      ← ここで初めて出た
```

**申告の文には見出し列を足していない。** `_print_note` が名前を挙げるのは見出し行
だけで、見出し列はアンカーの番地にしか出ない。番地が付いている以上どちらも読み直せる
ので、これは**忠実性の欠落ではなく提示の偏り**である ―― 読める場所に出ているものを
二重に言うかどうかは提示の決めごとなので、直さずに固定した
（`test_見出し列は申告の文には出ないが番地では読める`）。**気付かないまま片方だけ
出ている**のと、決めてそうしているのを分けておかないと、次に読んだ人が同じ調査を
やり直すことになる。

#### 時刻と経過時間は、YAML に素直に書くと数になる

YAML 1.1 は `02:00` を 120、`27:30` を 1650 と読む（60 進数）。`dataset.py` は明示形
（`時刻` / `経過` / `日時`）でそこを塞いであったが、**その明示形を使う検体が 1 つも
無かった**ので、塞げているかを誰も確かめていなかった ―― 検体のほうが壊れると、
パース結果は正しいのにテストが落ちる（直す場所がいちばん決まらない失敗である）。

詳細設計書のタイムアウト・リトライ間隔・測定日時はこの形でしか書かれない。しかも
**`27:30` は時刻としては存在しない** ―― 月次締めの累計処理時間は日を跨ぐので
`[h]:mm` でしか画面に出ず、時刻として読むと `03:30` になって**1 日ぶん短く見える**。
日付だけの欄・時刻だけの欄・経過時間の欄・日時の欄が 1 枚に並ぶのは詳細設計書だけで、
4 つは画面の見え方が似ているのに値の型が違う。

`Y` / `N` のフラグも同じ側にある。必須・入力可否は実物ではこの 1 文字で書かれるが、
YAML 1.1 はどちらも真偽値と読む ―― 14 冊目は見出しの `No` でそこを突いてあるが、
**値としての `Y` / `N` はどの検体にも無かった**。

#### この 1 冊を書いたのは Excel ではない

ブックのプロパティの作成アプリを `LibreOffice/7.6.4.1` にしてある。**そのぶん数式の
キャッシュが 1 つも入っていない** ―― 「計算結果が保存されていない」という申告
（`s5-f1`）に**資料の側の理由がある**ことが、`P005` と突き合わせて初めて読める。
受託先が Excel を持っていないのは実案件で普通に起きる形で、`_formula_note` の
docstring が挙げている 3 つの理由のうち 1 つが、これで検体になった。

#### 正解は置かない

丸ごと置いてあるのは 14 冊目だけである。**同じ役目の 2 冊目を置くと、同じ理由の
維持費が倍になる** ―― 正解を置くのは「出来上がりを人が読んで正しさを判定する」ため
であって、その役目は 1 冊が担げば足りる。15 冊目は 1 観点 1 本のテスト 9 件で押さえた。

#### 検体に入れられなかったものが 2 つある

どちらも**実物によくある書かれ方**なのに、`dataset.py` が組み立てると
**Excel がブックを開けなくなる**（実測 ―― `Workbooks.Open` が失敗する）。
パースは通るのでテストは緑のままで、**実物で開いた人にだけ壊れて見える**、
このリポジトリが何度も踏んでいるいつもの形である。

| 入れられなかったもの | 何が足りないか |
| --- | --- |
| `図表: {種類: 埋め込み}`（Word・PDF の貼り込み） | `graphicData` に中身が無く、埋め込み本体（`xl/embeddings/`）も種別の申告も無い。**現に `corpus.py` の OLE は手で書いた XML で、Excel で開いて確かめたことが一度も無い** ―― `parse.py` の見立て（描画パートの `graphicFrame` に ole の uri）が実物と合っているかも未確認である |
| `種別: グラフシート` | グラフを持たないグラフシートは Excel が受け付けない。`_fill` を通らないので中身を置く道も無い |

前者が入れられないせいで、`_drawing_note` の**埋め込みオブジェクトの一文が一度も
出たことがない** ―― `corpus.py` の OLE は「文字を持つ図形が 1 つも無いシート」に
載っているので、そちらの分岐へ先に落ちる。ここは検体を足せば済む話ではなく
`dataset.py` を直す話なので、**別の作業として切ってある**。

#### 実測

検体は **15 冊 43 シート**（YAML 1,693 行 ＋ 読み込み器 978 行）になった。組み立て
0.84 秒・パース 0.78 秒で、14 冊のとき（0.61 / 0.64 秒）から**1 冊ぶんしか増えて
いない**。パース結果は 38 本 37,442 字、うちこの 1 冊が 5 本 7,770 字（20%）で、
いちばん重いのが項目編集仕様の 2,417 字である ―― 16 列 × 17 行の表が 1 枚あっても、
現場の 1 冊（12,300 字）には届かない。

**実物の Excel で開いて確かめた**（Excel 16.0）。5 シートとも開き、項目編集仕様は
`PrintTitleColumns` が `$A:$C`・非表示列 D が隠れたまま・必須欄が `Y`（`TRUE` では
ない）で、エラー処理の `0:01` `0:03` `07:00` と性能の `27:30` も画面にそのまま出る。

### 16 冊目からは異常系 ―― 中身を読む前に壊れるもの（`tests/dataset/異常.yml`）

ここまでの検体はどれも**中身の書かれ方**を突いていた（結合・図形・コメント・書式）。
**その手前で壊れるもの**を 1 つも写していない ―― 開けない・大きすぎる・そもそも
資料ではない。実運用で 30 冊を通せば必ず 1 つは混ざるほうである。

観点を先に洗い出してから 6 つを検体にした。**うち 5 つは壊れており、1 つは
壊れていなかった**（後述）。

#### いちばん捨てる塊に、いちばん払っていた

工程表を年単位に伸ばすと、斜めに並んだ `■` は空白 1 マスずつで繋がって 1 つの塊に
なる ―― **枠は 5,000 行 × 5,000 列、中身は 5,000 セル**である。`_grid` がいきなり
2,500 万マスの格子を組み、そのあとで「すかすかだ」と捨てていた（`_sparse`）。
出来上がりは箇条書き 5,000 行なのに、**判定に届く前に 12.3 秒・211MB** を使う。
番地を作るところも枠を端から端まで舐めていたので、同じ面積ぶん掛かっていた。

| | 直す前 | いま |
| --- | --- | --- |
| 対角線 5,000 セル（枠 5,000×5,000） | 12.3 秒・211MB | **0.016 秒** |

いまは枠だけを先に決め（`Frame`）、**表として出すと決めたときにだけ格子を組む**。
出来上がりは 1 セルも変わらない ―― 枠が大きいほど中身が薄いのだから、すかすかの
判定に格子は要らなかった（面積と実セル数は枠から分かる）。

すかすか判定（`_SPARSE`）を入れた日に半分だけ直したことになる。**表の体裁をやめる
ところまでは直したが、やめると決める前に払う代償**は残っていた。

#### 大きい塊は大きいと言う

抽出ツールが吐いた一覧は 1 枚で数千行ある（設計書に添える「現行データの実績」が
この形）。**見出し行と最初の 20 行を見たかぎりでは、小さい表と見分けが付かない**
―― 読み手（整理層）は先頭だけ読んで「読んだ」と思う。

```
> アンカー `s1-t1`（A1:H1201）は 1201 行 × 8 列 ／ 9608 セルあります ――
  **先頭だけ読むと残りを見落とします**。落としている値はありません。
```

これは「読めなかったもの」の申告ではない（値は 1 つも落ちていない）。
`_sparse_note` と同じ**提示上の申告**である ―― 黙ると読み手が事実と違うものを
読む、というところが同じである。

**しきい値は 1,000 行／1,000 セル**にした。検体でいちばん大きい塊は工程表の
362 行なので、**現場の設計書では 1 度も出ない** ―― 何でも申告すると、本当に
読めていないもの（`f1` `e1` `g1`）が申告の山に埋もれて読み飛ばされる。
1 列に数千行という縦長の一覧はすかすかに当たらない（枠に隙間が無い）ので、
箇条書きの側にも同じ申告を掛ける。

**切り詰めない。** 大きいからといって行を落とすのは、資料の側から見れば
`_MAX_LIST` とは別の話である ―― あちらが truncate するのは申告文であって
中身ではない。

**追記 ―― 「現場の設計書では 1 度も出ない」は検体の側の事実でしかなかった。**
`限界.yml`（読み手に入らない量の検体）を足したところ、しきい値を超えたのは
**人が書いた設計書のまま大きい 2 枚**だった ―― 83 列 × 200 行の CRUD 図
（4,707 セル）と、紙に刷るために見出しを 6 回打ち直してある一覧（1,836 セル）
である。**しきい値は変えない**（下げれば申告の山に埋もれ、上げれば 6,000 行の
一覧が黙る）が、**申告文の「（抽出ツールが吐いた一覧はこの形になります）」は
出どころの決めつけ**である ―― 大きさは機械が数えた事実で、何の資料かは
そこから決まらない（`test_大きさの申告は数えるほどしか出ない`）。

実測（検体 29 冊 / 69 シート）―― しきい値を超えるのは 4 枚で、いちばん大きい
1 枚は 6,001 行 × 30 列（18 万セル）、パース結果は**1 本で 1,301,909 字**になる。
整理層が一度に読める量ではないので、**分けて読ませる前提**でしか使えない
―― 番地が付いているのはそのためでもある。組み立て 3.5 秒（`限界.yml` を足す前は
1.2 秒）、この 3 冊のパース 3.7 秒。**テスト全体は 30 秒から 55 秒になった** ――
18 万セルを 3 つの module fixture がそれぞれ組み直して読むためで、
重すぎるなら検体の `行数` を下げれば線形に減る（読み手に入らないことは
3,000 行でも変わらない）。

**1 セルの文字数は数えていない。** 3 万字（Excel の上限は 32,767 字）を 1 つの
欄に貼り込んだシートは、塊が 1 つ・セルが 3 つしか無いので**申告が 1 つも
出ない** ―― 出来上がりは 32,927 字で、6,000 行の一覧と同じく読み手に入らない
のに、大きいとは言われない（`限界.yml` の `注意事項`）。行とセルで数える
かぎり、**量の申告はこの形を素通りする**。

#### 「読めません」で終わる申告は、資料が 1 冊落ちたまま拾い直されない

開けなかった 1 冊に出ていたのは `読み込みに失敗しました: File is not a zip file`
だけだった。**事実ではあるが、その 1 冊を拾い直す手が 1 つも書いていない。**
しかも同じ文言が 4 通りの資料から出る ―― そして**次にやることは 4 つとも違う**。

| 先頭のバイト | 何であるか | 次にやること |
| --- | --- | --- |
| `d0 cf 11 e0 a1 b1 1a e1` | OLE 複合ドキュメント | 保護を外して `.xlsx` で保存し直す（旧 `.xls` も同じ） |
| `%PDF` | PDF に拡張子だけ付け替えた | **名前を `.pdf` に直して渡し直す** ―― そのまま読める。Excel で開き直しても直らない |
| `PK` ＋ `[Content_Types].xml` が無い | `.ods` / `.docx` | Excel で開いて `.xlsx` で保存し直す |
| `PK` だが zip が壊れている | 添付が途中で切れた | メールから取り出し直す |

読むのは先頭のバイト列そのものなので、**推測ではなく転記**である。取り違えないこと
のほうが大事で、PDF に「保護を外して」と言えば、`veryHidden` に「再表示して
ください」と言ったのと同じ ――**言われたとおりにやって届かないところで止まる**。

パスワード保護と旧 `.xls` は先頭 8 バイトが同じなので、**どちらかであるとしか
言わない**。中を割って区別することはできるが、そこから先は転記ではなくなる。

#### 客先からもらったフォルダには `.git` が付いてくる

既存資産の棚卸しでは資料とソースが同じ木に入って届く。そのまま `arp4 parse` に渡すと
`.git` だけで数万ファイルあり、**1 つずつ「読めない形式です」（`P001`）と言えば、
本当に読めなかった 1 冊がその山に埋もれる**。申告が読み飛ばされるのは、申告
しないのと同じである。

隠しフォルダ・`node_modules`・`__pycache__` は名前で切ってよい ―― 資料として
そこへ置く書き方が無いからで、`~$` を数えないのと同じ理屈である。**`.txt` は
切らない**（資料でないものだけを切るのであって、読めないものを黙るのではない）。

判定は**元の置き場からの相対**で行う。絶対パスで見ると、プロジェクトが `.cache`
の下にあるだけで資料が 1 冊も見えなくなる ―― 静かに 0 冊になる壊れ方である。

#### 既存資産の日本語は cp932 である

棚卸しの対象になるのは 10 年もののコードで、UTF-8 で書かれているほうが珍しい ――
そして `# -*- coding: -*-` は付いていないことが多い（当時の現場では既定がそれ
だった）。UTF-8 で決め打っていたぶん、**コメントに日本語が 1 文字あるだけで
そのファイルは骨格ごと落ちていた**（`P010`）。クラスもメソッドも取れない。
**シグネチャは ASCII なので、読めていれば出せたもの**である。

宣言があればそれに従い（PEP 263 / BOM ―― どちらもファイルに書いてある）、
無いときだけ cp932 で読み直す。日本語が両方で読める並びはまず無いので、
取り違えは起きない。

#### 読めた資料が書けずに消えるのは、読めなかったものが消えるのと同じ

`plan` は「1 冊が壊れていて 29 冊が落ちる」を避けるために例外を握っているのに、
**書き出しのほうは 1 本目で止まっていた**（`write`）。途中まで書いたパース結果
だけが残り、どこまで書けたのかは誰にも分からない。

いまは 1 本ずつ握って `P011` で申告する。実案件で効くのは Windows の 260 文字
（深いフォルダ ＋ 長いブック名 ＋ 長いシート名で普通に届く）で、そのとき出るのは
`FileNotFoundError`（「無い」）である ―― **資料の側は 1 つも間違っていない**のに
権限やディスクを疑って時間を溶かすので、パスの長さを添える。

#### 1 つは壊れていなかった ―― それでも検体を残す

HTML の画面仕様書には `#` も ` ``` ` も `|` も普通にセルに入っている。
`やっかいな値.xlsx` が突いた「セルの値はアンカーになれない」は `<!--` だけを
塞いだので、**残りの記法で同じことが起きないか**を書き出して読み戻すところまで
やって確かめた ―― 起きなかった。読み戻しはアンカー行だけを見ており（`mdio.read`）、
`|` と改行と `\` は表のセルに入れる時点で逃がしてある。

**直すところが無かったことも、検体にして固定する。** 次に読んだ人が同じ調査を
やり直さずに済む（`test_Markdownの記法はアンカーを増やさない`）。

#### 「1 冊が壊れて 29 冊が落ちる」は、ブックの中では守られていなかった

シート 1 枚の XML が壊れていると `load_workbook` は 1 冊まるごと投げる。
**3 枚のうち 2 枚は読めるのに、`P010` で 1 冊が誰の目にも触れない** ―― 資料の
側で守っている規律（1 冊が壊れても残りを読む）が、ブックの中には掛かっていなかった。
部分復旧したブック・帳票ツールが途中で書き出しをやめたブックがこの形になる。

いまは落ちたら `read_only` で読み直す（**救出モード**）。openpyxl はこの形だと
シートを 1 枚ずつ遅延で読むので、**壊れた 1 枚だけが落ちる**。

**代償は黙れない。** 救出モードの worksheet は結合・行列の寸法・コメント・
リンク・印刷設定を持たない ―― とくに**縦結合が広がらない**ので、区分の列は
2 行目以降が空欄になる（画面では全行に掛かって見えている）。黙れば整理層には
「区分の無い行」に見え、**「資料に無い」と「機械が読めていない」が混ざる**。

| どこで言うか | なぜ両方要るか |
| --- | --- |
| ブック単位（`P012`） | 壊れた枚数と**読めた枚数**を言う。「1 枚が壊れています」だけでは、残りが道連れになったのかが分からない |
| シートごと（`notes` の先頭） | findings はコンソールに 1 度出るだけで、**パース結果を読むときには手元に無い** ―― 空欄の隣に置く |

**「Excel で開いて保存し直してください」とは言わない。** 実物（Excel 16.0）で
確かめたところ、シートのパートが途中で切れたブックは**修復モードでも開けなかった**
―― `veryHidden` に「再表示してください」と言ったのと同じ失敗になる。確実なのは
元の資料をもらい直すことなので、そう書く。

**既定では使わない。** 救出モードを常用すると、取れているはずのものが静かに
取れなくなる ―― 落ちたときにだけ、落ちたと言ったうえで使う。

#### openpyxl が言ったことを、stderr へ流して消していた

いちばん効くのは**日付として範囲外のシリアル**である。納期の欄に年数や引き算の
結果が入っていると（実物では `#######` と表示される）、openpyxl はそのセルを
`#VALUE!` にして**警告する**。

その警告はどこにも残らないので、arp4 はそのセルを「エラー値（計算できていない）」
とだけ申告していた ―― **資料は壊れていないのに壊れていると言う**。読み落としより
悪い形である（申告のほうが嘘になる）。しかも `e1` の案内は「開き直しても直りません」
なので、**直しようのないものとして放置される**。

いまは読み込み中の警告を握って `P013` で出す。`e1` は残したまま**突き合わせられる
ようにする**のが狙いで、どちらかを消すのではない ―― 表の上では `#VALUE!` としか
見えないのだから、見分ける材料は申告にしか置けない。

検体（`納期管理表.xlsx`）でだけ出て、ほかの 21 冊では 1 件も出ない。

#### 検体にできなかったもの ―― Excel が受け付けない

**結合が重なっているブック**を検体にしようとした（大分類を掛け直したまま古い
結合が残っている形）。openpyxl は素直に両方を書くし、arp4 の縦結合の展開も
`setdefault` で先に置いたほうを残して通る ―― **パースは通り、テストも緑になる。**

実物の Excel で開いたら**通常では開けず、修復モードでのみ開いた**（そのとき
残るのは先に掛けたほう `A2:A3` だけである）。つまり**その状態のブックは資料として
存在しない** ―― 最後に Excel で保存された時点で直っている。

「帳票ツールの出力にもある」と書きかけたが、それは**実物を数えたのではなく類推**
だった（面結合を「タイトル用途が大半」と書いていたのと同じ形の間違いである）。
検体は落とし、ここに記録だけ残す。

#### 置き場そのものが壊れる ―― git の呼び方と、自分を指すリンク

どちらも**資料の中身とは関係が無い**ところで、資料が落ちる／同じ資料が何度も出る。

**git に 1 ファイルずつ聞いていた。** 上書き確認は「git 上で編集されているか」で
決めるが、`git status --porcelain -- <1 本>` を**書き出し先の数だけ起動**していた。
1 件 23ms はどうということのない数だが、**シート 1 枚がファイル 1 本**なので
30 冊 201 シートの再実行では 201 プロセスになる。

| | 直す前 | いま |
| --- | --- | --- |
| 201 シートの再実行で git に聞く時間 | 5.0 秒 | **0.02 秒**（2 回） |

パース本体が 1.3 秒なので、**確認のほうが本体の 4 倍**掛かっていた。ここは
「遅いから通さない」が始まる場所である ―― 使用範囲を端から端まで回して
1 シート 7.5 秒だったときと同じ形で、**性能の問題が網羅性の問題になる。**

まとめて聞くときの細かいところが 2 つある。`-z`（NUL 区切り）にするのは、既定の
形式が日本語のファイル名を引用・退避して返すからで、この置き場では自前で戻す羽目に
なる。`--untracked-files=all` にするのは、既定だと**書いたばかりのファイルが
フォルダにまとめられて 1 件も出てこない**からである。

**`None` と空集合を分ける。** git が使えないのは「分からない」であって
「1 件も編集されていない」ではない ―― 前者は全部を編集ありに倒す
（黙って上書きするより、確認が 1 回多いほうがましである）。

**自分の親を指すリンクで、同じ資料が 64 本になっていた。** `rglob` は接合点
（ジャンクション）を素直に辿るので、資料置き場の中に親を指すリンクが 1 つあると
同じ `a.txt` が何度も出てくる ―― 止まったのは Windows のパス長 260 文字で切れた
からで、**リンクを見分けたからではない**。同じ資料が何度もパースされ、書き出し先が
重なって `P002` の山になる。

いまは歩いた実体（`realpath`）を憶えて二度歩かない ―― 64 本が 1 本になる。
**リンクそのものは飛ばさない**。資料置き場を別のドライブへ逃がして接合点で繋ぐのは
実案件で普通にやることで、飛ばせばその先の資料が丸ごと消える ―― 落とすのは
「もう歩いた実体」だけなので、ここで消える資料は無い。

#### 確かめて、直さないと決めたもの

| 見たもの | なぜ直さないか |
| --- | --- |
| **zip の外を指す関係**（`.rels` の Target が `../../../../etc/passwd`） | arp4 は zip を**展開しない**。`_resolve` が返すのは `ZipFile.read` に渡すキーだけで、実体のパスにならない ―― 防御を足すと「zip の外を指す関係」をエラー扱いすることになり、**ブックを移動した跡で普通にそうなっている資料**が読めなくなる |
| **極端に圧縮されたパート**（zip bomb） | 読むのは自分たちが集めた社内の設計書で、送り手が敵ではない。**大きなシートと見分ける手が無い**（実物の 1 シートも数十 MB になる）ので、上限を置くと読めるはずの資料が落ちる |
| **極端な数**（`1e308` が 309 桁になる） | 15 桁超の会員番号を指数にしないと既に決めてあり、ここだけ指数にすると一貫しない。Excel の指数表示は**列幅で決まる**ので再現もできない（`￥1,200` を `1200` と出すのと同じ側） |
| **制御文字**（`\x0b` がセルに入っている） | Excel も openpyxl もセルに持てない（`IllegalCharacterError`）。**描けないものは検体ではない** |

#### 規模は書き写せない ―― 検体の書き方に足した宣言

`表` と `セル` は「B5 にこう書いてあった」という事実の列だが、**1,200 行の一覧を
1 行ずつ並べると、検体が読めなくなるだけで突くものは 1 つも増えない**（1,200 行が
同じ形をしていることこそが、その資料の性質である）。

| 足した宣言 | 何を書けるようにしたか |
| --- | --- |
| `生成`（`起点` / `行数` / `雛形` / `列送り`） | 繰り返しであることを宣言する。`列送り` で対角線（工程表）が引ける |
| `先頭16進` | **magic bytes だけを 16 進で**書く。全体を 16 進で並べると検体が読めなくなるので、続きは日本語のまま置く |
| `zip中身` | zip だが Excel ブックではない資料（`.ods` に拡張子を付け替えたもの） |
| `本文` ＋ `文字コード` | Excel ではない資料（cp932 のソース） |
| `そのまま` | **資料でないもの**（`.git` / `node_modules` / `~$`）を置き場に混ぜる |
| `壊す` | **シート 1 枚だけ**をパートごと途中で切る（ブックごと壊す `生バイト` とは別物） |

どれも `dataset.py` の側に資料の知識は 1 つも増えていない ―― 何行で、1 行が
どういう形かは YAML にある。

#### 実測

検体は **22 冊 50 シート**（うち 4 冊は開けない検体・1 冊は 1 枚だけ壊れている）
＋ ソース 1 本 ＋ 資料でない 1 式で、YAML 1,916 行 ＋ 読み込み器 1,028 行に
なった。組み立て 1.34 秒・パース 1.28 秒で、`異常.yml` を除くと 0.92 / 0.82 秒
―― **増えた 0.4 秒はほぼ全部が 1,200 行の生成**である。パース結果は 45 本
133,080 字（`異常.yml` の 4 本で 93,000 字 ―― 規模の検体なので当然この形になる）。

テストは 299 件。異常系で足したのは 21 件である。

**実物の Excel（16.0）で確かめた。** 受注明細抽出（2 枚・1,201 行）・画面項目
仕様書・納期管理表は開き、納期管理表の C3 は `#######` と表示される（申告の
「画面では `#####`」がそのとおりである）。移行データ仕様書は**通常でも修復でも
開けない** ―― これが `P012` の案内を「もらい直してください」にした根拠である。

### 続きの異常系 ―― 静かに 0 になるところと、案内が嘘になるところ

前の回は「中身を読む前に壊れるもの」を写した。**残っていたのはその裏側**である
―― 壊れていないのに落ちる、落ちたのに何も言わない、言ったことが当てにならない。
観点を先に洗い出し、**7 つを上から順に**潰した。

#### 「読めません」の続きを、形式に関わらず足していた

開けなかった 1 冊の理由（`_unopenable`）は先頭のバイトから決めているが、それを
**拡張子に関わらず**足していた。結果、`print "…"` の残った Python 2 のコードに
こう出ていた。

```
[error] P010 帳票出力.py: 読み込みに失敗しました: Missing parentheses in call to 'print'
（zip として開けません ―― 添付が途中で切れたか、別形式に拡張子だけを付け替えた資料です）
```

**メールの添付を探しに行かせて、そこに資料は無い。** `veryHidden` に「再表示して
ください」と言ったのと同じ形で、**案内どおりにやって届かない申告は、申告しないのと
同じ**である。しかも棚卸しの対象は 10 年ものの資産なので、これは珍しい資料ではない。

もう 1 つ間違っていた ―― **このファイルは壊れていない。** 原本はテキストなので
整理層が直接読める（意図の層はもともとそう読ませている）。取れていないのは骨格
（クラス・メソッドの一覧）だけなので、**資料を取り直す話にしてはいけない。**

いまは形式で分ける（`_why`）。Excel は先頭のバイト、ソースは例外の種類である ――
構文エラーなら上のように言い、cp932 でも UTF-8 でもないなら文字コードの話をする。

#### 申告の規律が掛かっていなかった唯一の入口 ―― マクロ

`.xlsm` を弾くのをやめたときに書いたのは「マクロが付いているだけで中身は同じ」
だった。**それは表の話でしかない。** 実案件のマクロは飾りではなく、採番規則・
入力チェック・帳票の組み立てが**そこにしか無い**ことがある ―― そのときシートに
書いてあるのは「ボタンを押す」だけである。

数式のキャッシュ無しも貼り付け画像も埋め込みオブジェクトも「読めていない」と
言っているのに、**マクロだけは、あることすら伝えていなかった** ―― 読み手には
マクロの無いブックと同じに見える（いちばん静かな消え方である）。

中身は取らない（`vbaProject.bin` は zip の中にある OLE 複合ドキュメントで、zip では
開けない）。**あることと、VBE で読めることだけ**を `P006` で言う。

**検体には置けなかった。** マクロは Excel が作るバイナリなので、写せば
「バイナリをリポジトリに置かない」に反し、でっち上げれば Excel が開かない
―― 制御文字・重なった結合と同じ側である（テストは zip を組み立てて押さえた）。

#### 読めた資料が 0 冊でも、parse は正常終了する

3 つとも**渡した人には「中身が空だった」ようにしか見えない**形だった。

| 何が起きるか | 直す前 | いま |
| --- | --- | --- |
| リンクの先が消えている・同期が実体を落としてきていない | `is_file()` も `is_dir()` も偽なので**黙って落ちる** | `P007`（同期を待つ／実体をもらい直す） |
| 打ったパスが無い | 同上。0 冊で正常終了 | `P007`（打ち間違い） |
| フォルダを一覧できない（権限・ロック） | `except OSError: continue`（コードに**「既知の穴」**と書いてあった） | `P007`（**その下の資料は 1 冊も読んでいない**と言う） |

3 つを同じ文句にまとめないのは、**次にやることが 3 つとも違う**からである
（開けない 4 冊を 1 つの文言で片付けていたのと同じ失敗になる）。

**ブック 1 冊から 1 本も出なかったときも言う**（`P009`）。値も図もコメントも無い
シートを出さない決まりは変えない ―― 変えると作業用の白紙がぜんぶパース結果に
なる。だが**それをブック 1 冊に掛けた結果**は黙れない。確かに渡した
1 冊が `parsed/` から丸ごと消えるのは、置かなかったのと区別が付かない。内訳
（シート何枚／うち非表示・読めなかった何枚）を添えるのは、それで次が決まるからで
ある。検体 23 冊では 1 度も出ない（＝ 白紙のブックが無い、ということが分かる）。

#### 読めなかった描画パートは「図形 0 個」と同じ顔をしていた

描画の XML が壊れていると `_shapes` は静かに空を返す ―― 例外を飲むのは正しい
（読めない 1 枚でパースを止めない）が、**飲んだことを言っていなかった。**
出来上がるのは「図の無いシート」で、`未読取` を宣言する先（`g1`）すら出ない。

**読めていないものほど静かに消える**という、いちばん避けたい形がここに残っていた。
いまは数えて（`Drawing.unreadable`）シートの申告に出し、`g1` も必ず出す
―― `arp4 render` で絵にすれば人には読めるので、**案内先がある**のがこの壊れ方の
救いである。ブックまるごと関係を辿れなかったときは `P008` で言う。

#### セルの書式は 1 つしか持てない ―― 一部だけの取り消し線

取り消し線を書式から取ると決めた理由は「**その書式だけが値を偽る**」ことだった。
ところが `cell.font.strike` は**セル 1 つに 1 つ**なので、`希望納期（廃止）` の
後半だけを消した欄は 1 件も引っ掛からない ―― **いちばん値を偽る書き方でだけ、
その規律が成り立っていなかった。**

読むのは共有文字列（`<si>` の中の `<r>`）とセルに直に書かれた文字列（`<is>`）の
両方である。openpyxl は前者を `rich_text=True` でしか返さず、既定では**繋げた
1 本の文字列**にしてしまう ―― そこで読み込み方を変えないのは、セルの値の型が
変わり（`CellRichText`）、書式を見ない 30 冊ぶんの読み込みまで道連れになるからで
ある。**シート XML はどのみち数式のキャッシュ無しで舐めている**ので、同じ 1 回の
走査に相乗りさせた（`sheet_facts`）。

**全部消してあるものと分けて数える。** 一部なら**残りは生きている**ので、値だけを
並べると「この行はまるごと廃止」に読める ―― `（廃止）` が消してあるだけの行を
`out_of_scope` に落とすと、**現行の項目が 1 つ消える。**

```
| B3 | 希望納期（廃止） ―― 消してあるのは「（廃止）」だけです |
```

#### 出せなかった文字と、資料に書いてある `?` を混ぜない

cp932 のコンソールで落ちない手当て（`_resilient_output`）は既に入っていたが、
置き換えが `?` だった。**出せなかった文字と、資料に元からある `?` が見分けられ
ない** ―― しかも `?` は Windows のファイル名に使えないので、`受?一覧.md` と
出たものを探しても**そんな名前のファイルは無い**。`backslashreplace` なら符号位置
が残る（`受\xa5一覧.md`）。パースの側でやっている「資料に無い」と「機械が読めて
いない」を混ぜない、と同じことである。

#### アンカーのずれは黙って壊れない ―― 言っていなかったのは理由のほう

アンカーの `s4` は**ブックの中でシートが何枚目か**なので、資料が改訂されてシートが
1 枚差し込まれると、それより後ろはまとめてずれる。ここは**黙って別の塊を指す**の
だと思っていたが、**確かめたら違った** ―― パース結果はシート 1 枚 1 ファイルで、
整理結果はそのファイルに対して書く。ずれた先は別のファイルにあるので、必ず
`G004`（アンカーがありません）になる。

困るのは**落ちる理由が「アンカーがありません」しか出ていない**ことである。200 件
まとめて落ちたとき、整理結果を書き直す話なのか資料が入れ替わった話なのかが決まら
ない。いまは**同じ塊が別のシート番号で出ていないか**を見て、出ていればそう言う
（`s1-t1` が無く `s2-t1` がある、は綴り違いでは起こらない形である）。

#### 確かめて、直さないと決めたもの

| 見たもの | なぜ直さないか |
| --- | --- |
| **`P008` を現実の壊し方で出す検体** | 関係が辿れないブックは **openpyxl も開けない**（`P010` が先に出る）。救出モードで開けたうえで深い関係だけが壊れている、という形でしか再現できなかった ―― 飲んだ例外を黙らないための**受け皿**として残し、テストはその形で押さえた |
| **CSV を読むこと** | 区切りと文字コードが資料ごとに違い、**当てにいけば値が変わる**（`,` 区切りだと思って読んだ住所は列がずれる）。Excel で開けば人がそこを決められるので、`P001` で通ってもらう |
| **zip の中を読むこと** | 同じ理屈で、展開は人の作業である。ただし**中の資料をまだ 1 冊も読んでいない**ことは言う（黙ると 30 冊が 1 行になる） |
| **`.txt` に次の一手を書くこと** | README かもしれない。**資料でないものだけを切る**のと同じで、当てずっぽうの案内はしない |

## 絵に紙の装飾を焼き込んでいた（`arp4 render`）

`render` はヘッダ・フッタを**空にしてから撮る**。紙の装飾は絵にとって雑音で、中身
（文書番号・版・機密区分）はパースが `s?-p1` で別に申告しているので、絵に要るものは
1 つも無い。

**その消去が 1 行も効いていなかった。** `PrintCommunication` を落としている間、Excel は
**ヘッダ・フッタへの代入だけを黙って捨てる** ―― まとめて書いている 9 種類のうち、
印刷範囲・見出し行・余白・ズーム・向きは全部通るので、1 種類だけ落ちていることに
気付けない。実測で切り分けた。

| 書き方 | `PrintArea` | `PrintTitleRows` | `LeftHeader` |
| --- | --- | --- | --- |
| まとめの**中**で消す（元のコード） | 通る | 通る | **元の文字列のまま** |
| まとめの**前**で消す（直した形） | 通る | 通る | 空になる |
| まとめを使わない | 通る | 通る | 空になる |

直しは消去をまとめの外へ出すだけである。まとめ自体（1 項目ごとにプリンタドライバへ
往復すると設定だけで数秒かかる）は geometry のために残す。

### 落ちていると、撮る対象そのものを潰す

雑音が乗るだけでは済まなかった。**余白を 0 にしてある**（余白は受け取り側で
トークンを食うだけで何も伝えない）ので、ヘッダは 1 行目と同じ高さに来る ――
表の見出しへ**重ね刷り**になり、`エラー処理` の 1 行目は
`SCB00口受注登錄区分…詳細設計書 第1.4版リトラ↑閒隔` と読めない字になっていた。

**フッタは絵を 4 倍に膨らませていた。** ページの下端に文字があるぶん、焼いたあとの
余白切り落とし（:func:`_rasterize`）が下まで詰められない ―― 中身が 8 行しか無い表が、
長辺 1400 px のうち 988 px を使っていた。

### なぜ今まで出なかったか

`ヘッダ左` と `ヘッダ中` は `dataset.py` の**死んだ書式**で、どの検体も使って
いなかった。基本設計書（`設計書.yml`）は `ヘッダ右` とフッタだけなので、**内容の
無い右上と下端に出るぶん、無害に見えていた** ―― 詳細設計書（`詳細設計書.yml`）で
左と中央を初めて使ったときに、1 行目を潰すことが分かった。

回帰は `_FakeSetup` に**実物の癖を写して**押さえてある（`PrintCommunication` を
落としている間の代入を捨てる）。写していないと、消去をまとめの中へ戻す変更が
テストを通ってしまう ―― 絵が壊れるのは**実物で撮った人にだけ見える**。

#### 実測

K（10 シート）＋ L（5 シート）を `--all` で撮った 15 枚。画素の総量は
**19.6M → 10.0M px（49% 減）**、撮影時間は 27 秒で変わらない。

| シート | 直す前 | 直した後 |
| --- | --- | --- |
| K / 課題管理 | 1400x988 | **1400x153**（85% 減） |
| K / 外部IF一覧 | 1400x989 | **1400x212**（79% 減） |
| L / エラー処理 | 1400x988 | **1400x189**（81% 減） |
| L / 性能と試験 | 1400x988 | **1400x232**（77% 減） |
| K / システム構成図 | 1400x904 | 1400x904（`印刷` を持たないシートは変わらない） |

減った 11 枚はすべてヘッダ・フッタを持つシートで、持たない 4 枚
（目次・システム構成図・画面レイアウト 2 枚）は 1 px も動いていない ――
**変わったものと変わらないものが、資料の側の違いで説明できる。**

## 切り口が貼り付け画像を貫いていた（`arp4 render`）

分割の境界は**結合セルを避ける**ように戻していた（見出しだけが前のタイルに残る）。
**図形は避けていなかった。** 撮る理由そのものが図形なので、こちらのほうが損が大きい。

出たのは `test_data` を丸ごと撮ったときで、`画面レイアウト` が横に 2 枚へ割れる。

| | 直す前 | 直した後 |
| --- | --- | --- |
| 切り口 | `A1:AH35` ｜ `AG1:AS35` | `A1:AE35` ｜ `AD1:AS35` |
| 注記の箱（AF3:AL7） | **貫かれる**（1 枚目に左側、2 枚目に右側） | 2 枚目に丸ごと |
| 貼り付け画像 2 枚（AF9:AN22 / AF24:AN34） | **貫かれる** | 2 枚目に丸ごと |

**セルの重なりでは繋がらない。** 重ね幅（`OVERLAP`）は 2 列で、方眼シートのここでは
**128 px しかない**（タイル 1 は 2176 px、タイル 2 は 832 px）。図形は AF〜AO の
**576 px** に載っているので、2 列重ねたところで左右に分かれたままである。

### なぜ気付きにくいか

**絵は 2 枚とも「写ってはいる」。** 撮影は成功し、白紙にもならず、`render` は
「12 枚を書きました」と言う ―― パースの申告（`未読取`）にも出ない。読む側も、
1 枚目の右端に図の左半分、2 枚目の左端に右半分が来るので、**縮尺が違うだけの
同じ絵に見える**（2 枚目は余白を落としたぶん 2.6 倍に拡大される）。
実際、この重なりは**人が絵を見比べて**「なぜ同じものが 2 枚にあるのか」と
聞くまで誰も数えていなかった。

### なぜ合成した検体では出なかったか

**セルより図形のほうが右まで届いていて、なおかつ横に割れるだけ広い 1 枚**が要る。
`画面レイアウト` はセルが AB 列まで・図形が AO 列までで、合計 2880 px が
`WIDE_PX`（2200）を超える。単体テスト用に組んだシートは図形もセルも同じ幅に
置いていたので、境界が図形の**外**に落ちていた。回帰は検体の 1 冊
（`設計書.yml`）で押さえてある ―― `plan_sheet` が返す区画のどれかに、
図形 3 個がそれぞれ**丸ごと**入ることを見る。

直しは `_merges`（割ってはいけない区間）に図形のアンカーを足すだけである。
図形 1 個が予算より大きいときに諦めて切るのは結合セルと同じ ――
**進まないより切れたほうがよい。**

### 同じ 1 冊で、計画側が壊れた資料に守られていなかった

同じ `test_data` を丸ごと渡したとき、**`render` が 1 冊目で落ちていた。**
`J/添付_破損.xlsx`（zip として壊れた検体）を `load_workbook` がそのまま投げ、
**残りの 13 冊が 1 枚も撮れない。** 撮影側（`render_all`）は「1 冊の失敗で全部を
落とさない」ように書いてあり、`parse` も `P010` にして続けるのに、**計画側にだけ
守りが無かった** ―― 撮影の前に全冊を開いて回る層なので、いちばん先に当たる。

開けなかった資料は**「撮らないシート」に混ぜない**。図形が無いから撮らないのと、
読めなかったから撮れないのとでは、次のラウンドですることが正反対である
（前者は放っておいてよく、後者は資料を取り直す）。名指しで理由まで出し、
終了コードは 1 にする。

```
  開けなかった資料 1 冊（ほかは撮ります）
    J/添付_破損.xlsx ―― BadZipFile: File is not a zip file
ラウンド r001 ― 15 冊 / 撮る 11 シート / 12 枚
```

`--pending` の側も同じ形にした。あちらは**前のラウンドの宣言から資料へ戻る**ので、
一巡目に読めた 1 冊がその間に差し替わって壊れていることがある。

## Markdown と素のテキストは原文のまま出す

**設計の正本が Markdown で置かれている現場はもう珍しくない** ―― このリポジトリ自身の
正本が `docs/` と `surface/` である。弾いていたあいだ、arp4 は**自分の仕様を読めなかった**
（`docs/decisions.md` に決定が 12 件書いてあるのに、課題管理表は空で出ていた）。

Excel は「セルの面」を紙の見た目へ寄せ直す必要があるが、**テキストの資料は原本が既に
読める形**なので寄せ直すところが 1 つも無い。表に組み直したり箇条書きへ畳んだりすると、
入れ子・コードブロック・引用が平らになって**資料に書いてあったことが減る**だけである。
`Chunk.text` はそのために足した（`rows` / `cells` と用途が違う）。

見出しごとに 1 塊、`at` は `docs/decisions.md#L30-L52`。実測は自分自身
（`docs/` + `src/arp4/` + `tests/`）で 55 本 / 319 塊 / 0.3 秒。

やめた案と、突いた欠陥：

| | 何で駄目だったか |
| --- | --- |
| 行頭の `#` を素直に見出しにする | **手順書はシェルの例を必ず載せる**。コードブロックの中の `# コメント` を見出しに取ると塊が本文の途中で切れ、`at` の行範囲も本文とずれる |
| 見出しをそのまま書き出す | **見出しがアンカーを偽造できた。** セルの `<!-- a:s9-t9 -->` は塞いであったが、Markdown は見出しの行がそのまま資料の文字である ―― 読み戻し側は先に出てくる偽アンカーを拾い、**本物の塊が丸ごと別の id の中へ消える**。`mdio.dump` は見出しと `at` も `_safe_comment` に通す |
| 見出しの前の本文を捨てる | 改訂日・適用範囲はそこに書かれる。捨てると**アンカーが 0 個の資料**ができ、`freeze` の未整理一覧に上がらないまま消える |

見出しの深さ（`##` か `###` か）は塊の見出しからは落ちる ―― 塊は並列に並ぶものなので
階層を持てない。**代わりに `at` が行範囲を持つ**ので、原本を開けば 1 手で読み直せる。

## DDL は書いてあるものをそのまま出す

`entity` / `data-item` / `index` という語彙も、テーブル定義書と CRUD図という様式も
揃っていて、**中身だけが空**だった。DDL は AST と同じで曖昧でないので、当てにいく
ところが 1 つも無い ―― 読んでいなかっただけである。

**型は寄せない。** `NUMBER(11, 2)` を「数値」にするのはメタモデルの enum に当てはめる
作業で、それは意味の判断である（方言ごとの型が同じものかは、資料と実装を見た人にしか
決められない）。桁と小数を分けるのも同じ理由で整理層に渡す。

**表に掛かる制約は列と別のアンカー**にする（`t1` と `k1`）。主キーと外部キーはテーブル間
の関係の根拠になるので、列 1 本の話と混ぜると「どの事実を出典にしたいか」が選べない。
**列の論理名は `COMMENT ON` にしか無いことがある** ―― Oracle/PG の現場では日本語の
項目名をコメントだけで持つ運用が普通で、そこを読まないと「論理名」列が丸ごと空になる。

読むのは `CREATE TABLE` / `CREATE INDEX` / `COMMENT ON` だけで、**残りは数えて名指しする**
（ビューとストアドの中に仕様が入っていることがある）。素朴に `;` で切ると、行コメント・
ブロックコメント・文字列リテラルの中の `;` で**1 つのテーブルが 2 つになって出る**。

## PowerPoint はスライド 1 枚 = ファイル 1 本

**書き足したのは入口だけである。** スライドの図形は `p:sp` / `p:cxnSp` で、Excel の
`xdr:sp` / `xdr:cxnSp` と**外側の名前空間しか違わない** ―― 箱の中の文字（`a:t`）も、
接続の端点（`a:stCxn`）も、矢羽根も、線の見た目も、まったく同じものである。だから
`_shapes` は 1 本のままで、入れ物（`Holder`）だけを差し替える。2 本書けば**同じ規律を
2 度書いて片方だけ直した状態**が必ず生まれる。

アンカーの語彙も増やしていない ―― `s<並び順>-t1` `-g1` `-c1` `-i1` `-o1` `-m1` `-a1`
`-k1` は Excel と同じ意味である。増やしたのは `n1`（発表者ノート）だけで、これは
PowerPoint にしか無い置き場であり、**そう決めた理由がそこにしか書かれていない**ことが
実際にある（スライドの箱は結論だけを載せる書き方をするので）。

表は `a:tbl` に入っている。埋め込みオブジェクトとして数えて中身を捨てると、**スライドの
表が 1 枚も仕様にならない** ―― PowerPoint の一覧はすべてこの形である。縦結合（`vMerge`）
は Excel の結合セルと同じく下へ広げる。

レイアウトとマスターの文字は取らない（全スライドに同じ文字が並ぶと資料が増えたように
見える）が、**取っていないことは申告する** ―― 文書番号・版・機密区分がそこにしか
書かれていないことがある。非表示のスライドは読まず、`P003` で数える（非表示シートと
同じ事情である）。

`arp4 render` は使えない ―― あれは Excel を起こして印刷する仕掛けなので、スライドは
撮れない。申告の「次にやること」は `PowerPoint で開いて` に差し替わる（`Holder` が持つ）。

## Word は見出し 1 の節 = ファイル 1 本

Excel はシート、PowerPoint はスライドという「資料の側が決めた 1 枚」を持っているが、
**Word は 1 冊が 1 本の流れ**である。そのまま出すと 200 ページの設計書が 1 本の md に
なり、出典として指せる先が「その 1 本」しか無くなる ―― 整理層はどの節の話かを言えず、
`未読取` を宣言する先も 1 つしか持てない。

割るのは**資料自身が持っている構造**（見出し 1）だけである。**見出しが 1 つも無ければ
1 本のまま出す** ―― 段落数や字数で割ると、資料に無い切れ目を機械が作ることになる。

やめた案と、突いた欠陥：

| | 何で駄目だったか |
| --- | --- |
| 見出しをスタイル id で判定する | **日本語版の Word は組み込みスタイルに `a3` のような id を自動生成する。** `w:name` のほうに英語の綴り（`heading 1`）が入っており、画面に出る「見出し 1」は表示名で XML には無い ―― id だけを見ると 1 つも当たらず、**1 冊が丸ごと 1 本のまま出る**（割れなかったことに気づけない） |
| `w:delText` を本文に残す | まだ確定していない改訂が「生きている仕様」として出る |
| `w:delText` を黙って落とす | 同じものが「もう消した」として出る。**どちらも資料はまだ決めていない** ―― 本文は反映後の姿にし、消された文字を `d1` に出して `P019` で言う |
| ヘッダ・フッタを節ごとに写す | Word のヘッダ・フッタは**文書全体**に掛かる（Excel の印刷設定がシートごとに掛かるのとは違う）。12 節ある資料で同じ 3 行が 12 回並ぶ ―― 別の 1 本（`00_ヘッダとフッタ.md`）に出す |

図形の取り出しだけは自前である ―― Word の図形は `wps:wsp`、画像は `pic:pic` で、
**接続子そのものが無い**（`a:stCxn` に当たるものを Word は持たない）。器（`Drawing`）と
申告（`_shape_note`）と画像・OCR の道は Excel と同じものを使う。旧 Word のテキスト枠は
VML（`v:shape`）で、中身は `w:txbxContent` に Word の段落として入っている。

## PDF はしおりの節 = ファイル 1 本

PDF は「もらったまま読むしかない資料」の代表である ―― 検収仕様書・議事録・他社製品の
仕様書・官公庁の様式は PDF でしか配られないことが普通で、原本の Excel や Word はこちらに
来ない。

読み手は `pypdfium2` である（`arp4 render` と同じもので、**本体依存なので常に入って
いる** ―― 「この環境では PDF が読めない」は無い）。しおり（アウトライン）の第 1
階層で節に割り、無ければ 1 冊 1 本にする。
アンカーは**ページ番号**で振る（`p12-x1`）―― PDF に番地は無く、そこにあるのはページ
番号だけである。

**表は組み直さない。** PDF の中に「表」という構造は無く、あるのは**位置を持った文字**
だけである。列の切れ目は文字の隙間から当てにいくしかなく、閾値を外すと**列がずれた表が
「読めた」顔で出る** ―― CSV の区切りを機械に当てさせないと決めたのと同じ理由である。

**テキスト層の無いページは、字が無いのではない。** 紙をスキャンしただけの PDF（押印付きの
検収書・FAX で回ってきた仕様変更）は機械にとって 1 枚の絵である ―― 黙って空のページを
出すと、整理層は「資料に何も書いていない」と読む。`P017` で数え、ページを焼いて `i1` へ、
中の字は Windows OCR が読んで `o1` へ出す（貼り付け画像とまったく同じ扱い）。**`--no-ocr`
でも絵は出す** ―― 落とすのは機械の読みだけで、実体を渡さないことではない。

## CSV は当てた区切りと文字コードを申告する

長らくここは「Excel で開いて `.xlsx` として保存し直してください」だけを返していた。理由は
正しい（区切りと文字コードは資料ごとに違い、当てにいけば値が変わる）が、**その助言に
従える現場ばかりではない** ―― 移行データの一覧・コード値の一覧は数百本の CSV で配られ、
1 本ずつ Excel で開き直す作業を誰も引き受けない。実際には、その数百本が 1 件も仕様に
ならないまま終わっていた。

**当てるのをやめたのではなく、当てた結果を黙らないことにした。** 決めた区切りと文字
コードと、行ごとの列数がどれだけ揃ったかをパース結果の頭に書く。

```
> 文字コードは cp932（Shift_JIS）、区切りは `,`（カンマ） として読みました
  （120 行のうち 100% が 7 列）。**どちらも機械が決めたものです** ―― …
```

決め方は 2 つだけである。

- **文字コード** ―― BOM があれば資料が名乗っているものを使う（疑う理由が無い）。
  無ければ UTF-8 を厳密に試し、駄目なら cp932。どれでも読めなければ `errors="replace"`
  まで落ちて、**その欄の値は資料の値ではない**と書く
- **区切り** ―― `,` `	` `;` `|` を 1 つずつ実際に割ってみて、**行ごとの列数が揃うか**で
  決める。出現数では決めない（コメント欄にカンマの多い CSV で `;` が正解になる）

**決められなければ表にしない**（`P018`）。1 列しかない CSV（手順を Excel の 1 列に書いて
書き出したもの）はどの区切りでも「揃って」見えるので、そこで先頭の候補を選ぶのは偶然に
賭けているだけである ―― 原文のまま出す。値は 1 つも落ちていない。

**例外の出ない失敗が 1 つある。** EUC-JP のかな（`う` = `0xA4 0xA6`）は**すべて cp932 の
半角カタカナの範囲**（`0xA1`〜`0xDF`）に収まるので、`UnicodeDecodeError` が出ない ――
「cp932 で読めました」と言いながら `うけつけ` が `､ｦ､ｱ､ﾄ､ｱ` として表に入り、整理層は
それを資料の字として読む。`�` すら出ないので、読めた中身のほうを見るしか気づく手が無い。
数えているのは**字種の割合だけ**（本文の 3 割以上が半角カタカナ）なので、「これは EUC-JP
だ」とは言わない ―― 言うのは数えた事実と、それが起きる典型的な理由だけである。

## 対応していないもの

**画像・PDF からの表の復元**（罫線と桁を読んで表に戻す）はやらない。上の PDF の節に
書いたとおり、当てにいけば**列がずれた表が「読めた」顔で出る**からである。

画像の中の**文字**は読む（上記「貼り付け画像は中の文字も読む」）。読めるのは行であって
表ではない ―― `o1` に並ぶのは engine の読んだ順の行で、どの列のどのセルだったかは
そこには無い。

旧形式（`.xls` / `.xlsb` / `.doc` / `.ppt`）は開けない。どれも zip ではないので、
`P001` で「Excel / Word / PowerPoint で開いて新しい形式として保存し直してください」まで
言う ―― 「読めません」で終わる報告は、その資料が誰にも拾い直されないまま終わる。

`.xlsm` / `.pptm` / `.docm` は読む（**中身は同じ**である ―― マクロそのものは取らず、
あることだけを `P006` で言う。上の「申告の規律が掛かっていなかった唯一の入口」）。
弾いていた間、**読めるものを「読めない」と言っていた**。
