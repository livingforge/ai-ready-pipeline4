# 意味抽出の出力を絞る方針

LLMが毎回記述する説明を減らし、引用・条件・数量の照合、未処理文字、独立レビュー、承認前の受入条件の検証は維持します。

## 分類理由・検証方法

`statement` は任意です。構造化した subject/property/condition/value の言い直しなら省略し、CLIが表示文を機械的に構築します。役割・例外など、構造化項目に含まれない意味がある場合は記載してください。既存の明示文は維持します。保存モデルでは引き続きstatementを保持します。

`evidence` は追加の根拠だけを記載します。CLIが数量の根拠、条件の根拠、原表の各区分のセル参照を解決・重複排除して合流するため、同じ引用の二重記述は不要です。他の欄に根拠がある場合は `evidence: []` にできますが、合流後の根拠が空なら拒否します。引用の完全一致・出典範囲・単位・条件・数量の検証は従来どおりです。

抽出返信の `classification.reason` と `verification` は任意です。明確な分類に定型的な理由を付けたり、参考情報のセル照合を繰り返す必要はありません。曖昧な分類・例外的な解釈には理由を添え、未解決の疑問は `open_issues` に残します。説明が必要な曖昧さは独立レビューでも確認します。

省略は「未記載」であり「検証済み」「該当なし」ではありません。保存モデル・台帳にも架空の説明を補完しません。記述する場合は非空文字列が必要です。推測条件・複合条件・除外・監査・承認・矛盾解決の理由は従来どおり必須です。要件・仕様の承認には引き続き受入条件が必要です。

## 抽出後の関連付け

初回抽出では `classification.requirements` と `related` を省略します。ワークフローは全文書・全区画がそろってから `link` タスクを作り、独立レビューの前に関係を補完します。

- 省略: 未処理。リンク補完対象。
- 明示的な `[]`: 検討したが原資料から支持される関係なし。独立レビューは引き続き必要。
- 値あり: 提出済みの関係。補完段階では削除せず、独立レビューで妥当性を確認。

返信は `packet`、`links`、`open_issues`。各 `links` 要素は `item`、`requirements`、`related` を持ち、IDはすべて `document/key` 形式です。全対象項目への明示的な回答を要求し、未知のID・自己参照・重複・不正な分類間の関係・古いパケットを拒否します。元の主張は変更できません。生成後も文書別・全体レビューが必要です。

従来の返信に両リストがあれば追加の補完タスクは作りません。修正・構造変更で省略された新規項目にも補完が走ります。`link` は `--extract-effort` / `--extract-max-tokens` を使用し、通常の呼び出し回数・費用・履歴の管理対象です。

個別の `semantic assemble` は省略リストを空のモデル配列へ展開するだけです。自動補完はワークフローの機能なので、個別操作では全項目がそろった後に関連を補い、独立した全体レビューで確認してください。

## 参考・実績・試算表の保持

抽出例（通常の返信のitemsに入れる項目）:

```json
{
  "key": "monthly-results", "name": "月別実績", "section": "other",
  "subject": "利用実績", "property": "原表",
  "condition": {"basis": "unspecified"},
  "value": {"kind": "table", "title": [], "description": [], "cells": ["s1", "s2", "s3", "s4"], "notes": []},
  "statement": "原資料の月別実績表",
  "evidence": [],
  "classification": {"category": "observation", "module": "usage"}
}
```

`reference` / `observation` / `estimate` に使用できます。見込みの原表は意味に従い `estimate` として保持します。抽出時に表題・説明・表本体・注記のセルを選び、CLIが各区分をセル全文の参照へ展開して根拠にも合流します。LLMがセル値を転記・正規化する必要はありません。表題と説明は表の前、注記は表の後に表示し、表本体だけを元の行列位置でMarkdown表にします。各区分内の本文表示は選択順です。列・行見出しと単位は表本体に残します。追加の `evidence` は表の表示セルへ自動転用しません。

例えば「2. 背景」、背景本文、課題一覧が同じシートにある場合、節見出し・独立した背景本文を別に扱い、課題一覧だけを表にします。その表専用の導入説明であることが原文から明確なら、表の説明として関連付けられます。`spec structure` の整理結果は判断材料であり、描画時の自動分離規則ではありません。分離は初回抽出時に判断し、抽出後の項目分割はレビューを経てrestructureで修正します。

全区分のセル全文・同一文書／シート・証拠との対応と、区分内・区分間の重複を検証します。値と数式、結合範囲、出典も保存します。部分引用や別シートを一つの表に混ぜることは拒否します。同じセルの中に本文と注記が混在する場合、セル全文を保持し、セル内の自動分割はしません。区画分割時は部分表として保持でき、未収録セルを推測で埋めません。旧形式からの自動移行はなく、新しい返信契約で再抽出します。

これは原データの保存であり、数値の意味解釈や計算結果の保証ではありません。原表内の要件・仕様・制約、表から導いた数量主張は別項目として抽出し、従来の数量照合を通します。要件・仕様に `table` は使えません。試算の原表を保持しても、数値の意味解釈を検証したことにはなりません。独立レビューは誤分類・隠された設計条件・抜けた注記や例外も確認します。

## 数量検査と評価

数量検査は `円`・`トークン`・`チャンク`・`倍`・`枚`・`問`・`次元`・`段階`・`か所/箇所` と、`KB/チャンク`・`件/回` 等の複合単位に対応します。千/万/億はamountへの換算と、対応する接頭辞付きunitの保持を区別し、二重換算を拒否します。`A100 x2` / `A100 × 2` は個数2を照合しますが、枚などの単位はunit_basisで原文から指定します。

`basis` は修飾語を含む数量句全体を選びます。`p95 で 800ms 以内` のbasisは `800ms 以内` とし、p95や周辺条件はproperty/condition/evidenceに保持します。引用範囲の不一致は `quantity_basis_mismatch`、複数数量は `ambiguous_quantity_basis` として候補を返し、field_repairへ進めます。候補は解釈の承認ではなく、数値から自動選択しません。固定語彙外の単位は `interpretation.kind=opaque_unit` と `unit_basis` で原文に結び付け、登録規則のない表現は `quantity_expression` と `quantity_interpretation_required` で保持します。実際の値・単位・比較・意味種別の不一致は `quantity_source_mismatch`、字句対応不足は `unsupported_quantity_expression` / `unsupported_quantity_unit` で区別します。範囲・符号・未知の複合単位を部分引用して検査を回避することはできません。

日付・年度・版数（例：`第 1.0 版`）のラベルをtextに残せますが、同じ文中の保持期間などの数量は引き続き検査します。`5年保持` や `12時間以内` はscalar、反復する周期はperiodです。数量チェックだけでは文章全体の意味は証明できず、独立レビューは必要です。

返信は現在のreply_schemaに従います。新しいCLI・プロンプトの検証は新規rootで行います。バイナリとpacketの一致検証は維持し、進行中の案件は書き換えません。

テストは構造・引用・リンク・描画・レビュー経路の回帰を検証します。実際のLLM料金削減率や意味品質は未測定です。同じ資料で欠落・誤分類・数値／条件の誤り・レビュー修正量・総費用を比較し、リンク補完の追加呼び出しを含めて評価します。
