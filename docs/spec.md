# 正本 ― `.arp/spec/`

**プロジェクトが決めたこと。** 整理結果（資料が言っていること）とは分けて持つ。
混ぜると、決定の責任者が誰なのかが永久に分からなくなる。

```
.arp/spec/
├── metamodel.yml     extends: jp-sier-std（追加と厳格化だけ）
├── concepts.yml      **同一性の台帳** ―― ラウンドをまたぐ
├── items/*.yml
└── relations/*.yml
```

## concept 辞書 ―― 凍結物を無傷に保つ間接層

```yaml
# .arp/spec/concepts.yml
- concept: c-受注番号
  type: データ項目
  label: 受注番号
  aliases: [受注No, 注文番号]        # 表記ゆれ。整理②が見つけたもの
  since: 2026-08-02                  # 初出ラウンド
  item: di-9a3c4f21b8e0              # 正本アイテムへの写像
```

`concept` を item の ID と**同一視しない**のが肝である。同一視すると、あとで
「この 1 アイテムは 2 つに分けるべきだった」となったときに、**凍結済みの整理結果が
指す先が壊れる**。写像を正本が持てば、item を分割・統合しても凍結物は無傷のまま
でいられる。

```yaml
# 分割したとき ―― 凍結物（concept 参照）は 1 文字も変わらない
- concept: c-受注番号
  item: di-9a3c4f21b8e0          # 受注ヘッダの受注番号
  split_note: 明細側は c-受注明細番号 として 2026-11-14 に分離
```

もう 1 つの効果として、**機械のマージ判断が「同じ concept なら同じアイテム」だけ**に
なる。類似度計算も裁定台帳も要らない（3 の `reconcile` / `ledger` が丸ごと消えた）。

## `arp4 build` がやること・やらないこと

**やること**（すべて意味の判断を含まない）

| | 中身 |
| --- | --- |
| マージ | 同じ `concept` のレコードを 1 アイテムに畳む。属性が食い違えば `B022`、本文が食い違えば `B023` |
| 関係のマージ | 同じ組み合わせを別々の資料が張ったら**属性を重ねる**。食い違いは `B024` |
| 採番 | 表示 ID（`FR-001` / `SCR-001` / `E-0001`）。**一度振ったら動かさない** |
| 向きの補正 | 抽出は「自分は誰に属するか」（メソッド → モジュール）で出がちだが、メタモデルは親 → 子で宣言している。逆向きで成立するならそちらを採る |
| 出典の引き継ぎ | ラウンド・ファイル・アンカーを `source` に載せる |
| `known_gaps` の引き継ぎ | 整理層が書いた宣言を同じ欄へ運ぶ。**正本側に既にある宣言は上書きしない**。同じ concept で理由が食い違えば `B027`（先に読んだほうを採る） |
| 矛盾の起票 | 整理②の `contradictions` を課題にし、争点へ `disputes` を張る |

関係の属性をマージするのは、**捨てると整理層から検知できない**ためである。
テーブル定義書の `has-column` は `pk: true` を持ち、データ項目一覧の `has-column` は
`pk` 列を持たない。2 本目以降を捨てる実装では、処理順によって PK が黙って消えていた。

**`multi: true` の属性（CRUD・権限）は和集合にする。** ここが先勝ちだった頃は、
モジュール一覧の `crud: [C]` が処理仕様書の `crud: [C, R]` を押しのけ、
**CRUD 図から `R` が消えていた**。値集合の違いは矛盾ではなく詳しさの違いなので、
和集合にすれば落ちるものが無く、`B024` を出す必要も無い。

本文（`statement`）は**完全なレコードのうちいちばん長いもの**を採る（要約は作らない）
が、文字数は情報量の代理指標として弱い。だから**採らなかった本文まで `B023` で
見せる** ―― 機能一覧の長い文が画面一覧の適切な説明を押しのけたとき、黙っていると
原因に辿り着けない。参照だけのレコードは本文を持たないので、`B023` は「**本当に
食い違っている 2 つの完全なレコード**」だけに絞られる → [organized.md](organized.md)

**向きを補正できるのは、from と to の種別が非対称な関係だけ**である。`refines`
（`same_type_only`）や `calls`（`module → module`）は両向きとも宣言に合うので、
書いた向きがそのまま残る。黙って残すと「機械が直す」と読んで逆向きに書いた
トレースがそっくり落ちるので、決められなかった組み合わせを `B026` で 1 件に
まとめて出す ―― 実測では業務要件 31 件がトレース表から丸ごと消えた。

**やらないこと**

- **推測しない。** 関係は整理結果の `refs` からだけ張る
- **必須属性を埋めない。** `E010`（必須属性が無い）は「人が埋めよ」の正しい信号である。
  2 側は `physical_name = name` をコピーしていて、それが「人が直しても戻る」の元凶
  だった
- **承認しない。** すべて `status: review` で入る。`approved` に上げるのは人の操作

表示 ID を動かさないのは、**採番が動くと設計書・議事録・課題票の参照が一斉に壊れる**
からである。

## `overridden` ―― 出典と異なる値の記録

凍結後に分かったことは、整理結果ではなく正本で直す。

```yaml
- id: ent-9a3c4f21b8e0
  type: entity
  name: 受注
  physical_name: T_ORDERS
  status: review
  source: { round: 2026-08-02, file: 資料/A/…/受注テーブル.yml, anchor: s1-t1 }
  overridden:
    physical_name:
      was: T_ORDER
      reason: 実装確認の結果、資料が旧名のままだった（PR #142）
      at: 2026-08-20
```

3 の `edited`（再変換で人の編集を潰さないための保護）とは意味が違う。**4 は再生成
しないので保護は要らない** ―― 必要なのは「なぜ出典と違うのか」の記録である。

**`reason` は必須**（無ければ `E017`、属性名の誤字は `E016`）**。** 空を許すと、単なる上書きと区別がつかなくなる。設計書の生成時に
「資料と異なる」を注記できるので、あとから来た人が「資料を読み違えたのか、資料が
間違っていたのか」を判断できる。

## `known_gaps` ―― 資料に定義が無いことの表明

`overridden` が**値**の記録なのに対し、`known_gaps` は**欠落**の記録である。

```yaml
- id: ent-5c54d300c228
  physical_name: M_PRICE
  known_gaps:
    has-column:
      reason: テーブル定義書に得意先別単価マスタの列定義シートが無い。先方へ依頼済み
      at: 2026-08-03
```

一覧には載っているのに定義シートが無いテーブル・帳票・画面は実案件で必ず出る。
`check` は `E027`（多重度違反）で正しく拾うが、**承知していることを書く場所が
無かった** ―― `out_of_scope` は整理層のアンカーに対するもので正本アイテムには
使えず、`overridden` は値の上書きである。結果、資料が揃うまで `publish --force` を
打ち続けることになり、**`--force` が常態化して本物の error を見落とす。**

載っている多重度違反は error から **warn（`W032`）へ落ちるだけで、消えはしない**。
理由つきで出続けるので「なぜ列が無いのか」を後から追える。埋まったら `W033`
（宣言が古い）が出る。`reason` は `overridden` と同じく必須（無ければ `E019`）で、
関係型の綴り違いは `E018` ―― **守っているつもりで守られていない状態を作らない。**

**`W031`（`warn_if_no_upstream` の関係が 0 本）にも同じ口が効く**（→ 決定 49）。
縛る先がラウンドの資料に入っていない制約・検証相手を張れないテストケースは
実在し、宣言の口が無いと**正しく処理した warn が毎回鳴り続けて**、警告一覧の中で
処理済みと未処理が区別できなくなる。

```yaml
- id: cst-19
  known_gaps:
    constrains:
      reason: 縛る先（build/build.py）がこのラウンドの資料に入っていない
      at: 2026-08-10
```

**書ける場所は正本だけではない。** 同じ形の宣言を整理結果のレコードにも書ける
（→ [organized.md](organized.md)）。ここが正本にしか無かったあいだ、**`build` を
打った人しか宣言できなかった** ―― 分担しているとき配る側は `build` を禁じるので、
整理層は `G020`（`W031` を凍結の手前へ前倒ししたもの）を warn のまま残すしか
手が無い。`build` は整理層の宣言を**正本にまだ無い名前だけ**足す。`known_gaps` は
そもそも上書き保護の対象なので、**凍結後に人が書いた理由は消えない** ―― 後から
来た機械が人の理由を書き換えると、なぜ理由が変わったのかがどこにも残らない。

## メタモデルの拡張

```yaml
# .arp/spec/metamodel.yml
extends: jp-sier-std
version: 3
item_types:
  帳票レイアウト:                # 整理②が提案し、人が承認したもの
    layer: 基本設計
    attributes:
      font: { kind: string }
```

**追加と厳格化だけが許される。** 既存種別の必須属性を外すような緩和は
`conform` が拒否する ―― 緩和を許すと、案件ごとに設計書の様式が崩れ、標準パックを
持つ意味が消える。

## 検証（`arp4 check`）

| 系 | 内容 |
| --- | --- |
| 構造 | メタモデルに無い属性・enum 外・必須欠落・一意違反 |
| 参照整合性 | 関係の相手が存在するか、`from` / `to` が宣言どおりの種別か |
| 多重度 | 列 0 本のテーブル、何も表示しない画面は `error` |
| カバレッジ | 実現されない要件、上流に繋がらない画面、参照されないメッセージ |
| **出典** | `source` のラウンド・ファイル・アンカーが実在するか。凍結ハッシュと一致するか |
| **`overridden`** | `reason` が空でないか |
| **`known_gaps`** | 関係型・属性名が実在するか、`reason` が空でないか、宣言が古くないか |

**`error` は「データの不備」であって、メタモデルを緩めて通すものではない。** `E010`
（必須属性が無い）と `E027`（多重度違反）は資料側の実際の欠落であることが多い。検証が
正しく指摘しているのであって、通すために正本を捏造しない。**資料が届くまで直しよう
がないものだけ**が `known_gaps` の対象で、それも黙って消すのではなく warn に落ちる。

## 生成（`arp4 publish`）

出力は `.arp/out/<番号>_<工程>/`（Markdown と HTML）。**直接編集しない** ―― 直しても
次の `publish` で消える。直すのは正本のほうである。

プロジェクト計画書 / 要件定義書 / 基本設計書 / 詳細設計書 / テーブル定義書 /
画面帳票項目定義書 / CRUD 図 / 権限マトリクス / トレーサビリティ・マトリクス /
テスト仕様書 / テスト結果報告書 / 課題管理表。様式は標準パックの `documents/*.yml`
が宣言し、表紙・改訂履歴は `.arp/publish.yml` に書く。

**工程ごとにフォルダを分ける。** 様式の `phase:` が工程を宣言し、番号はメタモデルの
`layers`（V 字の順）で付く。日本の受託開発ではレビューと承認の単位が工程なので、
12 種を 1 階層に並べるとその単位が読み手に見えなくなる → [decisions.md](decisions.md)

**マトリクスは関係が 0 本の行・列を畳む。** r001 の CRUD 図は 22 × 16 の升のうち
埋まったのが 7.2%、権限マトリクスは 30.3% だった。空欄の大半は資料に画面 × テーブル
のアクセス表が無いことの正しい反映なのだが、**升からは「資料に無い」と「関係を張り
忘れた」が見分けられない**ので、読み手には壊れて見える。

畳んだ行・列は表の下に**名前つきで全部並べる**（`関係の記載が無いため省略した行:
画面 20 件（受注一覧・受注入力・…）`）。畳むことが目的ではなく、名前を並べるのが
目的である ―― 黙って落とすくらいなら空欄のほうがまだ正直だった。全部の升が要るなら
`arp4 publish --full`。

畳むのは**関係が 0 本の行・列だけ**である。名前が似ているレコードは畳まない
（「営業」というロールと「営業部」という組織は資料上別物であって、名寄せは整理②の
仕事である）。

**1 行も出なかった設計書は理由を書く。** 空の表を置くだけだと「作ったが空」と
「作っていない」がレビューで区別できないので、本文の冒頭に不足している語彙の名前
（`test-case` / `verifies`）と想定される原因（その工程の資料が資料一式に無い）を書き、
目次には `（対象データなし）` を付ける。r001 ではテスト仕様書とテスト結果報告書が
これに当たった（sources 30 冊にテスト設計書が 0 冊だった）。

書くのは「アイテムがありません」ではなく「**データがありません**」である ―― CRUD 図は
エンティティが揃っていても `accesses` が 1 本も無ければ空になるので、足りないのは
種別とは限らない。

列見出しの日本語はメタモデルの `labels` に 1 箇所で持つ。様式ごとに書くと、様式を
足すたびに翻訳が漏れる。

**様式の ID 列に内部 ID を出さない。** アイテムの内部 ID（`rul-215d5bb15cf9`）は
concept の SHA-256 に由来するので読めない。`id` を列に出してよいのは、その種別に
`sequence`（表示 ID）が宣言されていないときだけ ―― ではなく、**そういう種別では
そもそも ID 列を出さない**か、種別に `sequence` を足す。実測では業務ルールと
制約・前提がこれに当たり、設計書 3 種に内部 ID が 421 行出ていた（いまは `RUL-001` /
`CST-001`）。その種別に表示 ID が振られるかは `arp4 model` が出す。

## 受け入れ条件

`jp-sier-std` は `test-case`（`precondition` / `expected`）と `verifies`（→ requirement）
を持つので、受け入れ条件はまずこれで表す。Given/When/Then を第一級の属性として
持たせるかは、実データを 1 案件通してから決める ―― 型を増やすのは後からでもできるが、
減らすのは難しい。
