# テスト資材 — 社内エンベディング基盤 Kotonoha（架空）

`arp4` の動作テスト用に、**社内で内製したプラットフォームの資産一式**を作る。
Python 110 本・DDL 7 本・設計メモ 22 本・OpenAPI 1 本・Excel 8 冊。
実在の企業・システムとは関係がない。

**`sales-corpus` の鏡像である。** あちらは「Excel の設計書 30 冊が先にあって
実装が後」の検体で、日本の SIer のウォーターフォール開発を写している。
こちらは軸を反転させた ——**実装が先にあって、文書が後追いで、しかも
散らばっている**という、内製のプラットフォームで実際に起きる形である。

| | sales-corpus | kotonoha（これ） |
| --- | --- | --- |
| 起点 | Excel 30 冊（文書が先） | **コード・DDL・Markdown**（実装が先） |
| 案件の形 | 受託 SI・ウォーターフォール | **社内内製**のプラットフォームを他部門へ提供 |
| `arp4 draft` | 使わない（Java を読ませていない） | **主役**。Python から 130 ファイルを機械生成 |
| `.sql` / `test_*.py` / `.md` | 無し | **有り** → テーブル定義書・テスト仕様書の語彙がここから立つ |
| 主なノイズ | 上流と下流の設計書が矛盾する | **文書が存在しない仕様**・決定記録とコードのズレ・**機械が読めない資料** |
| Excel | 30 冊（設計書） | 8 冊（**稟議・台帳・点検表**という別の層） |

README の「コードと DDL と設計メモも渡すこと。Excel の資料だけを渡すと、
テスト仕様書・テーブル定義書・課題管理表が空のまま出る」を示す例が無かった。
ここがそれである。

```bash
python examples/kotonoha/build.py --clean     # 資料/ に Excel 8 冊
python -m kotonoha.demo.main                  # 実装が動くことを確かめる（依存ゼロ）
python -m pytest examples/kotonoha/tests -q   # 406 件
```

## 生成物は Excel だけ

**`src/` `tests/` `ddl/` `docs/` `openapi.yaml` は git 管理のテキストで、
生成物ではない。** `build.py` が作るのは `資料/` の Excel 8 冊だけである。

sales-corpus は全文書を `spec.py` から生成している。文書間の辻褄を合わせる
ためで、あの資材では正しい。こちらで同じことをすると、**いちばん試したい
「コードにしか正本が無い」状態が資材の側で崩れる** ―― 生成器という上位の
正本ができてしまうためである。

`spec.py` は Excel が参照する設計データで、**実装とは食い違っている箇所が
ある**（下の B・C）。それは不具合ではなく検体である。

## 仮想システム

- **アダタム工業株式会社**（産業機械メーカー・従業員 12,000）の
  デジタル基盤本部 AI基盤グループが**内製**。SRE の一部を
  トレイリサーチ株式会社へ委託
- 2025 年度に PoC、**2026 年 4 月に社内サービス化**。いまは第 1 次リリース直後
- 提供するのは**検索まで**。回答生成は各部門が自分で行う ―― ただしこの
  線引きは合意できていない（下の D1）

社名は sales-corpus と同じく**例示用に用意された実在しない会社名**
（Adatum / Trey Research の日本語表記）。定義は
[sheetkit.py](sheetkit.py) の `COMPANY` / `VENDOR`。

一方、構成部品として挙げる製品名（PostgreSQL・pgvector・OpenSearch・
Redis・Kubernetes）と埋め込みモデル名（Voyage AI の `voyage-4` 系）は
**実在のものをそのまま書く**。現場の文書がそう書くためで、企業を騙る類の
記述ではない ―― sales-corpus が PostgreSQL・JP1/AJS3 を実名で書いているのと
同じ扱いである。

### 利用テナント 4 部門

**機密区分がこの資材の芯である。** 極秘は外部 API へ出せないので、
経路そのものが分かれる。

| テナント | 部門 | 用途 | 区分 | 埋め込み |
| --- | --- | --- | --- | --- |
| `cs-support` | カスタマーサポート部 | 保守問合せの回答支援 | 10 一般 | `voyage-4`（外部 API） |
| `qa-defect` | 品質保証部 | 不具合報告の類似検索 | 20 社外秘 | `voyage-4`（外部 API） |
| `legal-contract` | 法務部 | 契約書の条項検索 | **30 極秘** | **`voyage-4-nano` を社内 GPU で自前ホスト** |
| `sales-proposal` | 営業本部 | 提案書の再利用 | 20 社外秘 | `voyage-4`（外部 API） |

`voyage-4-nano` はオープンウェイト（Apache-2.0）なので社内に置ける。
**極秘を扱える唯一の選択肢**という設定になっている。精度は落ちる
（PoC の評価で 0.82 → 0.71）が、それを承知で合意した、という形にしてある。

## 依存ゼロで動く

FastAPI・Pydantic・psycopg・OpenSearch・voyageai の代わりに、
`framework/` と `demo/` の薄いスタブを置いてある。**呼び出しの形は本番と
同じ**なので、差し替えるのは `demo/wiring.py` の 1 か所で済む。

疑似の埋め込みは文字 3-gram のハッシュから**決定的に**作る。検索の順位が
意味を持つ程度には似ていて、外部依存はゼロ。

```
$ python -m kotonoha.demo.main
── 8. 検索する（ハイブリッド）
  0.80000 [B-4400 型 減速機 取扱説明 > 2. 異音がするとき] ## 2. 異音がするとき…
  候補=8 rerank=True 経路=['vector']

── 20. 仕込んだ食い違い（README の期待値と対）
  A1 チャンク分割 target=512 overlap=64 → 4 個（設計文書に記載なし）
  A2 RRF の定数 k=60（設計文書に記載なし）
  B1 量子化 quantized=True（ADR-003 は 1024 次元 float のまま）
  C1 法務部の上限 台帳=100,000 / 実装の既定=300,000
```

`store/` の SQL 実装は psycopg を import せず、`Connection` という約束越しに
SQL を投げる。**動かないが読める** ―― `ddl/` の表定義と対で見ると、どの列が
どう使われているかが分かる。

## 仕込んだノイズと期待値

sales-corpus は「上流の設計書と下流の設計書が矛盾する」を仕込んだ。
こちらは軸が違う。

### A. 正本がコードにしかない

**設計文書に存在しない仕様。** 整理層はコードから起こすしかない。

| # | 仕様 | どこにあるか |
| --- | --- | --- |
| A1 | チャンク分割（512 トークン・重なり 64・見出し優先） | `ingest/chunker.py` だけ |
| A2 | RRF の定数 `k=60` | `search/fusion.py` だけ |
| A3 | **レート制限が二重にあって値が違う** | `common/settings.py` は 100 rps・`docs/runbook/rate-limit.md` は 60 rps |
| A4 | キャッシュに当たった分を課金しない | `billing/meter.py` と ADR-008 の「書かれていないこと」 |
| A5 | 原文のバケットを機密区分ごとに分ける規則 | `store/object_store.py` の `BUCKETS` だけ |
| A6 | HNSW の `m` / `ef_construction` の根拠 | どこにも無い |

A3 は**コードだけを読んでも気づけない**形にしてある。Ingress 側の設定は
このリポジトリに入っていないので、runbook を読んで初めて食い違いが分かる。

### B. 決定記録（ADR）と実装がズレている

sales-corpus の C4・C5 に相当するが、対比する相手が Excel ではなく ADR。

| # | 論点 | ADR | 実装 |
| --- | --- | --- | --- |
| B1 | 埋め込みの持ち方 | ADR-003「1024 次元の float」 | `embed/quantize.py` で **int8 量子化**（2026/05 に運用の場で判断・ADR 未更新） |
| B2 | リランクの提供時期 | ADR-005「第2次リリース（2026年10月）」 | `search/rerank.py` で**既に有効**（2026/06 に前倒し・ADR 未更新） |

**どちらも ADR 本文の末尾に「★ 実装が先行している」と自己申告を書いてある。**
経緯は `docs/runbook/reindex.md` と `docs/runbook/search-tuning.md` の
覚え書きに数行あるだけで、**誰が決裁したのかは記録されていない。**

ADR-001（決めたことを記録に残す）自身が「決定が変わったら書き直す」と
定めており、**そのルールが守られていない**ことも書いてある。

### C. Excel と実装が食い違う

| # | 論点 | Excel | 実装 |
| --- | --- | --- | --- |
| C1 | 法務部の月間上限 | 利用申請台帳「100,000」 | `tenant/quota.py` の既定は **300,000**（2026/06 に口頭で増やして表だけ直した） |
| C2 | 監査ログの本文 | 情報セキュリティ点検表 指摘 2「本文を残さない・**対応済**」 | `common/audit.py` が **DEBUG でクエリ本文を出す**（2026/05 に足したまま） |

C2 は**点検表からは分からない**ようにしてある ―― 点検は 2026/03 で、
違反する変更は 2026/05 に入ったため。点検表の申し送りに
「ログの出力水準を変更したときに本文が出ないことを確認する手順を
運用に組み込むこと」とだけ書いてある。

`tests/test_audit.py` に**違反していることを固定する検証**を置いてある。
直したらそのテストが落ちるので、直したことに気づける。

### D. 決着していない争点（自動解決してはいけない）

| # | 論点 | 一方 | もう一方 |
| --- | --- | --- | --- |
| D1 | 回答生成は誰が持つか | 稟議書のスコープ欄「含まない: 回答文の生成」 | `docs/meeting/2026-05-20-cs-scope.md`「PoC の報告会では回答生成までデモしていた。基盤で持つべき」 |

**どちらかに寄せる判断は機械もエージェントもしない。** 両論を残して課題に
起票し、争点へ `disputes` を張るのが正しい振る舞いである。

議事メモには「その後」として**まだ宙に浮いている**ことまで書いてあり、
決着していないことは資料から読める ―― 決定日も承認者も無いので、
「新しい決定が古い記述を置き換えた」とは読めない。

### E. Excel の内部で閉じた食い違い

A〜D は**コード・ADR と Excel を突き合わせて**初めて見えるものだった。
ここは違う ―― **Excel 8 冊だけを渡したラウンドで、資料の中だけを読んで
摘出できるか**を試す仕掛けである。コードも ADR も要らない。同じ冊子の
別のシートどうし、2 冊の Excel どうし、あるいは同じシートの中の凡例と図が
食い違っている。

実務でよくある**曖昧さ**の形にしてある。どれも「片方が明確な誤り」とは
言い切れず、**書いた人が別々で、突き合わせていない**だけに見える。
**自動でどちらかへ寄せてはいけない。** 両方を残して課題に起票し、
確認先（部門・担当）を添えるのが正しい振る舞いである。

| # | 論点 | 一方 | もう一方 |
| --- | --- | --- | --- |
| E1 | 点検の指摘は何件で、全部片付いているか | 情報セキュリティ点検表 `1.点検概要`「条件付き適合（**指摘 5 件**・すべて回答済み）」 | 同じ冊子の `3.指摘と回答` は **6 件**あり指摘 6 が「★ 未対応」・`2.点検項目` No.10 の結果は **×（不適合）** |
| E2 | 障害の二次対応は夜間・休日もあるか | 運用引継ぎ資料 `1.委託範囲`「二次対応＝内製・**平日 8:00-20:00**」 | 同じ冊子の `2.連絡体制` は夜間（平日 20:00-8:00）・休日の**二次を AI基盤グループ（当番）が受ける** |
| E3 | 委託先の一次受けは夜間だけか | 運用引継ぎ資料 `1.委託範囲`「警報の一次受け＝委託・**夜間・休日を含む**」（平日日中も委託と読める） | 体制・要員計画 `要員計画` の委託先の役割は「監視・**夜間**一次受け」 |
| E4 | PoC を実施した部門はいくつか | 稟議書 `5.リスク`「PoC で先行している **2 部門**を初年度の利用者として確保済み」 | 同じ冊子の `4.効果`「部門個別の PoC 件数 **4 件** → 0 件」 |
| E5 | 予備費は初年度投資額の内数か別枠か | 稟議書 `1.趣旨`「初年度 **3,850 万円**」＝ `3.投資内訳` の金額欄の合計（1,850+420+680+540+360）とちょうど一致する | 同じ表の予備費は金額欄が「**—**」で、備考が「総額の 10% を上限に部長決裁で執行」 |
| E6 | 凡例は線の意味を網羅しているか | 体制・要員計画 `体制図` の凡例は「**実線=指揮命令 / 破線=委託**」の 2 分類 | 接続 7 本のうち `点検依頼`（本部長 → 情報セキュリティ部）・`提供`（基盤開発 → 利用部門）・`月次締め`（運用 → 経理部）の **3 本はどちらでもない** ―― 相手はいずれもデジタル基盤本部の**外**の部署で、指揮命令でも委託でもない |
| E7 | 外部 API 利用料は初年度いくらか | 稟議書 `3.投資内訳`「外部 API 利用料 **680 万円**（初年度見込み）」 | テナント別コスト実績 `3.端数` の外部 API 実額は **月 1.2〜2.3 万円**（12,600 / 17,120 / 23,364 円。年換算 21 万円ほど）。キャパシティ試算 `2.月次推移` の 2026/12 累計 4,310 千チャンクで初年度をフルに見積もっても外部 API 分は 10 万円台で、**2 桁合わない** |

E1 と E5 は**数字が読めば分かる**形、E2・E3 は**時間帯の言い回し**の形、
E4 は**同じ冊子の別の章が別の数を挙げている**形、E6 は**凡例が現実を
説明しきれていない**形、E7 は**見込みと実績の桁が違う**形にしてある。
整理層が「Excel を 1 冊ずつ読んで終わり」ではなく、**冊子をまたいで
突き合わせているか**がここに出る。

E6 の期待値は「凡例のとおりに線を分類すること」ではない ―― **凡例を
線種の一覧として鵜呑みにせず、凡例に収まらない線があることを摘出できるか**
である。凡例が 2 分類しか挙げていないからといって、7 本を無理に 2 つへ
割り振ってはいけない。「提供先・費用配賦先に見えるが凡例に無い」と
申告して課題に起票し、確認先（作成者）を添えるのが正しい。

**線種そのものは実装が転記する。** `arp4 parse` が接続の線種と
コネクタ名（`点検依頼` `提供` `月次締め`）をパース結果に出すので、
「どの線が実線でどの線が破線か」は機械から読める事実として届く。
**残るのは意味の判断のほうである** ―― その線が指揮命令なのか委託なのか、
凡例のどちらにも当てはまらないのか、を決めるのは整理層の仕事で、
機械はそこへ踏み込まない。凡例（セル由来・`sN-x*`）と線種（図形由来・
`sN-c*`）は**出典が別**なので、突き合わせたという判断も整理層に残る。

E7 の期待値は「稟議書を実績へ書き換えること」ではない。稟議は 2026/02 に
決裁された文書で、実績は 2026/04-06 のもの ―― **後から出た数字で決裁済みの
文書を直すのは、整合ではなく改竄である。** そして**見込みの前提（何チャンクを
どの単価で見て 680 万円としたのか）はどの資料にも書かれていない**ので、
「見込みが外れた」のか「見込みが別のものを含んでいる」のかも資料からは
決まらない。起案部門（AI基盤グループ 田村）へ確認を立てて課題に残すのが
正しい。**計算して閉じられる食い違いと、閉じられない食い違いを見分けられるか**
がここに出る ―― 同じコスト実績の中の按分・単価・占有秒はすべて計算で閉じる。

なお、**同じ資料の中で計算が合わないもの**（按分の端数・埋め込みの単価・
法務部の見込みチャンク数・GPU の月間処理能力・社内 GPU の占有秒・
課金チャンク数の累計と当月増分の混在）は仕込みではなく取りこぼしだったので、
生成器の側で閉じてある。**この表に数字で残してあるのは E1・E5・E7 の 3 つ
だけで、いずれも「計算が合わない」ではなく「別々に書かれた数が突き合って
いない」形**である ―― E1 は件数、E5 は合計と但し書き、E7 は見込みと実績。
どれも片方を計算し直せば閉じる類のものではない。

### F. 機械が読めないもの

**この資材でいちばん価値がある仕込み。** sales-corpus は「読めるが断片化する」
を試した。こちらは**そもそも読める形で届かない**を試す。

| # | もの | 実測の申告 |
| --- | --- | --- |
| F1 | `openapi.yaml`（**API 仕様の正本**） | `[warn] P001 読めない形式です: .yaml` |
| F2 | キャパシティ試算のグラフ | 題・系列・参照範囲は `sN-k1` に出るが「**グラフに描かれている数そのものはここにありません**」 |

F1 が要点である。**API の正本はこのファイルにしかない**のに、
`arp4 parse` の対応拡張子（`.xlsx` `.xlsm` `.py` `.md` `.txt` `.sql`
`.ddl` `.java`）に `.yaml` が無い。

正しい振る舞いは「資料に定義が無い」ではなく「**機械が読めていない**」と
申告することである ―― 前者は「探したが無かった」、後者は「まだ見ていない」で、
意味が違う。`0_この設計書の穴.md` の直接の検体になる。

実装側に `api/schemas.py` と `tests/test_api.py` があるので、機械が読める
形の仕様がまったく無いわけではない。**ただし `openapi.yaml` にしか無いもの**
（エラーコードの一覧・`explain` の説明・サーバの URL）がある。

### G. 既知の穴（コードが自分で申告しているもの）

不具合ではなく「まだやっていない」と分かっている箇所。設計文書と
コードの両方に書いてある。

| # | 穴 | 書いてある場所 |
| --- | --- | --- |
| G1 | 画像だけの PDF を取り込めない（OCR 未対応） | `ingest/extract/pdf.py`・`docs/runbook/ingest.md` |
| G2 | `readyz` が依存の疎通を見ていない | `api/app.py`・`docs/runbook/oncall.md`・`openapi.yaml` |
| G3 | 極秘の保持期間 3 年が自動で効かない | `docs/data-model.md`・点検表の指摘 6 |
| G4 | 検索精度を継続して測る仕組みが無い | `docs/slo.md`・PoC評価報告書 |

### H. 表記ゆれ（名寄せの対象）

正準名は `docs/glossary.md` にある。**用語集の側が「揃えきれていない」と
認めている**のがこの資材の性格である。

## 通し方

```bash
python examples/kotonoha/build.py --clean          # まず Excel を作る

R=/tmp/kotonoha && mkdir -p "$R"
arp4 init  --root "$R"
arp4 model --root "$R"                             # ★ 使ってよい語彙を先に読む
arp4 parse --root "$R" \
    <このリポジトリ>/examples/kotonoha/src \
    <このリポジトリ>/examples/kotonoha/tests \
    <このリポジトリ>/examples/kotonoha/ddl \
    <このリポジトリ>/examples/kotonoha/docs \
    <このリポジトリ>/examples/kotonoha/資料 \
    <このリポジトリ>/examples/kotonoha/openapi.yaml
arp4 draft --root "$R"                             # ★ コードから整理結果の骨格
```

**`openapi.yaml` も渡すこと。** 読めないので P001 が出るが、
**渡さないと「読めなかった」ことすら残らない。**

パースの実測:

| 出たもの | 数 |
| --- | --- |
| パース結果のファイル | **206**（src 100 / tests 30 / ddl 7 / docs 22 / 資料 47） |
| 表のアンカー `sN-tM` | 46 |
| テキストのアンカー `sN-xM` | 38 |
| 印刷設定 `sN-pM` | 47 |
| 図形 `sN-gM` / 接続 `sN-cM` | 3 / 1 |
| グラフ `sN-kM` | 2 |
| **読めない形式** | **1**（`openapi.yaml`） |

| 読み込みエラー | 0 |

`draft` の実測:

| 出たもの | 数 |
| --- | --- |
| 整理結果の骨格 | **130 ファイル** |
| 機械が下した判断 | 184 件（`decisions.yml`） |
| 文章化スロット | 1,587 件（**これが整理層の作業キュー**） |

続きは整理層の仕事である。

```bash
arp4 declare --root "$R" 表紙 改訂履歴 --reason "表紙・改訂履歴（仕様ではない）"
arp4 freeze --root "$R" --dry-run     # 残作業（文章化スロット）を数える
#   ★ draft が空けた <TODO 抽出元 …> を埋める（整理①）→ _concepts.yml（整理②）
arp4 freeze --root "$R"
arp4 build  --root "$R"               # D1 が課題として起票されるのが正しい
arp4 number --root "$R"
arp4 check  --root "$R" --strict
arp4 publish --root "$R"
```

**110 本を一度に整理しようとしない。** パッケージ（`tenant` → `embed` →
`ingest` → `search` → …）ごとに整理し、`arp4 freeze --dry-run` で残りを
数えながら進める。

### 見どころ

- **`draft` がどこまで機械で書けるか。** 1,587 件の文章化スロットが
  整理層の実作業量である。`decisions.yml` の 184 件は**機械が下した判断**
  なので、そこに意味の判断が混ざっていないかを見る
- **A（正本がコードにしかない）を拾えるか。** チャンク分割規則も RRF の
  定数も、設計文書には無い。**コードから起こす**しかない
- **B・C（ズレ）を矛盾として扱えるか。** ADR にも Excel にも
  「★ 実装が先行している」「対応済」と書いてあるので、**文書だけを読むと
  ズレに気づけない**。コードと突き合わせて初めて分かる
- **D1 を決着させないか。** 決定日も承認者も無い争点なので、両論を残して
  課題にするのが正しい
- **E を Excel だけのラウンドで摘出できるか。** `資料/` の 8 冊しか渡さずに
  通したとき、E1〜E7 が課題として立つのが正しい。**コードも ADR も要らない**
  ―― 同じ冊子の別のシート、あるいは 2 冊の Excel を突き合わせれば分かる。
  逆に、**計算すれば閉じる数字を課題に混ぜていないか**も見どころである
  （按分・単価・GPU の処理能力・占有秒・課金チャンク数はすべて資料の中で
  計算が合う。合わないと言うなら計算違いを疑う）
- **F1 が「穴」に出るか。** `0_この設計書の穴.md` に「機械が読めなかった
  もの」として `openapi.yaml` が出るのが正しい。「資料に定義が無い」に
  混ぜてはいけない
- **テスト仕様書・テーブル定義書が埋まるか。** `test_*.py` 29 本と
  `ddl/` 7 本がその語彙。sales-corpus では空のまま出る部分である
