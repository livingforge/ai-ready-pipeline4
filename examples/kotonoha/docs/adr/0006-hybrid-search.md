# ADR-006: ハイブリッド検索

- 状態: 採用
- 決定日: 2026-01-14
- 決めた人: 田村・小島（AI基盤グループ）、承認: 大城（部長）
- 関連: ADR-005（リランク）

## 背景

PoC でベクトル検索だけを試したところ、**型番と品番がまったく当たらない**。
「A-2210」のような文字列は意味を持たないベクトルになり、コサイン類似度で
上位に来ない。

カスタマーサポート部と品質保証部の検索は、実際には型番から入ることが多い。
これが当たらないと業務で使えない。

## 決めたこと

**ベクトル検索と全文検索（BM25）の両方を引き、順位を RRF で融合する。**

- ベクトル: PostgreSQL + pgvector（HNSW）
- 全文: OpenSearch（日本語は kuromoji で分かち書き）
- 融合: RRF（Reciprocal Rank Fusion）

RRF は**点数ではなく順位だけ**を使う。コサイン類似度（0〜1）と BM25 の
スコア（上限なし）はそのままでは足せないので、順位に落としてから足す。
正規化の仕方を決めずに済むのが利点。

引用符で囲んだ検索語（`"A-2210"`）は全文の完全一致で引く。

## 選ばなかったもの

**ベクトルだけ**
: 型番が当たらない。ハイブリッドにした理由の 8 割はこれ。

**全文だけ**
: 「異音がするときの対処」のような言い換えに弱い。

**点数を正規化して足す**
: 重みを決める根拠が無い。BM25 のスコアは文書集合に依存するので、
  取り込みが進むと重みが合わなくなる。

**同義語辞書を持つ**
: 「サーボモータ」「サーボモーター」「servo motor」を寄せたい。
  ただし辞書の維持を誰がやるかが決まらない。**見送り。**
  正規化（NFKC・末尾の長音落とし）でできる範囲までにする。

## 結果として

- 型番の検索が当たるようになった
- 融合の定数（RRF の `k`）は原論文の値をそのまま使う
- 候補は `top_k` より多めに取る（片方でしか上位に来ない結果を拾うため）

## ★ 書かれていないこと

**RRF の定数 `k=60` はコードにしかない**（`search/fusion.py`）。
原論文の値をそのまま使っており、**社内のデータで調整していない**。
調整したほうがよいかもしれないが、誰も試していない。

**BM25 の係数（k1=1.2 / b=0.75）も既定のまま**である。調整する根拠に
なる評価データが無い。

**融合へ渡す候補数（`top_k` の 5 倍・最低 50）**も根拠が記録されていない。
