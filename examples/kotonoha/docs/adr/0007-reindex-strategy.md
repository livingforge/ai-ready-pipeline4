# ADR-007: 再インデックスのやり方

- 状態: 採用
- 決定日: 2026-02-19
- 決めた人: 田村（AI基盤グループ）、承認: 大城（部長）
- 関連: ADR-003（ベクトルの持ち方）

## 背景

埋め込みモデルは更新される。`voyage-4` から `voyage-4-large` へ移る日は
必ず来るし、量子化の方式を変えることもある。そのたびに全チャンクの
ベクトルを計算し直す必要がある。

品質保証部のコレクションは 200 万チャンクあり、計算し直すのに 12 時間
掛かる見込み。**その間ずっと検索が止まるのは許されない。**

## 決めたこと

**旧を読ませたまま新を作り、別名（alias）の張り替えで切り替える。**

1. 新しい実インデックス名（`idx_xxxxxxxx_v002`）を作る
2. 全チャンクを新モデルで埋め直して新インデックスへ入れる
   （**この間、検索は旧インデックスを読み続ける**）
3. 新旧を突き合わせる（件数・上位の重なり）
4. 別名（`col_xxxxxxxx`）が指す先を新へ張り替える —— **一瞬で終わる**
5. 旧を一定期間残してから消す

**再インデックス中は取り込みを止める。** 新旧の両方へ入れる作りにすると
複雑になりすぎる。取り込みは 12 時間止められるが検索は止められない、
という優先順位で決めた。

**API では公開しない。** 運用が CLI から回す。利用部門が勝手に走らせると
社内 GPU が埋まる。

## 選ばなかったもの

**止めて作り直す**
: 単純だが 12 時間止まる。業務が回らない。

**新旧の両方へ書きながら移す**
: 取り込みを止めずに済むが、二重書きの整合性を取るのが難しい。
  失敗したときにどちらが正なのか分からなくなる。

**チャンクごとに少しずつ移す**
: 移行の途中で新旧のベクトルが混ざる。ベクトル空間が違うので
  検索結果が壊れる。**これは選べない。**

## 結果として

- 検索は止まらない
- 取り込みは止まる（利用部門へ事前に知らせる）
- 切り戻しができる（旧が残っているあいだ）
- 突合に通らなければ張り替えない。人が承認すれば飛ばせる

## ★ 書かれていないこと

**旧インデックスを残す日数**（7 日）は `docs/runbook/reindex.md` と
コード（`reindex/switch.py` の `RETENTION_DAYS`）にしかない。
この ADR には「一定期間」としか書いていない。

**突合の閾値**（上位 10 件の重なり 0.6）も同様。根拠は「経験的に
これ以下だと苦情が来る」という線で、測ったものではない。
