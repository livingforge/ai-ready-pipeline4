# 全体構成

社内 wiki の「AI基盤 / Kotonoha / 構成」から書き出したもの。
2026/04 の正式サービス化のときに書き、以後**部分的にしか直していない**。

## 何をするものか

社内の各部門（テナント）へ、次の 3 つを API で提供する。

1. **エンベディング生成** — テキストをベクトルにする
2. **取り込み** — 文書を分割し、埋め込んで格納する
3. **検索** — ベクトルと全文を融合し、リランクして返す

**回答生成（LLM の呼び出し）は含まない。** 各部門が自分で行う。

> ※ この線引きはカスタマーサポート部との間で合意が取れていない。
> `docs/meeting/2026-05-20-cs-scope.md` を参照。

## 構成

```
   各部門のアプリケーション
        │  HTTPS + APIキー
        ▼
   ┌────────────────────────────────┐
   │ API サーバ（FastAPI / 6 ポッド）  │
   │  認証 → レート制限 → 経路        │
   └───┬──────────┬─────────┬───────┘
       │          │         │
       ▼          ▼         ▼
   取り込み     検索      利用量計測
   （キュー）  （融合）    （日次）
       │          │
       ├──────────┼──────────────┐
       ▼          ▼              ▼
   PostgreSQL  OpenSearch    Redis
   + pgvector   （BM25）    （キャッシュ・
   （HNSW）                   キュー）
       │
       ▼
   S3 互換（原文・スナップショット）

   埋め込みの経路（機密区分で分かれる）
     10/20 ──▶ Voyage AI（外部 API）
     30    ──▶ 社内 GPU（A100 x2 / voyage-4-nano）
```

## 層の分け方

コードは業務の語彙で分けてある。

| パッケージ | 受け持ち |
| --- | --- |
| `api` | HTTP の受け口。認証・レート制限・入出力の型 |
| `tenant` | テナント・API キー・コレクション・機密区分・上限 |
| `embed` | エンベディング生成。**経路の振り分けがここにある** |
| `ingest` | 取り込み。抽出・正規化・分割・キュー・ワーカ |
| `search` | 検索。ベクトル・全文・融合・リランク |
| `reindex` | モデル更新時の作り直し |
| `billing` | 利用量の計測と部門への按分 |
| `store` | 保存先の実装。**SQL はここにしかない** |
| `common` | 設定・ログ・監査・採番・ハッシュ |

**業務層は SQL も HTTP も知らない。** 保存先は `*/repository.py` の約束
越しに触り、HTTP のステータスは `api/errors.py` が翻訳する。

## 機密区分の扱い

**この基盤でいちばん気を遣っているところ。**

- 機密区分はテナントに付き、コレクションが継承する。**下げられない**
- 区分 30（極秘）は外部 API へテキストを出してはならない
- 経路の判断は `embed/router.py` に集約してある。ここを通らずに
  提供元を呼ぶ道は無い
- 監査ログに経路（external / internal）を残す。極秘で external が
  記録されたら事故なので、監視が拾う

法務部の契約書がこれにあたる。社内 GPU にオープンウェイトのモデル
（`voyage-4-nano`、Apache-2.0）を載せて対応している。精度は外部 API の
モデルに劣るが、それを承知の上で合意した。
