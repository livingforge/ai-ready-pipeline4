## 当番

平日 8:00-20:00 は AI基盤グループ（田村・小島・持ち回り）。
夜間・休日はトレイリサーチ（委託）が一次受け。
**二次受けは AI基盤グループ。** 電話番号は社内ポータルの当番表。

SLO の可用性は **99.5%（平日 8:00-20:00）**。夜間は対象外なので、
夜間の障害は翌営業日に対応してよい —— **ただし極秘に関わるものは
時間に関わらず即座に上げる**（下の「即座に上げるもの」）。

## 即座に上げるもの

**時間帯に関わらず、次の 2 つは即座に部長へ連絡する。**

1. **極秘データが外部経路へ出た記録がある**

   ```sql
   SELECT * FROM v_audit_violation WHERE occurred_at >= now() - interval '1 day';
   ```

   **0 件であるべき。** 1 件でもあれば事故として扱う。
   アプリログにも `極秘データが外部経路へ出ました` が出る。

2. **API キーが漏れた疑い** —— 失効させてから連絡する。

   ```sh
   kotonoha key revoke --key-id <key_id>
   ```

## よくある警報

### 検索が遅い（p95 > 800ms）

1. `span.model_request` のメトリクスでどの段が遅いかを見る
2. リランクが効いていることが多い。切って比べる
3. `docs/runbook/search-tuning.md` の「遅いと言われたとき」へ

### 取り込みが滞留している

`docs/runbook/ingest.md` の「詰まったとき」へ。

### 社内 GPU が詰まっている

極秘テナントの取り込みが待たされる。A100 が 2 枚しかない。

```sh
kubectl -n kotonoha logs deploy/kotonoha-inference --tail=100 | grep queue_depth
```

待ち行列が 64 を超えると受け付けを断る（`ProviderError`）。
**待たせるより断ったほうがよい**という設計なので、断っていること自体は
異常ではない。続くようなら法務部へ連絡して取り込みの時間帯をずらす。

### 外部 API が 429 を返す

再試行が入っているので一時的なら自然に収まる。続くようなら
取り込みワーカを減らす（増やすのではない）。

### pgvector のディスクが逼迫

```sql
SELECT index_name, count(*) FROM t_embedding GROUP BY 1 ORDER BY 2 DESC;
```

**再インデックスの旧世代が残っていることが多い。** 7 日で消える
はずだが、バッチが止まっていると溜まる。

## ★ 既知の穴: readyz が依存を見ていない

`GET /readyz` は依存（pgvector・OpenSearch・Redis）の疎通を見ていない。
**プロセスが生きていれば ready を返す。**

つまり DB が落ちていても Kubernetes はトラフィックを流し続ける。
2026/05/22 の障害はこれで気づくのが遅れた。直す必要がある（未対応）。

いまは Grafana の DB 接続数パネルで見るしかない。
