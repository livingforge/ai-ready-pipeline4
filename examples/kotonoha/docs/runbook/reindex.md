# 再インデックスの手順

最終更新: 2026-05-18（小島）
関連: ADR-007（再インデックスのやり方）

## いつやるか

- 埋め込みモデルを変えるとき
- 量子化の方式を変えるとき
- 索引のパラメータ（HNSW の `m` / `ef_construction`）を変えるとき

**チャンクの分割規則を変えたいときは再インデックスでは足りない。**
本文は変えないので、取り込みからやり直す必要がある。

## 前もってやること

1. **見積りを取る**

   ```sh
   python -m kotonoha.demo.cli reindex --collection <名前> --to-model voyage-4-large
   ```

   所要が 12 時間（SLO）を超えるなら分割して実施する。

2. **利用部門へ知らせる。** 取り込みが止まる。検索は止まらない。
   品質保証部の毎晩 2 時の同期とぶつからない時間帯を選ぶ。

3. **社内 GPU を使う場合は、ほかの極秘テナントの取り込みを止める。**
   A100 が 2 枚しかないので、並行すると両方遅くなる。

## 手順

```sh
# 1. 始める（コレクションが再構築中になる＝取り込みを受けなくなる）
JOB=$(kotonoha reindex start --collection <id> --to-model voyage-4-large)

# 2. 進める（区切りごとに繰り返す。落ちたら続きから再開できる）
kotonoha reindex step --job "$JOB"

# 3. 突合して張り替える
kotonoha reindex finish --job "$JOB"
```

3 で突合に通らなければ張り替えない。**通らない理由を確かめてから**
判断すること。どうしても進めるなら承認者を付けて飛ばせる。

```sh
kotonoha reindex finish --job "$JOB" --force-by <承認者>
```

## 突合で見ていること

| 見るもの | 通す条件 |
| --- | --- |
| 件数 | 新 ≧ 旧 |
| 上位 10 件の重なり | 0.6 以上 |

**0.6 という数字に根拠は薄い。** モデルを変えれば結果は変わるのが
当然で、どこまでなら「変わりすぎ」でないのかを決める材料が無い。
経験的にこれ以下だと苦情が来る、という線で置いてある。

## 切り戻し

旧インデックスが残っているあいだは戻せる。

```sh
kotonoha reindex rollback --job "$JOB"
```

## 旧インデックスの削除

**張り替えから 7 日経ったら消す。** 日次のバッチが自動で消すので、
普段は何もしなくてよい。

7 日にした理由は「1 週間使ってみて苦情が出なければ大丈夫だろう」という
だけである。ディスクに余裕があるうちは延ばしてもよい。
