# テスト資材 — 新販売管理システム（架空）

`arp4` の動作テスト用に、**日本の SIer のウォーターフォール開発で実際に出てくる形の
設計書一式**を xlsx で生成する。要件定義から詳細設計までの 30 文書・201 シート。
あわせて、その設計書と対になる**実装コード**（Java 114 本）も生成する。実在の企業・
システムとは関係がない。

さらに、**2 度目の束**として `追加資料/`（8 文書・56 シート）を生成する。仕込んだ
食い違いの決着と、あとから足りた仕様が入っている ―― 2 ラウンド目の検体である
（[追加資料（第2次リリース）](#追加資料第2次リリース)）。

**これは合成物である。** 実物の Excel 設計書から作ったものではないので、
ここで取れた数字（とくに図形の接続が 160 本すべて `stCxn`/`endCxn` を持つこと）を
「実案件でもこうだ」と読んではいけない。現場の図には目分量で置いた線もスクリーン
ショットの貼り付けもある。実物が数冊でも手に入ったら数え直すこと。

実装コードは**外部ライブラリに依存しない**ので、JDK さえあれば
`javac` でビルドして `java` で動かせる（手順は `実装/README.md`）。
このリポジトリは JDK も Maven も同梱せず、ソースとビルド手順だけを配る。

```bash
python examples/sales-corpus/build.py --clean     # 資料/ に 30・追加資料/ に 8・実装/ に 116 ファイル
```

生成物（`資料/` `追加資料/` `実装/`）は追跡しない。内容を変えるときは `spec.py` /
`spec_change.py` と `docs_*.py` / `code_impl.py` を直し、build を回し直す。

## 資材の 2 つの決めごと

### 1. 設計項目に ID を振らない

要件・機能・画面・帳票・外部インターフェース・業務ルール・モジュール・
メッセージ・課題に、**採番した ID を一切書かない**。文書番号も付けない。
文書間の対応は「対応する要件」「関連する業務ルール」列に**名前**を書くだけで、
突き合わせるには名前で引くしかない。

現場の Excel 設計書はたいてい名前だけで書かれている。ID を最初から与えてしまうと、
パイプラインが本来やるべき名寄せと採番を資材の側で肩代わりしてしまい、
テストにならない。

例外は**業務データそのもの**である値で、これは書く:

| 書くもの | 例 | 理由 |
| --- | --- | --- |
| テーブル・列の物理名 | `T_ORDER` / `ORDER_NO` | DB オブジェクトの名前。設計項目の ID ではない |
| インデックス名 | `IX_T_ORDER_01` | 同上 |
| コード値 | 受注ステータス `10` / `20` / `40` | システムが扱うデータの値 |
| クラス名・メソッド名 | `OrderRegistService#registerOrder` | コード上の識別子 |
| 業務キーの書式 | `R + YYYYMMDD + 3 桁連番` | 実行時に採番される番号の仕様 |
| 表の行番号 | `No` 列の 1, 2, 3… | 順序を示すだけで識別子ではない |

### 2. セル結合と図表を厚く使う

現場の Excel 設計書は、**結合セルと罫線と図形**でできている。
テキストとして素直に読める表だけの資材では、抽出器の本当の相手にならない。

「表」の数は生成後の表の実数（同じ書き方をループで 16 画面ぶん出せば 16 表）。
全体で 148 表ある。

| 手法 | 使いどころ | 実測 |
| --- | --- | --- |
| 2 段見出し（横結合） | `項目 → 物理名 / 論理名`、`データ型 → 型 / 桁`、`制約 → キー / 必須` | 75 表 |
| 表題の帯（横結合） | 表の直上に表題を 1 行の結合セルで置く | 100 表 |
| 区分列の縦結合 | サブシステム・区分列の「同上」書き | 43 表 |
| 大分類の縦結合 | 縦持ちの定義表を大分類でくくる（3 列表） | 31 箇所 |
| 図形＋コネクタ | 構成図・フロー図・ER図・状態遷移図・遷移図 | **15 シート / 173 ノード / 160 接続** |
| 結合セルの作図 | 画面レイアウト・帳票様式・ガントチャート | 5 シート |
| **結合セル合計** | | **1,163** |

### 3. 1 シート = 1 章

**列幅はシート単位の資源**である。1 シートに列数・列幅の違う表を積むと、後に
書いた表が先に書いた表の列幅を上書きし、先の表が崩れる（Excel で開くまで
気づけない）。そこで章ごとにシートを分け、シート名を章の見出しに合わせてある。

同じ列幅を共有できる表だけは 1 シートに積む（議事録の開催情報＋議事内容、
画面仕様書の画面概要＋イベント一覧＋業務ルールなど）。表領域が縦に複数並ぶ
状態は抽出側の領域分割の検体として要るので、意図的に残している。

食い違いは `xlsxkit._set_width` が生成時に `LayoutError` で弾くので、
黙って崩れた資材が出ることはない。

## 構成

```
資料/
├── 00_全体/        17 文書（計画 2・要件 2・基本 9・詳細 4）
├── 10_受注管理/     4 文書（要件 1・基本 1・詳細 2）
├── 20_在庫管理/     3 文書（要件 1・基本 1・詳細 1）
├── 30_請求管理/     3 文書（要件 1・基本 1・詳細 1）
├── 90_議事録/       2 文書
└── 91_課題管理/     1 文書

追加資料/            2 度目の束（第2次リリース）
├── 00_全体/         5 文書（要件 1・基本 2・詳細 1・変更管理 1）
├── 10_受注管理/     2 文書（基本 1・詳細 1）
└── 90_議事録/       1 文書
```

サブシステム別バインダの下に工程フォルダを置く構成にしてある。arp4 は
**フォルダ構造をそのままパース結果へ写す**（`.arp/rounds/r001/parsed/資料/10_受注管理/…`）
ので、この 2 階層がそのまま出典のパスになる。サブシステム軸・工程軸を機械が
決めることはない ―― それは意味の判断なので整理層の仕事である。

各文書は「表紙 → 改訂履歴 → 本体シート」の 3 点セット（議事録と課題管理表を除く）。
表紙には版数・作成者・承認欄が入り、改訂履歴には版を重ねた形跡が残っている。

実装コードは Java のパッケージで分ける（設計書のバインダ名には合わせない）。

```
実装/
├── README.md      ビルドと実行の手順
├── sources.txt    javac へ渡すソース一覧（javac @sources.txt）
└── src/main/java/jp/co/contoso/sps/
    ├── framework/   3 本 Spring の代わりに自前で宣言した注釈（@Service など）
    ├── order/      29 本 受注管理（サービス 5・バッチ 1・DTO/エンティティ 20・リポジトリ 3）
    ├── inventory/  20 本 在庫管理（サービス 5・DTO/エンティティ 11・リポジトリ 4）
    ├── billing/    23 本 請求管理（サービス 3・バッチ 2・DTO/エンティティ 14・リポジトリ 4）
    ├── common/     30 本 共通基盤（認証・マスタ保守・採番・消費税・カレンダー・監査ログ）
    └── demo/        9 本 メモリ実装・配線・Main / WebMain と 16 画面
                          （動かすための足場。設計書には無い）
```

設計書の**モジュール一覧 18 本**と**メソッド一覧 24 件**、**画面一覧 16 画面**は
すべて実装がある。機能要件 21 件のうち 4 件（受注内容の変更・在庫照会・
売掛残高管理・マスタ保守）は詳細設計がモジュールを起こしていないため、
対応するサービスはコード側にしか存在しない（下の G7 を参照）。

`demo` と `framework` は**動かすための足場**で、設計書に対応する成果物ではない。
`framework` を置いてあるのは、Spring に依存させると Maven とネットワークが必要に
なり「配るだけで動かせる」が崩れるため。`@Service` などの書き方は本番と同じ形で
残るので、資材としての見た目は保たれる。

`資料/` と `実装/` を分けてあるのは、上の期待値（30 文書・201 シート・
サブシステム別の件数）を実装コードで崩さないため。

**arp4 は実装コードを読まない**（`parse` が読むのは `.xlsx` / `.xlsm` / `.py` で、
Java は入っていない）。`実装/` は、設計書とコードが食い違っている状態
（下の C4・C5・G6・G7）を**人が目で確かめるための対照**として残してある。
Java を骨格まで取り込めるようにするなら、まずここが検体になる。

## 仮想システム

- 発注者: コントソ食品株式会社（食品卸）／受託: ファブリカム株式会社
- 本稼働 2026 年 4 月。現行機の保守切れと流通BMS 対応が動機
- サブシステム: 受注管理 / 在庫管理 / 請求管理 / 共通基盤
- 規模: 機能要件 21・非機能要件 15・画面 16・帳票 6・外部IF 5・テーブル 16・
  業務ルール 15・モジュール 18・メソッド 24・メッセージ 13

社名は**例示用に用意された実在しない会社名**を使う（Contoso / Fabrikam /
Woodgrove Bank の日本語表記。Java パッケージも `jp.co.contoso.sps`）。
実在の企業名を架空の設計書に書かないための決めごとなので、名前を変えるときも
同じ性質のものを選ぶ。定義は [xlsxkit.py](xlsxkit.py) の `CLIENT` / `VENDOR` / `BANK`。

| 役 | 名前 | 定義 |
| --- | --- | --- |
| 発注者（食品卸） | コントソ食品株式会社 | `xlsxkit.CLIENT` |
| 受託（SI ベンダ） | ファブリカム株式会社 | `xlsxkit.VENDOR` |
| 振込先の銀行 | ウッドグローブ銀行 | `xlsxkit.BANK` |
| 発注者の既存会計パッケージ | ライトウェア会計 | `spec.ACCOUNTING_SYSTEM` |

会計パッケージも架空名にしてある。ほかの製品と違って**発注者の既存システム
そのもの**として書かれるので、実在の製品名を当てると「実在企業がこの案件に
関わっている」ように読めてしまう。

一方、本システムの構成部品として挙げる製品名（PostgreSQL・nginx・Spring Boot・
JP1/AJS3・SVF・Zabbix）と規格名（流通BMS・全銀フォーマット）は実在のものを
そのまま書く。現場の設計書がそう書くためで、企業を騙る類の記述ではない。

内容の正本は [spec.py](spec.py)。全 30 文書がここを参照して書かれているので、
文書間で辻褄が合う。**合わないところは意図的に合わせていない。**

## 仕込んだノイズと期待値

### 1. 矛盾（自動解決してはいけない）

上流と下流で**両立しない**記述。整理②（`_concepts.yml` の `contradictions`）に
両論を残し、`arp4 build` が課題として起票して争点へ `disputes` を張るのが正しい
振る舞い。**どちらかに寄せる判断は機械もエージェントもしない** ―― 人へ渡す。

| # | 論点 | 上流の記述 | 下流の記述 |
| --- | --- | --- | --- |
| C1 | 在庫引当のタイミング | 基本設計「引当は**受注確定時**に行う」（基本設計書 8.業務ルール一覧 / 要件定義「在庫引当」） | 詳細設計「引当は**出荷指示の実行時**」（処理仕様書_在庫引当 1.処理概要、処理仕様書_受注登録「本処理では引当を行わない」） |
| C2 | 受注取消の期限 | 要件定義「取消は受注日の**翌営業日まで**」 | 詳細設計「**出荷指示済（40）より前**であること」（処理仕様書_受注取消） |
| C3 | 消費税の計算単位 | 基本設計「**明細単位**に計算し円未満**切り捨て**」 | 詳細設計「**請求単位**で計算し円未満**四捨五入**」（処理仕様書_請求締め、請求書の様式イメージの注記） |

C1〜C3 はいずれも 90_議事録 と 91_課題管理/課題管理表 に経緯が残っている。
**議事録・課題管理表まで読めば、どちらが新しい決定かは判断できる**——
出典つきで筋を通せるかの試験になる。

ノード / 接続の合計と一致する。

### 7. 結合セルで描いた作図（既知の弱点の検体）

図形を使わず、**結合セルと罫線だけ**で描いた作図。日本の設計書では
画面レイアウトと帳票様式はこちらの方式が多い。

| 文書 / シート | 内容 |
| --- | --- |
| 受注管理_画面仕様書 / 受注入力 レイアウト | 受注入力画面のモック（ヘッダ部・明細部・合計・ボタン） |
| 在庫管理_画面仕様書 / 在庫照会 レイアウト | 検索条件と一覧のモック |
| 請求管理_画面仕様書 / 入金消込 レイアウト | 入金一覧と消込候補の 2 ペイン |
| 帳票一覧・レイアウト / 請求書 様式イメージ | 請求書（A4縦）の様式 |
| WBS・体制図 / スケジュール | 結合セルの帯で描いたガントチャート |

**期待される挙動は「読めるが断片化する」**。`arp4 parse` は非空セルの連結成分で
塊を切るため、幅 3 セル以上の結合セル（値は左上のみ）は空白ギャップ 2 以上と
みなされて**列ごとの断片に分かれる**。たとえば受注入力のレイアウトは
「ラベル列の表」「値列の表」…に割れ、明細部は列ごとに 8 個の表になる。

**これは値の欠落ではない。** 塊の区切りは提示上の都合で、`at=` にセル番地が必ず
併記されるので、整理層は元の位置関係を読み直せる（区切りを間違えても回復できる形に
してあるのはこのため）。それでも読み切れないときは `arp4 render` で絵にする。

これは資材の作りが特殊なのではなく、**現場の Excel をそのまま入れたときに起きること**
である。この 5 シートはその再現。レイアウト・帳票様式を 1 つのまとまりとして読める
ようにするなら、結合範囲を考慮した領域検出が要る ―― ただし「どこまでが 1 つの
レイアウトか」は意味の判断に踏み込むので、**やるなら忠実性の回復として説明が付く
範囲まで**（`docs/parsed.md`）。

### 8. コードと設計書の食い違い（実装/）

設計書どうしの食い違い（C1〜C3）とは**別の軸**。現場では「実装だけが直っていて
設計書が古い」と「設計書だけが直っていて実装が追随していない」が同時に起きる。

まず、**上流だけが古い**もの。実装は詳細設計に従っているので、
C1・C2 は「基本設計・要件定義だけが取り残されている」形で確認できる。

| # | コードの実装 | 対応する記述 |
| --- | --- | --- |
| C1 | `OrderRegistService#registerOrder` は引当を呼ばず、`ShipmentInstructionService#createInstruction` が `StockAllocationService#allocate` を呼ぶ | 詳細設計と一致・基本設計と矛盾 |
| C2 | `OrderCancelService#isCancelable` はステータスが 40 未満かだけを見る（受注日からの経過日数を見ない） | 詳細設計と一致・要件定義と矛盾 |
| C3 | `OrderRegistService#calcAmount` は明細単位に `RoundingMode.FLOOR`、`BillingCloseBatch` は請求単位に `HALF_UP` | 両方がコード内に同居する（現実の状態） |

次に、**コードだけが違う**もの。arp4 は Java を読まないので、これは
**人が目で突き合わせる対照**である。理由は javadoc に書いてあるので、
「設計書だけを見て正本を作ると何を取りこぼすか」の見本になる。

| # | 論点 | 設計書 | コード |
| --- | --- | --- | --- |
| C4 | 受注明細の上限行数 | 詳細設計「明細 1〜50 行」 | `MAX_DETAIL_ROWS = 100`（EDI で 50 行超が届いたため実装で引き上げ・設計書未改訂） |
| C5 | 採番のロック待ち | 詳細設計「10 秒を超えたらエラー」 | `LOCK_TIMEOUT_SECONDS = 30`（月末の締めでタイムアウト頻発のため延長・設計書未改訂） |

次に、**コードにしか無い**記述（G6）。`OrderRegistService#validateOrder` は
得意先コードを前ゼロ埋めで 8 桁に正規化する。設計書のどこにも書かれていないが、
課題管理表 No.7（現行 6 桁 → 新 8 桁の移行）と地続きの処理である。

最後に、**設計書にモジュール定義が無いサービス**（G7）。機能要件にはあるのに
詳細設計のモジュール一覧が起こしていない機能が 4 つある。実装しなければ機能
要件を満たせないので、コード側だけにサービスが存在する。設計書だけから作った正本では
`arp4 check` の**カバレッジ**（実現されない要件）がこの 4 件を拾うはずで、
それが出れば正しい。javadoc に「詳細設計にモジュールの定義が無い」と書いてある。

| クラス | 対応する機能要件 |
| --- | --- |
| `OrderUpdateService` | 受注内容の変更 |
| `StockInquiryService` | 在庫照会 |
| `ReceivableInquiryService` | 売掛残高管理 |
| `MasterMaintenanceService` | マスタ保守 |

定数・enum はコードから業務ルールを起こす材料として置いてある
（`OrderStatus` のコード値 10/20/30/40/90、`ClosingType` の 20日締め・末日締め、
`MoveType` の在庫移動区分、`InvoiceStatus` の請求ステータス、`OrderRoute` の
受注経路）。締め日そのものは非機能要件「保守性」に従って締め日マスタから引くので、
コードには入っていない。

## 追加資料（第2次リリース）

`資料/` を 1 度取り込んだあと、**2 度目の束が届いたら整理結果に足せるか**を試すための
資材である。8 文書・56 シート。内容は 2 種類しかない。

1. **是正** ―― 上の C1〜C5・G6・G7 の決着。変更管理委員会（2026/02/06）が寄せ先を決め、
   **変更前・変更後・決定理由・決定日・承認者・経緯の出典**を残した形で書いてある
2. **追加** ―― 第2次リリース（2026年10月稼働）で足す**返品管理**。要件・業務ルール・
   コード定義・テーブル・画面・モジュール・処理仕様まで一式ある

**差し替え版ではない。** `資料/` の記述はそのまま残っているので、同じ論点について
**両立しない 2 つの記述**が束をまたいで存在する。これを「矛盾」ではなく
「新しい決定が古い記述を置き換えた」と読めるかが、この資材の試験である
―― 決定日・承認者・変更前の引用がすべて揃っているので、**出典つきで筋を通せる。**

```

├── 00_全体/04_変更管理/設計変更管理表.xlsx          変更要求 12・決定 8・影響 16・申し送り 4
├── 00_全体/01_要件定義/要件定義書_第2版差分.xlsx     機能要件の改訂 3・追加 5、非機能 2、用語 4、業務フロー図
├── 00_全体/02_基本設計/基本設計書_システム方式_第2版差分.xlsx
│                                                  業務ルールの改訂 4・追加 6、コード 13、状態遷移図
├── 00_全体/02_基本設計/テーブル定義書_追加分.xlsx    追加 2 表・既存への列追加 3・索引 5・ER図
```

### 決着させたもの

| # | 論点 | 寄せた先 | 直る文書 |
| --- | --- | --- | --- |
| C1 | 在庫引当のタイミング | **出荷指示の実行時**（＝詳細設計・実装） | 要件定義・基本設計 |
| C2 | 受注取消の期限 | **出荷指示済（40）より前**（＝詳細設計・実装）。出荷後の戻しは返品へ | 要件定義・基本設計 |
| C3 | 消費税の計算単位 | **明細単位・切り捨て**（＝基本設計）。請求単位は明細の単純合計 | 詳細設計・帳票（★実装は要修正） |
| C4 | 受注明細の上限行数 | **100 行**（＝実装 `MAX_DETAIL_ROWS`） | 詳細設計 |
| C5 | 採番のロック待ち | **30 秒**（＝実装 `LOCK_TIMEOUT_SECONDS`） | 詳細設計 |
| G6 | 得意先コードの前ゼロ埋め | **業務ルールとして明記**（実装にしか無かった） | 基本設計 |
| G7 | モジュール定義の無い 4 機能 | **モジュール一覧へ追加**（受注変更・在庫照会・売掛残高照会・マスタ保守） | 詳細設計 |

C3 だけは**逆向き**である ―― 設計へ実装を寄せるので、`BillingCloseBatch` の
`HALF_UP` が残ったままになる。これは設計変更管理表 5.申し送り事項に**開いたまま**
書いてある。**是正のラウンドを回しても全部が閉じるわけではない**という形を残すため。

G1〜G5（粒度差）・表記ゆれ・重複は**そのまま**にしてある。あれは不具合ではなく、
`refines` と名寄せの検体だからである。

### 追加したもの（返品管理）

出荷後の戻しを扱う機能で、C2 の決着（出荷指示済以降は取り消せない）と地続きになる。
`資料/` の在庫移動区分に `12 返品入庫` だけが定義されていて機能が無かった穴も埋まる。

| 層 | 追加分 |

| 非機能要件 | 返品処理の件数（性能）・返品受付期限の変更容易性（保守性） |
| 業務ルール | 返品受付の期限・返品数量の上限・返品後の受注取消の禁止・返品の品質区分・返品の売上戻し・得意先コードの正規化（6 件） |
| コード定義 | 返品ステータス 5・返品理由区分 6・品質区分 2 |
| テーブル | `T_RETURN` / `T_RETURN_DETAIL`、既存 3 表への列追加（`RETURN_LIMIT_DAYS` / `DEFECT_FLAG` / `RETURNED_QTY`） |
| 画面 | 返品入力・返品承認・返品一覧照会 |

**実装（`実装/`）は足していない。** 返品は第2次リリースの製造工程で作るもので、

申し送り事項に書いてある ―― 設計だけが先行している状態は現場にふつうにあり、
`arp4 check` のカバレッジがどう出るかの検体になる。

## 通し方

```bash
python examples/sales-corpus/build.py --clean     # まず資材を作る

R=/tmp/sps && mkdir -p "$R"
arp4 init  --root "$R"
arp4 model --root "$R"                            # ★ 使ってよい語彙を先に読む
arp4 parse --root "$R" <このリポジトリ>/examples/sales-corpus/資料
```

**基準は渡したパスの共通の親になる**ので、`--base` は要らない ―― パース結果のパスは
`資料/10_受注管理/…` の形で残る（基準を `資料/` 自身にすると先頭の `資料/` が消え、
どの束から来たシートか出典から読めなくなる）。**成果物は `$R/.arp/` に出る。**

パースの実測（30 冊）:

| 出たもの | 数 |
| --- | --- |
| パース結果のファイル（＝シート） | 201 |
| 表のアンカー `sN-tM` | 207 |
| テキストのアンカー `sN-xM` | 240 |
| 図形のアンカー `sN-g1` / 接続 `sN-c1` | 15 / 15 |
| 図形テキスト / 接続 | 173 / 160 |
| **アンカーが 0 のファイル** | **0**（読めなかったシートも申告先を持つ） |
| 読み込みエラー | 0 |

続きは整理層の仕事である。

```bash
arp4 declare 表紙 改訂履歴 --reason "表紙・改訂履歴（仕様ではない）"
arp4 freeze --dry-run     # 残作業（未整理のアンカー）を一覧する
#   ★ parsed/ を読んで organized/ を書く（整理①）→ _concepts.yml（整理②）
arp4 freeze
arp4 build                # C1〜C3 の矛盾が課題として起票されるのが正しい
arp4 number
arp4 check --strict       # G7 の 4 件がカバレッジで出るのが正しい
arp4 publish
```

**30 冊を一度に整理しようとしない。** 201 シートは整理層の 1 セッションに入らない。
束（`00_全体` → `10_受注管理` → …）ごとに整理し、`arp4 freeze --dry-run` で
残りを数えながら進める。

### 2 ラウンド目（`追加資料/`）

1 ラウンド目を `publish` まで通したあと、**同じ根に**新しいラウンドを開いて
2 度目の束を渡す。`資料/` は渡し直さない（r001 のパース結果と整理結果はそのまま残る）。

```bash
arp4 parse --root "$R" --new-round <このリポジトリ>/examples/sales-corpus/追加資料
#   → .arp/rounds/r002/parsed/追加資料/… に 56 シート
arp4 declare --root "$R" 表紙 改訂履歴 --reason "表紙・改訂履歴（仕様ではない）"
arp4 freeze --root "$R" --dry-run
#   ★ parsed/ を読んで organized/ を書く（整理①）→ _concepts.yml（整理②）
arp4 freeze --root "$R"
arp4 build  --root "$R"
arp4 number --root "$R"
arp4 check  --root "$R" --strict
arp4 publish --root "$R"
```

**見どころは 3 つ。**

- **決着が矛盾に化けないか。** 同じ論点について `資料/` と `追加資料/` に両立しない
  記述がある。`追加資料/` 側は決定日・承認者・変更前の引用を持っているので、
  整理層は**置き換え**として書けるはずである（両論を残して課題にするのは、
  どちらが新しいか読めないときの振る舞い）
- **追加分が既存の正本へ乗るか。** 返品管理は新しい `concept` を持ち込むが、
  受注・得意先・商品・倉庫は**既存の concept と同じもの**である。ここを別物に
  してしまうとトレーサビリティが切れる
- **カバレッジがどう動くか。** G7 の 4 件は塞がり、返品管理の 2 モジュールが
  「設計はあるが実装が無い」側で新しく開く

### 実装コード（`実装/`）

**arp4 は Java を読まない。** `実装/` は設計書との食い違い（C1〜C5・G6・G7）を
人が目で確かめるための対照として置いてある。JDK があれば
`javac @sources.txt` でビルドして動かせる（手順は `実装/README.md`）。

体制図がその例）。この資材の 15 シート・160 接続はすべて既定（実線）である。

寄せる設定）は arp4 に該当する仕組みが無いので**外してある**。arp4 はフォルダ構造を
そのままパース結果へ写すだけで、軸を機械が決めることはない。
