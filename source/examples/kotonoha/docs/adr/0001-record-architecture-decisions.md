# ADR-001: 決めたことを記録に残す

- 状態: 採用
- 決定日: 2025-11-04
- 決めた人: 田村（AI基盤グループ）

## 背景

PoC のあいだに何度も「なぜこうなっているのか」を思い出せなくなった。
チャンクの長さも、モデルの選定も、試して決めたはずなのに根拠が残って
いない。**人が入れ替わったときに引き継げない。**

内製なので設計書のレビュー工程が無く、決定が会話の中で流れていく。

## 決めたこと

**アーキテクチャ上の決定を ADR として `docs/adr/` に残す。**

書くのは次のときだけにする。

- 後から変えるのに費用が掛かる決定（保存先・モデル・分離の方式）
- 選ばなかったものがある決定（**選ばなかった理由を残すのが本題**）
- 外部との約束になる決定（API の形・機密区分の扱い）

書かないもの。

- 実装の細部（変数名・関数の分け方）
- 運用の手順（`docs/runbook/` に書く）
- 一時的な回避（コードのコメントに書く）

書式は「背景 / 決めたこと / 選ばなかったもの / 結果として」の 4 節。
状態は `提案` `採用` `棄却` `置き換え` のいずれか。

## 選ばなかったもの

**社内 wiki に書く**
: 検索性は上だが、コードと一緒にレビューできない。ADR はコードと
  同じリポジトリに置いて、変更と一緒に見えるようにしたい。

**設計書を作る**
: 内製で 6 名の体制では維持できない。作った瞬間から古くなる。

## 結果として

- `docs/adr/` に連番で置く
- **決定が変わったら ADR を書き直すか、新しい ADR で置き換える**

---

## ★ この決めごとは守られていない

ADR-003（ベクトルの持ち方）と ADR-005（リランク）は、実装が変わったのに
書き直されていない。「決定が変わったら書き直す」という上のルールに
反している状態が続いている。

原因は単純で、**書き直す担当を決めていない**。実装を変えた人が ADR を
直すのか、レビューした人が指摘するのかが決まっていないので、誰も直さない。
