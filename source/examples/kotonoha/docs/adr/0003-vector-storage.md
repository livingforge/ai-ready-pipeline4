# ADR-003: ベクトルの持ち方

- 状態: 採用
- 決定日: 2025-12-08
- 決めた人: 田村（AI基盤グループ）、承認: 大城（部長）
- 関連: ADR-002（埋め込みの提供元）、ADR-006（ハイブリッド検索）

## 背景

PoC ではベクトルをファイル（numpy の `.npy`）に置いていたが、正式サービス
では検索の絞り込みとメタデータの管理が要る。専用のベクトルデータベースを
入れるか、いま運用している PostgreSQL に載せるかを決める必要がある。

想定する規模は初年度でチャンク 500 万件。

## 決めたこと

**PostgreSQL 16 + pgvector に載せる。索引は HNSW。**

**埋め込みは 1024 次元の float で持つ。** Voyage のモデルはいずれも
1024 次元を既定としており、次元を落とす（Matryoshka の切り詰め）ことも
できるが、精度への影響を測る余裕が無いので既定のまま持つ。

500 万件 × 1024 次元 × 4 バイト ＝ 約 20GB。索引を含めて 60GB 程度を
見込む。いまの DB のディスクに収まる。

## 選ばなかったもの

**専用のベクトルデータベース（Pinecone / Weaviate など）**
: 検索の性能は上だが、社内に運用の知見が無く、極秘データを外部の
  マネージドサービスへ置けない。自前で立てるなら PostgreSQL のほうが
  運用が楽。

**IVFFlat 索引**
: HNSW より作成が速くメモリも少ないが、再現率が安定しない。
  データが増えたときに作り直しが要るのも運用の負担になる。

**次元を 256 に落とす**
: 保管量は 1/4 になるが、精度への影響が読めない。**測る余裕が無い**
  ので、まず既定の 1024 で出して、困ったら考える。

## 結果として

- 保管量は見積りどおりに収まる見込み
- HNSW の `m` と `ef_construction` は運用しながら調整する
- 次元を落とす判断は先送り

---

## ★ この ADR は実装に追いついていない

**2026/05 に int8 量子化を入れたが、この文書を書き換えていない。**

品質保証部の取り込み量が試算の 3 倍になり、ベクトルの保管費が予算を
超えたため、運用の場で量子化する判断をした。上の「1024 次元の float で
持つ」は**もう実態と違う**。

経緯は `docs/runbook/reindex.md` の末尾に 3 行だけ残っている。
実装は `embed/quantize.py` と `ddl/07_migration_20260518.sql`。

この ADR を書き直すか、新しい ADR を起こすかを決めていない。
