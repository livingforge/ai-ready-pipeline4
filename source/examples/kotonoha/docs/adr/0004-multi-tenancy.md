# ADR-004: テナントの分離

- 状態: 採用
- 決定日: 2025-12-18
- 決めた人: 田村（AI基盤グループ）、承認: 大城（部長）、情報セキュリティ部レビュー済
- 関連: ADR-002（埋め込みの提供元）

## 背景

複数の部門が同じ基盤を使う。法務部の契約書とカスタマーサポート部の
保守マニュアルが同じデータベースに入ることになる。

分離をどこまでやるかを決める必要がある。物理的に分けるほど安全だが、
6 名で運用できる範囲に収めたい。

## 決めたこと

**論理分離。ただし機密区分ごとに要素を分ける。**

| 対象 | 分け方 |
| --- | --- |
| テーブル | 共有。`tenant_id` / `collection_id` で絞る |
| ベクトルの索引 | コレクションごとに別の索引名（別名で切り替える） |
| 原文（オブジェクトストア） | **機密区分ごとに別バケット**。極秘は別の鍵で暗号化 |
| 埋め込みの経路 | 機密区分で分ける（ADR-002） |
| 埋め込みキャッシュ | モデル名を鍵に含めるので**結果として区分ごとに分かれる** |
| API キー | テナントごと。複数発行できる |

**検索で機密区分の絞り込みはしない。** コレクションが区分を持ち、
テナントは自分のコレクションしか引けないので、区分をまたぐ検索は
そもそも成立しない。検索のたびに区分を突き合わせると漏れが出る。

## 選ばなかったもの

**テナントごとにスキーマを分ける**
: 部門が増えるたびにマイグレーションが増える。6 名では回らない。

**極秘だけ別のデータベースに置く**
: 安全側だが、運用が二重になる。原文のバケットと埋め込みの経路を
  分ければ、実質的なリスクは十分下がると判断した
  （情報セキュリティ部の確認済み）。

**行レベルセキュリティ（RLS）を使う**
: PostgreSQL の RLS で `tenant_id` を強制する案。強いが、接続の
  ロール管理が複雑になる。アプリ側の絞り込みで足りると判断した。
  **将来入れる余地は残す。**

## 結果として

- 他テナントのものを指したときは **404 を返す**（403 ではない）。
  403 だと「存在はする」と分かってしまう
- 停止中のテナントも **401**（403 ではない）。同じ理由
- 監査ログにテナント・区分・経路を残す

## ★ 書かれていないこと

**原文のバケットを機密区分ごとに分ける規則**は、この ADR に方針として
書いてあるだけで、**バケット名の対応表はコードにしかない**
（`store/object_store.py` の `BUCKETS`）。運用の手順書にも無い。
