# ADR-005: リランクの扱い

- 状態: 採用（**ただし実装が先行している。下の追記を参照**）
- 決定日: 2026-01-14
- 決めた人: 田村（AI基盤グループ）、承認: 大城（部長）
- 関連: ADR-006（ハイブリッド検索）

## 背景

PoC の評価で、融合しただけの結果は上位 3 件の精度が伸び悩んだ。
リランク（`rerank-2.5`）を掛けると明確に良くなることが分かっている
（PoC の比較では上位 3 件の適合率が 0.71 → 0.84）。

一方で、リランクは 1 回の検索あたりの費用が埋め込みの数倍になる。
検索の呼び出し回数は取り込みより桁が多いので、費用の見通しが立たない。

## 決めたこと

**第1次リリース（2026年4月）ではリランクを入れない。**

第2次リリース（2026年10月）で、次の条件が揃ってから入れる。

1. 検索の呼び出し回数の実績が 3 か月ぶん取れていること
2. チャージバックの単価に反映できる目処が立っていること
3. リランクを掛ける／掛けないを利用側が選べること

**極秘（機密区分 30）には掛けない。** リランクの提供元は外部 API しか
なく、本文を送出することになるため。これは第2次リリース以降も変えない。

## 選ばなかったもの

**第1次から入れる**
: 費用の見通しが立たない。「使ってみたら請求が想定の 5 倍だった」は
  内製の基盤として避けたい。

**自前でリランカを持つ**
: クロスエンコーダを社内 GPU に載せる案。GPU は極秘の埋め込みで
  埋まっており、余裕が無い。

## 結果として

- 第1次リリースは融合までで出す
- 検索の呼び出し回数を計測しておく（`t_usage_daily.search_calls`）
- 単価の枠だけ先に作っておく（`m_price` の `rerank_call`）

---

## ★ 実装が先行している

**2026/06 にリランクを入れた。この ADR は書き換えていない。**

品質保証部から「不具合報告の類似検索で、上位に関係ないものが混ざる」
という要求が出て、前倒しで入れた。上の「第1次リリースでは入れない」は
**もう実態と違う**。

- 実装: `search/rerank.py`、既定で有効（`settings.rerank_enabled = True`）
- 利用側は `rerank: false` で切れる（条件 3 は満たしている）
- 極秘に掛けない扱いはそのまま守られている
- 単価（`rerank_call`）は入っているが、**実績に基づいて決めた値ではない**

**誰が決裁したのかが記録されていない。** 条件 1・2 が揃っていたのかも
確かめられない。`docs/runbook/search-tuning.md` に 2 行だけ経緯がある。
