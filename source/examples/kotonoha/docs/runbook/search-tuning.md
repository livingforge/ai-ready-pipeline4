# 検索の調整

最終更新: 2026-06-11（小島）
関連: ADR-006（ハイブリッド検索）、ADR-005（リランク）

## 触れるつまみ

| つまみ | 既定 | 効果 |
| --- | --- | --- |
| `hnsw.ef_search` | 100 | 大きいほど当たるが遅い |
| 融合へ渡す候補数 | `top_k` × 5（最低 50） | 大きいほど拾えるが遅い |
| RRF の `k` | 60 | 大きいほど上位と下位の差が縮む |
| リランクの候補数 | 50 | 大きいほど良いが費用が増える |

## `ef_search` の決め方

SLO（検索の p95 が 800ms）から逆算した。

- pgvector の HNSW は `ef_search` に対しておおむね線形に遅くなる
- 200 万チャンクで実測すると `ef_search=100` で p50 が 42ms、p95 が 180ms
- 全文検索と融合とリランクを足して p95 が 600ms 前後
- SLO まで 200ms の余裕がある

**200 まで上げても SLO には収まる**が、再現率の改善が小さいので 100 に
してある。データが増えたら測り直すこと。

## 当たらないと言われたとき

順に見る。

1. **型番か。** ベクトルでは当たらない。引用符で囲んで完全一致にして
   もらう（`"A-2210"`）
2. **表記が揺れていないか。** 「サーボモーター」と「サーボモータ」は
   正規化で寄るが、「servo motor」は寄らない（同義語辞書は持っていない）
3. **絞り込みの鍵が合っているか。** メタデータの鍵は基盤側で正規化
   しない。「部署」と「部門」は別物として扱う
4. **チャンクの境界に跨っていないか。** 64 トークンのオーバーラップが
   あるが、長い記述はそれでも割れる
5. **内訳を見る。** `"explain": true` を付けると、ベクトルと全文の
   どちらから来た結果なのかが分かる

```sh
curl -s -X POST "$BASE/v1/collections/$CID/search" \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"query":"異音","top_k":5,"explain":true}' | jq '.data[].explain'
```

`vector_only` ばかりなら全文の索引が入っていない疑い、`keyword_only`
ばかりならモデルが合っていない疑いがある。

## 遅いと言われたとき

1. `span` のメトリクスで、どの段が遅いかを見る
2. リランクが効いていることが多い。`"rerank": false` で切って比べる
3. 絞り込みが効いていると候補を全件走査するので遅い（メモリ実装ではなく
   本番でも `chunk_ids` の `IN` 句が長くなる）。絞り込みの値を減らして
   もらう

## 覚え書き

- 2026/04/22 `ef_search` を 64 → 100 へ。再現率が 0.79 → 0.86。
  p95 は 140ms → 180ms で SLO 内。
- 2026/06/09 **品質保証部の要求でリランクを有効にした。** 上位 3 件の
  適合率が 0.71 → 0.84。ADR-005 は「第2次リリース」のままなので
  直す必要がある（未対応）。
- 2026/06/11 リランクの候補数を 100 → 50 へ。精度はほぼ変わらず、
  費用が半分になった。
