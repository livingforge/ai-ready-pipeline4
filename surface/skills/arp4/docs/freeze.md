# ② freeze ― 凍結する

```bash
arp4 freeze --dry-run          # ゲートだけ見る（残作業の一覧になる）
arp4 freeze --dry-run --list   # 未整理のアンカーを全部出す（既定は先頭 20 件）
arp4 freeze                    # 通ったらハッシュを固定する
```

**1 つの操作で 3 つのことをやる。**

1. **網羅の確認** ― 資料が落ちたまま残っていないか
2. **ハッシュの固定** ― 以後、出典が動かないことの保証
3. **機械に渡せる状態であることの検査** ― 通れば `build` は失敗しない

**`--dry-run` は書く前と書いたあとの 2 回打つ。**前は作業キューを出すため、あとは書いた
YAML が機械に読めるかを確かめるためである。

## その前に（`G014` ― YAML として壊れている）

**5 条件と並ぶものではなく、5 条件が意味を持つための前提である。**

壊れたファイルは読み飛ばされるので、そのファイルのレコードは 0 件になり、覆っていた
アンカーが丸ごと `G001`（未整理）として出てくる。画面には「未整理 296 件」としか
出ないので、**整理のやり残しにしか見えない。**

そのため `G014` が 1 件でもあるあいだ、**他の条件の件数は当てにならない。**先にこれを 0 に
してから未整理を数える。直し方は → [organize.md](organize.md)「YAML が壊れる値」。

## `arp4 lint` ― 1 ファイル書くたびに打つ

```bash
arp4 lint --root "$R" .arp/rounds/r001/organized/資料/A/受注テーブル.yml  # 書いた 1 本だけ
arp4 lint --root "$R" .arp/rounds/r001/organized/資料/A          # 書き上げた 1 冊ぶん
```

`freeze --dry-run` は 200 ファイルを読むうえ、出てくるのは未整理数百件なので、いま書いた
1 件が埋もれる。`lint` は、そのファイルだけで決まるものに絞る。

| 出る | 出ない（`freeze` の仕事） |
| --- | --- |
| `G014` 構文 / `G000` 形 / `G006` 必須欄 / `G008` 属性の置き場所 / `G011` 区分 | `G001` 未整理 |
| `G002` 語彙 / `G016` 属性名 / `G028` enum の値 / `G012` 関係の組み合わせ | `G003` `concept` が実在するか |
| `G004` アンカー実在 / `G005` 作文の疑い | `G013` 参照だけのレコードしかない |
| `G018` 出典の欄の取りこぼし / `G029` / `G030` `description` への流し込み | `G019` 原本のずれ / `G020` 要る関係が 0 本 |
| `G031` `known_gaps` の名前が語彙に無い（error） | `G031` の「宣言したのに関係が書いてある」（warn） |

右の列が `lint` に出ないのは、1 ファイルだけでは判定できないからである。原本 1 件は
複数のパース結果にまたがり、同じ `concept` のレコードは複数のファイルに散る。
**`G031` だけは線の両側にある** ―― 名前が語彙にあるかは 1 ファイルで決まる（相手は語彙で
あって他の整理結果ではない）が、「宣言したのに関係が書いてある」は関係が別のファイルに
ありうる。`lint` の集計には **`known_gaps の宣言 N`** が出る ―― `G020` が出ない層では、
**0 なら書いた場所か綴りが違う**という手がかりが件数しか無い。

フォルダを渡してもよい（分担で配る単位は 1 ブック＝1 フォルダ）。中に整理結果が 1 本も無い
フォルダ・当たらないパスは `exit 2` で止まる。打ち間違い 1 つで「直したファイルが検査され
ないまま成功扱い」になるのを防ぐためである。

### `lint` は完了条件にならない

**`lint` が通っても凍結できるとは限らない。**未整理も `concept` の実在も 1 ファイルでは
決まらないので見ていない（判定そのものは `freeze` と同じ関数なので、`lint` が出したものは
`freeze` も必ず出す）。

**分担するときはここが事故になる。**「`lint` が error 0 / warn 0 なら完了」と配ると、上の
右の列が全員の完了報告のあとに `freeze` で一度に出る。**完了条件は 2 つ揃えて配る**
（→ [split.md](split.md)）。

```bash
arp4 lint   --root "$R" <担当ぶんのフォルダ>              # ① 1 ファイルで決まるもの
arp4 freeze --root "$R" --dry-run --path <担当ぶん>      # ② 残りのうち自分に効くもの
```

`--path` は表示だけを絞る（判定はラウンド全体で行う）。隠した件数は必ず出るので、「自分の
ぶんは error 0」を「凍結できる」と読まないこと。

### `--fix` は 1 種類しか直さない

直すのは **`G008`（レコード直下に書いた属性を `attrs` の中へ移す）だけ**で、しかも語彙に
宣言されている名前に限る。`桁数` のような語彙に無い名前が `length` なのか `precision` なのかは、
資料を読まないと決まらない（そこはあなたの仕事である）。

`G014` は直さない。構文解析できないファイルへの直しはすべて本文の推測になり、引用符の位置を
1 つ間違えると、資料の値が気づかれないまま別のものになる。**凍結済みのラウンドでは動かない。**

## ゲートの 5 条件

| コード | 条件 |
| --- | --- |
| `G001` | 未整理のアンカーが 0 |
| `G002` | 語彙に無い `type` / `rel` が 0 |
| `G003` | `concept` が実在する |
| `G012` | 関係の**組み合わせ**が宣言と合う |
| `G013` | 参照だけのレコードの種別が決まる |

`G012` は `G002` の次に来る条件である。`G002` は「語彙にある関係か」しか見ないので、
**語彙にある関係を語彙に無い組み合わせで使っても `G002` は通る。**向きは機械が直すので、
逆向きに書いてあることは `G012` にならない（ただし直せる関係とそうでない関係が
ある → [organize.md](organize.md)）。

補助として次も見る。**どれも warn なので凍結は通るが、通っても正しいとは限らない。**

- **`G016`（宣言に無い属性名）。**`build` は宣言に無い属性を捨てるが、それが分かるのは
  凍結したあとで、そのときには整理結果はもう編集できない。関係の属性（`refs[].attrs`）は
  `build` が指摘なしに捨てるので、こちらは言われなければ気づけない
- **`G005`（本文に語が無い）。**warn に留めるのは、言い換えが許されるので機械が真偽を
  決められないためである。出たら出典の取り違えを疑う（コード起点では正常なことが多い
  → [code.md](code.md)）
- **`G015`（絵があるのに `未読取` のまま）。**絵を読んで確定できたならレコードにし、絵でも
  確定できないなら**開いた絵の名前を `reason` に書く**（`p007.png を開いたが押印で潰れて
  いる`）。名前が入っていれば消える ―― 見ているのは名前が出てくるかだけで、文の意味は
  判断しない。二巡目の撮影は `arp4 render --pending` で行う（宣言そのものが撮り直しの
  依頼になる）
- **`G007`（語彙の追加提案が未承認）。**`status: deferred` ＋ `deferred_reason` で保留に
  できる（保留なら warn になって凍結が通り、提案は決定の記録として残る）。理由の無い保留は
  error のまま

### `G018`（出典に書いてあったのに書かなかった）

`G005` の裏返しである。`G005` は「出典に無いことを書いた」を疑い、`G018` は「出典に書いて
あったことを書かなかった」を数える。`raises` を書かずに凍結すると、正本では例外を投げない
メソッドと見分けが付かなくなる。判定は空か空でないかだけで、値そのものは比べない。

宣言の無い欄では何も出さない。Excel の見出しは資料ごとに揺れるので（「戻り値」「返却値」）、
照合できるのは、見出しを arp4 自身が書いている表（コードのメンバ表）だけである。

### `G020`（要る関係が 1 本も無い）

**語彙が「1 本は要る」と定めている関係が 1 本も無い状態である。**多いのは `constraint` の
`constrains` と `test-case` の `verifies` である。何も制約していない制約は守られているかを
誰も確かめられず、何も検証していないテストケースはトレーサビリティに 1 行も出ない。それで
いて、どちらも設計書には ID も名称も仕様も揃った行として出るので、**繋がっていないことが
読み手からは見えない。**

相手はたいてい本文に書いてあるので、**いまそのファイルを開いているうちに** `refs` へ足すこと。
同じことは `build` の後に `W031` も出すが、そのときに渡されるのは `cst-…` という内部 ID の
一覧である。

**ただし「調べたうえで相手がいない」は正しい申告である**（張れないほうが正しいことのほうが
多い）。

| 資料の形 | なぜ張れないか | どうするか |
| --- | --- | --- |
| 母集合を縛る制約（「帳票は SVF を流用」「端末は Windows 11」） | 縛る先が全部なので 1 本に落ちない | 張らない。そのレコードへ `known_gaps` |
| 規模の想定（項目・値・備考の 3 列しかない表） | 縛る先の列がそもそも無い | 同上 |
| 評価報告書の候補行（PoC の比較表を `制約・前提` 1 行 1 件に割ったもの） | **候補はまだ何も縛っていない。**採用したものが縛る先は `決定事項` の `establishes` が指す | 張らない。実測では PoC 評価報告書の 14 件が全件鳴っており、**鳴るのが正常である**（→ [sheets.md](sheets.md)「評価報告書」）。同じく `known_gaps` |
| 相手の型が語彙で許されない（メッセージの表示方法） | `constrains` の相手に無い | 同上 ＋ 語彙の不足として `_metamodel-add.yml` の `notes` |
| ドメイン定義（`数量` `金額` `区分`…） | その名前のデータ項目は存在しない | 名前・説明・型が資料の中で一致するものにだけ張る |

**推測で消さない。**出ていること自体が「調べた結果、資料が相手を書いていない」という記録に
なる。**降ろす口はいま開いているファイルにある** ―― そのレコードの `known_gaps` に関係型と
理由を書けば `G020` は出ず、降ろした件数が集計に出る（`build` が正本へ運び、`check` では
`W032` として理由つきで出続ける）→ [organize.md](organize.md)「「調べたうえで相手がいない」は
宣言する」。**`build` を待たない** ―― 分担では配る側が `build` を禁じるので、待つと
「調べた」と「まだ調べていない」が正本を組むまで分けられなくなる。

### コード整理の規約と文章化（`G022`〜`G027`）

コードのアンカー（`m1` / `v1` / `i1` / `t1` / `p1` / `j1`）にだけ掛かるので、シートの整理では
出ない。

| コード | 規約 |
| --- | --- |
| `G022` | 取り込み（`i1`）から張る `calls` の相手はモジュールへまとめる（メソッドにしない） |
| `G023` | dunder（`__init__` 等）は `method` に起こさず、親の `description` に本数で申告 |
| `G024` | `package` はファイルの路（concept のパス）から取る。越境させるなら根拠を `description` に書く |
| `G025` | ファイル単位のモジュールの出典は「モジュール関数」の塊か `i1` |
| `G026` | 文章化が残っている（`<TODO 抽出元 …>`）。error なので、埋めるまで凍結できない |
| `G027` | 抽出的文章の外形（10〜200 字・識別子の包含）。`drafted:` の印のあるファイルだけ |

規約の中身と `G026` / `G027` の埋め方 → [code.md](code.md)

### `description` を書き先の代わりにしない（`G029` / `G030`）

`description` は補足を受け取る欄である（`merge: append`）。**書ける場所を減らす話ではない。**

**「`description` はどこにも出ない」ではない。**様式の多くの章が「補足」列を持っている
（標準パックでは表を持つ 68 節のうち 56 節）。変えたいのは、**宣言済みの欄がある列を補足
1 本へ畳んで、列として引けなくすること**である ―― 畳んだぶんの列は空のまま出て、
`0_この設計書の穴.md` が `W046` / `W047` として「資料に無い」側に並べる
（→ [organize.md](organize.md)「`description` が設計書に出るかどうかは、種別と章による」）。
`description` は予約キーなのでスキーマ検査を素通りし、畳んだこと自体は指摘されない。

| コード | 言うこと | 次にやること |
| --- | --- | --- |
| `G029` | 宣言済みの欄があるのに `description` へ流した | 名指しされた欄へ写す |
| `G030` | 同じ見出しが同じ種別で 4 件以上あり、受け皿の属性が無い | `_metamodel-add.yml` へ属性を提案する（資料の言い回しが揃っているだけなら `statement` へまとめる） |

見出しは `物理名 ORDER_NO ／ 既定値 0` のように割れているものを、属性の `label` と完全一致で
当てる。2 つ以上一致して初めて指摘し、対応する欄が既に埋まっていれば何も出さない。

**`G030` の 2 通りは、その見出しが何を数えているかで選ぶ。**

| その見出しは | どちらを選ぶか |
| --- | --- |
| 複数の資料・複数のレコードに**同じ形で繰り返し出る** ―― 資料の側にある列である | `_metamodel-add.yml` へ**属性を提案**する（帳票の「取得元」、外部 IF の「異常時の扱い」）。提案が通れば、次のラウンドから列として引ける |
| **その資料 1 冊の言い回しが揃っているだけ** ―― 書き手の癖であって列ではない | `statement` へまとめる（1 冊の中でだけ「前提：…」で始めている、など） |

**迷ったら提案側にする。**提案は却下されても `_metamodel-add.yml` に記録として残るが、
`statement` へ畳んだ値は列として引けなくなり、畳んだこと自体がどこにも残らない
（→ [organize.md](organize.md)「`description` が設計書に出るかどうかは、種別と章による」）。

**`G029` にこの選択は無い。**写す先の欄が名指しされているので、値を書き直さずに欄を移す
（`statement` へ畳むのは直し方ではない）。

出口の側からも同じ穴を見る。`description` に残ったものがどの設計書にも出ていなければ、
`arp4 check` が `P111` で指摘する。どちらを直すかは人が決めるので、機械は両側から同じ穴を指す。

## 凍結すると何が起きるか

```yaml
# .arp/rounds/r001/organized/.frozen.yml
frozen_at: '2026-08-02'
files:
  資料/A/基本設計書.xlsx/受注テーブル.yml: b864bb061a8c
records: 412
out_of_scope: 61
unreadable: 18        # うち「機械が読めていない」もの（次のラウンドで拾い直す）
```

以後、整理結果を編集すると `arp4 check` が `G009` で検出する。

## 凍結後に誤りが見つかったら

| 状況 | 手当て |
| --- | --- |
| 軽微（属性 1 つ、名前が不適切） | **正本側で `overridden`**（理由必須）→ [build.md](build.md) |
| 資料の解釈が根本から変わる | **新しいラウンドを起こす**（`arp4 parse --new-round`） |
| 利用者が明示的に整理結果の修正を求めた | 直したうえで `.frozen.yml` の `amendments` に理由を残す |

原則は正本側で直す。整理結果は「資料はこう書いていた」の記録で、正本は「我々はこう決めた」の
記録なので、あとから分かったことは正本の変更として残る。

更新されていない資料について、正本のレコードは前のラウンドの整理結果を指し続ける。
**これが正常な状態である。**
