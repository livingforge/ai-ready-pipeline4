# 整理① ― パース結果を型付きレコードにする

このスキルの中心となる作業である。意味を判断するのはここだけで、前後（`parse` / `build`）は
照合しかしない。ここで書いた内容が、そのまま設計書の内容になる。

この文書はレコードの書き方を定める。ほかは →
[sheets.md](sheets.md)（日本の Excel 設計書の読み方）／[code.md](code.md)（コード資産）／
[reconcile.md](reconcile.md)（横断・食い違い）

## 手順

```bash
arp4 model                # ① 使ってよい語彙（type と rel はここにしか無い）
arp4 model --attributes   #   属性名・enum の値まで
arp4 freeze --dry-run     # ② 残作業の一覧（未整理のアンカー）
```

`G001` の一覧が作業キューである（既定は先頭 20 件。全部見るなら `--list`）。
1 パースファイルを読んで 1 整理ファイルを書く、を繰り返し、キューが空になったら
横断整理（→ [reconcile.md](reconcile.md)）へ進む。

```
.arp/rounds/r001/parsed/資料/A/基本設計書.xlsx/受注テーブル.md   ← 読む
.arp/rounds/r001/organized/資料/A/基本設計書.xlsx/受注テーブル.yml ← 書く
```

対応は 1:1 で、拡張子だけが違う。そのため `source` に書くのはアンカーだけでよい。
**一度に全部読み込まない。**1 ファイルずつ処理すれば、途中で止まっても
`freeze --dry-run` が残りを教えてくれる。

**1 ファイル書いたら `arp4 lint <そのファイル>` を打つ。**200 ファイル書いてからまとめて
`freeze` を打つと、壊れたファイルが覆っていたアンカーは丸ごと `G001`（未整理）として出る。
`lint` は書いた 1 本だけを見て `ファイル:行` の形で指摘するので、その場で直せる
（何が出て何が出ないか → [freeze.md](freeze.md)）。

**資料名が `_` で始まっていてもそのまま写す。**`organized/` 直下の `_concepts` と
`_metamodel-add` は予約名だが、名前が完全に一致したときだけである。
`__init__.py.yml` は普通に読まれるので、リネームして避けない（出典が元資料と食い違う）。

## レコードの形

形の正本は `arp4 schema` である。以下は読み方の説明で、どの欄が要るか、破ると
どのコードが出るかはすべてそちらにある。

レコードには形が 2 つある。

```yaml
records:
  # ① 完全なレコード。この concept を定義する。1 concept につき 1 ファイルだけ
  - concept: c-T_ORDER                # 同一性キー。これだけで機械はマージする
    type: エンティティ                 # arp4 model の語彙
    name: 受注                         # 設計書の見出しになる
    statement: 受注テーブル T_ORDER は受注 1 件を 1 レコードで保持すること
    attrs: { physical_name: T_ORDER, entity_kind: トランザクション }
    source: { anchor: s1-t1 }         # パース結果のアンカー
    refs:
      - { rel: has-column, to: c-受注番号,
          attrs: { physical_name: ORDER_NO, pk: true, not_null: true } }

  # ② 参照だけのレコード。「このアンカーも同じ concept の話をしている」だけ。
  #    type / name / statement は書かない（他ファイルの完全なレコードから決まる）
  - concept: c-T_ORDER
    source: { anchor: s6-t1 }
    attrs: { volume: "1,200,000/年" } # そのシートにしか無い属性は書いてよい
    refs:
      - { rel: has-index, to: c-IX_T_ORDER_01 }

out_of_scope:
  - { anchor: s1-x1, reason: 表題と改訂番号（仕様ではない） }
  - { anchor: s2-t1, kind: 未読取, reason: 業務フローは図形で描かれており本体が出ていない }
```

| 欄 | 必須 | 注意 |
| --- | --- | --- |
| `concept` | ○ | 命名は後述。一度使ったら変えない |
| `source.anchor` | ○ | 根拠のある塊。表なら `s1-t1`、セルなら `s1-x1` |
| `type` | ①のみ | `arp4 model` の「整理結果に書く type」から選ぶ |
| `name` | ①のみ | 設計書の見出し。対象を名指しする（後述）。表の見出し語（「論理名」等）を入れない |
| `statement` | ①のみ | 「〜すること」。1 文で閉じる（用語・登場人物は文型が違う。後述） |
| `attrs` | | 種別ごとの属性。レコード直下に書くと拾われない（`G008`） |
| `refs` | | 本文に根拠がある関係だけ。向きは後述 |
| `known_gaps` | | **調べたうえで相手がいない**ことの宣言（関係型・属性名 → `reason`）。後述 |

**レコード直下に書けるのはこの 8 つだけ。**`description` `priority` `owner` は、
`name` や `statement` と同じ共通属性だが `attrs` の中に入れる。

`type` / `name` / `statement` は 3 つ揃えるか 3 つとも省くかのどちらかである。1 つだけ
書き忘れると `G006` で止まる（書き忘れと「参照だけのつもり」は区別できないため）。

### 同じ対象が複数シートに出るとき

**いちばん詳しい 1 シートで完全なレコードを書き、残りは参照だけにする。**

日本の設計書は同じ対象を必ず複数シートに書く。画面「受注入力」は画面一覧・機能一覧・
画面仕様書・項目一覧の 4 シートに現れ、アンカーはレコードでしか解決できない（`G001`）。
4 か所すべてで `statement` を書くと食い違いが起きやすく、`build` は「長いほうを採る」
しかできない（`B023`）。

```yaml
# 受注管理_画面仕様書.xlsx/受注入力 ← いちばん詳しいのでここが完全なレコード
- { concept: c-scr-受注入力, type: 画面, name: 受注入力,
    statement: 受注入力画面は得意先・商品・数量を入力して受注を登録すること,
    attrs: { screen_id: SCR-001 }, source: { anchor: s3-t1 } }

# 画面一覧.xlsx/画面一覧 ← 同じことしか書いていないので参照だけ
- { concept: c-scr-受注入力, source: { anchor: s1-t1 } }
```

どこにも完全なレコードが無ければ凍結が `G013` で止まる（前のラウンドで定義済みの
concept なら台帳から引けるので、参照だけで通る）。

**同じアンカーに完全なレコードと参照だけのレコードを並べてよい。**アンカーは 1 件でも
レコードに覆われれば未整理（`G001`）から消えるので、1 枚の表から「ここで定義する concept」と
「ここでは名指ししているだけの concept」を同時に起こせる（テーブル定義書の 1 シートなら、
テーブルは完全なレコード、参照先のマスタと共通のデータ項目は参照だけのレコードになる）。
**`lint` も `freeze` も何も言わないのは、それが正常な形だからである。**ただし
**同じ concept を同じアンカーで 2 度書かない** ―― 完全なレコードを書いたうえで同じ
concept の参照だけのレコードを足しても、増えるのは出典の重複だけである（`build` は同じ
concept のレコード群の出典を全件そのまま運ぶので、`0_元資料と設計書の対応.md` に同じ写しが
2 度並ぶ）。そのシートにしか無い属性は、完全なレコードの `attrs` に書けばよい。

#### 関係にもオーナーが要る

レコードの分担を決めても、関係の分担は決まらない。同じ 2 つの concept を結ぶ関係を
2 枚のシートが張ると、属性（`note` / `control` / `crud` / `permission`）が食い違って
`B024` になり、先に読んだほうが採用される。レイアウトは配置を、項目一覧は物理名と型を
書いていて、資料としてはどちらも正しいのに片方しか残らない。

**属性を持つほう（ふつうは項目一覧・仕様書）が関係を張り、もう一方は参照レコードで
アンカーを回収するだけにする。**レイアウトにしか無い情報（ゾーン・配置・並び）は、その
参照レコードの `description` へ書く。食い違うなら `contradictions` へ回す。

### `name` は対象を名指しする（資料の文体を写さない）

`name` は設計書の見出しになる。読み手は一覧を上から見て「これは何についての決めごとか」を
探す。「何を求めるか」は `statement` が書くので、**`name` に主張を持たせない。**

| | `name` | `statement` |
| --- | --- | --- |
| 役割 | 何についてか（対象） | 何を求めるか（「〜すること」） |
| 例 | 資料が 1 冊も読めなかったときの申告 | 資料が 1 冊も読めなかったときは、リンク切れ・打ち間違い・一覧できないの区別を付けて申告し、正常終了で終わらせないこと |

```yaml
name: 静かに 0 冊にならない            # × 資料の見出しの写し。一覧で読み比べられない
name: 資料が 1 冊も読めなかったときの申告  # ○ 対象を名指しする
```

ただし肯定形に直すという意味ではない。「〜しない」を「〜する」に書き換えると意味が変わる
（禁止そのものが仕様のことがある）。**禁止は `statement` に禁止のまま残し、`name` には
その禁止が何についてかを書く。**これを崩すと、要件定義書が能力の一覧ではなく禁止事項の
一覧として出る。

**資料の語から変えたら、元の語を `aliases` に残す。**資料の「移行」「保守性」のような 1 語の
要件名を「移行するデータの範囲」「業務ルールの変更のしやすさ」に直すのは、この節のとおりで
正しい。**ただし直した語しか残らないと、資料を持っている人が名寄せできなくなる。**元の語は
`_concepts.yml` の `new[].aliases` に入れる（→ [reconcile.md](reconcile.md)）。表記ゆれの
ためだけの欄ではなく、**整理層が読みやすさのために変えた跡を残す欄でもある。**分担していて
`_concepts.yml` への書き込みを禁じられているなら、最終報告へ回す
（→ [split.md](split.md)「共有ファイルは書き込み役を決める」）。

```yaml
new:
  - concept: c-nfr-移行するデータの範囲
    type: 非機能要件
    label: 移行するデータの範囲
    aliases: [移行]                    # ← 資料の要件名
    reason: 非機能要件一覧の要件名が「移行」の 1 語で、一覧で読み分けられないため改名
```

### 資料に無い欄は空けておく（設計書の列を埋めない）

`priority` / `owner` / `rule_kind` のような欄は、設計書の表に列がある。資料がその値を
書いていないなら空けておくこと。空欄は `E010` として人に渡るが、埋めた値は誰にも検算
できない。

**`arp4 model` が「必須」と書いている欄も同じである。**`decision.decided_on` /
`decided_by` / `rationale` や `test-run.executed_on` のように必須と宣言された属性でも、
資料が書いていないなら空けておく。整理層で埋めると、出典の無い日付・出典の無い決定者が
正本に入る。**空のままでも `lint` も `freeze` も止まらない**（必須属性を見るのは `build`
の後の `arp4 check` である）。そこで `E010` として出るので、`known_gaps` に「資料に欄が
無い」のか「欄はあるが空」のかを書き分けて申告する ―― 書く先は整理層のレコード（次節）で、
凍結したあとに気づいたときだけ正本側になる →
[build.md](build.md)「`E010`（必須属性が無い）が出たら」。

桁数・物理名と違って `priority` はもっともらしい既定値が思いつくので、つい埋めてしまい
やすい。全件「必須」で埋めると、全部同じ値なので列としての情報量は無いのに、「この要件は
必須だと資料が言っている」と読める形で設計書に出る。

**そのために関係を捨てない。**「関係があるのは確かだが、属性が資料に書いていない」ときは、
関係を張って属性を空けておく。`freeze` も `check` も指摘しないので捨てるほうを選びやすい
が、捨てた関係は誰にも見えない。空欄は空欄として読み手に見えるのに対して、無い関係は
「まだ調べていない」のか「無いと分かった」のかすら残らない。

### 「調べたうえで相手がいない」は宣言する（`known_gaps`）

前節の裏側である。**空けた欄・張れなかった関係について、探したうえでそう決めたと書く
場所がレコードにある。**キーは関係型でも属性名でもよく、`reason` は必須（無ければ
`G006`）。

```yaml
- concept: c-cst-月間上限-cs-support
  type: 制約・前提
  name: cs-support の月間上限
  statement: テナント cs-support の月間上限を 500,000 チャンクとすること
  source: { anchor: s4-t1 }
  known_gaps:
    constrains:                # 関係型 ―― この関係が 1 本も張れない
      reason: 規模の想定で、縛る先の列がそもそも無い（このラウンドの資料に無い）
    data_type:                 # 属性名 ―― 資料にその欄が無い、でもよい
      reason: 帳票の出力項目シートに型の欄が無い
```

| どこで | 何が起きるか |
| --- | --- |
| `freeze` | 宣言した関係の `G020` を出さない。**降ろした件数は必ず集計に出る** |
| `build` | 正本の `known_gaps` へそのまま運ぶ（正本側に既にある宣言は上書きしない） |
| `check` | `W032`（承知している欠落）として理由つきで出続ける。**消えはしない** |

**`build` を待たない。**同じ宣言は正本にも書けるが（→ [build.md](build.md)）、そちらは
`build` を打った人の欄である ―― 分担しているとき配る側は `build` を禁じるので、
宣言する口が無いと `G020` を warn のまま報告文に書くしかなくなる。**「調べた」と
「まだ調べていない」を分けられるのは、資料を開いた本人だけ**で、合流したあとでは戻れない。

**綴りは `G031`（error）で止まる。**誤字の宣言は二重に効く ―― `G020` を降ろさないうえ、
`build` がそのまま正本へ運ぶので**凍結の向こうで `E018` になり、そのとき整理結果はもう
編集できない。**名前が語彙にあるかは 1 ファイルで決まるので `lint` でも出る。逆に
**関係を書いたのに宣言が残っている**なら `G031`（warn）が「宣言を消せ」と言う（`freeze`
だけで出る）―― 古い言い訳が正本に残るほうが error より始末が悪い。

**種別を名乗らない参照だけのレコードでは、属性名は照合できない**（属性は種別が決まって
初めて引ける）。そこは黙るので、宣言は完全なレコードの側に書く。

### 資料にある値は宣言済みの欄へ入れる（`description` / `note` は最後の手段）

前節が「資料に無いものを埋めるな」なら、こちらは対である。**資料にある値を、宣言済みの欄が
あるのに `description` / `note` へ流さない。**

**資料の 1 列を写す前に `arp4 model --attributes` でその種別・関係を引き、同じ意味の欄が
宣言されていないかを確かめる。**この確認は列ごとに要る。種別に受け皿が無いことと、関係に
受け皿が無いことは別だからである（`displays` は `physical_name` と `default_value` を
持つが、`has-index` は何も持たない）。

流してしまうと、設計書のその列は**空のまま出る。**しかも `0_この設計書の穴.md` は
それを「様式にあるのに正本が値を持たない列」（`W046`）として並べる。

> **読み手は「資料に無い」と読む。値はあるのに無いと報告されるのが、いちばん悪い形である。**

空欄なら `E010` で人に渡り、誰かが資料を探しに行く。`description` に埋もれた値は、
資料にあるのに誰も探しに行かない。**空欄より悪い。**

#### `description` が設計書に出るかどうかは、種別と章による

**「`description` はどこにも出ない」ではない。**標準パックの様式 12 種を数えると、表を持つ
68 節のうち 56 節が `description` を「補足」列に持っている。持たない 12 節はすべて
トレーサビリティ・マトリクス（`kind: trace`）で、そこは空欄そのものが結論なので列を畳ま
ない。**ただし補足列は全行が空なら畳まれ、畳んだことは章末の脚注 1 行になる**ので、「補足に
書いたのに出ていない」は起こる（種別・章によって列の有無が違う）。**どの章に補足列があるかは、様式を見ないと分からない** ―― 様式は
パック側（`packs/<パック名>/documents/*.yml`）にあり、章ごとの `columns` に
`description` が並んでいるかで決まる。**「出るはずだから補足でよい」と当てにしない。**

**それでも、宣言済みの欄がある列を `description` へ流してはいけない**（`G029`）。理由は
「出ない」ではなく、**列として引けなくなる**ことである。補足列は 1 本しか無いので、物理名・
初期値・起票日を 1 つの散文へ畳むと、物理名列・既定値列・状態列は空のまま出て（`W046` /
`W047`）、読み手はその列で並べ替えることも、ほかの資料と突き合わせることもできない。
目で読める形にはなっているが、データとしては失われている。

**`statement` へ畳むのも同じことである。**`G029` / `G030` を消す手として `statement` に
まとめると、値は 1 文の中へ入って列からは消える。`G029` は写す先の欄を名指ししているので、
**値を書き直さずに欄を移す**のが直し方である（`G030` の 2 通りの選び方 →
[freeze.md](freeze.md)）。

実測で流れやすかったものを挙げる。どれも宣言済みの欄がある。

| 資料の列 | 流しがちな先 | 正しい欄 |
| --- | --- | --- |
| 画面項目の物理名・初期値 | `displays.note` | `displays.physical_name` / `default_value` |
| 課題の状態・起票日・工程・区分 | `open-issue.description` | `state` / `raised_on` / `raised_phase` / `category` |
| バッチの起動時刻・実行周期 | `batch.trigger` に合成 | `batch.start_time` / `schedule` |
| 業務ルールの区分・条件・処理 | `business-rule.description` | `category` / `condition` / `action` |
| 電文項目の必須・開始位置 | `interfaces.note` | `interfaces.not_null` / `position` |
| テーブルの保持期間 | `entity.description` | `entity.retention` |
| 画面パス・パッケージ・公開定数 | `description` | `screen.route` / `module.package` / `constants` |

**1 列を 2 つの欄へ分けることをためらわない。**「時刻起動 09:00」は `trigger: 時刻起動` と
`start_time: "09:00"` の 2 つである。1 つに合成すると、起動時刻の列は空で出る。

`description` / `note` が受けるのは、**宣言済みの欄がどれも当たらない 1 列**だけである
（帳票の「取得元」、課題の「対応方針」など）。それも `G030` で数えられ、続くなら
`_metamodel-add.yml` の `notes` へ属性の提案として上げる → 後述。

## 分類 ― 目の前のファイルから決めない

`arp4 model --attributes` で `※設計書の節になる` と印の付いた属性（`category` /
`nf_category` 等）は、そのまま設計書の章立てになる。他の属性と違って、これだけは
1 ファイルの視野では決められない。目の前の 1 ファイルしか見えていないと、分類はその
ファイルの名前をなぞるだけになり、要件定義書の目次がファイル一覧になる。

**上から順に見る。**

1. enum に合う値があるなら選ぶ（`arp4 model --attributes` に出る値）
2. 合う値が無くても、そのまとまりを言い当てる語があるなら書く。`category` は `extensible`
   なので語彙の宣言は要らない。出典のシート名が手掛かりになる（「未分類」に落ちた制約の
   出典がどれも同じシートなら、そのシートが区分を書いている）
3. どちらでもないものだけ空けておく。目の前のファイル名・シート名を入れない。
   `parse.py` を読んでいるからといって、「パース」は分類ではなく出典である

空けたものと、語彙に無い分類が要るものは、整理②でまとめて決める →
[reconcile.md](reconcile.md)。`check` の `P108`（未分類がこの章の 1/4 を超えた）が
出たら、2 をやり直す。

`constraint.category` の enum（技術・運用・法令・契約・体制・規模）では、規模・件数・
保存期間の想定は `規模` に入れる（性能試験と容量設計の入力になる。技術方式と混ざると
探せない）。

### 主軸（`subsystem`）は例外（資料の列に書いてあるので、語彙が無くても写す）

上の 3 段は自分で決める分類（`category`）の話である。`subsystem` は違い、
一覧の左端の列に書いてある（機能一覧・画面一覧・バッチ一覧・業務ルール一覧・
モジュール一覧・要件と機能の対応表が揃ってこの列で始まる）。書いてあるものを写すのは
分類の判断ではなく資料への忠実さなので、enum の値が宣言されていなくても資料の語を
そのまま入れる。

```yaml
- concept: c-req-受注登録
  type: 機能要件
  attrs:
    subsystem: 受注管理        # 区分の上段（節になる）。資料の語をそのまま
    category: 受注業務         # 区分の下段（列になる）
```

**節に出ない種別でも埋める。**主軸を節にできるのは件数のある種別だけだが、帳票・バッチ・
モジュール・業務ルールでは列に出る。`※設計書の節になる` 印は節に出るかどうかを言うだけ
なので、印が無いことを「書かなくてよい」と読まない。

書く先が無いと、この列は `description` の散文か `refines` の相手に流れる。`refines` へ
流すと関係型の意味が二重になり、「所属」と「詳細化」が同居する。関係の章は関係型でしか
引けないので、後から分けられない。

### enum は行き先の一覧であって、選ぶ根拠ではない

**規則は 1 つ。資料に根拠（注釈・継承・名前・見出し）があるなら付け、無いなら空ける。**

**`arp4 model --attributes` の enum の末尾に付く `…` は `extensible`（宣言に無い値も
通る）の印である。**`…` の無い enum は宣言された値しか受けず、外れた値は `G028` になる
（`constraint.category` は `技術/運用/法令/契約/体制/規模…` なので資料の語を足せるが、
`displays.io` は `入力/出力/入出力` の 3 つで閉じている）。

**`…` が付いている enum には、資料の語をそのまま足してよい。**語彙の宣言も
`_metamodel-add.yml` への提案も要らず、`lint` の `G028` も `check` も鳴らない
（`extensible` な enum は値の検査から外れる）。**寄せ先を増やしてよい欄なので、資料の語を
宣言済みの近い値へ丸めるほうが情報を落とす。**実測では `actor_kind: 要員`（体制図の個人）・
`test-case.level: 点検`（情報セキュリティ点検表）・`constraint.category: 規程` がこれで、
どれも資料の語のまま入れるのが正しい（`要員` を `利用者` に、`点検` を `受入` に丸めると、
体制の一覧にも試験の一覧にも別のものとして並ぶ）。`…` の無い enum で外れた値は `G028` に
なるので、当たる値が無いなら空ける。

宣言された値の一覧は「どこへ入れるか」の選択肢を示しているだけで、「この 6 つのどれかを
必ず選べ」という意味ではない。根拠が無いまま一覧から選ぶのは `priority` を全件「必須」で
埋めるのと同じだが、値が散らばるぶんもっともらしく見えて気づかれにくい
（`check --strict` も error 0 で通る）。

ただし空けるほうへ寄せ過ぎない。空けても節が消えるわけではなく、値の無いものは
`未分類` に集まり、まとまりが 1 つしか無ければ節に割らずに表 1 枚で出る。

## 対象外と未読取

`kind` は 2 つだけ。既定は `対象外` で、省略してよい。

**`対象外` は取り消しの効かない宣言である。**`未読取` は次のラウンドの拾い直し対象として
数えられ、`0_この設計書の穴.md` にも出る。**`対象外` はどちらにも出ない。**宣言した時点で、
そのシートは誰の目にも触れなくなる。

| `kind` | 意味 | 次のラウンドで |
| --- | --- | --- |
| `対象外` | 資料にそもそも仕様が書かれていない（表紙・改訂履歴・WBS） | 変わらない |
| `未読取` | 機械が読めていない（図形・画像）。資料には書いてある | 拾い直す対象 |

区別しないと、「まだ取れていないもの」が「もう見なくていいもの」に紛れる。

### `対象外` にする前に、列を 1 本ずつ見る

**シート単位で「これは例示だから」「これは集計だから」と決めない。列で決める。**そのシート
の列を 1 本ずつ見て、**「他のシートにも出るか」**を確かめる。1 本でも「ここにしか無い」列が
あれば、**そのアンカーはもう対象外にできない。**

**「この列だけ対象外」は書けない。**`out_of_scope` の粒度はアンカー（表 1 枚）であって列
ではなく、アンカーはレコードで覆われた時点で解決済みになるので、「1 列だけレコードにして
残りを対象外」という書き方も無い。できるのは次の 2 つである。

1. **その表をレコードで覆う。**ここにしか無い列を持つ行を、いちばん近い種別で起こす。
   残りの列は宣言済みの欄へ入るぶんだけ入れ、入らないものは空ける（空欄は `E010` で
   人に渡る）
2. **受け皿の無い列は `_metamodel-add.yml` の `notes` に申告する。**「この表のこの列は
   どの種別にも受け皿が無いので写していない」を `about` / `reason` / `source` の形で
   書く → 後述「語彙に無い種別が要るとき」

**表を丸ごと `対象外` にしてよいのは、1 本も「ここにしか無い」列が無かったときだけである。**

実測での取りこぼしを挙げる。どれも「例示・集計だから仕様ではない」と宣言され、消えた。

| 対象外にしたシート | そこにしか無かった列 |
| --- | --- |
| 処理仕様書「7.締め期間の例」 | **末日締めの締め期間**（20日締めのぶんは業務ルールにあるが、末日締めは無い）と支払期日の算出結果 |
| 課題管理表「集計」 | 状態別の件数に付いた備考（「うち 2 件は上流文書への反映が済んでいない」） |

**理由文に「なお〜はこの表にしか出てこない」と書きたくなったら、それは対象外にしては
いけない合図である。**実測ではその一文を理由に書いたうえで対象外にしており、宣言した本人が
気づいていた。気づいたことを理由文へ書いても、**理由文は誰の作業キューにも載らない。**

「例示」「集計」は、元の定義が別にあるときだけ成り立つ。**元をこの目で確かめてから宣言する**
（「業務ルール 請求の締め日 にある」と書くなら、そこを開いて末日締めが書かれているかを見る）。

### `未読取` をどう拾い直すか

**まず `s4-g1`（図形のテキスト）と `s4-c1`（図形の接続）を読む**（→ [parse.md](parse.md)）。
箱の名前と線の繋がりはここに出ているので、業務フローの順序・分岐、ER 図の関連、画面遷移は
たいていこれで起こせる。`未読取` にせず、そのままレコードにしてよい。

`未読取` にするのは、取れていないものが仕様そのもののときである。取れていないものは
2 つに限られる。配置（枠で括られたゾーン・段組み）と、繋がっていない線である。

**ただし宣言する前に絵を見る。**`arp4 render` を回すと図形のアンカーに絵が貼られる。
`s4-g1` の直下に `![…](../../images/…png)` があれば、Read で開くと配置も読める。読んで
確定できたならレコードにしてよい（出典はその `s4-g1`。絵は本文の一部である）。
**絵と `c1` が食い違ったら `c1` を採る。**`c1` は資料に書いてある id の転記だからである。

**`arp4 render` には Excel が要る。**入っていない環境では絵が作れないので、「宣言する前に
絵を見る」がそもそも実行できない。**そのときは `c1` と `g1` だけで確定できるかを見る** ――
絵にして初めて読めるのは配置（枠・ゾーン）と繋がっていない線の 2 つだけなので、次の 2 つが
揃っているならその 2 つは無く、絵は要らない。

- **`c1` の `元` / `先` に出てくる箱が、すべて `g1` に出ている**（線の両端が名前で解決できる
  ＝ 繋がっていない線・相手が文字を持たない線が無い）
- **`g1` の箱のうち、`c1` に一度も出てこないものが無い**（どこにも繋がっていない箱が無い）

**揃っているなら、絵を見ずにレコードにしてよい**（出典は `c1` と `g1` のまま）。実測では
体制図がこれで確定できている。揃っていないとき ―― 名前で解決できない端がある、`c1` が
出ていない ―― だけ `未読取` にし、`reason` に「Excel が無く `render` を打てない」と
書く（`G015` は「絵があるのに `未読取`」を数えるので、絵の無いこの形では鳴らない。次の
ラウンドで撮る根拠になる）。

絵が無い、または絵を見ても確定できないときだけ `未読取` にする。再 `parse` しても接続は
読めないので、宣言した時点でどちらの方法を採るかまで決める。

**絵を見たうえで確定できなかったときは、その絵の名前を `reason` に書く**（`p007.png を
開いたが押印で潰れている`）。`G015` は名前が入っていれば出ない ―― 見ているのは名前が
出てくるかだけで、文の意味は判断しない。名前は機械が付けたものなので、**書くには写しを
開くしかない。**

| 図に描かれている仕様が | 採る方法 |
| --- | --- |
| 別のシートの表にもある（状態遷移表・「遷移先」列・ジョブ定義表） | そちらを出典にしてレコードを起こし、図のほうは `対象外` に変える（理由に「仕様は s5-t2 の表にあり、図は同じ内容の絵」と書く） |
| その図にしか無い（業務フロー図・システム構成図・外部連携図） | `arp4 render` で絵にして読む。それでも確定できないときだけ、人が `parsed/**.md` に図の内容を書き足して新しいアンカー（`s4-x1b`）を振る → 次のラウンドで整理する |

判断は「その仕様を表から復元できるか」だけで決める。復元できるなら、図は絵であって
出典ではない。`未読取` のまま次のラウンドへ持ち越してもよい（件数は `freeze` が毎回出す）。

#### グラフのアンカー（`s4-k1`）は参照範囲で決まる

`g1`（図形テキスト）・`c1`（接続）と並んで、**グラフは `k1` に出る。**中身はタイトル・
系列名・参照範囲の 3 つで、**描かれている数そのものは無い**（→ [parse.md](parse.md)）。
上の「表から復元できるか」を、参照範囲がそのまま答えてくれる。

| `k1` の参照範囲 | どうするか |
| --- | --- |
| 同じシート・同じブックの表を指している | その表が出典で、グラフは同じ内容の絵である。表からレコードを起こし、`k1` は `対象外`（理由に「値は s3-t1 の表にあり、グラフはその絵」と書く） |
| グラフ側にしか無い語がある（系列名の単位・区分、タイトルのしきい値、目標線） | それはレコードにする。出典は `k1` |

**`未読取` にはしない。**参照範囲は同じブックの中を指すので、再 `parse` しても
`arp4 render` で絵にしても、新しく読めるものは無い。拾い直しの対象として次のラウンドへ
送っても、次の担当がやることは「参照範囲の先の表を読む」で今と同じである。

### 印刷のアンカー（`s1-p1`）は、開いてから決める

`p1` はヘッダ・フッタと印刷タイトル行である（→ [parse.md](parse.md)）。紙には全ページに
刷られているのに、セルには 1 つも書かれていない。**開かずに `対象外` へ回さない。**文書
番号・版・機密区分がそこにしか無いことがあり、シート 1 枚がファイル 1 本になる以上、その
ファイルが何の文書の何版かは `p1` にしか残らない。

- **資料名とページ番号しか無ければ `対象外` でよい**（理由に何が書いてあったかを残す）。
  実測（kotonoha r001）では 8 冊 47 シートのフッタが全部これで、`対象外` が正しかった
  ―― **正しいと分かったのは開いたからである**
- そこにしか無いものが見つかったら、書き先を探してから宣言する。前節「`対象外` にする前に、
  列を 1 本ずつ見る」と同じ規律である
- ページ設定はシートごとに掛かるので、1 冊の中で版が食い違っていることがある。どれが
  正しいかは機械が決めないので、食い違いは `contradictions` へ回す
  （→ [reconcile.md](reconcile.md)）

## 関係

### 接続（`c1`）をどの関係にするか

**まず既存の関係で書けないかを見る。**図の 1 本 1 本には、たいてい対応する関係型がある。

| 図 | `c1` の 1 本 | 使う関係 | 出る設計書 |
| --- | --- | --- | --- |
| 画面遷移図 | 画面 → 画面 | `transitions`（`event` / `condition` つき） | 基本設計書「画面遷移」 |
| ジョブフロー図 | ジョブ → ジョブ | `triggers` | 基本設計書 |
| バッチの処理フロー | ステップの順序 | `has-step`（バッチ限定） | 詳細設計書「バッチ構成」 |
| 処理フロー（オンライン） | 呼び出しの順序 | `calls`（`has-step` は使えない） | 詳細設計書「呼出関係」 |
| 外部連携図 | 外部 IF → データ | `interfaces` | 基本設計書 |
| 業務フロー図 | 手順 → 手順 | `has-flow-step` ＋ `leads-to`（下記） | 要件定義書「業務フローの手順」 |
| ER 図 | 実体 → 実体 | `references`（下記） | 基本設計書「テーブル関連」 |
| システム構成図 | 構成要素 → 構成要素 | 線に当たる関係型は無い。箱は `制約・前提`（`category: 技術`）へ 1 行 1 件で写す | 基本設計書「システム方式」 |
| 体制図 | 組織 → 組織 | `reports-to`（指揮命令）／`outsources-to`（委託）。箱は `利用者・ロール`（`actor_kind: 組織`）（下記） | ― |

**体制図は組織どうしの関係として起こす。**箱（情報システム部・業務部門・ベンダ）を
`利用者・ロール`（`actor_kind: 組織`）にし、線を `reports-to` か `outsources-to` で張る
→ [sheets.md](sheets.md)「WBS・成果物一覧・体制図」。**この 2 つは区別して張る** ―― 体制図
では指揮命令の線と委託の線が同じ矢印で描かれることが多く、凡例か注記にしか区別が書かれて
いない。1 本にまとめると、誰が指示できて誰が契約で縛られているのかが後から分かれなくなる。
区別が資料から読み取れないなら、張らずに `_metamodel-add.yml` の `notes` へ「凡例に区別が
無い」と申告する（推測で振り分けない）。**向きは `arp4 model` の `[関係]` で確かめる** ――
どちらも from と to に同じ種別（`actor`）が並ぶので、`※向きは書いたまま入る` のほうに
当たる。機械は直さないので、書いた向きがそのまま正本に入る（下記「`refs` の向き」）。

**「凡例が無い」と「凡例はあるが、その凡例で説明できない線がある」は別である。**前者は
語彙の側の話（どちらの関係か決められない）だが、後者は**資料の中の食い違い**なので、
`_metamodel-add.yml` ではなく `_concepts.yml` の `contradictions` へ回す
（→ [reconcile.md](reconcile.md)）。**凡例に無い線種の線は関係を張らない。**実測の体制図では
7 本のうち 3 本が凡例に無い線種（凡例は実線＝指揮命令 / 破線＝委託の 2 つだけ）で、担当が
最も時間を掛けた判断がここだった。**推測でどちらかへ寄せると、指揮命令か委託が 3 本ぶん
増える** ―― 増えたことは `freeze` も `check` も数えないので、誰にも見えない。

**要員（個人）も `利用者・ロール` にして、所属する組織へ `reports-to` を張る。**体制図には
組織の箱だけでなく個人名が載る（「基盤開発 田村」）。`reports-to` は `actor → actor` なので、
個人 → 所属チームは指揮命令の系統としてそのまま書ける。**新しい関係型は要らない。**張らないと
要員は組織と繋がらないまま体制の一覧に並ぶ（実測で 6 名がそうなった）。個人の `actor_kind` は
`組織` ではないので、資料の語（「要員」など）を入れる（`actor_kind` は `…` 付きの enum
なので資料の語を足せる → 前述「enum は行き先の一覧であって、選ぶ根拠ではない」）。

**`has-step` はバッチ（`batch → batch-step`）にしか張れない。**サービスクラスの処理フローに
張ると `G012` で凍結が止まる。オンラインの処理は順序ではなく呼び出しとして `calls` に
書く。順序そのものが仕様なら、資料が手順表を持っているはずなので、図ではなくその表を
出典にする。

### ER 図は `references` で書く

対応する関係型はある。`references`（`entity → entity`）が `fk_columns` /
`cardinality` / `required_flag` / `note` を持つ。

```yaml
- concept: c-T_ORDER
  source: { anchor: s9-c1 }
  refs:
    - { rel: references, to: c-M_CUSTOMER,
        attrs: { fk_columns: CUSTOMER_CD, cardinality: 1対多, required_flag: 必須 } }
```

**向きは 多 → 1** で、外部キーを持つ側が `from` になる。ER 図の矢印は凡例上たいてい
1 → 多なので、図とは逆に書く。`references` は向きの自動補正が効かないので、ここが
食い違うと後から復元できない。

**張らなくても検査には出ない。**`freeze` も `check` も `references` の欠落を数えないので、
「書く先が無い」と判断して落とすと、そのまま誰にも気づかれない。

遷移先の画面がまだレコードになっていなくても、前のラウンドで定義済みなら台帳から
引けるので、参照だけのレコードで通る。

```yaml
# 画面遷移図.yml ― 画面そのものは別シートで定義済み。ここは遷移だけを足す
- concept: c-scr-受注一覧照会
  source: { anchor: s4-c1 }
  refs:
    - { rel: transitions, to: c-scr-受注入力 }
```

**`triggers`（ジョブフロー図）も同じである。**図にしか無い先行後続は、その図を読んだ担当が
参照だけのレコードで足す。**オーナー表を「自分はジョブの持ち主ではない」と読んで張らずに置くと、
その線は誰にも張られない**（ジョブの持ち主はジョブを書くが、線は図にしか無い）。実測で
ジョブフロー図の 9 本のうち 5 本がこれで落ち、整理②が拾い直している。**`transitions` も
`triggers` も、欠落は `freeze` も `check` も数えない**（`references` と同じ）ので、落ちても
誰にも気づかれない。

### 関係そのものについて資料が書いていることは `note` に書く

表が関係 1 本ごとに 1 列を持っていることがある（呼出関係の「呼び出す目的」、遷移の
「条件」など）。専用の属性が無いからといって捨てない。`refs` の `note` が関係の本文に
なり、設計書の列に出る。**関係そのものは張られているので、この列を落としても `check`
にも `freeze` にも出ない。**

```yaml
- concept: c-mod-BillingCloseBatch
  source: { anchor: s5-t2 }
  refs:
    - { rel: calls, to: c-mod-TaxCalculator, note: 請求単位の消費税額を計算する }
```

属性で表せるもの（`transitions.event` / `has-column.pk`）は属性に書く。`note` は
語彙に専用の属性が無い 1 列のためのものである。

**`note` という名前の属性を宣言している関係では、直下に書いてはいけない。**`refs` 直下の
`note` は関係の `description` に入る（属性ではない）ので、`note` 属性を持つ関係にそう書くと
**設計書の `note` 列は空のまま、値は「補足」列へ流れる。**`arp4 model` の `[関係]` で属性を
確かめ、宣言があるなら `attrs` の中、無いなら直下にする。宣言しているのは
`displays` / `has-column` / `references` / `accesses` の 4 つである。

```yaml
refs:
  # displays は note 属性を宣言している → attrs の中
  - { rel: displays, to: c-di-請求番号,
      attrs: { io: 出力, note: 取得元 T_INVOICE.INVOICE_NO ／ 区分 ヘッダ } }
  # calls は宣言していない → 直下（description になり「呼び出す目的」列に出る）
  - { rel: calls, to: c-mod-TaxCalculator, note: 請求単位の消費税額を計算する }
```

間違えると `G029`（宣言済みの欄があるのに `description` へ流した）か `G030` が鳴る。
どちらも「中身が違う」ではなく**置き場所**の指摘なので、値を書き直さずに欄を移す。

### 業務フローの手順は `flow-step` にする

`c1` の表がそのまま関係になる。

```yaml
- concept: c-bf-受注受付
  type: 業務フロー
  name: 受注受付から出荷指示までの流れ
  statement: 受注は FAX 注文の代行入力または EDI 受注取込で受け付け、…すること
  attrs: { trigger: FAX 注文の受領, phase: 現行 }
  source: { anchor: s4-c1 }
  refs:
    - { rel: has-flow-step, to: c-fs-受注受付-与信判定 }

- concept: c-fs-受注受付-与信判定
  type: 業務フローのステップ
  name: 与信の枠内？
  statement: 受注の金額が得意先の与信の枠内であるかを判定すること
  attrs: { step_kind: 判定 }        # 凡例の「菱形: 判定」に対応する
  source: { anchor: s4-g1 }
  refs:
    # 分岐条件は関係側に持つ。ステップに書くと「どちらの枝の条件か」が消える
    - { rel: leads-to, to: c-fs-受注受付-在庫引き当て,
        attrs: { condition: 与信の枠内であるとき } }
    - { rel: leads-to, to: c-fs-受注受付-保留,
        attrs: { condition: 与信の枠を超えるとき } }
```

**`steps`（文章）とは併用しない。**手順を関係で持ったなら `business-flow.steps` は
書かない。二重に持つと片方が必ず古くなる。`steps` は線が繋がっていない資料
（`c1` が出ない図）のために残してある。

1 図形 = 1 レコードになるので件数は増える（業務フロー 1 枚で 10 レコード前後）。

### `refs` の向き（機械が直せるものと直せないもの）

from と to の種別が違う関係（`has-column` `realizes` `displays` 等）は、逆向きに
書いても機械が直す。

**from と to に同じ種別が並ぶ関係は直せない。**両向きとも宣言に合うので、書いた
向きがそのまま正本に入る。`arp4 model` の `[関係]` に `※向きは書いたまま入る` と出る
ものがこれである。

| 関係 | 正しい向き |
| --- | --- |
| `refines` | 詳細 → 概要（機能要件 → 業務要件、子モジュール → 親モジュール） |
| `calls` | 呼ぶ側 → 呼ばれる側 |
| `transitions` | 遷移元 → 遷移先 |
| `references` | 多 → 1（外部キーを持つ側が from）。**ER 図の矢印とは逆に書く**（前述「ER 図は `references` で書く」） |
| `reports-to` | 部下 → 上司（下位 → 上位）。**体制図の矢印とは逆に書く**（下記） |
| `outsources-to` | 委託する側 → 委託される側（発注者 → ベンダ）。体制図の矢印と同じ向きである |

**体制図から起こすときは、`reports-to` だけが図と逆になる。**日本の体制図は上に上位組織を
置いて上から下へ矢印を引くので、線をそのまま写すと「上司 → 部下」になる。`reports-to` は
「誰に報告するか」なので、**部下 → 上司へ反転して書く。**`outsources-to` は「誰に委託するか」
なので、委託元 → 委託先で図のまま入る。**同じ 1 枚の図から起こすのに、片方だけ反転する。**
どちらも from と to が `actor` なので機械は直さず、逆に書いても `freeze` も `check` も
通る ―― 出るのは、部下が上司を束ね、ベンダが発注者へ委託している体制図である。

間違えると `check` は通るのに、トレーサビリティ・マトリクスから丸ごと落ちる。業務要件
一覧の「関連する要件」欄のように、対応が下流側にしか書かれていないときは注意する。
そのまま業務要件レコードから張ると逆向きになるので、機能要件レコード側に `refines` を書く。

**`refs` の相手は種別まで合っていること。**`arp4 model` の `[関係]` に無い組み合わせは
凍結が `G012` で止める。

## YAML が壊れる値

例は `attrs: { physical_name: T_ORDER }` と 1 行で書いてあるが、値にカンマや `{` が
入ると YAML が壊れる。日本の設計書には普通に出てくる形なので気をつける。

```yaml
# 壊れる。カンマが区切りとして / {0} がフローマッピングの開始として解釈される
attrs: { physical_name: T_ORDER, volume: 1,200,000/年 }
attrs: { severity: エラー, body: {0}を入力してください。 }

# 正しい。ブロック記法にするか、引用符で囲む
attrs:
  volume: "1,200,000/年"
  body: "{0}を入力してください。"
```

**`:` ＋空白はフロー記法でなくても壊れる。**これが最も多い。「（固定: 130010）」
「（例: 翌月末）」はよく出てくるので、`statement` にも現れる。

```yaml
statement: 借方勘定科目コードは売掛金（固定: 130010）とすること      # 壊れる
statement: "借方勘定科目コードは売掛金（固定: 130010）とすること"    # 正しい
```

`1,200,000/年`・`1,000 件`・`{0}を…` は、資料にそのまま書かれている値である。丸めて
書かない。

**引用しないと型が変わる。**壊れないぶん、こちらのほうが見つけにくい。YAML は
`2026-02-24` を日付、`10` を数値、先頭 0 のある `010` を 8 進数（＝ 8）として読む。
`executed_on` も `value` も宣言は `string` なので（数値・真偽値のまま書くのは `length` /
`decimals` / `pk` / `not_null` のように `int` / `bool` で宣言された欄だけである）、
**資料の文字をそのまま渡すには引用符が要る。**

```yaml
attrs: { executed_on: 2026-02-24, value: 010 }        # 日付型・数値 8 になる
attrs: { executed_on: "2026-02-24", value: "010" }    # 正しい
```

**桁落ちは検査に出ない。**書式（`pattern`）の検査は値を文字に直してから当たるので、日付は
そのまま通る。**先頭 0 のあるコード値・郵便番号・電話番号がいちばん危ない**（`010` が `8`
になっても、`lint` も `check` も何も言わない）。

**日本語で `>-`（折り畳み）を使うと、語の間に空白が入る。**折り畳み記法は改行を半角スペース
に置き換えるので、`_metamodel-add.yml` の `reason` のような長い文を折り返して書くと
「この 2 列を持ち、 運用に直結する」と空白の混じった 1 文になる（語を空白で区切る言語の
ための記法である）。**改行をそのまま残す `|-` を使う**か、折り返さずに 1 行で書く。

`arp4 lint` は属性名の綴り違い（`桁数` / `primary_key`）も `G016` で指摘する。`build` は
宣言に無い属性を捨てるので、凍結してから気づいても整理結果はもう直せない。
`attrs` の外に書いてしまったら `arp4 lint --fix` が中へ移す（語彙に宣言されている
名前だけ）。YAML が壊れているものは、直すこと自体が本文の推測になるので `--fix` は
手を出さない。

## concept の付け方

`concept` はラウンドをまたいで同じものを指す鍵なので、安定させる。

| 対象 | 付け方 | 例 |
| --- | --- | --- |
| 物理名があるもの | `c-<物理名>` | `c-T_ORDER` |
| 物理名が無いもの | `c-<論理名>` | `c-受注番号` |
| 同名で別物 | 文脈を足す | `c-受注番号-明細` |

コード資産の命名は元ファイルのパスから機械的に導く → [code.md](code.md)。

**種別ごとの接頭辞（`c-scr-` 画面 / `c-rule-` 業務ルール / `c-cst-` 制約・前提 …）を使うかどうかは、
配る側が決める。**この文書は接頭辞の一覧を持たない ―― 資料ごとに要る種別が違うので、
揃えられるのは較正で分担を配る側だけである（→ [split.md](split.md)）。使うときの書き方は
3 つ。

- **接頭辞は上の表の鍵の前に付ける。**`c-<接頭辞>-<物理名 or 論理名>` の形にし、鍵そのもの
  （物理名・論理名）は変えない（`c-scr-受注入力`。`c-scr-画面001` のように鍵を表示 ID へ
  すり替えない → 後述「表示 ID を鍵にしない」）
- **1 つの対象に 2 つの接頭辞を使わない。**同じ制約を `c-cst-…` と `c-nfr-…` の両方で
  名乗ると、機械には別の concept に見える
- **接頭辞は `type` の代わりにならない。**機械は concept 名から種別を決めないので、
  `c-nfr-…` と書いても `type` は必ず書く（省くと `G006`）

`concept` は同一性の鍵であって見出しではないので、`name` には読みやすい名前をそのまま
書いてよい。**2 回目以降のラウンドでは `.arp/spec/concepts.yml` を先に引く。**新しく振ると、
同じものが 2 アイテムになる。

**迷ったらまとめない。**同じ「顧客コード」でも、文脈が違って同一と言い切れないなら別の
`concept` にしておく。統合は後からできるが、記録を残さずに統合したものを分けるのは難しい。

### 表示 ID を鍵にしない（資料に列があるとは限らない）

`req_id` / `screen_id` / `message_id` は arp4 が採番するもので、資料の列ではない。
日本の設計書は名前だけで相互参照していることが多く、ID の列そのものが無い資材も
普通にある。

鍵は「その資料が実際に何で相手を名指ししているか」で決める。**分担するときは、鍵に
使う列が全資料に実在することを較正で 1 度確かめる**（→ [split.md](split.md)）。無い資料が
1 冊でもあれば、鍵を変えるか、その資料だけの鍵を明示して配る。

## 書いてよいこと・いけないこと

**言い換えてよい。**原文をそのまま写す必要はない。アンカーは凍結後も動かないので、原文は
いつでも引ける。表の断片（`受注番号 / ORDER_NO / ○`）を「受注番号は主キーであること」と
読める文にするのが、この層の仕事である。

### 正本の語彙を本文に書かない

`name` / `statement` / `description` / `note` は、**そのまま設計書の列に印字される**
（`description` が出るかは種別と章による → 前述）。読み手は `.arp/spec/` も `arp4 model` も見ないので、正本のフィールド名・関係型名・
コードを本文に書くと、その行はそこで読めなくなる。

| 本文に出てしまった実例 | 何が問題か | 資料の言葉で書くなら |
| --- | --- | --- |
| 両論は `positions` を見ること | `positions` は正本のフィールド名。読み手に辿る手段が無い | 両論は課題管理表の両論欄にある |
| 当たる画面が画面一覧に無いため `operates` を張っていない | `operates` を知らないと意味が取れない | 当たる画面が画面一覧に無いため、権限の升に出せない |
| メッセージ定義書に本文が無いため `raises` は張っていない | 同上 | メッセージ定義書に対応する本文が無い |

**整理層の申し送りを本文へ書かない。**「なぜ関係を張らなかったか」は整理層の事情であって
仕様ではない。書く先は `out_of_scope` の `reason` か `_metamodel-add.yml` の `notes` で、
どちらも設計書の本文には出ない。**本文に書くと、読み手には仕様の一部として届く。**

### `statement` の文型は種別で変わる

`statement` の既定は「〜すること」だが、**要求を書く種別のものである。**すべてに当てると
定義や登場人物まで要求文になり、読めなくなる。

| 種別 | 文型 | 例 |
| --- | --- | --- |
| 要件・業務ルール・制約・画面・帳票・バッチほか | 〜すること | 出荷指示済みの受注は、明細の追加・変更・削除を行えないこと |
| `用語`（`glossary-term`） | 定義文（〜をいう／〜である） | 引当とは、受注に対して在庫を確保し、他の受注に使えないようにすることをいう |
| `業務フローのステップ` のうち登場人物・外部システム（`step_kind: 開始` / `他システム`） | 役割の記述 | 得意先は、この業務の流れの起点として発注を出す社外の相手である |
| `利用者・ロール`（`actor`） | 役割の記述 | 情報システム部は、基盤の維持と障害の一次受けを担う社内の組織である |
| `現状課題`（`current-issue`） | 状態の記述（いま起きていること） | 受注の入力は全件が手入力で、1 件あたり 8 分かかっている |
| `リスク`（`risk`） | 状態の記述（まだ起きていないこと） | 移行対象に旧コード体系のデータが残っており、切替時に名寄せができなくなるおそれがある |
| `決定事項`（`decision`） | 決定の記述（〜とする） | 消費税は請求単位で税抜き積上げにより計算するものとする |

**`決定事項` に「〜すること」を当てない。**決定は合意された事実であって要求ではない。
要求文で書くと、同じ議事録の 1 行から起こす `業務ルール`（中身）と同じ文が 2 つ並び、
どちらが記録でどちらが仕様かが読み手から見えなくなる（決定は「記録」と「中身」の 2 つに
分かれる → 後述「1 枚のシートが 2 冊に分かれるとき」）。**いつ誰が決めたかは `statement` に
書かず、`decided_on` / `decided_by` へ入れる**（資料に無いなら空ける → 前述「資料に無い欄は
空けておく」）。

**組織と状態に「〜すること」を当てない。**「情報システム部は基盤を維持すること」は体制の
記述ではなく体制への要求として読まれ、「手入力に 8 分かかること」に至っては、いま起きて
いる困りごとが目指す姿として要件定義書に載る。**現状課題とリスクは、直す前の姿を書く欄
である。**

```yaml
statement: 引当は受注に対して在庫を確保し、他の受注に使えないようにすることであること  # ×
statement: 引当とは、受注に対して在庫を確保し、他の受注に使えないようにすることをいう    # ○
```

用語集は定義の一覧であって要求の一覧ではない。**「〜することであること」が出てきたら、
種別を見直す合図である。**

**ただし本文から辿れること。**`statement` の語がアンカー本文にまったく出てこないと
`G005`（warn）が出る（コードの塊では取り違えでないことのほうが多い → [code.md](code.md)）。
warn を消すために情報を削らない。`G005` は「出典を取り違えていないか」という確認であって、
禁止ではない。

**関係は本文に根拠があるものだけ。**「たぶんこの画面はこの要件を実現している」は書かない。
それは正本を人が育てる過程で決まる。

**パース結果が間違っていたらそこで直す**（アンカーは消さない・編集理由をコミット
メッセージに残す → [parse.md](parse.md)）。凍結した後に気づいたら、[build.md](build.md) の
`overridden`（軽微）か、新しいラウンド（根本から違う）で対応する。

## 語彙に無い種別が要るとき

```yaml
# .arp/rounds/<ラウンド>/organized/_metamodel-add.yml
add_item_types:
  - name: 帳票レイアウト
    layer: 基本設計
    reason: 帳票定義書 4 冊が持つ「印字位置・書体・改ページ」を既存 report では持てない
    attributes:
      font: { kind: string }
```

**人が承認するまで凍結は通らない**（`G007`）。まず既存種別で書けないかを確かめること。
種別が案件ごとに増えると、設計書の様式も生成側も安定しない。分担中に凍結を止めたく
ないなら `status: deferred` ＋ `deferred_reason` を付ける。

**機械が受け取るのは `add_item_types` と `notes` の 2 節だけである。**「既存種別に属性を
足したい」「関係の組み合わせを足したい」は語彙の不足として最も多い形だが、それらは
`notes` に書く（受け取れない節は `G000` で指摘する。形は `arp4 schema metamodel-add`）。

```yaml
notes:
  - about: external-interface に「異常時の扱い」「再送・再実行」の受け皿が無い
    reason: |-                              # 日本語は `|-`（`>-` は改行が空白になる）
      外部 IF 一覧の 5 件すべてがこの 2 列を持ち、運用に直結する（冪等・自動再試行
      3 回・手動再送）。description の散文にすると、どの IF が自動で戻るのかを
      運用設計から絞り込めない。
    source: { file: 資料/00_全体/02_基本設計/外部インターフェース仕様書.xlsx/IF一覧,
              anchor: s3-t1 }
```

`notes` は機械が解釈せず、承認する人が読む。ただし書いたものが記録から消えることはない。

**書く前に `arp4 model --attributes` で確かめる。**「受け皿が無い」と思ったものが宣言済み
だと、同じ提案が毎ラウンド起票され、読む人は同じものを何度も却下することになる。実測で
課題管理表の 状態・区分・起票日・工程 がこれになっていた（→ [sheets.md](sheets.md)
「課題管理表から起こすとき」）。

**語彙は版で増える。この文書群に「その属性は無い」と書いてあっても、それを根拠にしない。**
属性があるか無いかを言えるのは `arp4 model --attributes` だけである。手順書のほうが古い
ことがあり、実測ではそれが起きて、宣言済みの 4 属性が丸ごと `description` へ流れた。

**受け取れない欄・行をコメントに書かない。**YAML のコメントは機械に見えない。freeze の
未整理一覧にも `_metamodel-add` にも上がらず、書いた本人しか知らない記録になる。受け取れ
ないものは `out_of_scope`（reason 付き）に入れるか、語彙の不足として `notes` に申告する。
どちらも機械が数える場所である。

書く先に迷いやすいものを挙げる。**「出る章」まで見ること。**書き先を選ぶことは、その資料が
どの設計書のどこに出るかを選ぶことである。「潰れるもの」は、その写し方で必ず失われる形で、
資料の 1 覧を別の軸へ組み替えるときに起きる。

| 資料にあるもの | 書く先 | 出る章 | 潰れるもの |
| --- | --- | --- | --- |
| 機能一覧（機能名・種別・関連する画面/帳票） | バッチ→`バッチ処理`、共通部品→`モジュール`、オンライン→画面/帳票から `realizes` | 基本設計書「画面一覧」「帳票一覧」「バッチ処理一覧」 | **機能という単位そのもの。**機能一覧の章は無い。1 画面に複数の機能が当たる行（受注変更・受注照会・注文請書出力）は画面へ合流して識別子を失う → 下記「解体したら数えて申告する」 |
| モジュール間の呼出関係 | `calls`（業務ルールにまとめない） | 詳細設計書「呼出関係」 | ― |
| 画面遷移（遷移先列） | `transitions`（`event` / `condition` に契機と条件） | 基本設計書「画面遷移」 | ― |
| 状態遷移表・状態遷移図 | 業務ルール（`rule_kind: processing`）。**遷移 1 本 = 1 件に割る**（下記） | 基本設計書「業務ルール」 | **行×列の構造。**1 件にまとめると表として復元できない |
| 権限マトリクス（○/△/×） | `operates` ＋ `permission` / `condition` → [sheets.md](sheets.md) | 権限マトリクス | **行が機能であること。**升は画面で組まれるので、当たる画面が無い行（「与信保留の解除」）は升から消える |
| バッチの入出力ファイル | `制約・前提`（`category: 技術`）を 1 行 1 件 | 要件定義書「制約・前提」 | ― |
| ドメイン定義（型と桁の共通定義） | `制約・前提` ＋ 名前が一致するデータ項目へ `constrains` | 要件定義書「制約が縛るもの」 | ― |

### 状態遷移表は遷移 1 本を 1 件に割る

専用の型は無いので業務ルールに写すが、**表全体を 1 件にまとめない。**まとめると
「受注ステータスは、受注登録により受付(10) または 与信保留(20) となり、与信承認により…」
という 1 文になり、**どの操作でどこへ行くかを表として復元できなくなる。**

```yaml
- concept: c-rule-受注ステータス-引当完了
  type: 業務ルール
  name: 引当完了による受注ステータスの遷移
  statement: 受付(10) の受注は、引当完了により 引当済(30) へ遷移すること
  attrs:
    rule_kind: processing
    condition: 受注ステータスが 受付(10) で、引当完了が起きたとき   # 遷移前 × 操作
    action: 受注ステータスを 引当済(30) にする                     # 遷移先
  source: { anchor: s10-t1 }
```

`condition` / `action` に割ると、遷移表の行と列がそのまま欄に載る（`business-rule` は
両方を宣言している）。**「遷移しない」の升も 1 件として起こす。**禁止そのものが仕様である
（「出荷指示済(40) からは取り消せない」）。**図と表の両方があるときは表を出典にし、図に
しか無い線は矛盾として `contradictions` へ回す** → [reconcile.md](reconcile.md)。

### 解体したら、数えて申告する

機能一覧・権限マトリクスのように、**資料の 1 覧が別の軸へ組み替わるときは、対応が付かな
かった行を数えて `_metamodel-add.yml` の `notes` に書く。**

```yaml
notes:
  - about: 機能一覧 23 行のうち 3 行が機能としての識別子を失った
    reason: |-
      受注変更・受注照会・注文請書出力は、いずれも既存の画面へ realizes で合流させた。
      画面は 1 つなので、機能の粒度（変更と照会が別の機能である）は正本に残っていない。
      機能一覧に当たる章は生成物に無いため、資料を渡した側からは 23 行が消えて見える。
    source: { file: 資料/00_全体/02_基本設計/機能一覧.xlsx/機能一覧, anchor: s3-t1 }
```

**23 行が 20 行になったことは、書かなければ誰にも見えない。**`freeze` も `check` も、
資料の行数と正本のアイテム数を突き合わせない。`0_元資料と設計書の対応.md` は
「出典に引かれた」までしか数えないので、**引かれたうえで単位が変わったことは出ない。**

### 1 枚のシートが 2 冊に分かれるとき

`arp4 model --attributes` で `※設計書の節になる` 印の付いた属性は、**値が配置先を決める。**
`rule_kind` を `business` にするか `validation` にするかで、そのルールが基本設計書に出るか
詳細設計書に出るかが変わる。

実測では業務ルール一覧 1 シート 15 件が、基本設計書 8 件（`business` / `calculation`）と
詳細設計書 7 件（`validation` / `processing`）に分かれた。**分かれること自体は様式どおりで
正しいが、どちらの設計書にもその旨が書かれていない。**読み手は「業務ルール一覧」を 1 冊の
中に探すので、7 件が抜けていると読む。

**1 枚のシートから起こしたものが 2 冊に分かれると分かった時点で、`notes` に書く。**

**決定は「記録」と「中身」の 2 つに分かれる。**議事録の 1 行「消費税は請求単位で税抜き
積上げとする（2026-08-22 / 基本設計レビュー）」からは 2 つ起こす。`決定事項`（いつ誰が
決めたか。`establishes` で相手を指す）と、`業務ルール`（計算方法そのもの）である。
どちらか片方では足りない。記録だけだと何が変わったのかを辿れず、中身だけだと覆るまでの
拠り所が残らない。

**`決定事項` と `decisions.yml` は別物である。**`decisions.yml` は**機械**（`draft` /
`build` / `auto`）が下した判断の全件で、`決定事項` は資料に書いてある人間の合意である。
整理層が書くのは後者だけ。

**あなたが下した判断は `decisions.yml` に残らない。**あそこは機械の 3 つしか書き込まない。
整理層の記録になるのは `organized/**.yml` そのもの（git の差分）と、`out_of_scope` の
`reason`・`known_gaps` の理由である ―― **迷って決めたことは、そこに 1 行書いておかないと
どこにも残らない。**
