# ARP workflowの進行管理

親Agentがworkflowを開始・再開するときに読む。原本操作だけなら不要。既存実行はstatus --summaryから再開し、新規の入力準備・initは [操作リファレンス](operations.md) の「メタモデルと設計書」を参照する。

## 担当の割当と再利用

1. 同じ実行ファイル・作業ディレクトリ・`spec workflow --root <root> --run-id <run-id>` を使って `status --summary` を取得する。tasksのページを必要に応じて送り、next_actionsの先頭一覧だけで残件を判断しない。
2. 未割当のpending/failedタスクの `handoff --task <ID>` を取得する。返されたagent名でカスタムAgentを呼び、handoffをそのまま渡す。本文・packet・返信JSONの先読みや書き戻し、共通ブリーフの複製をしない。担当にはインスタンス固有のactorを伝える。
3. 同時に作業する担当は既定で最大3、ユーザー指定とホストの利用可能枠があればそれに合わせる。これは親の配分方針で、CLIの予約や強制上限ではない。文書数・タスク数だけのAgentを一括起動しない。少数タスクなら必要な数だけ起動する。
4. 担当の役割・ホストのAgent ID・actor・実行中と割当済み未実行のtask_ref・作成修正への参加歴を管理する。next/handoffは占有しないので、同じタスクを二重割当しない。空いた同じ役割の担当へ次のhandoffを渡し、1件ずつ読取・検証・提出させる。待機中の担当もホストの枠を使う場合は、不要になった担当を終了して枠を空ける。
5. ホストの完了通知（返信が必須なら「完了」）または中断通知を受け、親の割当記録にある各タスクを `receipt --task <ID>` で確認する。通知だけで提出済みと判断しない。nullは未提出、falseは拒否。続行可能なら同じ担当へ訂正を戻す。続行できなければ新しい同役割の担当へ最新handoffを渡し、readの診断・draftから再開させる。複数割当の途中終了では全件のreceiptを確認し、受理済みを再提出させず、未実行分の割当を解除する。受理済みならstatus --summaryを確認し、残件を空いた担当へ配る。段階の適用・advanceは当該段階の作業中担当がなくなってからnext_actionsに従う。失効したタスクは再割当せずstatusから選び直す。

ホストが同じAgentへの続行を提供する場合はそのIDで再開する。提供しない場合は、小さい同段階のタスクを少数のhandoff一覧として1回の呼出しにまとめ、担当内では1件ずつ提出させる。目安は最大3件で、大きさが不明なら1件。タスクの契約・返信・監査範囲は結合せず、CLIのrepairの指摘集合も再分割しない。担当は提出拒否を同じタスク内で訂正し、受理まで次へ進まない。訂正不能や実行失敗で返されたら、親が担当の停止と状態を確認して未実行分の割当を解除する。

長いタスクの後、文脈混同が見られる場合、別runへ移る場合は新しい担当に切り替える。新規担当は最新handoffから再開する。ホストにカスタムAgentが見つからなければ `arp4 skills install --root <project> --agent <対応先>` で配置し、ホストの再読込手順を確認する。委任機能自体がなければ独立した担当セッションへ引き継ぎ、親の自己点検で独立レビューを代用しない。

通常の進行確認は `status --summary` を使い、詳細診断・計測・レビュー設定が必要なときだけ通常のstatus/historyを参照する。短縮表示でもconcerns・blocked・escalation・成果物は確認する。一緒に完了した担当分は一度のstatusで確認する。資料の量が不明なら1件ずつ割り当て、量を測るためだけに親がinspect/readを追加実行しない。診断の詳細や修正内容の検討は担当に任せ、親がreadしたり長い報告の再送を求めたりしない。

## 独立性と修正

handoffのagentが委任先を示す。作成・修正担当はextract/link/repair/restructure、レビュー担当はreview/global-reviewを扱う。作成・修正を行ったインスタンスを、このrunのレビュー担当へ転用しない。レビュー担当もモデルの修正はせず、指摘を提出する。指摘後のrepair/restructureは作成・修正担当へ戻す。役割名やactorの変更だけでは独立性にならない。

文書別レビューと全体レビューはCLIの計画に従って別タスクとして割り当てる。監査範囲と確認方法はレビュー担当の定義とreadの契約に従う。変更後に必要な再レビューや同一packetの再利用はCLIの計画に従う。既知指摘・unresolvedを無制限に再試行せず、次の操作が要判断なら理由と必要な情報をユーザーへ返す。

## 完了の確認

receiptのtrueは提出受理であり、意味的正解・公開承認ではない。statusと出力成果物で完了を確認し、未解決事項と草稿はその状態で報告する。採用・承認・原本への反映は利用者から与えられた権限内で行う。

親は既知指摘をstatusのconcernsで確認し、レビューcontextは担当だけが読む。needs_decisionは人判断待ち、improvementは任意改善であり、unresolvedファイルへの記載有無だけで残件を判断しない。

修正回数の上限は実行全体のrepair/restructure適用回数に対する予算である。上限後は修正確認を終えて残件付き草稿を出し、自動で追加ラウンドを開始しない。improvementは今回の利用を妨げない改善候補として保存され、修正ループを開始しない。同じ文書のレビュー担当は可能なら継続し、完了判定は担当の記憶ではなくCLIに従う。

## 計測・比較を行う場合

比較する場合は同じ入力・モデル・監査範囲で、起動数、同時実行数、経過時間、実測トークン/費用、拒否と修正・再レビューの往復を記録する。submitのusageだけでは親や未提出作業の消費を含まないため、ホストの総量と区別する。取得できない値を推測で埋めず、並列化だけで費用削減したと判断しない。

実測値が提出後に判明した場合は、[操作リファレンス](operations.md)のrecord-usage手順でタスク内の提出番号に追記する。担当再利用時の累計値は提出ごとの差分にし、割り当てられない消費はホスト側の記録に残す。
