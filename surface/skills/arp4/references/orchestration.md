# ARP workflowの進行管理

親Agentがworkflowを開始・再開するときに読む。原本操作だけなら不要。既存実行はstatus --summaryから再開し、新規の入力準備は [capture](spec-cli.md)、initは [workflowのCLI操作](workflow-cli.md) を参照する。

親が行うのはCLIによる状態確認・割当・提出確認・段階の進行で、資料の読取と判断は担当が行う。親がread・inspectで資料を読む、担当に長い報告を求める、のどちらも親の文脈を増やすだけなので行わない。

## 進行の繰り返し

1. **状態を確認する**: 同じ実行ファイル・作業ディレクトリ・`spec workflow --root <root> --run-id <run-id>` で `status --summary` を取得する。tasksは必要に応じてページを送る。next_actionsは先頭の一覧なので、それだけで残件を判断しない。concerns・blocked・escalation・成果物も確認する。詳細診断・計測・レビュー設定が必要なときだけ通常のstatus/historyを使う。
2. **handoffを取得する**: 未割当のpending/failedタスクの `handoff --task <ID>` を取得する。失効したタスクは再割当せず、statusから選び直す。
3. **担当へ渡す**: handoffの `agent` の名前でカスタムAgentを呼び、handoffをそのままと、担当インスタンス固有のactorを渡す。本文・packet・返信JSONの先読みや書き戻し、共通ブリーフの複製、readの `--known-contract` の参照は渡さない（参照は担当が自分で読んだものだけを使う）。
4. **通知を受けて確認する**: ホストの完了通知（返信が必須なら「完了」）または中断通知を受けたら、割当記録にある各タスクを `receipt --task <ID>` で確認する。通知だけで提出済みと判断しない。見るのは `submission_accepted` で、trueは受理、nullは未提出、falseは拒否。受理後の `state` は `complete` または `retired` で、どちらも通常の状態である。
   - 全件受理なら `status --summary` を確認し、残件を空いた担当へ配る。一緒に完了した担当の分は一度のstatusで確認する。
   - 未受理が残り、続行可能なら同じ担当へ訂正を戻す。続行できなければ新しい同じ役割の担当へ最新のhandoffを渡し、readの診断・draftから再開させる。
   - 複数割当の途中で終了した場合は、担当が停止していることと全件のreceiptを確認し、受理済みを再提出させず、未実行分の割当を解除する。
5. **段階を進める**: 段階の適用・advanceは、その段階で作業中の担当がなくなってからnext_actionsに従う。

## 割当の管理

- **記録する**: 担当ごとに、役割・ホストのAgent ID・actor・実行中と割当済み未実行のtask_ref・作成修正への参加歴。next/handoffはタスクを占有しないので、二重割当を防ぐのは親の記録である。
- **同時に動かす数**: 既定で最大3。ユーザー指定とホストの利用可能枠があればそれに合わせる。これは親の配分方針で、CLIの予約や強制上限ではない。文書数・タスク数と同じ数のAgentを一括起動せず、少数タスクなら必要な数だけ起動する。
- **再利用する**: 空いた同じ役割の担当へ次のhandoffを渡す。同じ担当は2件目以降の指示文を読み直さずに済む。ホストが同じAgentへの続行を提供する場合はそのIDで再開する。待機中の担当もホストの枠を使う場合は、不要になった担当を終了して枠を空ける。
- **続行できないホストではまとめて渡す**: 小さい同段階のタスクを少数のhandoff一覧として1回の呼出しにまとめる。目安は最大3件で、大きさが不明なら1件。量を測るためだけに親がinspect/readを実行しない。タスクの契約・返信・監査範囲は結合せず、CLIがまとめたrepairの指摘集合も再分割しない。担当は1件ずつ提出し、拒否は同じタスク内で訂正する。
- **切り替える**: 長いタスクの後、文脈の混同が見られる場合、別runへ移る場合は新しい担当にする。新しい担当は最新のhandoffから始める。
- **担当を呼べない場合**: カスタムAgentが見つからなければ `arp4 skills install --root <project> --agent <対応先>` で配置し、ホストの再読込手順を確認する。委任機能自体がなければ独立した担当セッションへ引き継ぐ。

## 独立性

- 作成・修正担当（`arp4-worker`）はextract/link/repair/restructure、レビュー担当（`arp4-reviewer`）はreview/global-reviewを扱う。
- 作成・修正を行ったインスタンスを、このrunのレビュー担当へ転用しない。役割名やactorを変えるだけでは独立にならない。親の自己点検も独立レビューの代わりにならない。
- レビュー担当はモデルを修正せず、指摘を提出する。指摘後のrepair/restructureは作成・修正担当へ戻す。
- 文書別レビューと全体レビューは、CLIの計画どおり別のタスクとして割り当てる。変更後に必要な再レビューと同一packetの再利用もCLIの計画に従う。監査範囲と確認方法はレビュー担当の定義とreadの契約が決める。
- 同じ文書のレビュー担当は可能なら継続する。完了の判定は担当の記憶ではなくCLIに従う。

## 修正と残件

- 既知の指摘はstatusのconcernsで確認する。レビューのcontextは担当だけが読む。
- `needs_decision` は人の判断待ち、`improvement` は今回の利用を妨げない任意の改善候補で、修正ループを開始しない。unresolvedファイルに記載があるかどうかだけで残件を判断しない。
- 修正回数の上限は、実行全体のrepair/restructure適用回数に対する予算である。上限後は修正確認を終えて残件付きの草稿を出し、追加のラウンドを自動で開始しない。
- 既知の指摘やunresolvedを無制限に再試行しない。次の操作に判断が要るなら、理由と必要な情報をユーザーへ返す。

## 完了の確認

statusと出力成果物で完了を確認し、未解決事項と草稿はその状態のまま報告する。receiptのtrueは提出受理であり、意味的正解や公開承認ではない。

## 計測・比較を行う場合

比較する場合は同じ入力・モデル・監査範囲で、起動数、同時実行数、経過時間、実測トークン/費用、拒否と修正・再レビューの往復を記録する。submitのusageだけでは親や未提出作業の消費を含まないため、ホストの総量と区別する。取得できない値を推測で埋めず、並列化だけで費用削減したと判断しない。

実測値が提出後に判明した場合は、[workflowのCLI操作](workflow-cli.md) のrecord-usage手順でタスク内の提出番号に追記する。担当再利用時の累計値は提出ごとの差分にし、割り当てられない消費はホスト側の記録に残す。
